## 未来去哪

> 以下是**方向**，不是承诺。没实测过的事标「不知道」。

**终局**：企业不再需要 FDE。AI 节点部署后自主运行，审计模块持续盯变更，编排模块自动纠偏，知识库自我积累——人只需要偶尔看一眼 dashboard 确认一切正常。我们做的不是给企业装 AI，是让企业忘了我们的存在。

> 连创造 AI 的人都在公开表达方向失控的不安（DeepMind 创始人 Hassabis 2026 年访谈）——「AI 可以被管住」的 Harness 中间件不是选配，是刚需。

**为什么是现在——转折点的三信号**：单一信号不够，三信号同时成熟才构成真正的范式转折点：

| 信号 | 维度 | 内容 |
|------|------|------|
| 供给侧 | AI Coding 成本趋零 | FDE 借 AI Coding 1 天出 Demo，瓶颈从技术能力转向**业务抽象能力**（能否把 SOP 拆成 Agent 工作流） |
| 治理侧 | Agent IAM 组织身份 | Agent 有工号/权限/审计/全生命周期管理，从「工具」变「员工」，才能进生产环境 |
| 能力侧 | 协同飞轮持续进化 | 每次人工纠正/确认/追问回流为结构化学习信号，越用越懂企业 |

**现实验证**：工作流主语从「人」迁移到「Agent」——SOP 拆为 Agent 工作流、给 Agent 派工号、人工纠正回流为学习信号——三信号同时成熟的落地案例。

sofagent 的定位正卡在这个转折点上：审计模块（治理侧）+ Ontology（能力侧）+ 开源 MIT（供给侧）——三信号缺一不可，单独做任何一个都不够。

**供给侧技术拼图已齐**（NVIDIA 2025.7 判断：模型/微调框架/示范方案/沙盒/工具链全部就绪）——sofagent 的 `install.sh` + FDE 四阶段示范方案直接给一套可以跑的蓝图，不是告诉企业"该做"。

两条路径：**FDE 驻场部署**（传统中小企业，FDE 进场→四阶段十二步流程→交付→撤离）和 **开发者自部署**（开源社区，git clone→install.sh→审计→CI 集成）。

设备端形态：安装时可配置 Agent 平台（OpenClaw / WorkBuddy 等），审计结果通过 MCP server 推到企业协同平台。**数据主权在设备**——所有记忆、日志、决策记录永不离开本地。

## 版本规划

> 以下带状态版本表为权威源；各版本子项定义见各行「日志」列链接的规划文件。

### 排期准入判据

> **每版交付章上限 10 章**（v1.5.0 已冻结的章节不追溯；自 v1.5.1 起适用）。超限章**优先后移到后续版本**（用版本序列承接，不轻易退回探索方向表——先把版本排满再谈砍）；后移顺序按下方权重从低到高。

| 权重 | 来源 | 判据 |
|:--:|------|------|
| **W1** | 具名消费方诉求 | 指认得出消费方——G 编号 / 平台层或模型层接口表 / 真实客户诉求 |
| **W2** | 数据飞轮链路缺口 | 一体机链路（session→分拣→脱敏→数据集→训练→灰度）上缺失的那一环 |
| **W3** | 已交付能力的缺陷与债务 | 存量红、命名债、假绿、跨仓漂移、悬空承诺 |
| **W4** | 外部对照研究收编 | 须能回答「服务于 W1 或 W2 的哪一条」；答不出按 W5 处置 |
| **W5** | 内部灵感 / 远景 / 纯评估报告 | 默认进探索方向表，不占版本章；已排者超限时优先移出 |

**两条落地纪律**：① **收编须指认消费方**——进 changelog 的每章须能指认 W1/W2/W3 至少一项，不能指认的移入探索方向表；② **不设冷却期**——外部研究的吸收节奏由维护者按当期上下文人工裁定，登记（[VALIDATION](./VALIDATION.md)）与承诺（changelog）分离的原则不变。

### 判定底座施工期（v1.6.0 – v1.9.0 · 四阶段四版）

> **起点与依据**：判定底座（可治理的决策模型底座）的施工从 **v1.6.0** 起，四个阶段各一版（原十二细版按「同一阶段 = 同一工作面群」归并）。**为何分阶段**：判定底座是一个**模型**——其开发量落在「判据 / 数据 / 训练 / 校准 / 接线 / 分发 / 收敛 / 验证」多个独立工作面，任一面的实际工作量都可能超出预估；版本颗粒度粗会让单版内容失控，或让「还没做完」被挤成「先宣告再补」。

| 阶段 | 版本 | 主题 | 该阶段出口条件 |
|:--:|------|------|------|
| 一 | v1.6.0 | 判据与数据地基——让概率有训练目标 | 判据 schema 定稿 + 数据集可校验 + 零样本基线落数 |
| 二 | v1.7.0 | 模型与校准——让概率变得有意义 | **ECE 达阈** + 判定质量与概率可信度双达阈 |
| 三 | v1.8.0 | 接线与分发——让概率可用 | DecisionChannel 实现 + 一体机离线推理 + 权重分发通路 |
| 四 | v1.9.0 | 消费与收口——让概率进入既有判定面 | 三原语补概率 + 假概率正名 + 四层性能标准落数 |

**版本弹性机制**（防止「后面版本不够」而挤版）：

- **阶段内开发量超出** → 在该阶段内**增补补丁位**（`vX.Y.1`），不挤进后续阶段（阶段内主题一致、依赖连续，增补成本最低）
- **本版交付后发现缺陷需修补** → 在该 minor 内开补丁位（`vX.Y.1`），不挤后续 minor
- **出现新识别工作面** → 在阶段之间**插入新阶段**（如 `v1.10.x`），**保持原四阶段编号不重排**（编号稳定便于引用，避免全仓版本号重写）
- **V2.0 时点不锁死** → V2.0 在「四阶段收口达阈」时点到来，**不由版本号决定**；未达阈则增补版本而非放宽标准。**V2.0.0 已定位为 S1M 宣告版**（身份切换 FDEing × S1M × Harness，宣告版零新能力；**版本边界纪律**——V2.0 起版本全部是 S1M 的迭代域，V2.0 前的能力不放 V2.0 后的版本去迭代，网络出口治理面与 AI 节点已按归位再分配分落 v1.5.2 / v1.5.4）
- **增补须有依据** → 每次增补须有明确的未达阈项或新识别工作面，「感觉还没做完」不构成依据
- **不允许**：把多个阶段的工作挤进一版；或为「按计划进 V2.0」而放宽达阈标准

> 📖 各版完整交付与验收标准见 [changelog 目录](./changelog/README.md)；设计依据（三原语对位、权重分发与制品架构、判定面边界）见维护者侧判定底座设计文档（仓外）。

| **投机式预判（Jev 生态启发）** | 一次往返**投机性地问出多个可能目标**、按最终操作结果丢弃其余（生态实现：`browser-use/jev-ultrafast` 的多目标一次往返）——用一次判定的成本换掉串行等待，代价是算多余的份。与 [v1.9.0 第四章](./changelog/v1.9/v1.9.0.md)「打包并发的成本杠杆」同族（都指向「别串行问」），但多一层「预先猜后续路径」。**边界（与打包的划界，2026-09-22 登记）**：打包问的是**已定**的多问（同状态一次前向），投机问的是**未定**的候选路径——① 后者的多余成本**不得混入** [v1.9.0 第四章](./changelog/v1.9/v1.9.0.md) 判定调用密度与成本基线的读数；② 立项前须先答「多问是否共享同一 state」——不共享则打包不成立、成本杠杆不适用，需另算账。**不提前抽象**：打包问句已覆盖「同状态并行」这一层；触发条件=出现「判定延迟成为端到端瓶颈、且后续路径可枚举」的真实场景，届时**先量猜测命中率**再决定是否立项 |
| **单机全流程（训练 → 推理 → 后训练不出本机）** | 目标是「一台普通笔记本跑完全流程」：用户从 GitHub 取本仓与基座权重，在本机完成 LoRA 后训练、本机推理判定、本机继续积累迭代——**数据不出机、模型可替换、后训练权在用户手里**。**三块地基已在**：[PHILOSOPHY · 远期演化愿景](./PHILOSOPHY.md#远期演化愿景从内置小模型到自动化企业后训模块) 的「本地小模型可跑」、[v1.7.0 第一章](./changelog/v1.7/v1.7.0.md)「本地 LoRA 档为交付形态下限」、[v1.8.0 第三章](./changelog/v1.8/v1.8.0.md)「最低可用档 · 无独立 GPU 的单机」。**对外口径先立死三条**：① 「能跑」按**可用内存档位**说（可训规模由可用内存决定，不由机型品牌决定）② 「单机」须**分清推理侧与训练侧**（生态实测：推理侧笔记本档已可直接服务，训练侧小档已跑通、大档仍在云卡）③ 基座选型必答「**目标硬件上有没有快核**」（生态实测：同尺寸换用无该硬件快核的架构后慢 3–7 倍）。落数见 [v1.9.0 第四章](./changelog/v1.9/v1.9.0.md) 端到端档位分列。无版本单元格、不排期，触发条件=首个真实用户在单机上走通「后训练 → 判定服务」闭环并留下可复算读数 |
| **运行期宿主装配（通道章宿主侧收尾）** | v1.5.1 的三条通道章（G12 设备 OTA / 任务下发通道二期 / `sofagent demo`）交付的是**契约与执行侧**，宿主侧装配不在该版落点，留下三项悬空：① **签名者信任锚**——`verifyDeliverySignature` 只证「摘要由信封**自带公钥**签出」的自洽性，全链无平台公钥 pin / 无 principal 白名单 / 无设备注册表绑定（[SECURITY](../SECURITY.md#g12-设备远程下发面升级--内容下发--任务推送) G12 ① 已如实披露）② **订阅登记调用方归属**——`registerDeviceSubscriptions` / `deviceTaskReceipt` 零生产调用方，需定「`device_register` 成功后调用」还是「设备进程启动时注册」（含重启幂等语义）③ **死信批量排空器**——`listDeadLetters()` 聚合枚举已在位，缺的是批量**动作**入口；排空器须逐条确认，沿用 `replayDeadLetter` 的「非 retryable 需显式 `force`」守卫。**触发条件 = 首次接真实传输通道**：第①项在该时点由「设计期已知缺口」直接变为「已暴露面」（当前三条下发面均为注入端口、外部不可达），须同批落地；②③ 可与①同批，也可在设备侧生命周期语义定稿后单独落地。归因 **W3**（已交付能力的缺陷与债务 · 悬空承诺）｜ 无版本单元格 |

## 分层模型架构（v3.x 远景概述）

核心驱动力 = **数据主权**（企业数据进 API key 大模型 = 一定被拿去训练）。三层模型 + Harness 路由：云端档负责规划推理 → 翻译成标准化指令 → 本地档执行工作流判定与多步 workflow → 本地管道档跑固定管道（模板/格式/字段提取）。敏感数据只在本地处理，通用知识才走云端。**具体模型规格不写死在文档层**——由业务窄域宽度、延迟预算与客户硬件决定，路由层只认抽象档位。**约束层只做模型路由（`model-router.ts` 已有云端两档 / 本地两档插槽 + 判定档 + 拦截出口），通用大模型精调属模型层非开源范围；决策模型为约束层自有底座，随本仓开源。** 路由层本体已在位、不依赖精调模型（调用侧分流归位 [v1.5.4](./changelog/v1.5/v1.5.4.md)）；**外部 AI 节点治理接入见 [v1.5.4 第五章](./changelog/v1.5/v1.5.4.md)**（不做「引擎烧进 USB」的运行时合体，改为 DeepSeek harness 造节点 + LangChain/LangGraph 编排 + 本仓治理接入——版本边界纪律下归位 V2.0 前）；v3.x-v4.x+ 剩企业专属小模型精调（QLoRA distill 轻量化）。完整技术骨架（Mermaid 图 + 选型表 + 实现难度）见 [PHILOSOPHY · 远期演化愿景](./PHILOSOPHY.md#远期演化愿景从内置小模型到自动化企业后训模块)。
