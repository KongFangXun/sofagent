# sofagent 叙事标准（Narrative Standard）

> 适用范围：sofagent 全部对外与核心文档——双语 README、HANDBOOK、ARCHITECTURE、PHILOSOPHY、VALIDATION、WIKI、DEVELOPMENT、FDE/（README 与 GUIDE）、发布物文案。
> 本文档 = 全站叙事 SSOT：主轴、术语、结构公式。改任何对外文案前必读，改动后同步更新。

---

## 一、主轴（唯一）

**sofagent 全部叙事的主语是同一件事——判断（该不该做、做到什么算好、谁拍板）。**

- **进场**：把判断写成文件（工作流梳理、本体数据构建、AI 节点部署、merge_criteria / approver / trigger 冻结）
- **离场**：按文件执行与审计（7×24 巡检、25 条规则裁 git diff 硬证据、进化时写回）

一切对外表述必须能挂到这条主轴上。讲某个能力时先问：它是判断的生成、执行、验证还是沉淀？

## 二、术语决策（已拍板，全站生效）

| 术语 | 决策 | 理由 |
|---|---|---|
| **判断 / 判断力** | 叙述用「判断」；「判断力」仅保留两处：命题专名「判断力上移」、评估维度「判断质量」 | 「判断力」中文语境难解且学院派；降词后语义通顺 |
| **判据** | 定位层术语，正式使用 | 「判据」= 判断的依据（merge_criteria / approver / trigger / ontology）；中文可懂（判案的依据）；PHILOSOPHY「没有业务判据可审」已在用 |
| **部署 AI 节点** | 保留「部署」 | FDE 语境指交付动作，不违反马鞍铁律；普通人可懂 |
| **总称** | 不造新总称词（不叫「判据机器」等） | 定位句用动作表述：「把业务判断写成判据，让系统替你执行它、审计它」 |
| **动作控制 / 判据控制** | 边界表述术语 | 平台治动作（能不能删库，generic），sofagent 治判据（交期对不对，业务）；两层互补不互替 |
| **纳管** | 不使用 | 用户否决——普通人难懂 |
| **数字员工 / 硅基员工 vs 7×24 自动执行任务** | 对外产品文案（README 首屏 / 发布物）统一用「7×24 自动执行任务」；深度文档沿用行业原词，判据是语境三条件——① 管理哲学论述（岗位/绩效/准入/边界）② 转述行业机构观点（用原词是学术诚实）③ 语法必要性（需与「人」对举或作主语时，动词短语塞不进主语位）。直接引文任何情况下不改 | 品牌口径管对外，学术诚实管转述；语境判据优于文件名单 |

## 三、三件事的表述公式（消割裂感）

旧形态（禁止再用于新文案）：
> ~~进场梳理工作流、构建本体图谱、部署 AI 节点、离场后 7×24 自己跑~~

新形态（主轴从句结构）：
> **进场把业务判断写成文件**（梳理工作流、构建本体图谱、部署 AI 节点），**离场按文件执行与审计**

要点：
1. 主语统一为「判断」，三件事变从句，割裂感消失
2. 括号内的具体动作保持递进链：工作流 → AI 节点 → 每次变更（判据的来源 → 载体 → 落点）
3. GitHub 面保持书面语，不用纯口语动词化

## 四、定位句（分层）

| 场景 | 句子 |
|---|---|
| 一句话（对外） | sofagent 把企业的业务判断写成判据，让系统替你执行它、审计它——人走了，判断还在 |
| 管什么（三层） | 提示工程管「说什么」，上下文工程管「知道什么」，约束工程管「跑在哪」，sofagent 管**判据**——交期改得对不对、报价能不能发 |
| 边界（vs 平台） | 平台拦得住 Agent 删库，拦不住 Agent 把交期改错——「交期对不对」不在平台的知识里，在你的本体数据里 |
| 护城河机制 | 平台吸收的是动作控制，吞不走判据控制——平台在教育「Agent 需要被治理」这个市场，判据层站在它教育完的地面 |

## 五、文档分工与主轴落位

| 文档 | 角色 | 主轴落位 |
|---|---|---|
| README（双语） | 门面 | 两相位结构（进场生成判断 / 离场驻留判断）+ 核心特性两相位分组 |
| HANDBOOK | 用户手册 | 能力列表两相位三组（进场 / 离场 / 全程底座）+ 5 分钟速览 |
| PHILOSOPHY | 设计哲学 | 产品哲学三段 + §一判断主轴导读 + 两相位节（主轴最佳载体）+ 判据定位句 |
| ARCHITECTURE | 架构参考 | 心智模型 + 对外核心能力节「控制的两层」 |
| VALIDATION | 行业印证集 | 每节独立成立，无叙事线要求；主轴只出现在定位句 |
| WIKI | 导航索引 | 产品叙事节主轴引导句 |
| DEVELOPMENT | 开发者参考 | 开篇主轴句即可，正文技术叙述不强制 |
| FDE/README + GUIDE | 方法论 | README 开篇主轴句；GUIDE 教科书体不动 |

## 六、能力叙述纪律

1. **能力列表按两相位分组**（进场生成判断 / 离场驻留判断 / 全程底座），不按交付版本堆积罗列
2. 新能力入列表时先判相位归属，再选组
3. 版本号标注（如「v1.4.2」）保留在条目内，不作为分组依据

## 七、禁用形态清单

- ❌ 四并列 feature-list 形态的「三件事」（本标准 §三旧形态）
- ❌ 「判断力」作叙述词（保留两处除外，见 §二）
- ❌ 「纳管」「接管」等用户否决词
- ❌ 「判据机器」等新造总称
- ❌ GitHub 面纯口语动词化（如「帮你盯着」作主叙述）

## 八、变更纪律

- 改主轴相关文案前：grep 断言面（acceptance-test.sh / doctor / storefront 等是否锚定旧串）
- 改完必扫 U+FFFD（node，禁 shell）
- 双语 README 同批同步
- 本标准与实际文案漂移时，同批修齐
