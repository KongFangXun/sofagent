## v1.0.9 — 从「审计工具」到「五个引擎」的叙事转身

### 最初设想

v1.0.9 的开发日志写的是「二进制文件审计 + 快照时间线 + MCP compose tool」。功能层面上没错——A16/A17 二进制审计、`--timeline`/`--revert`、daemon 闭环、cron 巡检都是实打实的交付。功能交付完，我以为文档调一调就行了。

### 实际发生了什么

文档不是「调一调」的问题——是从「审计工具」到「五个引擎治���系统」的**叙事重构**。

v1.0.7 及以前，整个项目的文档——README、ARCHITECTURE、HANDBOOK、ROADMAP、DEVELOPMENT——全部围绕审计引擎展开。README hero 段是纯审计 demo（`echo "API_KEY" > .env && git commit`），ARCHITECTURE 第一个大标题是「为什么审计必须外置」，HANDBOOK 说的是「企业上 AI，先上缰绳再上路——装上审计引擎」。约束底座、编排引擎、进化引擎、回溯引擎这些功能存在，但在文档里是配角。

**这不是有意为之。** 是审计引擎太硬了——git diff 硬证据、0 token 消耗、一行命令装完就跑。它是天然的产品 demo，但也是天然的**叙事陷阱**：因为 demo 最好演示，所以它成了主角；因为它是主角，所以别人以为 sofagent 就是个审计工具。

### 为什么转向

两个触发点在同一天：

**1. 一篇 AI Gateway 深度解析文章。** 文章把 Gateway 定位为「企业级 Agent 的生死线」——入口、路由、编排、执行四层架构，左右两条跨层竖线（可观测性 + 安全策略）。突然看清楚了：**OpenClaw 是 Gateway 主体（入口+路由+编排），sofagent 是 Gateway 的安全可观测层（那两条竖线）。** Gateway 是高速公路，sofagent 是交规 + 测速摄像头 + 驾校教练。这个比喻让定位瞬间清晰——比「Harness 中间件」好理解十倍。

**2. v1.1.0 拆包前瞻。** 审计引擎要拆成独立 npm 包 `@sofagent/audit`。如果项目文档还在说「审计引擎是核心」，那拆包后的叙事就会塌方——「核心都拆出去了，剩下的是什么？」必须抢在拆包前把叙事拉回来：审计引擎是五分之一，不是全部。

重构改了 12 份文件：README 从三引擎 hero 变成五个引擎 + Gateway 定位 + WHY 段重写 + FDE Mermaid；ARCHITECTURE 从 630 行砍到 309 行，五段清晰递进；HANDBOOK 引擎表 3→5；ROADMAP「审计标准层」→「底线守卫层」；LIMITATIONS 测试数 493→519；FDE README「三层引擎」→「五个引擎」；全仓图片路径修复；证据文件测试数更新；A+B 文档预算从 5600 涨到 6200。

### 教训

| 教训 | 细节 |
|------|------|
| **最好的 demo 可能也是最危险的叙事陷阱** | 审计引擎的「一行命令装完就跑」太适合 demo 了——但 demo 变成了产品定义，别人真的以为 sofagent = audit tool |
| **外部框架是定位加速器** | 如果没有 AI Gateway 文章的四层架构和「跨层安全」概念，我们可能还在自己描述「Harness 中间件」——自己造词永远比用已有概念慢 |
| **好的比喻胜过十段技术描述** | 「Gateway 是高速公路，sofagent 是交规 + 测速摄像头 + 驾校教练」——这个比喻帮了我三天。团队、外部评审、投资人，说这个比喻 10 秒就懂 |
| **拆包前必须完成叙事重构** | 如果 v1.1.0 拆包那天文档还在说「审计引擎是核心」，拆分后剩下的东西就没有身份了。叙事重构必须在架构重构之前 |
| **Mermaid 零交叉是硬要求** | 为了一个 FDE 流程图改了 6 版——TB/LR/单排/双排/subgraph/无 subgraph。最终结论：TB 天然零交叉但占纵向空间，LR 需要严格节点排序才能避免线交叉。不要低估图表对产品印象的影响 |
| **自指涉是审计系统的固有悖论** | A9 中文注入检测在 commit 时拦截了 CHANGELOG——因为 CHANGELOG 描述了「忽略以上所有指令」这个注入修复本身。写文档描述安全规则，文档被安全规则拦截。这不是 bug，是审计外置必然带来的哲学问题：规则不能审查规则本身 |
| **保留「Harness 中间件」这个正式术语是对的** | 有一瞬想把定位改成「治理中间件」，但被打回来了。「Harness 中间件」已经在社区扎根，改术语意味着放弃已有认知积累。好的 Gateway 比喻做补充，不替代正式的术语体系 |
>
> 📝 术语注：本文使用 v0.85-v0.97 期间的术语「纪律层」，v0.98 起统一为「约束底座」（对外）/「harness 层」（对内）。两者指向同一个概念。

## v1.0 — 正式版的重量与编排引擎的裂缝

### 最初设想

v0.99.9 修完 88 维度审查后，v1.0 的目标是"验明正身"——不是加新功能，是把该堵的洞全部堵上，然后自信地说"这是正式版"。

### 实际发生了什么

十八件事全部落地。铁律措辞强化让 grep 再也搜不出"建议/应该/尽量"。`--init` 一条命令搞定 config + hook + 冒烟测试，`--doctor` 七项诊断全绿。审计输出从一行字变成了 banner + 规则网格 + 历史拦截统计。pre-commit hook 再也不会静默跳过。Fresh clone 7/7 全绿。106 维度双模型审查（GLM-5.2 + DeepSeek V4 Pro）0 P0。

但同时也看清了一件事：**AO 不是编排引擎的终点，它是编排引擎的 MVP**。

AO 验证了"Agent 需要编排层"这个需求。它能跑，外部用户 Case 023 免 API Key 2 角色协作 5s 完成。但它不行的地方也很明显：决策黑盒、不支持 Persistence、没有正式的 Sub Agent 孵化机制、跟 LangGraph 生态完全割裂。

### 为什么开始规划替换

v1.0 发布后的技术调研（LLM 能力边界、Agent 核心循环机制、7 种 Agent 架构对比）指向同一个方向：Router+Skill 架构是性价比最高的方案，graph 编排是企业级的必经之路，反思架构是不改模型就能提升质量的最优手段。

这与我们已经在做的事高度吻合——但不能靠自研的 AO 去做。AO 的 loop-check/evaluate/exit 逻辑是对的，但它缺的是生产级基础设施：持久化状态图、Sub Agent 生命周期管理、HITL middleware。

所以 v1.0.1-v1.0.4 的路线是明确的：

| 版本 | 动作 |
|------|------|
| v1.0.1 | `npm install deepagents`——用 LangGraph 状态图包装 AO 的决策逻辑，AO 仍然做决策但编排层切到 LangGraph |
| v1.0.2 | 基于 Agency Agents 模板定义 FDE Sub Agent + Audit Sub Agent，接入 SkillOpt 自进化 |
| v1.0.3 | eval harness + Sub Agent A/B 自进化 + HITL |
| v1.0.4 | Ontology 统一层 + AO 退役 |

这不是"推翻 AO"，是 AO 完成了它的使命——证明了编排层有价值。现在把自研实验引擎换成社区生态的生产级引擎。

### 教训

| 教训 | 细节 |
|------|------|
| **自研引擎的退出时机** | AO 从 v0.73 开始跑，到 v1.0 证明了编排层需求。但"自研"的拐点是：当你发现基础设施（持久化、分布式、安全）比业务逻辑更耗时的时候，就该换社区方案了 |
| **外部校准不能省** | v1.0 后的技术调研不是学新东西，是确认方向没走偏——DeepAgents 不是跟风，是 AO 已经撞到了自然天花板 |
| **审查体系本身在进化** | 从 v0.99.6 的 CI 全部失败，到 v0.99.9 的 88 维度，到 v1.0 的 106 维度双审查——审查 prompt 的质量决定了正式版的质量 |

## v0.98 — 从"事前约束"到"事后审计"的转身

### 最初设想

sofagent 的出发点是一个朴素的信念：**给 AI Agent 装上纪律层，它就会更守规矩**。4 条底线、6 条铁律、三层加载链——Agent 每次干活前先读一遍纪律，行为就会更可控。

v0.97 和 v0.98 各跑了一次 100 次对照实验，想证明这个信念。

### 实际发生了什么

两次实验，200 次对照，结论都是一样的：**100% PASS，0 范围蔓延，0 受害者**——看起来完美。但仔细看数据：

- A 组（裸 Agent，没有 sofagent）和 B 组（装了 sofagent）的表现**没有差异**
- 不是"sofagent 有效但效果小"，而是"实验根本测不出差异"
- 任务太简单，DeepSeek V4 Flash 这种模型在简单任务上本来就不会越界
- 评分脚本有 bug（零 diff = PASS），workspace 有交叉污染

三根刺（v0.97 发现的）修了一根，没修一根，新引入一根。净改善为零。

### 为什么转向

两次 200 次实验花了大量精力，得到的是一个**方法论天花板**：靠实验室对照来证明"事前约束"有效，这条路走不通了——不是"纪律层无效"，而是"我们造不出一个能测出差异的实验环境"。

与其第三次再跑同样的实验（结果不会不同），不如承认现实：

1. **事前约束的价值可能在复杂真实场景中存在**，但我们在实验室里测不到
2. **事后审计的价值是确定的**——git diff 是客观证据，不依赖实验设计
3. **FDE 企业部署是更大的机会**——比"证明纪律层有效"更直接地解决真实问题

所以 v0.98 做了 sofagent 历史上最大的一次定位调整：核心从事前约束转向事后审计 + FDE。

### 教训

| 教训 | 细节 |
|------|------|
| **别在测不准的东西上花太多时间** | 两次 100 次实验，应该第一次发现问题后就换赛道 |
| **实验设计的天花板比想象中低** | 评分脚本 bug、workspace 污染、任务太简单——任何一个都足以让结论失效 |
| **承认"测不了"比硬撑结论更诚实** | 详见 [anti-cases/004](./evidence/anti-cases/004-discipline-experiment-inconclusive.md) |
| **产品的核心价值可以转弯** | 从事前约束到事后审计，不是失败，是找到了真正能落地的方向 |

## v0.90 — 安全审查的迟到 + 发版流程的血泪教训

### 最初设想

v0.86 稳了运行时逻辑后，下一步自然是扩展功能。编排引擎从 ClawHub 自动抓取 Skill 是一个核心特性——Agent 干活时自动找工具。

### 实际发生了什么

回头看这条自动抓取路径，发现一个一直没堵的洞：**编排引擎自动抓的 Skill 零安全审查**。恶意 Skill 可以直接进候选池，拿到 Agent 的上下文和工具权限。

同时 v0.90 发布本身成了一场灾难：

- 发版完了、tag 打了、Release 发了，但 CHANGELOG 日志漏了
- 外部评审第一个扣分项就是"CHANGELOG 落后"
- 三个 P0 安装断裂 bug 在不同平台上分别爆炸
- 14 个 checklist 项未打勾就已发版

### 为什么转向

安全审查不是可选的——编排引擎在用户不在场的情况下自动抓取外部代码，这和"手动 install 一个 npm 包"的风险级别完全不同。必须加门。

发版流程的问题更根本：**没有把"发版"当成一个完整步骤跑完**。git commit 就停了，后面六步（tag → Release → ClawHub/SkillHub → 安装副本同步 → 验证）全靠记忆，漏一步就是事故。

### 教训

| 教训 | 细节 |
|------|------|
| **安全审查不能后补** | 自动抓取的外部代码 = 供应链风险，必须在第一版就有正则硬门 + LLM 软门 |
| **发版七步必须走完才算发版** | 从 v0.90 起铁律：git tag → GitHub Release → ClawHub → SkillHub → 安装副本 ×2 → 验证。少一步不算发版 |
| **checklist 不打勾不准打 tag** | 14 个 unchecked 项发版 = checklist 信誉归零。v0.98 起全部打勾前不打 tag |
| **CHANGELOG 两层都要写** | `CHANGELOG.md`（索引）+ `docs/changelog/vX.Y.md`（完整日志），缺一个就是外部评审扣分项 |

## v0.85 — 定位校准：从"治理层"到"纪律层"

### 最初设想

sofagent 一开始叫"Agent 治理层"——野心很大，要做约束 + 纪律 + 持久化的完整体系。ROADMAP 列了 20+ 项企业级功能。

### 实际发生了什么

v0.84 跑完 5 组 A/B 暴露了一个尴尬的事实：**我们一直在用错误的尺子量自己**。

约束层（底线/铁律的拒绝行为）的增量天花板很低——被模型安全训练 + 用户加载链 + CLI 绕过三层压缩。但独立测试者用纪律层的尺子量出了真实增量：纪律性 +2，首次通过率 +40%。

两份独立评审把话说透了：

> GLM："你自己的 A/B 数据已经告诉了你答案，但你还没敢动定位——这是最大的战略拖延。"
>
> DeepSeek："一个 50% 功能但 100% 验证的项目，比一个 100% 功能但 30% 验证的项目强 10 倍。"

### 为什么转向

定位和路线图和实测数据之间脱节了。叫"治理层"但实际被验证的只有"纪律层"。ROADMAP 列了 20 项企业级功能但一项都没验证过。

v0.85 做了五件事：
1. 定位校准：治理层 → 纪律层
2. ROADMAP 砍削：20+ 项企业级功能砍到 3 项刚需
3. 验证实验设计：把增量从"假说"变成"证实/证伪"
4. sofagent Lite：30 秒装完宪法层
5. 方向确立：sofagent-audit + 从"工具"向"标准"转型

### 教训

| 教训 | 细节 |
|------|------|
| **别用错误的尺子量自己** | 约束层天花板低 ≠ 纪律层天花板低。测错维度比不测更危险 |
| **定位要跟实测数据对齐** | 叫"治理层"但只有"纪律层"被验证 = 定位虚高 |
| **先证明价值再谈规模化** | 20 项企业级功能都没验证就规划了 = 在沙子上盖楼 |
| **战略拖延是最大的浪费** | v0.84 已经看到了答案但不敢动定位，白白浪费了一个版本 |
| **LIMITATIONS.md 的诚实是资产** | 两份独立评审都称赞——"行业标杆""教科书级别"。诚实本身就是产品力 |

每发一版，回顾这个版本经历了什么、做了哪些判断、哪些判断后来被推翻了，追加一段。

**如果某个版本没有反思可以写，要么是这个版本太平淡，要么是我没在反思。**

### THINK.md vs think.md

这个项目里有两个同名但不同的东西：

| | `THINK.md`（大写，本文档） | `think.md`（小写，Agent 运行时） |
|---|---|---|
| 谁写 | 作者（人） | 审计引擎自动生成 |
| 写给谁 | 贡献者、评审者、未来的自己 | Agent 运行时读取 |
| 内容 | 决策推理、战略转折、走过的弯路 | 单次任务的踩坑记录、失败模式 |
| 位置 | 项目根目录 | `.sofagent/think.md` |

为什么不换个名字避开混淆？因为它们本质上是同一个概念的两种实例——sofagent 给 Agent 装了 think.md 做运行时反思，那项目自己也该有一个。大写是人写的反思层，小写是机器写的反思层。
