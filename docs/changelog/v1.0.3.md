## 背景

v1.0.2 做了 FDE Sub Agent + Audit Sub Agent。但它们是静态的——Agent 配置写完就不会自己优化。v1.0.3 给 Sub Agent 装上进化引擎：用 A/B 测试验证哪个版本好，用 eval harness 做量化评分，用 HITL 在高风险操作时让人介入。

## 交付内容（4 件事）

### 1. eval harness——评分体系

DeepAgentsJS 自带 `@deepagents/evals` 包，本版接入 sofagent 体系。

| 组件 | 做什么 |
|------|------|
| golden set | FDE 部署时为每个 Workflow 节点建一批标准 case（已知正确答案的任务），作为回归测试 |
| offline eval | 非实时的基准评估——Skill 或 Sub Agent 更新后，先跑 golden set 看评分 |
| online eval | 真实任务运行中采集的指标——正确率、成功率、Token 消耗、用户反馈 |
| 成本基线 | 从 task/logs 提取历史消耗 → 建立基线（均值 ± 标准差） → 异常检测 |

**数据流向**：
```
golden set（FDE 部署时人工标定）
  ↓
offline eval（SkillOpt 训练 / Sub Agent A/B 时）
  ↓
online eval（实际任务运行中）
  ↓
scoring.md → SkillOpt reward / Agent A/B 评分
```

### 2. Sub Agent A/B 自进化

Sub Agent 配置本身也需要进化——tool 组合、middleware 选择、prompting 策略，这些不是 SkillOpt 能管的（SkillOpt 只优化文本文档）。

**A/B 测试流水线**：
```
Agent A (current) 和 Agent B (candidate) 同时跑同一 golden set task
  → 比较：正确率？Token 消耗？用户满意度？
  → A 胜 → 丢弃 B，记录「candidate 未达标」
  → B 胜 → B 替换 A → git commit + SOFAGENT_AUDIT_EVOLVE 标记
  → 分数接近（差异 < 阈值）→ 保留两个版本，人工裁决
```

**触发条件**：
- 累积 N 条 real task 数据后自动触发（config 可配置）
- FDE 手动触发：`sofagent evolve --agent fde-sub-agent`

**和 SkillOpt 的分工**：

| | SkillOpt（v1.0.2） | Sub Agent A/B（v1.0.3） |
|------|------|------|
| 优化对象 | Skill 文档（文字内容） | Agent 配置（tools/middleware/prompt） |
| 方法 | 文本编辑（add/delete/replace） | 配置变体 + A/B 对比 |
| 粒度 | epoch-wise 批量训练 | 逐配置迭代 |
| 引擎 | `skillopt-sleep` CLI | eval harness + DeepAgents |

### 3. HITL middleware——高风险人工审批

DeepAgentsJS 内置 HITL middleware，本版接入 sofagent 的风险分级系统。

> 行业分析表明，HITL 并非全量审核——仅约 1% 的高风险输出需要人工介入。四类必须强制人工审批的场景：涉及人身财产安全的决策、涉及法律合规与品牌声誉的输出、涉及关键业务协作的敏感操作、AI 系统冷启动阶段。详见 THANKS.md 人工审核条目。

**风险分级**（从 entry-gate 配置读取）：

| 级别 | 操作类型 | 行为 |
|:--:|------|------|
| 🟢 低风险 | 只读查询、代码审查、生成报告 | 自动放行 |
| 🟡 中风险 | 修改 Skill 文件、更新知识库、修改 Workflow 定义 | 需确认（但可自动放行超时场景） |
| 🔴 高风险 | 直接操作生产环境、删除数据、调第三方付款 API | 必须人工审批 |

**和 sofagent-audit 的关系**：HITL 是事前审批，sofagent-audit 是事后审计。两者不替代——HITL 拦可以拦的（高风险操作），审计引擎看所有的（git diff）。

### 4. A15 审计规则——动作约束验证（Ontology 第 3 步）

v1.0.2 Workflow 节点声明了 `actions`（能做什么操作、在什么对象上、有什么约束）。v1.0.3 审计引擎检查 Agent 实际执行的动作是否在声明范围内。

```
A15 不越动作 [约束]: Agent(AP-审批) 对 Payment-2026-001 执行了 approve
  → 检查 AP-审批 的 actions 声明
  → approve 在 [approve, reject, escalate] 内 ✅
  → amount 10万 <= Supplier.credit_limit * 50% = 25万 ✅
  → 通过
```

```
A15 不越动作 [约束]: Agent(工程-部署) 对 Payment-2026-003 尝试执行 approve
  → 检查 工程-部署 的 actions 声明
  → approve 不在 node 声明的 actions 内 ❌
  → 标记 FAIL
  → 建议：如确需此操作，更新 workflow.yml 的 actions 声明
```

> ⚠️ **已知盲区——跨 Agent 约束接力**：A15 当前只验证单 Agent 单次 action。跨 Agent 的约束传递（如 AP-审批 设定的额度上限，AP-执行 时是否遵守）需要 Ontology constraints 层就绪（v1.0.4）。届时扩展为 A15-multi，检查 Agent B 执行时是否遵守 Agent A 审批时声明的约束边界。
