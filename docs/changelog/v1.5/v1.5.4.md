## 定位


> ⚡ **执行模块 · 路由决策链**——把一条决策链的两段一次交付：**往哪走**（模型路由层——云端规划 / 本地执行 / 管道分层 + 敏感度 fail-closed + routeReason 留痕）与**去不了怎么办、怎么判**（本地槽位排队与判定分层——本地并发槽位信号量 3–5 + 排队超时按合规升级云端 + L0 声明式映射 / L1 embedding 分类 / L2 难例兜底，判定链不占本地主模型槽 + 决策下达面补齐 v1.4.9 承接面的反向通道）。

> ⚡ **执行模块 · 凭证与验证**——执行层的两条安全线：**凭证不出 Vault**（Agent 代码 / 日志 / 审计面均见不到 token 明文，轮换与吊销在位）与**结论要多方表决**（同任务 N 实例并发 + 交叉比对 + 多数表决，分歧超阈值路由 HITL 或升级大模型重跑）。

> 🤝 **执行模块 · AI 节点治理接入（2026-09-22 归位再分配迁入）**——外部 Agent 节点纳入治理面：节点本体用 DeepSeek harness 加 plugin 构建、编排用 LangChain/LangGraph，本仓不做运行时合体，只做治理接入（注册/事件挂接/出站管控消费/引用契约）。分工三句：DeepSeek harness 造节点（生成侧），LangChain/LangGraph 编排（工作流侧），本仓治理节点（判定与审计侧）。

> 🧾 **执行模块 · 授权与凭证对账（自探索方向迁入 · 2026-09-22 用户拍板）**——两处证据到位后做交叉对账：**授权记录**（谁批的 / 批了什么——[v1.5.2 第七章](./v1.5.2.md) 的 mandate 签发面）与**凭证签发记录**（发了什么范围——本版第三章 Vault）分属两处，两者不一致即风险（批了一件小事却发下大范围凭证）。本章把两面对起来：范围不一致即判定为越权风险并留痕。

## 二、本地槽位排队与判定分层（一体机在线服务面 · 2026-09-18 用户拍板独立成章）


> **形态归属**：`[主干]`（判定·槽位/分层/决策下达）｜ L1 关档
>
> 📋 **来源**：排期准入判据 **W1 具名消费方**（企业内网私有化部署的一体机形态——模型全部跑在客户自有硬件上，本地推理槽位是稀缺资源，真实客户诉求）+ **W2 链路缺口**（一体机**在线服务链路**缺这一环；数据飞轮链路 session→分拣→脱敏→数据集→训练→灰度已在 v1.4.9 整链成型）。
>
> **与第一章的关系**：第一章「模型路由层」解决**往哪走**（云端/本地/管道分流决策）；本章解决**去不了怎么办**（本地并发槽位满了如何排队与升级）与**怎么判**（判定链如何不占本地推理槽）。两章同属一条决策链的相邻段，分章为保交付面清晰。
>
> **与 v1.4.9 第七章的关系（双向闭环）**：v1.4.9 已交付 router 伴生 exporter——**数据承接面**（router → 引擎：过站 session / usage / 路由决策推送 + HMAC 验签 + 幂等）。本章补**决策下达面**（引擎 → router）——引擎判定出的去向决策下达给 router 执行，两向合起才是完整回路。
>
> **纪律承继（不自研 router 本体）**：v1.4.9 已拍板「router 基于开源自建、引擎不自研 router 本体、key 发放/吊销/管理归 router」——本章**不碰转发实现、不碰 key 生命周期**，只交付决策产出、槽位管理与决策下达协议。

### 交付

| 组件 | 能力 |
|------|------|
| **本地并发槽位信号量** | 本地推理槽位上限可配（一体机默认 3–5）；超限请求排队（FIFO + 优先级），前台可见排队位置与预估等待；**排队是治理策略不是模型能力**——vLLM 双实例无全局视图，router 无 GPU 槽位概念，引擎是唯一看得到全局的层 |
| **排队超时升级** | 排队等待达阈值 → 按合规路由决策**自动提议转云端**（合规允许出门时）或继续等待（信创全封场景）；升级动作留痕 routeReason，可查可举证 |
| **判定分层编排（L0/L1/L2）** | **默认不用本地主模型做判定**（占槽 / 循环依赖 / 判定延迟放大 / 判错路由错下游放大四问题）：**L0 声明式映射**——请求来自已定义 workflow 的 Agent 节点，直接查节点级 modelPreference 映射（复用 v1.4.8 已交付 schema，零模型成本）→ **L1 语义分类**——自由文本走 embedding 相似度分类（复用本地 RAG 的 embedding 模型，零新增组件，不占本地推理槽）→ **L2 难例兜底**——置信度低于阈值时按配置分流（判定特征走云端强 API / 信创场景本地低峰复核） |
| **L1 判定通道接口（DecisionChannel）** | L1 语义分类的**可插拔判定源协议**（研究收编：System One 决策模型 Jev 启发，2026-09-19 拍板）：`judge(state, questions) → typed answers + 概率` 标准接口，Noul/Choice/Score 三问题原语语义对齐。**通道而非依赖**——引擎定义接口与编排，实现由用户按 TrainChannel 同款纪律自带（云端 provider 走用户 key opt-in，默认关闭；本地部署走开源并行约束解码方案——KV cache 广播 + 单次前向出全部字段，开源 RLCD 小权重可跑一体机，数据主权不破）。判定结果带概率落 decision-log 留痕（类型化输出天然可审计）。**边界**：决策模型不进信任地基（其可被 state 内容操纵的失灵面已知）——只坐确定性规则之后的语义兜底层，24 条审计规则判定面零改动 |
| **决策下达面** | 引擎产出去向决策（目标模型 / 降级路径 / 槽位归属）按标准 schema 下达 router 执行（与 v1.4.9 exporter 同族 schema，反向）；schema 校验 fail-closed，坏格式拒绝下达而非静默放行 |

## 三、凭证隔离 Vault（OMA 启发）


> **形态归属**：`[通道]`（**执行层安全基础设施**——凭证托管/轮换/吊销是通用轮子，换 HashiCorp Vault 价值不受损；**「Agent 代码碰不到 token」的拦截约束留主干**）｜ L1 关档
>
> 📋 **探索方向表收编**：沙箱发 HTTP 请求时动态注入凭证、Agent 代码碰不到 token——执行层安全基础设施，v1.3.7 虚拟 key 凭证边界已部分覆盖，完整 Vault 前移本版。

### 交付

| 组件 | 能力 |
|------|------|
| **Vault 服务** | 凭证托管：Agent 运行时凭证不出 Vault（动态注入请求头，Agent 代码/日志/审计面均见不到 token 明文） |
| **轮换与吊销** | 凭证可轮换（定时/事件触发）+ 单凭证吊销（泄露响应） |
| **凭证范围声明（闭合审计盲区）** | Vault 侧掌握「这条凭证是什么、属于谁、本任务申请了什么范围」——除托管 / 轮换 / 吊销外，**产出一条凭证范围声明**（本任务申请范围 + 实际签发范围 + 比对结果）并挂审计链。**为什么**：审计面的**凭证范围**盲区（凭证是否为本任务的**最小授权**）本质是**证据面缺口**——A22 查「有没有提权」查的是权限本身，而「权限与任务的匹配度」需要 Vault 侧的事实才可观测。**事实不可观测时加规则无用**：只会得到永远弃权或永远放行的假规则。**行业印证（凭证与能力解耦）**：Meta Muse 零日漏洞实证反面教材——一个未校验的配置端点即可窃取 token 全权接管，根因即 token 同时承担「身份」与「能力开关」两职（[ARCHITECTURE](../../ARCHITECTURE.md) 过程/结果面分工段有判据全文）；Vault 的「凭证不出托管 + 范围声明 + 授权对账」正是把两职拆开的工程形态——**界面开关状态不作为控制面依据，控制面只认数据面事实** |

### 验收标准

- [ ] Agent 沙箱 HTTP 请求经 Vault 动态注入凭证，代码层拿不到 token
- [ ] 凭证轮换/吊销可用
- [ ] `npm test` 全绿

| **插件可用性预检（挂载探针）** | 第三方插件挂载前跑四段预检（与 [v1.5.2 第九章](./v1.5.2.md) 我方插件同款验证面）：声明的事件主干有没有 / 调的服务在不在 / apply 是否成功 / 探针事件是否触发产出——**四段全过标「可用」，任一不过标「只挂载不生效」并明示缺口**（用户看到的是"这个插件读得出/读不出"，不是装完才发现空壳）。**预检结论随版本复检**：宿主接口集升级（DSH 发新版）时既有插件预检重跑——上次可用不代表这次可用，接口集漂移靠复检暴露，不等运行时炸 |

## 七、授权面与凭证面对账（两处证据交叉核验 · 自探索方向迁入 · 2026-09-22 用户拍板）


> **形态归属**：`[主干]`（判定·授权范围与凭证范围一致性）｜ L1 关档
>
> 📋 **为什么现在排**（2026-09-22 用户拍板 · 版本边界纪律）：本项原为探索方向，触发条件写的是「凭证范围声明与门禁三态记录均落地后」。改判理由是**版本边界纪律**——本项属 V2.0 前治理面能力，V2.0 后无承接窗口；而**两处前置证据在本版内全部就位**（本版第三章 Vault 出凭证范围声明 + [v1.5.2 第七章](./v1.5.2.md) mandate 出授权三元素），时机上「等」已无意义。
>
> 📋 **为什么必须对账**（两处记录各自的盲区）：授权记录只说「批了什么」，凭证记录只说「发了什么」——**单看任一侧都自洽**。风险恰恰在两侧之间：批了一件小事却发下大范围凭证，两张表分开看都「合法」。对账是把两个自洽面之间的**缝**变成一条可判定的命题。

### 交付

| 组件 | 能力 |
|------|------|
| **范围一致性判定** | 以授权三元素（范围 / 时效 / 审批人）与凭证范围声明逐项比对：凭证范围 ⊄ 授权范围 / 凭证时效 > 授权时效 / 无对应授权记录 ⇒ **越权风险**判定 |
| **证据取用不改写** | 两侧记录均为**只读取用**（本版不改 mandate 与 Vault 的落盘 schema），对账结论另立记录并挂 HMAC 链 |
| **错位即留痕** | 不一致即进 decision-log 并挂链（谁在何时用哪个授权发了哪个范围凭证）——对齐本版第五章出站裁决留痕形态，不另立通道 |
| **对账面可关** | 默认关（L1）——关闭后不产生对账判定与记录，两侧行为与今日一致，不留半开状态 |
