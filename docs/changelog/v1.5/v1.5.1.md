- **设备侧验签无可信根**：`engine/daemon/src/ota/upgrade-executor.ts` 的 `verifyDeliverySignature`
  第三步 `verifyAgentIdentity(asSignerIdentity(sig))` 只证明「摘要是由**信封自带的那把公钥**签出」这一
  **自洽性**——**无平台公钥 pin / 无 principal 白名单 / 无设备注册表绑定**（本目录 `trusted|allowlist|pinned`
  零命中）。⇒ 挡得住**篡改与传输损坏**，**挡不住**持有自洽密钥对的外来伪造签名者。
- **`device.task.dispatch` 零验签**：`engine/daemon/src/ota/subscriptions.ts` 的 `deliverTaskDispatch`
  **全路径无任何 `verifyDeliverySignature` 调用**——该调用只出现在 `device.deploy` 分支（:257）。
  任务下发通道目前**没有签名校验面**（升级面 `device.upgrade` 走执行器内部验签）。
- **接真实传输即成远程包注入面**：本章三条远程下发面（`device.upgrade` / `device.deploy` /
  `device.task.dispatch`）当前**未接真实传输通道**（npm registry / 制品库 / 安装脚本均为**注入端口**，
  缺省只落盘内联内容），故上述两项在本版**不可被外部触发**；一旦接上真实传输通道，它们会直接构成
  **远程包注入面**——信任锚与任务面验签须随该批落地。

## 七、审计输入面扩容（调用意图 + 结果文本 + 门禁留痕 · 2026-09-16 用户拍板排期本版）

> **形态归属**：`[主干]`（判定·审计输入面扩容——规则判定逻辑零改动）｜ L1 关档
>
> 📋 **本版事件总线的第一个消费方**：现有审计输入面是 **git diff（结果文本）** 单一通道——但 Agent 的危险动作往往在**参数级**（`rm -rf` 的 path、写文件的落点、外发请求的目标 host），diff 只能看到事后的残留产物，看不到「调用意图」。本版借事件总线把审计输入扩为**双通道：调用意图 + 结果文本**。
>
> **与 v1.5.0 第十章的边界**：第十章做的是**接线**（把宿主事件位接到既有 bridge API，判定逻辑零改动）；本章做的是**消费**（把意图流做成审计输入面的第二通道，供规则判定与留痕举证使用）。审计仍零执行权限——事件流只读消费 + 落盘留痕；短路拦截属宿主事件位能力（第十章），不是审计越权。
>
> **不新增规则**：本章只扩输入面，规则判定逻辑零改动；新规则走 v1.5.3 第二 / 三章。
>
> **第三源：门禁留痕（补记录，不造流程）**——意图流记「**想干什么**」，还须一路记「**批没批**」。门禁判决记录 `TOOL_GATE` 的类型声明是「拦截 / 放行 / 告警」三态，实现**只落「告警」一态**（放行与拦截不留痕），本版一并补齐；人审支路 `hitl/resolved/*.json`（`approved` / `rejected` + 起止时间）**已在落盘、已被治理报表消费**，本版把它纳入审计输入面。**为什么**：只有意图流而无判决记录时，**「无记录」既可能是「合法放行」，也可能是「绕过门禁」，两者不可区分**——这是审计面对**授权过程**的失明。补齐后即可正向对账：**有动作、无放行、无批准 ⇒ 未授权执行**。
