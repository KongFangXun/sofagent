> ⚡ **编排模块 · 事件驱动**——业务节点从「指令驱动」升级为「事件驱动」：上游节点产出、外部事件（邮件到达/表单提交/定时器）自动触发下游节点，编排模块从「人来派活」变成「事件来了自己跑」。与 v1.3.8 cron + 依赖图同向但更彻底：触发源泛化到业务事件。外加理解债务应对——审计已覆盖「发生了什么」，补「为什么这么做」。

## 七、审计输入双通道（调用意图 + 结果文本 · 2026-09-16 用户拍板排期本版）

> **形态归属**：`[主干]`（判定·审计输入面扩容——规则判定逻辑零改动）｜ L1 关档
>


> 📋 **本版事件总线的第一个消费方**：现有审计输入面是 **git diff（结果文本）** 单一通道——但 Agent 的危险动作往往在**参数级**（`rm -rf` 的 path、写文件的落点、外发请求的目标 host），diff 只能看到事后的残留产物，看不到「调用意图」。本版借事件总线把审计输入扩为**双通道：调用意图 + 结果文本**。
>
> **与 v1.5.0 第十章的边界**：第十章做的是**接线**（把宿主事件位接到既有 bridge API，判定逻辑零改动）；本章做的是**消费**（把意图流做成审计输入面的第二通道，供规则判定与留痕举证使用）。审计仍零执行权限——事件流只读消费 + 落盘留痕；短路拦截属宿主事件位能力（第十章），不是审计越权。
>
> **不新增规则**：本章只扩输入面，规则判定逻辑零改动；新规则走 v1.5.2 第十 / 十一章。

### 交付

| 组件 | 能力 |
|------|------|
| **意图流接入** | 订阅 `tools/pre-execute` + `tools/result` 事件，落 `intent.jsonl`（tool 名 + 参数摘要 + 会话标识 + 时间戳；**参数经既有脱敏管线**处理后才落盘） |
| **双通道输入面** | 规则判定入口接受「意图 + 结果」两路输入——意图通道供**事前**判定（越界参数在执行前暴露），结果通道维持既有 git diff 事后判定 |
| **通道声明语义** | 规则显式声明取哪个通道（默认结果通道，意图通道 opt-in）——消灭「规则自己猜输入源」整类 bug（对齐探索项「审计范围语义一等公民化」的最小版本） |
| **同链留痕** | 意图流与结果流进同一 HMAC 链（条目类型区分）——举证时可对照「当时想干什么」与「实际改了什么」 |
