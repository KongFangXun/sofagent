## 定位


> 🔍 **审计模块 · 对外开放面**——审计对外可消费的两面：**数据面**（history 可查——MCP `audit_query` 只读 + 事件订阅推送）与**规则面**（ruleset 可导出——机器可读 JSON，导出格式即加载格式双向可逆），外加**举证面**（独立验签工具——第三方无需安装 sofagent 即可验 HMAC 链）。本版是审计模块「从内部审计走向对外可举证」的收口。

> 🔍 **审计模块 · 判定链与结论语义**——把「判定」管两头：**开工前**（五问判定链——健康 / 人审 gate / 证据等待 / 专注等待 / 配额，任一不过则挂起等条件满足，挂起非失败）与**结论后**（失效语义——结论不是永久有效，授权变更 / 压缩不兼容 / 风险升级三触发即标失效，失效结论不当新证据用）。与 [v1.5.3](./v1.5.3.md) 同属「审计模块自我完善」：那里保证规则**加载时**是对的，本版保证判定**开工前**成立、结论**消费时**还有效。

## 二、约束导出与证据链外部可验（24 条规则 → 机器可读 + 密码学可验）


> **形态归属**：`[主干]`（举证面·独立验签工具）｜ L1 关档（导出面可关，链本体不受影响）
>
> 📋 **约束导出通道缺口（规划文档 §2.5 四缺口最后一块）**（2026-09-01 拍板排期本版）：②workflow 容器 ③ontology_import ④ruleset 市场均已交付，仅剩 ①约束导出——24 条审计规则硬编码在 TS 里，外部（训练管线）无法机器可读消费。与第一章「audit 数据对外」同属审计模块对外开放面：**数据面（history 可查）+ 规则面（ruleset 可导出）**。v1.2.9 ruleset JSON 格式已定义机器可读格式，导出通道半成熟；v1.4.x 后训模块已交付，训练侧消费方就位。
>
> 📋 **2026-09-16 并入验签工具**（用户拍板）：与「规则可被外部消费」同属约束对外可消费面——审计证据链目前只能由 sofagent 自身校验，作为举证材料的可信度依赖维护方中立性；独立验签器把可信根从「信任 sofagent」换成「信任密码学」，且三仓共用（平台层 PR 审阅举证 / 模型层训练信号溯源 / 开源用户合规举证）。**边界**：只读校验，无写权限、不加载引擎代码。
>
> 📋 **2026-09-16 验签器扩双链**（用户拍板）：现状是审计数据面**双链只写一验**——history.jsonl 有 `--verify-chain` + doctor 校验通道，decision-log.jsonl（决策因果链，十万条级）100% 带链字段写入但零消费校验（`checkDecisionChainDetailed` 已实现并经 public-api 导出，生产消费方为零）。验签器出生即双链：同一次校验覆盖 history + decision 双文件，顺带补齐 decision 链的机内校验入口（`sofagent audit --verify-chain` 同批扩展）。

### 交付

| 组件 | 能力 |
|------|------|
| **规则导出 MCP tool** | MCP `ruleset_export`：24 条默认规则 + 已加载扩展规则导出为标准 JSON（与 v1.2.9 `--ruleset-path` 加载格式同构——导出格式即加载格式，双向可逆） |
| **规则语义元数据** | 每条规则附训练消费元数据（rule_id + 检测意图 + 违规样例 + 严重级别）——训练管线可直接把「约束」构建为 reward 信号或 SFT 语料 |
| **版本与指纹** | 导出物带规则集版本号 + 内容指纹（对齐 v1.4.1 可复现指纹——训练任务引用规则集版本可追溯） |
| **审计留痕** | 每次导出进 audit history（谁在何时导出了哪个版本的规则集） |
| **独立验签工具** | 单文件零依赖的哈希链校验器（`tools/verify/verify-chain.mjs`，裸 node 可跑）——输入 `history.jsonl` + 链头指纹，独立重算并校验 HMAC 链完整性；第三方（审计师 / 监管 / 法院技术顾问）无需安装 sofagent 即可举证。**输出三态**：链完整 / 某条断裂（给出条目号与期望值）/ 链头不匹配 |
| **decision 链双覆盖** | 验签器同批支持 `decision-log.jsonl`（决策因果链）——同一工具校验双链；机内 `sofagent audit --verify-chain` 同步扩展 decision 链校验（消费既有 `checkDecisionChainDetailed`，消除「只写不校验」通道缺口） |

## 四、审计结论失效语义（Codex Guardian 启发 · 2026-09-16 用户拍板排期本版）


> **形态归属**：`[主干]`（判定·失效词汇表与触发）｜ L1 关档
>
> 📋 **研究收编**（codex-rs [guardian/](https://github.com/openai/codex/tree/main/codex-rs/core/src/guardian) 源码核验）：Codex 给审查结论定义了一套**失效条件**（`GuardianReviewReason`）——`FreshRequired`/`StaleScore`/`AuthorizationChanged`/`IncompatibleCompaction`/`ElevatedRisk`/`ScoringFailure`。本仓现状：审计结论（history.jsonl）与 HITL 授权一经产生即视为永久有效，下游消费方无法判断「这条结论还能不能信」。与 [v1.5.3 第二章](./v1.5.3.md) 自测 schema 同属「审计模块自我完善」主题：那里保证规则**加载时**是对的，本章保证结论**消费时**还是对的。
>
> ⚠️ **马鞍边界（四问过筛已过，边界在此）**：只吸收「失效原因词汇表」与判定逻辑——属共享账本层豁免（词汇表不是执行器）。**不吸收** Guardian 的 reviewer pool / 同步审查会话 / 预热机制（那是审查的马场：换 fresh-eyes 或任何外部审查器，本失效语义价值不受损）。

### 交付

| 组件 | 能力 |
|------|------|
| **失效原因词汇表** | 审计结论 schema 新增 `invalidationReason` 字段（枚举：授权变更/压缩不兼容/风险升级/分数过期/需新鲜结论），对齐 Guardian 六原因语义取子集 |
| **失效判定钩子** | 三个事件触发失效标记：①授权或白名单配置变更（AuthorizationChanged）②压缩/摘要事件发生（IncompatibleCompaction——对应 L2 工具输出总结、加载链压缩）③后续轮次风险升级（ElevatedRisk——同一对象后续被更严规则命中） |
| **下游消费语义** | 带失效标记的结论不作为后续判定的输入（fresh-eyes 审查输入、HITL 免检依据、治理 KPI 统计均须过滤）——「过期结论不当新证据用」 |
| **留痕不删除** | 失效结论保留原文 + 失效标记（对齐 HMAC 链只追加不删改——失效是标记不是抹除） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/audit/src/decision-schema.ts` | 修改 | 结论 schema 加 `invalidationReason` 枚举字段（可选，缺省=有效） |
| `engine/audit/src/invalidation.ts` | 新建 | 三钩子：授权变更/压缩事件/风险升级 → 标记既有结论失效 |
| `engine/audit/src/__tests__/invalidation.test.ts` | 新建 | 单测（三触发路径/失效结论被下游过滤/原文保留） |

### 验收标准

- [ ] 失效原因词汇表落地（schema 字段 + 枚举值）
- [ ] 三触发钩子生效：授权变更/压缩事件/风险升级 → 既有结论标记失效
- [ ] 失效结论被下游过滤（fresh-eyes 输入/HITL 依据/KPI 统计）
- [ ] 失效结论原文保留（HMAC 链不破坏）
- [ ] `npm test` 全绿
