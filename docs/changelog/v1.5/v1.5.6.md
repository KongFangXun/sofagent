## 一、模型路由层（Harness 路由 · 云端/本地分流）

> **形态归属**：`[主干]`（判定·分流 + fail-closed + routeReason 留痕）｜ L1 关档
>
> 📋 **ROADMAP 分层模型架构**：云端档负责规划推理 → 本地执行档跑多步 workflow → 本地管道档跑固定管道。**引擎层只做模型路由（`model-router.ts` 已有云端两档 / 本地两档插槽 + 判定档 + 拦截出口），通用大模型精调属模型层非开源范围；决策模型为约束层自有底座，随本仓开源。路由层不依赖精调模型——对接现有云端 API + 本地推理服务（Ollama 等）即可交付。**

### 交付

| 组件 | 能力 |
|------|------|
  | **路由策略引擎** | 任务分级路由：规划类→云端强档 / 执行类→本地执行档 / 管道类（模板/格式/字段提取）→本地管道档——按任务类型+数据敏感度双维决策 |
| **敏感度路由** | 数据分级（公开/内部/敏感）自动决定可否走云端——敏感数据强制本地（fail-closed）；**分类输入前置件已前移 [v1.4.9 第八章](../v1.4/v1.4.9.md)（2026-09-08 拍板）**，本版消费分类结果做调用侧分流 |
| **路由可解释** | 每次路由决策附 routeReason（复用 v1.3.6 EndpointProfile + route-policy 模式；v1.4.9 session 承接的路由决策回流经本层全链路可查） |
| **降级梯队** | 云端不可用→本地承接（复用 v1.3.6 分级降级梯队） |
| **本地端点注册** | model-registry 注册本地推理服务端点（Ollama 兼容协议），云端/本地统一注册面 |

## 二、本地槽位排队与判定分层（一体机在线服务面 · 2026-09-18 用户拍板独立成章）

> **形态归属**：`[主干]`（判定·槽位/分层/决策下达）｜ L1 关档
>
> **形态归属**：`[主干]`（判定·槽位/分层/决策下达）｜ L1 关档
>
> 📋 **来源**：排期准入判据 **W1 具名消费方**（企业内网私有化部署的一体机形态——模型全部跑在客户自有硬件上，本地推理槽位是稀缺资源，真实客户诉求）+ **W2 链路缺口**（一体机**在线服务链路**缺这一环；数据飞轮链路 session→分拣→脱敏→数据集→训练→灰度已在 v1.4.9 整链成型）。
>
> **与第一章的关系**：第一章「模型路由层」解决**往哪走**（云端/本地/管道分流决策）；本章解决**去不了怎么办**（本地并发槽位满了如何排队与升级）与**怎么判**（判定链如何不占本地推理槽）。两章同属一条决策链的相邻段，分章为保交付面清晰。
>
> **与 v1.4.9 第七章的关系（双向闭环）**：v1.4.9 已交付 router 伴生 exporter——**数据承接面**（router → 引擎：过站 session / usage / 路由决策推送 + HMAC 验签 + 幂等）。本章补**决策下达面**（引擎 → router）——引擎判定出的去向决策下达给 router 执行，两向合起才是完整回路。
>
> **纪律承继（不自研 router 本体）**：v1.4.9 已拍板「router 基于开源自建、引擎不自研 router 本体、key 发放/吊销/管理归 router」——本章**不碰转发实现、不碰 key 生命周期**，只交付决策产出、槽位管理与决策下达协议。

### 交付

| 组件 | 能力 |
|------|------|
| **本地并发槽位信号量** | 本地推理槽位上限可配（一体机默认 3–5）；超限请求排队（FIFO + 优先级），前台可见排队位置与预估等待；**排队是治理策略不是模型能力**——vLLM 双实例无全局视图，router 无 GPU 槽位概念，引擎是唯一看得到全局的层 |
| **排队超时升级** | 排队等待达阈值 → 按合规路由决策**自动提议转云端**（合规允许出门时）或继续等待（信创全封场景）；升级动作留痕 routeReason，可查可举证 |
| **判定分层编排（L0/L1/L2）** | **默认不用本地主模型做判定**（占槽 / 循环依赖 / 判定延迟放大 / 判错路由错下游放大四问题）：**L0 声明式映射**——请求来自已定义 workflow 的 Agent 节点，直接查节点级 modelPreference 映射（复用 v1.4.8 已交付 schema，零模型成本）→ **L1 语义分类**——自由文本走 embedding 相似度分类（复用本地 RAG 的 embedding 模型，零新增组件，不占本地推理槽）→ **L2 难例兜底**——置信度低于阈值时按配置分流（判定特征走云端强 API / 信创场景本地低峰复核） |
| **L1 判定通道接口（DecisionChannel）** | L1 语义分类的**可插拔判定源协议**（研究收编：System One 决策模型 Jev 启发，2026-09-19 拍板）：`judge(state, questions) → typed answers + 概率` 标准接口，Noul/Choice/Score 三问题原语语义对齐。**通道而非依赖**——引擎定义接口与编排，实现由用户按 TrainChannel 同款纪律自带（云端 provider 走用户 key opt-in，默认关闭；本地部署走开源并行约束解码方案——KV cache 广播 + 单次前向出全部字段，开源 RLCD 小权重可跑一体机，数据主权不破）。判定结果带概率落 decision-log 留痕（类型化输出天然可审计）。**边界**：决策模型不进信任地基（其可被 state 内容操纵的失灵面已知）——只坐确定性规则之后的语义兜底层，24 条审计规则判定面零改动 |
| **决策下达面** | 引擎产出去向决策（目标模型 / 降级路径 / 槽位归属）按标准 schema 下达 router 执行（与 v1.4.9 exporter 同族 schema，反向）；schema 校验 fail-closed，坏格式拒绝下达而非静默放行 |
| **槽位与排队可观测** | MCP tool 查询槽位占用 / 排队深度 / 各请求等待时长（运维可见，数据本地不出门） |
| **三层队列边界** | 明确不重叠的分工：router 层管 per-key 限速与云侧 cooldown（防单 key 打爆配额）· **引擎层管本地 GPU 槽位**（本章核心）· vLLM 实例层管实例内 continuous batching 微调度 |

### 验收标准

- [ ] 本地槽位上限可配（一体机默认 3–5），超限排队，前台可见排队位置与预估等待
- [ ] 排队超时达阈值按合规决策升级云端（或在全封场景继续等待），升级留痕 routeReason
- [ ] 判定三层链可用：L0 命中零模型调用 / L1 embedding 分类不占本地推理槽 / L2 难例按配置兜底

- [ ] **判定链不调用本地主模型**（行为锁：判定期间无本地主模型推理请求）
- [ ] 决策下达 schema 校验 fail-closed（坏格式拒绝下达，不静默放行）

- [ ] 槽位与排队状态可观测（MCP tool 查询）
- [ ] 门禁断言同步：`playbook/acceptance-test.sh` 新增槽位/判定链行为锁场景
