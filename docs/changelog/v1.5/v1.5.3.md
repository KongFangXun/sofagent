## 定位


> 🔍 **审计模块 · 规则引擎统一与自测**——先收敛再自检：把两处规则引擎（tool-level 3 条 + git-diff 24 条）合并为单一引擎（一套定义、两种触发时机），再给规则本身装上**自测**——每条规则强制携带 `match` / `notMatch` 正负样例，加载时断言 fail-closed（规则写错立刻爆，不靠人记），FAIL 报文强制附替代建议、多规则命中取最严。A24 交付物落点规则是自测 schema 落地后的**首个新规则**：出生即带正负样例，不留旧账。**同版补两处规则面地基**：判决类记录**成对完整**的机械扫描（只记单边即报红——补上「无记录」这一盲区）与审计**范围语义一等公民化**（规则从 `AuditScope` 取输入、不再各调各的 git）。

## 一、双规则引擎统一（2026-09-08 排入 · 消除 ARCHITECTURE 悬空承诺）


> **形态归属**：`[非功能]`（重构——两处规则引擎收敛为一，不新增能力面）｜ —
>
> 📋 **背景**：`engine/rules/`（tool-level 规则，3 条）与 `engine/audit/src/rules/`（git-diff 规则，24 条）历史上并行维护，均含 secret-leak 检测，存在行为不一致风险。v1.3.0 已部分收敛（正则模式共享至 `@sofagent/core`），但**规则引擎仍是两套**，ARCHITECTURE 记载「统一排期见 ROADMAP」而 ROADMAP 此前无此单元格——属悬空承诺，本版补上落点。
>
> 统一方式：以 `ruleType` 字段在两种触发模式下复用同一套规则定义（tool-level 在调用前拦截、audit 在 commit 后审计），收敛为单一规则引擎 + 两种执行时机。
>
> **纪律外延（2026-09-08 补）**：判定规则**只有一个事实源**。企业侧若另建判定点（自建模型网关/代理做流量侧 PII 过滤与敏感度分流），必须集成本引擎的同一套规则与检测器（v1.4.9 第八章检测器插槽即可嵌入组件），**不得另起一套**——每多一处独立实现，就是一次口径分裂风险。

### 交付

|------|------|
| **单一规则引擎** | 两套规则定义合并为一套（含 `ruleType` 触发时机标记），tool-level 与 git-diff 两种执行模式共用 |
| **行为一致性回归** | 统一前后对同一输入的判定结果必须一致（回归锁，防统一过程引入行为漂移） |
| **ARCHITECTURE 同步** | 「已知技术债：双规则系统重叠」段改写为已排期指向本版 |

| 组件 | 能力 |

## 六、判决类记录成对完整（只记单边即记录面缺陷 · 自探索方向迁入 · 2026-09-22 用户拍板）


> **形态归属**：`[主干]`（判定·判决记录双边完整性）｜ L1 关档
>
> 📋 **为什么现在排**（2026-09-22 用户拍板 · 版本边界纪律）：本项原为探索方向，触发条件写的是「下一次审计输入面返工窗口」。改判理由是**版本边界纪律**——V2.0 起版本全部是 S1M 的迭代域，**本项属 V2.0 前的审计地基能力，V2.0 后没有承接窗口**；而「审计输入面返工窗口」已被 [v1.5.1 第七章](./v1.5.1.md) 用掉，长期挂着即等于永久孤儿。
>
> 📋 **与 [v1.6.0 第二章](./v1.6.0.md) 的关系**（判据侧纪律 vs 记录面实现，互补不重复）：v1.6.0 第二章已立「**判决类记录成对完整（证据面纪律）**」——判据不得建立在单边记录上，且明写「**先修记录、再谈判据**」。本章就是那句「先修记录」的落地：记录面机械扫描 + 逐类补齐 + 门禁。两处边界：① 判据侧纪律（判据面不得消费单边记录）留 v1.6.0，本章只管**记录面本身的成对完整性**；② 本章不新增也不可能新增判据——判据重述归 v1.6.0 第二章。
>
> 📋 **与 [v1.5.1 第七章](./v1.5.1.md) 的关系**（补单边 ≠ 泛化）：那章补的是 `TOOL_GATE` 的**三态实例**（告警 / 放行 / 拦截），本章要的是**全仓判决类记录类型的机械扫描**——凡「判决」必成对，只有单边落盘即报红。实例修好了不等于类修好了：新的判决点随时会长出新的单边记录，靠人记必漏。

### 交付

| 组件 | 能力 |
|------|------|

| **豁免与登记** | 天然单边的记录（如纯观测型事件）须显式登记豁免并写明理由，不做静默放行（对齐「静默即缺陷」纪律） |
