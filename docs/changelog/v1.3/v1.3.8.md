## 一、代理网关硬边界（原 v1.2.5 拆入）

### 交付

SubAgent 所有外部请求经网关（唯一出入口）：

```
SubAgent → 代理网关 → {allow/deny + 风险分级 + 超阈值人工批准} → 外部服务
```

| 能力 | 说明 |
|------|------|
| allow/deny | 域名白名单 + 路径白名单 |
| 风险分级 | 低（GET 公开 API）/ 中（POST 业务 API）/ 高（写数据库）/ 极高（转账/删除） |
| 超阈值人工批准 | 极高风险请求暂停，等 human_confirm |
| 审计日志 | 所有请求 + 决策 + 结果落 JSONL |

### 与 v1.3.7 沙箱的关系

沙箱是「SubAgent 侧」的隔离（虚拟文件系统 + 工具中介），网关是「外部侧」的隔离（唯一出口）。两者构成**双向边界**：

```
[SubAgent 沙箱] ←→ [sofagent 引擎] ←→ [代理网关] ←→ [外部服务]
```

### 网关攻击面声明

> 📋 **2026-08-10 补充（安全基线 · 与 v1.3.7 沙箱攻击面对齐）**：网关是唯一出入口，它自身的安全是双向边界的另一半——需要显式声明。

| 攻击面 | 防御措施 |
|--------|---------|
| **网关绕过**（SubAgent 直接调外部服务，不经网关） | 网络层强制路由（SubAgent 进程的网络出站全部经 network-gateway，v1.3.7 白名单兜底）+ 网关启动完整性自检 |
| **网关 DDoS**（SubAgent 高频请求耗尽网关） | 限速（复用 v1.3.7 token bucket）+ 超限 deny + 审计 |
| **请求伪造**（SubAgent 伪造请求来源/身份） | 请求强制带 SubAgent 身份码（v1.3.1）+ 网关校验身份与场景匹配（v1.3.7 场景权限） |
| **网关日志注入**（恶意请求内容写入日志后执行） | 日志写入前 sanitize（复用 v1.4.4 脱敏管线的结构化写入模式）+ 日志只 append 不执行 |

### 权限单调性守卫（补强 v1.3.7 场景权限）

v1.3.7 场景驱动权限实现了判定链（身份→场景→风险→放行），但**权限集在会话内可以扩大**——SubAgent 通过合法的场景切换逐步拿到更多工具面，累计权限可能超出任何单一场景的授权。本版在网关补一条硬约束：

> **单调守卫**：SubAgent 生命周期内权限集只减不增。场景切换可以收窄权限，不得扩大——累计权限以初始场景授权为上界，任何扩大尝试 deny + 审计留痕。

实现落点：网关是所有外部请求的唯一出入口（§一），在网关处对每个 SubAgent 维护权限上界快照（初始场景授权集），请求经网关时校验「当前所需权限 ⊆ 上界」，越界即 deny。这补的是 v1.3.7 scenario-router/policy-engine 的缺口——权限判定从「每次独立判」升级为「会话级单调约束」，接口与实现分离（判定走网关机制，不靠 prompt 约定）。

### 验收标准

- [ ] SubAgent 权限上界快照：初始场景授权集在首次请求时锁定
- [ ] 场景切换收窄权限生效，扩大权限的请求被 deny + 审计留痕（含尝试扩大的权限项）
- [ ] 越界请求不中断 SubAgent（deny 该次请求，任务继续）——与断路器（v1.3.7 ⑤）联动：高频越界尝试触发熔断

## 二、数据静态加密（age）

### 痛点

`~/.sofagent/data/` 审计数据当前明文落盘。合规场景（尤其受监管行业）要求静态加密。

### 交付

使用 [age](https://age-encryption.org/)（现代文件加密工具）对审计数据加密落盘：

- 加密范围：`data/audit/` + `data/forge-runs/` + `data/checkpoint/` + **`data/model-registry/`（2026-08-09 补充：v1.3.6 ⑤ 模型注册表含内部 endpoint 地址，属敏感配置，一并加密）**
- 密钥管理：本地 keypair（`~/.sofagent/keys/`），可选 passphrase 保护
- 透明读写：sofagent 引擎读写时自动加密/解密，用户不感知
- Dashboard 查看：通过引擎 API 读（自动解密），不直接读文件

| `engine/core/src/crypto/age-wrapper.ts` | 新建 | age 加密/解密封装 |

## 三、Durable Execution L3：完整 WAL（write-ahead log）

### 背景

v1.3.1 交付了 Durable Execution L1（graph 状态恢复）+ L2（工具幂等性）。L3 是完整的事务级 WAL——所有工具调用**先写日志再执行**，类数据库事务机制。

### 与 L1+L2 的区别

| 层 | 机制 | 恢复粒度 | 版本 |
|----|------|---------|:----:|
| L1 | graph checkpoint | 节点级（恢复到中断节点） | v1.3.1 |
| L2 | 副作用登记簿 | 工具级（已执行的跳过） | v1.3.1 |
| **L3** | **WAL（write-ahead log）** | **事务级（全回放或全回滚）** | **v1.3.8** |

### WAL 工作流程

```
工具调用请求：
  1. WAL 先写 {taskId, tool, params, expectedSideEffects} 到 wal.jsonl
  2. 执行工具
  3. 成功 → WAL 写 {taskId, status:"committed", actualSideEffects}
  4. 失败 → WAL 写 {taskId, status:"aborted", reason}

崩溃恢复：
  1. 扫描 wal.jsonl
  2. committed 但未确认 → 验证副作用是否生效
  3. aborted → 回滚（调用 undo 函数或 git restore）
  4. 未完成 → 重新执行或跳过（按幂等策略）
```

### 为什么放在网关层

本版有**代理网关**——所有工具调用必经网关。WAL 写在**网关层**最干净：

```
SubAgent → wrapToolCall middleware → [沙箱层] → 代理网关[WAL 写入点] → 外部服务
```

v1.3.1 的 L1+L2 写在 middleware 层（观测层），本版 L3 写在网关层（执行层）。两层分离，职责清晰。

### workflow 崩溃恢复（引擎级灾难恢复）

> 📋 **2026-08-10 补充（灾难恢复 · 与 v1.4.1 ⑨ 训练崩溃恢复对齐）**：WAL 不只管单次工具调用，也覆盖 **workflow 执行的崩溃恢复**——引擎崩溃（Node 进程挂）后重启，正在跑的 LangGraph workflow 怎么办？

WAL + L1 graph checkpoint 联动实现 workflow 级恢复：

```
引擎重启 → 扫描 wal.jsonl 中 status=未完成的任务
  → 查 L1 graph checkpoint 定位 workflow 中断节点
  → WAL 验证中断前的工具调用副作用状态（committed/aborted/未完成）
  → committed 但未确认 → 验证副作用是否生效
  → aborted → 回滚
  → 未完成 → 重新执行或跳过（按幂等策略）
  → 恢复 workflow 执行（从中断节点继续）
```

**与 v1.4.1 ⑨ 训练崩溃恢复的区别**：训练恢复管的是 train job（长任务，三选项人审），本版 WAL 管的是 workflow 工具调用（短任务，自动回放/回滚）。两者覆盖不同粒度的崩溃恢复，互补不重叠。

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/durable/wal-writer.ts` | 新建 | WAL 写入（append-only JSONL） |
| `engine/orchestrator/src/durable/wal-recovery.ts` | 新建 | WAL 崩溃恢复（扫描 + 回放/回滚） |
| `engine/orchestrator/src/durable/undo-registry.ts` | 新建 | 工具 undo 函数注册表（可逆操作回滚） |
| `engine/orchestrator/src/sandbox/network-gateway.ts` | 修改 | 网关层集成 WAL 写入 |

### 难度

⭐⭐⭐⭐（较高）。~1500 行+。难点不在 WAL 本身，而在 **undo 函数**——不是所有操作都可逆：
- ✅ 可逆：git 操作（git restore）、文件写入（删掉新写的）
- ⚠️ 部分可逆：PR 创建（关闭 PR）、飞书消息（撤回，2 分钟内）
- ❌ 不可逆：邮件发送、webhook 触发（已消费）
- 不可逆操作策略：WAL 标记 `irreversible: true` + 审计告警 + 不回滚（已发生的事实不篡改）

## 四、异步长任务自治（P2 · Durable L3 配套）

### 定位

Durable Execution L3 补上 WAL（向前续跑），但 daemon 当前仍是「文件监控」被动模式——检测到变更才跑。异步长任务自治让 daemon 从「被动监控」升级为「长任务自主运行」：FDE 离场后，daemon 按计划自主发起长任务（如每周 Benchmark 复测 / 每日知识健康巡检 / 每月审计链校验），不依赖外部触发。

### 交付（P2）

- daemon 长任务调度器：cron-like 触发（@daily / @weekly / @monthly）+ 依赖图（长任务间的前后依赖）
- 长任务与 Durable L3 联动：长任务崩溃 → WAL 续跑（不从头开始）
- 长任务注册表：FDE 交付时声明企业要哪些长任务，daemon 自主执行

### 验收标准

- [ ] daemon 支持 cron-like 长任务调度（@daily/@weekly/@monthly）
- [ ] 长任务间依赖图可声明（前任务 PASS 才触发后任务）
- [ ] 长任务崩溃后走 WAL 续跑（与 Durable L3 联动）
- [ ] FDE 可声明企业长任务清单（注册表落 `.sofagent/`）
