> 📋 **已排期。** 前置依赖：v1.3.1（Ontology + Schema + 审批 + 身份码 + LLM Trace）

> 状态：已排期 · 2026-08-09

## 背景

> 🔗 **为什么提前**：本版内容原属 v2.0「引擎层接口外化」——但它是**模型层（AIR）接入约束层的前置依赖**（模型自动生成的 workflow / ontology 必须能喂进引擎）。v2.0 排期太远，与 AIR 模型层开发时间错配，整体提前到 v1.3.x（详见 ROADMAP 版本规划说明）。2026-08-09 追加：训练语料导出 + SubAgent 托管 SDK 也并入本版——从「第一批」升级为「完整版」。

约束层四样核心能力（约束 / 编排 / ontology / 审计）目前是**内聚实现**——能力写死在代码里，缺**对外开放的标准化接口**。本版打开完整接口面——**四个数据接口 + 一个代码接口**：

```
AIR 模型层（生成端）                          sofagent 约束层（引擎）
  ├─ workflow.yml（标准格式）→ ① 运行容器加载执行 ──┐
  ├─ ontology（JSON Schema 校验）→ ② 注册接口注入 ──┼→ 注入 → 约束 → 审计 → 进化
  ├─ graph（LangGraph 自定义 Agent）→ ④ 托管 SDK ──┘
  └─ AIR 模型（vLLM/OpenAI 兼容）→ ⑤ 模型注册/灰度切换
                                                 ↓
  AIR 训练管线 ← ③ 训练语料导出（规则 + 方法论 + 样本）
```

| # | 接口 | 方向 | 服务对象 |
|---|------|:--:|---------|
| ① | Workflow 标准格式 + 运行容器 | 进 | 模型生成的 workflow |
| ② | Ontology 标准 Schema 注册接口 | 进 | 模型生成的 ontology |
| ③ | 训练语料导出三件套（规则 + 方法论 + 样本） | 出 | AIR 后训练管线（训练信号） |
| ④ | SubAgent 托管 SDK（`harness.wrap`） | 代码 | 开发者 / AIR 的 LangGraph 自定义 Agent |
| ⑤ | 模型注册 + 灰度切换（`model_register` / `model_switch`） | 进 | AIR 模型上线流程（评测 → 注册 → 灰度 → 晋升） |

## 一、Workflow 标准格式 + 运行容器

### 痛点

`workflow-parser.ts`（v1.3.0 交付）能解析 workflow YAML，但：
- 格式没有**公开定义**——字段（id/agent/task/depends_on）只有代码里的 TS 接口，没有机器可读 JSON Schema，外部无法按规范生成
- 没有**外部提交通道**——workflow 写死在仓库/代码里，模型层生成的 workflow 无处提交

### 交付

| 组件 | 能力 |
|------|------|
| **workflow JSON Schema** | `id / agent / task / depends_on` 字段的机器可读定义（对齐 v1.3.2 节点类型动态解析链——agent 字段支持任意类型，走 registry 查找 + agent-creation 兜底） |
| **运行容器** | 外部提交的 workflow（文件路径 / 标准输入 / MCP tool）→ schema 校验 → parser 解析 → dag-runner 加载执行 |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/workflow/schema/workflow.schema.json` | 新建 | workflow JSON Schema（节点/依赖/agent 类型） |
| `engine/orchestrator/src/workflow/container.ts` | 新建 | 运行容器——外部提交 → 校验 → 解析 → 加载执行 |
| `engine/orchestrator/src/workflow-parser.ts` | 修改 | 校验走 schema（单一事实源） |
| `engine/mcp/src/tools/workflow-submit.ts` | 新建 | MCP `workflow_submit` tool（外部提交入口） |
| `engine/orchestrator/src/__tests__/workflow-container.test.ts` | 新建 | 单测（外部提交 → 校验 → 执行） |

### 验收标准

- [ ] workflow JSON Schema 公开定义，schema 校验走单一事实源
- [ ] 外部提交的 workflow 可被引擎加载执行（文件路径 / MCP tool 两种入口）
- [ ] agent 字段支持任意节点类型（registry 查找 + agent-creation 兜底，对接 v1.3.2）
- [ ] 非法 workflow 返回结构化错误（不 crash）
- [ ] `npm test` 全绿

## 三、训练语料导出三件套（规则 + 方法论 + 样本）

### 定位

> 🔗 **2026-08-09 从 v1.3.9 提前**：原 v1.3.9「约束导出通道」只导出审计规则，但 AIR 训练需要三类语料——本版补全为三件套。依赖仅 v1.3.0 decision-log（已交付）+ v1.3.1 llm-calls/evaluation-log（样本富矿），不依赖沙箱/网关，提前到本版。

AIR §5.3 冷启动自述「开源 GUIDE / SKILL / 24 条规则 / 25 个案例就是第一版现成语料」——本版把这三类语料全部机器可读化：

| 语料 | 来源 | 现状 |
|------|------|------|
| **规则定义** | 24+3 条审计规则（TS 代码内聚） | 需序列化导出 |
| **FDE 方法论** | `FDE/GUIDE.md`（五要素/三问判定）+ SKILL 加载链 | 纯 markdown，需结构化导出 |
| **带标签审计样本** | `data/audit/` decision-log（v1.3.0）+ llm-calls（v1.3.1）+ evaluation-log（v1.3.1） | 数据已有，缺导出通道 |

**样本是训练信号里最值钱的部分**——真实的 FAIL/通过案例 = 带标签的「什么是对的」，对应 self-recording improvement（模型协作产生 trace → 用 trace 训练）。

### 交付

| 组件 | 能力 |
|------|------|
| **规则导出** | 24+3 条规则导出为 `{ruleId, ruleType, description, triggers, severity, examples}`（JSON/YAML 双格式） |
| **方法论导出** | GUIDE 五要素 / 三问判定 / 量化公式 / 加载链结构导出为结构化文档（markdown → JSON 摘要 + 原文） |
| **样本导出** | decision-log / llm-calls / evaluation-log 聚合导出为训练样本（脱敏 + 按任务分组 + 标签） |
| **版本化 + 签名** | 导出结果带语料集版本号 + HMAC 签名（防篡改，训练素材可追溯） |
| **双入口** | CLI `sofagent corpus export` + MCP `corpus_export` tool |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/audit/src/export/rule-schema.ts` | 新建 | 规则导出格式定义 |
| `engine/audit/src/export/exporter.ts` | 新建 | 规则 + 样本序列化 |
| `engine/core/src/export/methodology.ts` | 新建 | FDE 方法论结构化导出 |
| `engine/core/src/export/sample-aggregator.ts` | 新建 | decision-log/llm-calls/evaluation-log 聚合 + 脱敏 |
| `engine/mcp/src/tools/corpus-export.ts` | 新建 | MCP `corpus_export` tool |

### 验收标准

- [ ] 24+3 条规则全部可导出（零遗漏）
- [ ] GUIDE 方法论可结构化导出（五要素/三问判定/量化公式齐全）
- [ ] 样本聚合导出：decision-log + llm-calls + evaluation-log 三源合并，脱敏 + 分组 + 标签
- [ ] 导出结果带版本号 + HMAC 签名
- [ ] CLI + MCP 双入口可用
- [ ] `npm test` 全绿

### 合规红线（2026-08-09 补充 · 对齐 AIR §6.7 Q7）

审计样本可能含企业敏感数据（llm-calls 含 API 响应、decision-log 含代码片段、think.md 摘要可能含对话内容）——**导出即外发训练管线，必须明确什么能出、什么不能出**：

| 红线 | 规则 |
|------|------|
| **不落个体级数据** | 样本导出仅脱敏聚合，任何可反推具体企业/具体请求的原始字段一律剥离（对齐 AIR「仅以脱敏聚合基准对外」） |
| **字段白名单** | 可导出：ruleId / ruleType / severity / token 数 / 耗时 / 失败码 / 脱敏后的文本模式（变量名 → 占位符） |
| **字段黑名单** | 禁止导出：原始 API 响应体 / 密钥类值 / 企业专有名词 / 用户可识别信息 / 未脱敏的代码片段 |
| **导出审计** | 每次导出记 `corpus_export` 事件（谁导的、导了什么范围、签名）——导出行为本身受审计 |

> 与 AIR 的关系：此红线是 AIR 训练管线消费语料的合规前提——语料带 HMAC 签名（防篡改）+ 脱敏红线（防泄密），AIR 侧才能安全入库训练。

## 四、SubAgent 托管 SDK（`harness.wrap` · 代码接口）

### 定位

> 🔗 **2026-08-09 新增**：约束层作为引擎的**最终接缝**——开发者用 LangChain/LangGraph 写自己的 graph，一行包装即自动获得约束层全部能力。这也是 AIR C6「sub-agent 自动设计与训练」的落点（模型生成的 sub-agent 本质是 graph 配置，托管 SDK 让它们直接受约束层治理）。

**现状**：开发者/AIR 的 Agent 进约束层只有两条路——workflow.yml 映射（4 种内置类型）或 agent-creation 生成。**没有「自定义 graph 直接托管」的开发接口**。`wrapToolCall`（v1.3.0）有技术基础，但：① 无对外开发者文档/示例 ② 审批（v1.3.1）/身份（v1.3.1）/沙箱（v1.3.7）是独立组件，无完整托管封装。

### 交付

```ts
// 开发者 / AIR 视角——一行包装，获得约束层全部能力
const agent = harness.wrap(myLangGraphAgent, {
  approval: 'allow-with-audit', // v1.3.1 审批模式（默认 allow-with-audit）
  identity: 'agent-001',        // v1.3.1 身份码（可选，自动签发）
  sandbox: false,               // v1.3.7 沙箱（本版留空，v1.3.8 启用——见版本边界）
  trace: true                   // v1.3.1 LLM 调用级 Trace
});
// agent 自动获得：审计 / 审批 / 身份 / Trace / 决策审计
```

| 组件 | 能力 |
|------|------|
| **wrap 核心** | 包装任意 LangGraph StateGraph / createReactAgent → 自动接入 wrapToolCall 审计 + 审批 + 身份 + Trace |
| **类型化配置** | `HarnessWrapOptions`（approval / identity / sandbox / trace）——TS 类型完整，IDE 提示友好 |
| **开发者文档 + 示例** | `docs/guides/harness-sdk.md` + 示例项目（10 行代码跑通受约束 Agent） |
| **registry 集成** | 被托管的 agent 自动注册进 registry（可被发现、被编排） |

> 🔗 **兼容声明（2026-08-09 补充）**：开发者不一定用 `createReactAgent`——`wrap` 核心须**同时兼容两种形态**：① `createReactAgent`（v1.3.0 middleware 链路复用）② 纯 `StateGraph`（自定义节点图）——对纯 StateGraph 形态，wrap 在 `tools` 节点处注入审计/审批拦截（LangGraph `tools` node 是工具调用的必经点）。验收标准覆盖两种形态。

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/harness-sdk/wrap.ts` | 新建 | `harness.wrap()` 核心（组合 middleware + 审批 + 身份 + Trace） |
| `engine/orchestrator/src/harness-sdk/types.ts` | 新建 | `HarnessWrapOptions` 类型定义 |
| `docs/guides/harness-sdk.md` | 新建 | 面向开发者/AIR 的 SDK 文档 |
| `engine/orchestrator/src/__tests__/harness-sdk.test.ts` | 新建 | 单测（wrap 后审计/审批/身份生效） |

### 验收标准

- [ ] 自定义 LangGraph agent 经 `harness.wrap()` 后：工具调用进审计 + 审批生效 + 身份码可查 + Trace 落盘
- [ ] **createReactAgent 与纯 StateGraph 两种形态均可托管**（纯 StateGraph 在 tools 节点注入拦截）
- [ ] 未传 approval 时默认 allow-with-audit（保守默认，不破坏既有行为）
- [ ] 被托管 agent 自动注册进 registry
- [ ] SDK 文档 + 示例项目可跑（10 行代码示例）
- [ ] `npm test` 全绿

### 版本边界（sandbox 选项）

## 五、模型注册 + 灰度切换接口（模型上线流程）

### 定位

> 🔗 **2026-08-09 新增**：AIR 模型上线闭环的最后一块。现状：模型切换 = 手改 `model-router.json`（无审计、无灰度、无回滚）。v1.3.2 解决了「模型能不能接上」（`client_type: 'openai-compatible'` 插槽扩展），本接口解决「模型怎么安全上线」——**评测（v1.3.1 Benchmark）→ 注册 → 灰度 → 晋升**全流程可审计、可回滚。

### 交付

| 组件 | 能力 |
|------|------|
| **模型注册** | MCP `model_register` tool——注册 AIR 模型（endpoint + client_type + 模型名 + 元信息），写 `model-router.json` 走原子写 + 审计 |
| **灰度切换** | MCP `model_switch` tool——按档位（local-executor / local-pipeline）切换活动模型，支持「灰度比例」（如 10% 流量） |
| **晋升/回滚** | 灰度验证通过 → 全量晋升；异常 → 一键回滚（git snapshot 兜底） |
| **模型退役** | MCP `model_unregister` tool（2026-08-09 补充）——下线模型走退役标记（可恢复），对齐 v1.3.4 L3 养护环「失效退役」：无人调用/评测走低 → 标记退役 → 归档（不再参与路由） |
| **全程审计** | 每次注册/切换/晋升/退役记 `model_registry` 事件（谁操作、从哪版到哪版、审计留痕）——**晋升与退役强制人审**（对齐 v1.3.5 `promote_ab` 语义） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/model-registry.ts` | 新建 | 模型注册表（本地 data/ 存储 + schema 校验 + 退役标记） |
| `engine/mcp/src/tools/model-register.ts` | 新建 | MCP `model_register` tool |
| `engine/mcp/src/tools/model-switch.ts` | 新建 | MCP `model_switch` tool（灰度比例 + 强制人审晋升） |
| `engine/mcp/src/tools/model-unregister.ts` | 新建 | MCP `model_unregister` tool（退役 + 归档，强制人审） |
| `engine/orchestrator/src/model-router-config.ts` | 修改 | 活动模型从注册表读取（替代手改 JSON） |
| `engine/orchestrator/src/__tests__/model-registry.test.ts` | 新建 | 单测（注册/切换/回滚/退役/审计） |

### 验收标准

- [ ] `model_register` 注册 AIR 模型 → 写入注册表（原子写 + 审计）
- [ ] `model_switch` 按档位切换 + 灰度比例生效
- [ ] 晋升强制人审（无人审确认不执行，对齐 v1.3.5）
- [ ] 切换可回滚（异常 → 恢复上一活动模型）
- [ ] `model_unregister` 退役标记生效（不再参与路由，可恢复；强制人审）
- [ ] 每次操作 `model_registry` 事件留痕
- [ ] `npm test` 全绿
