## 背景

> 🔗 **为什么提前**：本版内容原属 v2.0「引擎层接口外化」——但它是**模型层接入约束层的前置依赖**（模型自动生成的 workflow / ontology 必须能喂进引擎）。v2.0 排期太远，与模型层开发时间错配，整体提前到 v1.3.x（详见 ROADMAP 版本规划说明）。2026-08-09 追加：SubAgent 托管 SDK 并入本版——从「第一批」升级为「完整版」。2026-08-10 更新：**训练语料导出三件套整体移至 v1.4.1（训练引擎主题版）**——训练相关内容统一归 v1.4.x，本版专注引擎接口外化（Workflow / Ontology / 托管 SDK / 模型注册）。

约束层四样核心能力（约束 / 编排 / ontology / 审计）目前是**内聚实现**——能力写死在代码里，缺**对外开放的标准化接口**。本版打开完整接口面——**三个数据接口 + 一个代码接口**：

```
模型层（生成端，商业侧）                     sofagent 约束层（引擎，开源）
  ├─ workflow.yml（标准格式）→ ① 运行容器加载执行 ──┐
  ├─ ontology（JSON Schema 校验）→ ② 注册接口注入 ──┼→ 注入 → 约束 → 审计 → 进化
  └─ graph（LangGraph 自定义 Agent）→ ③ 托管 SDK ──┘
       └─ 后训练模型（vLLM/OpenAI 兼容）→ ④ 模型注册/灰度切换
```

| # | 接口 | 方向 | 服务对象 |
|---|------|:--:|---------|
| ① | Workflow 标准格式 + 运行容器 | 进 | 模型生成的 workflow |
| ② | Ontology 标准 Schema 注册接口 | 进 | 模型生成的 ontology |
| ③ | SubAgent 托管 SDK（`harness.wrap`） | 代码 | 开发者 / 商业侧的 LangGraph 自定义 Agent |
| ④ | 模型注册 + 灰度切换（`model_register` / `model_switch`） | 进 | 后训练模型上线流程（评测 → 注册 → 灰度 → 晋升） |

## 一、Workflow 标准格式 + 运行容器

> 🔗 **DSH workflow seam 互转预留（2026-08-15 补充）**：格式设计时留与 DSH `ctx.workflowEngine` 的互转位（sofagent workflow 容器可作为 DSH 的 workflow 提供方，避免两套并行格式）——本版只做格式对齐评估与转换位设计，真实互转等 DSH 正式版 + 后端跑通后验证。

### 痛点

`workflow-parser.ts`（v1.3.0 交付）能解析 workflow YAML，但：
- 格式没有**公开定义**——字段（id/agent/task/depends_on）只有代码里的 TS 接口，没有机器可读 JSON Schema，外部无法按规范生成
- 没有**外部提交通道**——workflow 写死在仓库/代码里，模型层生成的 workflow 无处提交

### 交付

| 组件 | 能力 |
|------|------|
| **workflow JSON Schema** | `id / agent / task / depends_on` 字段的机器可读定义（对齐 v1.3.2 节点类型动态解析链——agent 字段支持任意类型，走 registry 查找 + agent-creation 兜底） |
| **运行容器** | 外部提交的 workflow（文件路径 / 标准输入 / MCP tool）→ schema 校验 → parser 解析 → dag-runner 加载执行 |

### 涉及文件（预估）

## 三、SubAgent 托管 SDK（`harness.wrap` · 代码接口）

### 定位

> 🔗 **2026-08-09 新增**：约束层作为引擎的**最终接缝**——开发者用 LangChain/LangGraph 写自己的 graph，一行包装即自动获得约束层全部能力。这也是「sub-agent 自动设计与训练」的落点（模型生成的 sub-agent 本质是 graph 配置，托管 SDK 让它们直接受约束层治理）。

**现状**：开发者/商业侧的 Agent 进约束层只有两条路——workflow.yml 映射（4 种内置类型）或 agent-creation 生成。**没有「自定义 graph 直接托管」的开发接口**。`wrapToolCall`（v1.3.0）有技术基础，但：① 无对外开发者文档/示例 ② 审批（v1.3.1）/身份（v1.3.1）/沙箱（v1.3.7）是独立组件，无完整托管封装。

### 交付

```ts
// 开发者 / 商业侧视角——一行包装，获得约束层全部能力
const agent = harness.wrap(myLangGraphAgent, {
  approval: 'allow-with-audit', // v1.3.1 审批模式（默认 allow-with-audit）
  identity: 'agent-001',        // v1.3.1 身份码（可选，自动签发）
  sandbox: false,               // v1.3.7 沙箱（本版留空，v1.3.8 启用——见版本边界）
  trace: true                   // v1.3.1 LLM 调用级 Trace
});
// agent 自动获得：审计 / 审批 / 身份 / Trace / 决策审计
```

| 组件 | 能力 |
|------|------|
| **wrap 核心** | 包装任意 LangGraph StateGraph / createReactAgent → 自动接入 wrapToolCall 审计 + 审批 + 身份 + Trace |
| **类型化配置** | `HarnessWrapOptions`（approval / identity / sandbox / trace）——TS 类型完整，IDE 提示友好 |
| **开发者文档 + 示例** | `docs/guides/harness-sdk.md` + 示例项目（10 行代码跑通受约束 Agent） |
| **registry 集成** | 被托管的 agent 自动注册进 registry（可被发现、被编排） |

> 🔗 **兼容声明（2026-08-09 补充）**：开发者不一定用 `createReactAgent`——`wrap` 核心须**同时兼容两种形态**：① `createReactAgent`（v1.3.0 middleware 链路复用）② 纯 `StateGraph`（自定义节点图）——对纯 StateGraph 形态，wrap 在 `tools` 节点处注入审计/审批拦截（LangGraph `tools` node 是工具调用的必经点）。验收标准覆盖两种形态。
>
> 🔗 **registry 执行链（2026-08-09 补充）**：`registry.ts` 存的是 **SubAgentDefinition（配置描述）**，而托管 SDK 的 graph 是**运行时执行体**——两者不直接等价。衔接方案：**wrap 后的 agent 注册进 registry 时注册「graph 构建器（工厂函数）」**，dag-runner 经解析链（v1.3.2 节点类型动态解析链）命中 registry 时**按需实例化构建器执行**——registry 存「怎么构建」，dag-runner 负责「什么时候构建」。避免「注册了但跑不起来」（dag-runner 不直接引用 registry，走 parser 解析链，链上补构建器实例化）。

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/harness-sdk/wrap.ts` | 新建 | `harness.wrap()` 核心（组合 middleware + 审批 + 身份 + Trace） |
| `engine/orchestrator/src/harness-sdk/types.ts` | 新建 | `HarnessWrapOptions` 类型定义 |
| `docs/guides/harness-sdk.md` | 新建 | 面向开发者/商业侧的 SDK 文档 |
| `engine/orchestrator/src/__tests__/harness-sdk.test.ts` | 新建 | 单测（wrap 后审计/审批/身份生效） |

### 验收标准

- [ ] 自定义 LangGraph agent 经 `harness.wrap()` 后：工具调用进审计 + 审批生效 + 身份码可查 + Trace 落盘
- [ ] **createReactAgent 与纯 StateGraph 两种形态均可托管**（纯 StateGraph 在 tools 节点注入拦截）
- [ ] 未传 approval 时默认 allow-with-audit（保守默认，不破坏既有行为）
- [ ] 被托管 agent 自动注册进 registry
- [ ] SDK 文档 + 示例项目可跑（10 行代码示例）
- [ ] `npm test` 全绿

> 🔗 **层级定位澄清（2026-08-16 复核撤回）**：曾考虑 `harness.wrap` 产物注册为 DSH 第七种 SubAgent 提供方——**已撤回**。DSH 六种提供方全是执行体（被委派干活的完整 Agent 实现），sofagent 是治理层不是执行体：我们的战场是约束与审计「干活的 Agent」（含 Codex/Claude Code 这些提供方本身），不是自己下场当一个可被委派的打工人。与 DSH 的集成层级收敛为 **plugin（能力挂载）+ 审批应答者（治理通道）** 两层，不做提供方。

## 四、模型注册 + 灰度切换接口（模型上线流程）

### 定位

> 🔗 **2026-08-09 新增**：后训练模型上线闭环的最后一块。现状：模型切换 = 手改 `model-router.json`（无审计、无灰度、无回滚）。v1.3.2 解决了「模型能不能接上」（`client_type: 'openai-compatible'` 插槽扩展），本接口解决「模型怎么安全上线」——**评测（v1.3.1 Benchmark）→ 注册 → 灰度 → 晋升**全流程可审计、可回滚。
>
> 🔗 **2026-08-10 更新（企业专属模型本地权重部署移至 v1.4.1）**：本版模型注册/灰度处理 **endpoint 型模型**（云端/可寻址服务）。「帮企业训专属后训练模型」的**本地权重文件部署链路**（权重目录规范 + 本地加载 + 版本回滚）随训练主题归入 v1.4.1（训练引擎）——本版 `model_register` 的 `source` 字段预留 `'local-path'` 扩展位，v1.4.1 填充。
>
> 🔗 **DSH provider 灰度对齐（2026-08-15 补充）**：跑在 DSH 执行层上时，sofagent 灰度切换的底层实现可对齐 DSH provider 机制（settings.yaml 四字段 + 模型切换无需重启）——sofagent 的审计/人审语义在上层不变，底层 provider 配置变更由 DSH 原生完成，省掉自建路由层。实现方式在 DSH 后端跑通后二选一（走 DSH provider vs 走自家 model-router），不预先锁死。
>
> 🔗 **2026-08-10 补充（模型路由边界收窄 · 第三方 model router 对接）**：**「workflow 节点选哪个模型」的通用模型路由，sofagent 不自研**——workflow 一旦配置好，节点模型基本不变；且做模型路由的厂商太多（LiteLLM / OpenRouter 等），**企业直接挂第三方 model router 即可解决**。sofagent 只保留两条：
> 1. **数据主权路由**（铁律不可外包）：restricted/confidential 数据 → 强制本地（local-executor/local-pipeline），绝不 fallback 云端——这条留在 model-router.ts 内部，是安全底线

>
> **边界结论**：workflow 节点不需要自带 `model` 字段（不重复造轮子）；需要换模型时改 `model_switch` 指向第三方 router 的新 endpoint 即可。**节点级模型选择（专属小模型挂 workflow 节点）是训练引擎 v1.4.4 产物注册衔接的领域**——训出的专属模型注册成 endpoint，`model_switch` 挂到对应 workflow 节点。

## 四补、路由决策可解释性（role-model 启发 · 补 Profiles/Policy 半个）

> 📖 **来源**：role-model（try-works/role-model）——能力感知的 AI 路由开放协议，把每次模型路由决策固化为 Requests / Profiles / Policy / Artifacts 四个标准化构件。sofagent 对照发现 **已有 3/4，只差两个"半个"**，本版补齐。

### 定位

> 🔗 **2026-08-13 新增**：sofagent 已明确「通用模型路由不自研，挂第三方 router」（见四章）。但**路由决策的可解释性**不能外包——"为什么这个任务派给了模型 A 而不是 B"这个决策理由链，是审计需求，必须留在约束层。role-model 的四构件设计是现成参考，但**不抄它的路由器实现**，只吸收"决策可解释性"思路，补在现有 decision-log 里。

**role-model 四构件 vs sofagent 现状对照**：

| role-model 构件 | 含义 | sofagent 现状 | 缺口 |
|-----------------|------|--------------|------|
| **Requests** | 任务类型、能力需求、模态、约束 | ✅ `route_workflow` 的 task + workflow 语义匹配 | 无 |
| **Profiles** | 可路由端点的能力画像（不是抽象模型名） | ⚠️ 半个——`model_register` 注册 endpoint，但**没有能力画像** | 本版补 |
| **Policy** | 硬性拒绝、偏好、预算、决胜规则 | ⚠️ 半个——数据主权路由（restricted→强制本地）是硬性拒绝，但**没有偏好/预算/决胜** | 本版补 |
| **Artifacts** | 决策记录、追踪、性能数据 | ✅ `emitDecision(kind=ORCHESTRATION)` 已经在记 | 无 |

### 交付

| 组件 | 能力 | 补的是哪个"半个" |
|------|------|:--:|
| **端点能力画像（EndpointProfile）** | `model_register` 注册时可选填能力画像：`{ strengths: string[], modalities, maxContext, costPerKToken, latencyP50 }`——注册表存储，查询时可按能力筛选 | Profiles |
| **路由策略配置（route-policy.yml）** | 新建 `.sofagent/route-policy.yml`——企业可配偏好规则（如"成本优先 / 延迟优先 / 能力优先"）+ 决胜规则（同分时谁赢）+ 硬性拒绝扩展（除数据主权外的业务规则） | Policy |
| **routeReason 结构化字段** | `model_switch` / `route_workflow` 记决策日志时，`why` 字段支持结构化 `routeReason`：`{ policy, matchedEndpoint, rejectedEndpoints, decisionScore }`——借鉴 role-model Artifacts | Artifacts（增强） |

**routeReason schema（扩展现有 DecisionWhy，不破坏向后兼容）**：

```typescript
interface DecisionWhy {
  text: string;              // 现有：人类可读理由
  tags?: string[];           // 现有
  confidence?: 'high'|'med'|'low'; // 现有
  triggeredRule?: string;    // 现有
  // ↓ 新增可选字段（v1.3.6）
  routeReason?: {
    policy: 'data-sovereignty' | 'cost' | 'latency' | 'capability' | 'preference' | 'default';
    matchedEndpoint?: string;       // 命中的 endpoint（Profiles 对应）
    rejectedEndpoints?: string[];   // 被规则拒绝的（Policy 硬性拒绝对应）
    decisionScore?: number;         // 决胜分（Policy 决胜规则对应）
  };
}
```

### 边界：不自研路由器

> ⚠️ **重申边界**（与四章一致）：本版补的是**决策可解释性**，不是路由器。实际路由仍由第三方 model router（LiteLLM/OpenRouter）做，sofagent 只在 `model_switch`（换模型）和 `route_workflow`（入口路由）这两个决策点记结构化理由链。企业挂什么 router、router 内部怎么选基座——不归 sofagent 管，也不可审计（那是别人的系统）。

## 五、训练协议三约定（双栈契约 · 前 v1.4.1 ①前移）

> 🔗 **2026-08-12 前移自 v1.4.1**：训练协议三约定（Node 控制面 ↔ Python 执行面）是双栈架构的契约，不依赖完整训练引擎骨架。提前定稿让接入企业专属模型的早期试点客户在 v1.4.1 完整训练引擎交付前就能跑通「Node spawn Python + 事件流回流」的最小路径。

### 背景

主流生产后训练框架（verl / TRL / NeMo RL / Oumi / open-instruct）在 2026 年全部是 Python（PyTorch + CUDA 生态决定）。Node 无法绕过——唯一纯 Node 方案是 `@mlx-node/trl`（仅 Apple Silicon，SFT/GRPO/DPO + 内置 reward + checkpoint），用于**个人 Mac 阶段 0 验证**（reward 规则 → 收敛），不用于客户交付。

**决策**：双栈不可避免，用「Node 控制面 + Python 执行面」控制——编排/审计/生命周期/预算全在 Node（像 dag-runner 管 Agent 一样管 train job），Python 只当被 spawn 的训练子进程（接口 = 进程参数 + JSON 事件 + 日志流）。**个人 Mac 阶段 0 用 @mlx-node/trl 纯 Node 跑通验证路径，再无缝换 Python 框架做生产——阶段 0 不用碰 Python**。

### 三个约定（接口即解耦 · 双栈的契约）

> 🔗 **协议即版本边界**：v1.4.1（完整训练引擎）定稿后不可随意增删字段，新增字段走版本号（config schema version）。
>
> 🔗 **schema 兼容承诺**：job.json schema 向后兼容**最近 3 个版本**。不兼容的 breaking change 走 **migrate 子命令**（`train migrate --from v1 --to v2`）+ 人审确认，不做静默升级。早期版本 schema 变动小，migrate 可后置；声明先行让企业有预期。

| # | 约定 | 方向 | 规范 | 备注 |
|---|------|:--:|------|------|
| **① 启动** | Node → Python | spawn | `python train.py --config <job.json>`——**参数收敛为一个 JSON 文件**（数据路径 + 基座 + 算法 + 超参 + checkpoint 路径 + 产物目录 + 预算），Node 不传散参数 | job.json 即训练任务的完整快照，审计可读 |
| **② 回报** | Python → Node | stdout 事件流 | Python **只往 stdout 打 JSON 行**：`{type:'progress', step, loss, reward}` / `{type:'checkpoint', path, step}` / `{type:'done'\|'failed', reason}`——Node 逐行解析更新状态 | 禁止 print 非 JSON 文本（污染事件流） |
| **③ 控制** | Node → Python | 信号 | Node 发 **SIGINT** → Python 捕获后**存 checkpoint 优雅退出**（退出码 0）→ Node 记录断点 → 续跑时从断点恢复 | 硬杀（SIGKILL）仅限沙箱超时兜底 |

**协议错误处理**：
- ② 流中一行 JSON 解析失败 → 记 `train_protocol_error` 审计事件 + 尝试续解析，不整体崩溃（容忍库的 warn 输出）
- ③ SIGINT 后超时（默认 30s）未退出 → 升级 SIGKILL + 记审计（进程卡死兜底）
- job.json 校验失败（zod schema）→ 拒绝 spawn，返回结构化错误（对齐本版 workflow_submit 模式）

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/train/train-protocol.ts` | 新建 | 协议三约定的类型定义（job.json schema / stdout 事件类型 / 信号处理） |
| `engine/orchestrator/src/__tests__/train-protocol.test.ts` | 新建 | 单测（JSON 行解析 + 错误容忍 + 信号超时） |

### 验收标准

- [ ] job.json schema 定义（zod），校验失败拒绝 spawn
- [ ] stdout JSON 流解析（progress/checkpoint/done/failed），坏行不崩溃
- [ ] SIGINT → 优雅退出（存 checkpoint，退出码 0）；30s 超时升级 SIGKILL
- [ ] `npm test` 全绿

## 🔒 双闸验证（P2 · 自 v1.3.5 移入 · 运维闭环增强）

> 📖 **来源**：v1.3.0 运行时审计只做「执行前 gate」，双闸补「执行后副作用复查」。

### 定位

v1.3.0 的 wrapToolCall middleware 是「执行前 gate」（拦截危险工具调用）。双闸验证补「执行后副作用复查」——工具执行完后，复查实际产生的副作用是否符合预期（如：写文件操作是否真的只写了预期文件、没误改其他文件）。前后双闸 = 执行前拦截 + 执行后复查。

### 交付（P2）

- wrapToolCall middleware 新增 `postToolCall` 钩子（v1.3.0 只有 pre）
- 副作用复查规则集：文件写入范围复查 / git 操作影响范围复查 / 网络外联目标复查
- 复查异常 → 写运行时审计 WARN + 中断后续工具调用

### 验收标准

- [ ] `postToolCall` 钩子存在并在每次工具执行后触发
- [ ] 至少 3 条副作用复查规则（文件 / git / 网络）
- [ ] 复查异常写审计 WARN 并中断

## 😴 Agent 疲劳度检测（P2 · 自 v1.3.5 移入 · 运维闭环增强）

### 定位

Agent 跑长循环时上下文窗口会被污染、决策质量会衰减——「疲劳」不是 metaphor，是可观测的信号（重复调用同一失败工具 / 忽略前文约束 / 输出质量下降）。本项给运维闭环补一个健康指标。

### 交付（P2）

- 疲劳信号采集：同一工具连续失败次数 / 上下文窗口占用率 / 输出与历史相似度（查重）
- 疲劳度评分 → 写 daemon-health.json（@hourly 采集）
- 疲劳度超阈值 → daemon 触发自动 `/compact`（v1.2.7 已有）或建议重启

### 验收标准

- [ ] 3 个疲劳信号可采集（连续失败 / 窗口占用 / 输出相似度）
- [ ] 疲劳度评分写 daemon-health.json
- [ ] 超阈值触发 compact 或重启建议

## 🪜 分级降级梯队（P2 · 自 v1.3.5 移入 · 韧性设计 · OpenFDE 启发）

> 📖 **来源**：OpenFDE 分级降级——console → TUI → spec 逐级降级，workflow never stops。

### 定位

sofagent 当前的降级是二态（全功能 / crash）。本项补分级降级梯队——当某个能力不可用时，逐级降级而非整盘崩溃：full（全部规则 + LLM 审计）→ rules-only（纯 git-diff 规则，LLM 不可用时）→ minimal（只跑 A1-A11 核心安全规则）→ safe-stop（全部规则都跑不动时，安全停止不破坏）。workflow never stops = 总有一级能兜底。

### 交付（P2）

- 降级触发器：LLM 不可用 / 审计引擎超时 / daemon 崩溃
- 三级降级：full → rules-only → minimal → safe-stop
- 每次降级写审计日志（记录降级原因 + 降级到哪级 + 持续多久）

### 验收标准

- [ ] 3 个降级触发器可检测（LLM / 审计引擎 / daemon）
- [ ] 三级降级状态机正确（full → rules-only → minimal → safe-stop）
- [ ] 每次降级写审计日志

## 📝 decisions.jsonl 完整版（P2 · 自 v1.3.5 移入 · 意图审计扩展 · OpenFDE 启发）

> 📖 **来源**：OpenFDE decisions.jsonl——每次判断落 `{kind, moment, why, spec_ref}`。v1.3.0 已交付 emitDecision（决策审计 MVP），本项扩展为完整版。

### 定位

v1.3.0 的 `emitDecision()` 只在关键节点（HITL / 审计 FAIL）触发。decisions.jsonl 完整版补「判断时刻日志」——Agent 每次做选择（走哪条路 / 选哪个方案 / 为什么跳过某步）都落 `{kind, moment, why, spec_ref}`，让意图审计从「只记关键决策」扩展到「记全部判断时刻」。

### 交付（P2）

- 扩展 emitDecision 触发点：从关键节点扩展到 Agent 的每次方案选择
- `kind` 分类枚举（route / select / skip / retry / escalate）
- decisions.jsonl 查询接口：按 kind / 按 moment / 按 agentId 回溯

### 验收标准

- [ ] emitDecision 触发点扩展到方案选择时刻
- [ ] kind 枚举至少 5 种（route/select/skip/retry/escalate）
- [ ] decisions.jsonl 可按 kind / moment / agentId 查询
