## 定位

v1.3.1 交付了 Onboard Agent **L1（工程判定）**——crash/error/超时检测 + 报错人工修。v1.3.2 补上 **L2-L5**，让 Onboard Agent 从"半自动"进化到"全闭环"：

```
v1.3.1 L1：跑没崩？→ 崩了报给人（半自动）
v1.3.2 L2：跑出来的对不对？→ Ontology 判据（语义判定）
v1.3.2 L3：不对的话哪不对？→ LLM 推理定位（自动定位）
v1.3.2 L4：定位到了怎么改？→ 自动改 + 审计兜底（自动修复）
v1.3.2 L5：改了再跑什么时候停？→ 连续 N 轮 PASS（循环收敛）
```

**完整闭环**：企业 AI 节点 activate → L1 跑一轮 → L2 判对错 → 不对 → L3 定位 → L4 修复 → L1 再跑 → L5 判收敛 → 收敛 PASS 或人工介入。

---

## L2：语义判定（Ontology 作判据）

### 痛点

L1 只判"跑没跑起来"——不判"跑出来的结果对不对"。一个客服节点可能跑起来了、没崩，但把"退货"处理成了"投诉"——L1 判 PASS，但语义错了。

### 判据来源：Ontology（v1.3.1 交付）

v1.3.1 的 Ontology 本体结构定义了每个 Action 的预期输出（实体类型 / 关系 / 约束）。L2 做的是：

```
节点实际输出（非结构化 / 半结构化）
  → 结构化提取（解析器）
  → 与 Ontology 定义的预期输出对比（对比器）
  → 差异报告（哪个字段缺了 / 哪个值错了 / 哪个关系断了）
```

**这不是"调一下 Ontology API"就行的**——中间的"结构化提取 + 比对逻辑 + 差异报告"是独立工程。

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/loop-agent/ontology-comparator.ts` | 新建 | Ontology 预期 vs 实际输出对比器 |
| `engine/orchestrator/src/loop-agent/output-extractor.ts` | 新建 | 非结构化输出 → 结构化提取（供对比器用） |
| `engine/orchestrator/src/loop-agent/diff-report.ts` | 新建 | 差异报告格式（给 L3 定位用） |

### 难度

⭐⭐⭐（中等偏难）。核心难点：非结构化输出 → 结构化提取的准确率。

## L3：自动定位（LLM 推理）

### 痛点

L2 判出"不对"了，但不知道**哪层出了问题**——是 Skill 写错了？是 Ontology 定义缺了？是 prompt 偏了？是知识库里少了某个概念？

### 解法：LLM 实时推理定位

初版不依赖错误模式库（那个需要 v1.3.1 L1 跑很久积累），而是用 **LLM 实时推理**——把 L2 的差异报告 + 审计日志 + Ontology 定义喂给强模型，让它推理"最可能是哪层出问题"。

| 错误源 | 推理输入 | 推理输出 |
|--------|---------|---------|
| Skill（工具描述/few-shot 不够） | diff-report + SKILL.md | "Skill 里工具描述不清晰，Agent 选错工具" |
| Ontology（实体/关系定义缺） | diff-report + entities/ | "Ontology 缺'退货'实体，Agent 无法识别" |
| Prompt（system prompt 偏） | diff-report + system-prompt | "prompt 未明确区分退货和投诉" |
| 知识库（缺概念） | diff-report + knowledge/ | "知识库无退货流程文档，Agent 无参考" |

**准确率取决于模型能力**——初版可能不够准，但比全靠人快。且定位错了不致命——L4 改完 L1 会再跑，L2 再判，循环收敛。

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/loop-agent/error-localizer.ts` | 新建 | LLM 推理定位器（输入 diff-report + 上下文 → 输出定位结果） |

### 难度

⭐⭐⭐（中等）。每轮调 LLM，有成本——但比人工定位快得多。

## L4：自动修复（审计兜底）

### 痛点

L3 定位到了"Skill 工具描述不清晰"，但谁去改？全靠人就没闭环了。

### 解法：自动改 + 审计引擎硬证据兜底

L3 定位结果 → LLM 生成修复方案 → 自动应用修改 → **审计引擎跑 git diff 卡关** → PASS 则进 L5 / FAIL 则回滚 + 报人。

**安全网**：L4 改错了不致命。审计引擎用 24 条规则 + git diff 硬证据拦——错误修复进不了生产。这就是"一步到位做 L4"的底气：改错了→审计拦→回滚→回 L1 重跑。

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/loop-agent/fix-applier.ts` | 新建 | 接收 L3 定位 → LLM 生成修复 → 应用 + 审计卡关 |

### 难度

⭐⭐⭐⭐（偏难）。需复用 FORGE 的 engineer pattern（已有参考实现）+ 审计引擎集成。

---

## L5：循环收敛（防发散）

### 痛点

L4 改了 → L1 再跑 → 又不对 → L3 再定位 → L4 再改……可能永远不收敛（改了 A 坏了 B，无限循环）。

### 解法：收敛判定

- **连续 N 轮 L2 PASS**（默认 N=3）→ 判收敛，Onboard Agent 退出
- **连续 M 轮 L4 改了但 L2 仍 FAIL**（默认 M=5）→ 判发散，停 + 报人
- **回归测试**：L4 每次改完后，跑之前 PASS 的 case，防退化

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/loop-agent/driver.ts` | 修改 | 集成 L5 收敛判定逻辑（并入 v1.3.1 已有的 driver） |

### 难度

⭐⭐（中等）。逻辑不复杂，关键是参数调优（N/M 取多少）。

## 验收标准

- [ ] L2：对 activate 生成的企业节点，实际输出与 Ontology 预期输出对比，生成差异报告
- [ ] L3：基于差异报告 + 上下文，LLM 推理输出定位结果（错误源 + 置信度）
- [ ] L4：自动应用修复 → 审计引擎 git diff 卡关 → PASS 进 L5 / FAIL 回滚 + 报人
- [ ] L5：连续 3 轮 L2 PASS 判收敛；连续 5 轮改了仍 FAIL 判发散
- [ ] **全链路**：activate → L1 跑 → L2 判 → L3 定位 → L4 改 → L1 再跑 → L5 收敛，无人介入跑通
- [ ] 调试记录带 agentId（身份码溯源，v1.3.1 身份码）
