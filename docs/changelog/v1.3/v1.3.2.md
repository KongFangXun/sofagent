## 定位

v1.3.1 交付了 Onboard Agent **L1（工程判定）**——crash/error/超时检测 + 报错人工修。v1.3.2 补上 **L2-L5**，让 Onboard Agent 从"半自动"进化到"全闭环"：

```
v1.3.1 L1：跑没崩？→ 崩了报给人（半自动）
v1.3.2 L2：跑出来的对不对？→ Ontology 判据（语义判定）
v1.3.2 L3：不对的话哪不对？→ LLM 推理定位（自动定位）
v1.3.2 L4：定位到了怎么改？→ 自动改 + 审计兜底（自动修复）
v1.3.2 L5：改了再跑什么时候停？→ 连续 N 轮 PASS（循环收敛）
```

**完整闭环**：企业 AI 节点 activate → L1 跑一轮 → L2 判对错 → 不对 → L3 定位 → L4 修复 → L1 再跑 → L5 判收敛 → 收敛 PASS 或人工介入。

## L2：语义判定（Ontology 作判据）

### 痛点

L1 只判"跑没跑起来"——不判"跑出来的结果对不对"。一个客服节点可能跑起来了、没崩，但把"退货"处理成了"投诉"——L1 判 PASS，但语义错了。

### 判据来源：Ontology（v1.3.1 交付）

v1.3.1 的 Ontology 本体结构定义了每个 Action 的预期输出（实体类型 / 关系 / 约束）。L2 做的是：

```
节点实际输出（非结构化 / 半结构化）
  → 结构化提取（解析器）
  → 与 Ontology 定义的预期输出对比（对比器）
  → 差异报告（哪个字段缺了 / 哪个值错了 / 哪个关系断了）
```

**这不是"调一下 Ontology API"就行的**——中间的"结构化提取 + 比对逻辑 + 差异报告"是独立工程。

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/loop-agent/ontology-comparator.ts` | 新建 | Ontology 预期 vs 实际输出对比器 |
| `engine/orchestrator/src/loop-agent/output-extractor.ts` | 新建 | 非结构化输出 → 结构化提取（供对比器用） |
| `engine/orchestrator/src/loop-agent/diff-report.ts` | 新建 | 差异报告格式（给 L3 定位用） |

### 难度

⭐⭐⭐（中等偏难）。核心难点：非结构化输出 → 结构化提取的准确率。

## L3：自动定位（LLM 推理）

### 痛点

L2 判出"不对"了，但不知道**哪层出了问题**——是 Skill 写错了？是 Ontology 定义缺了？是 prompt 偏了？是知识库里少了某个概念？

### 解法：LLM 实时推理定位

初版不依赖错误模式库（那个需要 v1.3.1 L1 跑很久积累），而是用 **LLM 实时推理**——把 L2 的差异报告 + 审计日志 + Ontology 定义喂给强模型，让它推理"最可能是哪层出问题"。

| 错误源 | 推理输入 | 推理输出 |
|--------|---------|---------|
| Skill（工具描述/few-shot 不够） | diff-report + SKILL.md | "Skill 里工具描述不清晰，Agent 选错工具" |
| Ontology（实体/关系定义缺） | diff-report + entities/ | "Ontology 缺'退货'实体，Agent 无法识别" |
| Prompt（system prompt 偏） | diff-report + system-prompt | "prompt 未明确区分退货和投诉" |
| 知识库（缺概念） | diff-report + knowledge/ | "知识库无退货流程文档，Agent 无参考" |

**准确率取决于模型能力**——初版可能不够准，但比全靠人快。且定位错了不致命——L4 改完 L1 会再跑，L2 再判，循环收敛。

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/loop-agent/error-localizer.ts` | 新建 | LLM 推理定位器（输入 diff-report + 上下文 → 输出定位结果） |

### 难度

⭐⭐⭐（中等）。每轮调 LLM，有成本——但比人工定位快得多。

## L4：自动修复（审计兜底）

### 痛点

L3 定位到了"Skill 工具描述不清晰"，但谁去改？全靠人就没闭环了。

### 解法：自动改 + 审计引擎硬证据兜底

L3 定位结果 → LLM 生成修复方案 → 自动应用修改 → **审计引擎跑 git diff 卡关** → PASS 则进 L5 / FAIL 则回滚 + 报人。

**安全网**：L4 改错了不致命。审计引擎用 24 条规则 + git diff 硬证据拦——错误修复进不了生产。这就是"一步到位做 L4"的底气：改错了→审计拦→回滚→回 L1 重跑。

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/loop-agent/fix-applier.ts` | 新建 | 接收 L3 定位 → LLM 生成修复 → 应用 + 审计卡关 |

### 难度

⭐⭐⭐⭐（偏难）。需复用 FORGE 的 engineer pattern（已有参考实现）+ 审计引擎集成。

## L5：循环收敛（防发散）

### 痛点

L4 改了 → L1 再跑 → 又不对 → L3 再定位 → L4 再改……可能永远不收敛（改了 A 坏了 B，无限循环）。

### 解法：收敛判定

- **连续 N 轮 L2 PASS**（默认 N=3）→ 判收敛，Onboard Agent 退出
- **连续 M 轮 L4 改了但 L2 仍 FAIL**（默认 M=5）→ 判发散，停 + 报人
- **回归测试**：L4 每次改完后，跑之前 PASS 的 case，防退化

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/loop-agent/driver.ts` | 修改 | 集成 L5 收敛判定逻辑（并入 v1.3.1 已有的 driver） |

### 难度

⭐⭐（中等）。逻辑不复杂，关键是参数调优（N/M 取多少）。

## agent-creation 方法论（Onboard Agent 完整版核心能力）

> 📖 **设计来源**：PenguinHarness `agent-creation` Skill（v7）方法论。完整设计文档见 `~/Desktop/penguin-harness-ref/design-doc.md`。

### 定位

Onboard Agent L2-L5 解决"节点跑起来了但结果不对"。但节点本身是怎么来的？当前依赖 FDE 手动搭建——FDE 离场后客户自己加新节点时没有方法论。

agent-creation 方法论补上这个缺口：**一句话需求 → 自动推导节点配置**。FDE 离场后，客户可以用这套方法论自己搭新 AI 节点。

### 核心流程（借鉴 PenguinHarness 重新写成 sofagent 术语）

| 步骤 | PenguinHarness 原版 | sofagent 适配 |
|------|---------------------|--------------|
| ① 需求推导 | 从一句话推导 Role + Domain guidance，不追问 | 同——从 workflow 节点描述推导角色 + 域规则 |
| ② 解析运行时 | 继承 provider/model_id + thinking_level | 继承 FDE 配置的 Agent 模型参数 |
| ③ 写行为层 | 写 AGENTS.md（注入 system prompt） | 写 think.md（L2 决策约束） |
| ④ 安装经验 | 从 skills/ 库安装匹配 Skill | 从 knowledge/ 库安装匹配经验条目（L4） |
| ⑤ 验证 | parse config + 确认非空 + skill name 匹配目录 | 约束层加载链校验 + 结构完整性检查 |

### 关键原则

1. **需求够具体就不追问**——一句话如"一个回答金融合规问题的专家"就能推导出角色 + 引用规则 + 拒绝规则
2. **只安装需要的经验**——避免过度配置（不是所有节点都需要全部 knowledge/）
3. **行为层简洁**——think.md 是 prompt context 不是文档，几行角色句 + 规则就够
4. **验证清单**——建完后自动检查：config 可 parse + think.md 非空 + knowledge 条目结构正确

### sofagent 术语映射

| PenguinHarness | sofagent | 说明 |
|----------------|----------|------|
| AGENTS.md | think.md（L2 决策约束） | 行为指导层 |
| Skills (`skills/`) | knowledge/（L4 经验层） | 可学习的经验知识 |
| system_config.yaml | permission.json + Agent 元信息 | 运行时配置 |
| Builder Session | FDE Agent | 建完后离场 |
| default_agent 模板 | Onboard Agent 模板 | 基础配置模板 |

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/onboard/agent-creator.ts` | 新建 | 需求推导 + think.md 生成 + knowledge 安装 |
| `engine/orchestrator/src/onboard/creation-validator.ts` | 新建 | 结构完整性验证（加载链校验 + 非空检查） |

### 验收标准

- [ ] 一句话需求 → 自动推导角色 + 域规则（不追问）

### workflow 批量自动生成（FDE 交付后的自动建 Agent）

> 📖 **设计来源**：PenguinHarness「用 Agent 构建 Agent」（100 倍速度）——本版落地开源侧「确定性生成」版本：规则驱动，非模型驱动（模型驱动的自动生成是商业版的能力，两者边界清晰）。

**定位**：上面的 agent-creation 是**人工触发**（FDE 离场后客户自己调用 `create_agent`）。本小节把它升级为 **workflow 驱动自动触发**：FDE 交付的 workflow.yml 含 N 个节点 → 系统自动为每个节点推导 sub-agent 配置。

```
FDE 交付 workflow.yml（N 个节点）
  → 遍历每个节点，提取节点描述
  → 复用 agent-creation 推导逻辑（Role + 域规则 + think.md + knowledge 安装）
  → 批量生成 N 个 sub-agent 配置（注册进 registry）
  → 主 agent 编排（分发 / 监控 / 审计 / 通讯，见 v1.3.3 L2 协作协议）
```

**与人工触发的区别**：人工 `create_agent` 是「客户要什么建什么」；workflow 批量生成是「FDE 梳理了什么就建什么」——节点描述来自 FDE 交付物，不是用户临时输入。这让 FDE 离场后企业 AI 节点**开箱即用**，不需要客户自己动手建。

#### 节点类型动态解析链（模型层对接前置）

**现状**：`workflow-parser.ts` 的 agent 映射表**硬编码 4 种类型**（developer / qa-engineer / researcher / technical-writer），「未知类型同路降级 general-purpose」——模型层（商业侧）自动生成的任意节点类型（产线校准、订单审批…）会被全部降级成通用 Agent，跑不出预期行为。

**解法**：解析链从「硬编码映射 + 降级」升级为「**registry 动态查找 + agent-creation 兜底生成**」：

```
workflow.yml 节点类型
  → ① registry 动态查找（已注册的 sub-agent 直接复用，不重复生成）
  → ② 查不到 → 复用 agent-creator 推导逻辑生成（Role + 域规则 + think.md + knowledge）
  → ③ 生成后注册进 registry，后续复用
```

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/workflow-parser.ts` | 修改 | agent 映射从硬编码 4 种改为 registry 动态查找 + agent-creation 兜底（移除「未知降级 general-purpose」路径） |
| `engine/orchestrator/src/__tests__/workflow-parser.test.ts` | 修改 | 补未知节点类型 → agent-creation 生成用例 |

**验收标准**（并入本节）：
- [ ] workflow.yml 含 N 个节点 → 自动生成 N 个 sub-agent 配置
- [ ] 复用 agent-creator 推导逻辑（不重复实现）
- [ ] 生成的 sub-agent 注册进 registry
- [ ] **未知节点类型不再降级 general-purpose——走 agent-creation 生成**（registry 已有类型直接复用）
- [ ] 主 agent 可编排（分发 / 监控 / 审计 / 通讯，对接 v1.3.3 L2 协议）
- [ ] `npm test` 全绿

## 企业专属 eval 套件（a16z 法则6 产品化 · 缺口补全）

> 📖 **设计来源**：a16z《You Just Hired a Million Bad Employees》法则6「考核 Evals」映射的 sofagent 缺口——审计 A1-A23 是 eval 底座，缺口在**企业行业模板层**。Satya Nadella「Every company will have its own private eval」为方向背书。

### 定位

Onboard Agent L5 已有回归测试雏形（「L4 每次改完后，跑之前 PASS 的 case，防退化」）——但那是**通用**回归。企业专属 eval 套件把它产品化：**FDE 交付时带一套可跑的企业行业 eval**，Onboard/Refine 跑闭环时有量化基线可对照。

### 交付

| 能力 | 说明 |
|------|------|
| **企业行业 eval 模板** | 按行业预置 eval case 模板（金融合规 / 制造流程 / 供应链等），FDE 交付时按客户 workflow 实例化 |
| **eval 基线冻结** | 首次交付时跑一轮冻结基线（对接 v1.3.1 Benchmark 评测体系的 Formal Baseline） |
| **回归门禁** | Onboard L5 / Refine 每次修改后跑企业 eval，防「修 A 坏 B」的行业场景退化（补齐 L5 从"通用回归"到"行业回归"） |
| **MCP `eval_suite` tool** | 触发/查询企业 eval 套件运行结果 |

## 模型接入插槽扩展（client_type · 模型层接入地基）

> 📋 **2026-08-09 从 v1.3.1 移入**（v1.3.1 交付已满 14 项）；穷尽性审查发现：`model-router-config.ts` 的本地模型 schema **写死只支持 `provider: z.literal('ollama')`**——后训练模型（vLLM / OpenAI 兼容接口部署）无法接入 local-executor / local-pipeline 档。这是模型层接入约束层的**地基**（模型先能接上，才谈得上 v1.3.6 的注册 / 托管 / 评测）。

### 定位

| 档位 | 现状 | 扩展后 |

## FDE 梳理辅助工具（workflow.yml 草稿生成 · 半自动引导）

> 📋 **2026-08-09 新增（穷尽性审查发现）**：workflow 批量生成假设 workflow.yml 已存在——但 workflow.yml 从哪来？**全靠 FDE 人工手写**。本工具补上「快速梳理 workflow」的数字化起点：**从五要素到 workflow.yml 草稿的半自动引导**。

### 定位：谁来生成？边界在哪？

| 版本 | 谁生成 workflow | 方式 |
|------|----------------|------|
| **开源本工具** | **FDE / 人工**（填五要素） | **规则驱动引导**——工具把 FDE 的判断数字化，**LLM 不参与 workflow 生成** |
| 模型层（商业侧） | **模型**（自动采集企业数据） | 模型驱动自动生成 → v1.3.6 ① 喂入 |

**边界铁律**：开源版**不做 LLM 生成 workflow**——那是模型层（商业侧）的模型驱动主战场（开源规则驱动 / 商业版模型驱动，边界清晰）。本工具是「给人用的加速器」，商业版是「模型替代人」。工具沉淀的 workflow.yml 同时是商业版的**对比基准与验证数据**（人工梳理结果 vs 模型生成结果可评测）。

### 实现方案

```
FDE 访谈 → 逐节点填五要素（输入/输出/负责人/耗时/最卡的地方）
  → 每节点三问判定（① 输入能自动取？② 规则能写清？③ 输出能自动推？）
      → 自动打分类标签（🔄 自动执行 / ⚡ 强化岗位 / 👤 暂不动）
  → 节点间依赖引导（哪个节点需要哪个节点的产出）→ depends_on
  → 自动生成 workflow.yml 草稿（name / description / nodes）
  → 格式校验（对齐 workflow-parser 现有格式：id/agent/task/depends_on）
  → 人工确认 → 落盘 workflow.yml → 接 workflow 批量生成（自动建 sub-agent）
```

| 组件 | 能力 |
|------|------|
| **交互式引导** | CLI `sofagent fde compose`——逐节点提问五要素，必填字段校验（缺「最卡的地方」不允许跳过） |
| **三问自动分类** | 每节点按三问判定自动打 🔄/⚡/👤 标签（FDE 可改，改后记录） |
| **依赖引导** | 节点产出物列表 → 后续节点选择依赖（自动校验无环——复用 workflow-parser DAG 校验） |
| **草稿生成** | 按现有 workflow-parser 格式生成 workflow.yml（v1.3.6 ① 的 JSON Schema 是对此格式的公开化，两者一致）——**`agent` 字段留空**（五要素不含 agent 类型，由节点类型动态解析链在批量生成时自动推导：registry 查找 → agent-creation 兜底） |
| **量化四字段收集** | 顺带收集 GUIDE §4.3 量化四字段（当前成本 / AI 后成本 / 年节省 / 回本周期，年节省=日耗时×时薪×250）——产出配套绩效表，**是绩效量化引擎的直接输入**（时薪暂用口述，后续可换市场基准） |
| **人工确认** | 生成后逐节点确认/修改，确认后落盘（审计留痕：谁建的、什么时候改的） |

> 🧠 **字段衔接（2026-08-09 补充）**：五要素（输入/输出/负责人/耗时/最卡的地方）里**没有 agent 类型**——草稿的 `agent` 字段留空，由 v1.3.2「节点类型动态解析链」在 workflow 批量生成时自动推导（registry 查找 → agent-creation 兜底），FDE 无需知道节点该用哪种 Agent。量化四字段是 GUIDE 方法论的自然延伸——工具一次收集，FDE 交付的绩效基线就齐了。

### Ontology 咨询式生成端（FDE Agent 主动沟通生成 · 2026-08-10 补充）
