## P2：养护（owner + 失效退役）——第五环

> 📖 **设计来源**：《AI 时代的组织应该是 GitHub 模式》（2026-07）「持续养护：明确 owner、审阅机制和回退权」+ FDE/GUIDE.md §5.12 能力资产管理——发布→发现→调用→评价四环缺「养护」：谁维护这项能力、谁能改、失效后怎样修正或退役。

**定位**：组织能力市场四环（发布/发现/调用/评价）管「能力流转」，但**没有管「能力存续」**——一项能力发布后，owner 是谁？失效了谁负责修？长期无人调用怎么办？这就是「养护」环。补上它，市场才完整（GitHub 模式里对应「仓库的 maintainer + issue 维护 + 归档」）。

### 交付

| 能力 | 说明 |
|------|------|
| **owner 声明** | 能力发布时强制声明维护人（复用 v1.3.1 Agent 身份码）——能力有主，改动有人负责 |
| **失效退役** | 长期无人调用 / 评价持续走低 / owner 主动下线 → 标记退役（不再被发现/调用，可恢复） |
| **养护记录** | 每次能力变更记录 owner + 变更原因（对接 decision-log evidence 字段）——养护可追溯 |
| **MCP `market_retire` tool** | 退役能力（强制 owner 确认） |

| 文件 | 改动 | 说明 |
|------|------|------|

### 验收标准（P2）

- [ ] 能力发布时强制声明 owner（无 owner 不可发布）
- [ ] 失效能力可退役（不再被发现/调用），可恢复
- [ ] 每次能力变更记录 owner + 原因（养护可追溯）
- [ ] MCP `market_retire` tool 可用（强制 owner 确认）
- [ ] `npm test` 全绿

> 🧠 **为什么补这一环**：市场四环管「能力流转」，养护环管「能力存续」——缺了它，市场里的能力会「只增不减」，长期无人维护的死能力污染检索结果（对应 GitHub 模式里无人维护的仓库会污染生态）。五环闭环 = 组织能力市场从「集市」升级为「会自我养护的树」。
