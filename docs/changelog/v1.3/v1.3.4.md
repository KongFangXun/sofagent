- **L3 组织能力市场**——Skill / Agent / 流程在企业内**发布 → 发现 → 调用 → 评价 → 养护**，高频高价值的能力自然胜出。这是"有身份 Agent 的协作成果"的变现层：L2 让 Agent 能协作，L3 让协作成果可复用、可交易（组织内的能力市场）。

## 养护（owner + 失效退役）——第五环

> 📖 **设计来源**：《AI 时代的组织应该是 GitHub 模式》（2026-07）「持续养护：明确 owner、审阅机制和回退权」+ FDE/GUIDE.md §5.12 能力资产管理——发布→发现→调用→评价四环缺「养护」：谁维护这项能力、谁能改、失效后怎样修正或退役。

**定位**：组织能力市场四环（发布/发现/调用/评价）管「能力流转」，但**没有管「能力存续」**——一项能力发布后，owner 是谁？失效了谁负责修？长期无人调用怎么办？这就是「养护」环。补上它，市场才完整（GitHub 模式里对应「仓库的 maintainer + issue 维护 + 归档」）。

### 交付

| 能力 | 说明 |
|------|------|
| **owner 声明** | 能力发布时强制声明维护人（复用 v1.3.1 Agent 身份码）——能力有主，改动有人负责。owner 记录同时承载 **trust 信誉分**（v1.3.4 新建，见待明确事项 #2） |
| **失效退役** | 长期无人调用 / 评价持续走低 / owner 主动下线 → 标记退役（不再被发现/调用，可恢复） |
| **养护记录** | 每次能力变更记录 owner + 变更原因（对接 decision-log evidence 字段）——养护可追溯 |
| **MCP `market_retire` tool** | 退役能力（强制 owner 确认） |

## 🛡️ SkillScan 安全扫描器（DeerFlow 启发）

> 📖 **来源**：DeerFlow 安全扫描理念。第三方 Skill 安装前做静态安全扫描。

### 定位

L3 组织能力市场的安全门——市场允许第三方 Skill 发布，但发布/安装前必须过安全扫描，防止恶意 Skill 注入或越权。这是市场五环中「发布」环节的安全前置。

### 交付

- Skill 安装前静态扫描：注入检测（`eval` / `child_process` / 网络外联）+ 越权检测（访问 `.env` / SSH key / 系统目录）+ 敏感信息泄漏
- 扫描结果三态（SAFE / SUSPICIOUS / DANGEROUS）——复用 `@sofagent/skillopt` 的 `scanSkillSafety()`（v1.0.3 已有）
- ⚠️ **扫描引擎归属（防重复建设）**：`scanSkillSafety()` 是 skillopt 封装入口，核心扫描引擎与规则库在 `@sofagent/audit` 的 `skill-safety-{engine,rules,reporter}.ts`（skillopt 从 audit import）。集成层只做发布/安装双触发接线，不新写扫描逻辑
- DANGEROUS 拦截安装，SUSPICIOUS 警告但允许，SAFE 直接放行
- 扫描报告进审计日志

### 验收标准

- [x] `scanSkillSafety()` 集成到 Skill 安装流程（发布 + 安装双触发）
- [x] 三态判定正确（SAFE/SUSPICIOUS/DANGEROUS）
- [x] DANGEROUS 被拦截，SUSPICIOUS 警告，SAFE 放行
- [x] 扫描报告写审计日志

## 📊 评估体系三步——Refine 质量规则集的反哺闭环

> 📖 **设计来源**：范冰《前线部署工程师》方法论（2026-08-13 补充）+ ROADMAP v1.3.4 行「评估体系三步落地」。Refine Agent（v1.3.3）质量规则集有三个静态来源（builtin / fde_delivery / team_feedback），但缺「从生产案例动态生长」的通道。评估体系三步就是这个通道。

**定位**：让质量规则不是写死的，而是从市场调用和 Refine 循环的真实结果里持续提炼、评审、晋升。三步闭环 = 真实案例长出来 → 业务方当评委 → 接到生产回路上。

### 三步设计

| 步 | 能力 | 复用 | 输出 |
|---|------|------|------|
| **① 真实案例长出来** | 从市场调用日志（低分差评）+ Refine 循环结果（反复触发同类问题）提炼规则候选 | `parseFdeDeliveryReport()` 解析逻辑 | `QualityRule[]` 候选（source=team_feedback，待评审） |
| **② 业务方当评委** | 候选规则跑过 Benchmark 题库看评分是否提升 + 业务方 HITL 批准/驳回 | v1.3.1 Benchmark 评测 + HITL 通道 | 业务方签字的规则（evidence=Benchmark 报告 hash） |
| **③ 接到生产回路** | 批准的规则晋升到 `builtinQualityRules()`，下次 Refine 循环自动加载 | `engine/audit/src/decision-log.ts`（kind=EVOLUTION + evidence） | 晋升记录写 decision-log，规则进 builtin |

## 🔌 编排层与执行层分离（DSH 执行后端接入 · 增量）

> 📖 **设计来源**：DeepSeek Harness（DSH）「一切皆插件」Cordis 运行时（github.com/deepseek-ai/DeepSeek-Harness，MIT，0.1.0-rc.5）+ sofagent「确定性审计依赖显式图结构」铁律——编排层不换（确定性），执行层可换（灵活性）。完整开发 prompt 见桌面 `v1.3.4-incremental-dsh-prompt.md`。

### 定位

sofagent 当前的编排层（LangGraph StateGraph）和执行层（createReactAgent）混在一起——launcher / FORGE driver / dag-runner / composer / loop 节点各自直连 `createReactAgent`，执行后端不可替换。本增量做分离的第一波：**定义 `ExecutionBackend` 接口 + DSH 适配器 + LangGraph fallback，先迁移 launcher 主入口 + FORGE 两个 driver**，其余调用点列入后续迁移清单。

### 边界规则

- **编排层永远不换**——24 条 git diff 审计规则 + HMAC 链 + DAG 波次审计依赖图结构
- **执行层可换**——只要实现 `ExecutionBackend` 接口
- **loop 编排规则留编排层**（verdict 解析 / 场景覆盖 / 行数警戒线 / 声称一致性 / 并发控制 / 超时兜底），**loop 内部 worker 跑 agent 那一步让给执行层**
- **工具 wrapper 原样透传**——FORGE 的运行时审计（audit-middleware，v1.3.0）与进度监控（progress-middleware）是包在工具 func 上的 wrapper，随 `ExecutionTask.tools` 走，任何后端不得重包装或替换工具实现

### 接口契约（要点）

```typescript
interface ExecutionBackend {
  readonly name: 'dsh' | 'langgraph' | string;
  execute(task: ExecutionTask): Promise<ExecutionResult>;
  close?(): Promise<void>;
}

interface ExecutionTask {
  systemPrompt: string;
  task: string;
  tools: unknown[];           // 含 audit/progress wrapper，原样透传
  modelName?: string;
  modelConfig?: Record<string, unknown>;  // FORGE profile 体系
  toolBudget?: { softLimit: number; hardLimit: number };  // 所有后端强制
  recursionLimit?: number;
}

interface ExecutionResult {
  output: string;
  rounds: number;
  hitRecursionLimit: boolean;
  debugLogs?: Array<{ agentId?: string; action: string; timestamp: string }>;
}
```
