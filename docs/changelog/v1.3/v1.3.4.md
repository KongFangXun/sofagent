## 定位

v1.3.4 实现 **L3 组织能力市场**（五环）+ **SkillScan 安全门** + **评估体系三步**：

- **L3 组织能力市场**——Skill / Agent / 流程在企业内**发布 → 发现 → 调用 → 评价 → 养护**，高频高价值的能力自然胜出。这是"有身份 Agent 的协作成果"的变现层：L2 让 Agent 能协作，L3 让协作成果可复用、可交易（组织内的能力市场）。
- **SkillScan 安全门**——市场允许第三方 Skill 发布，发布/安装前必须过安全扫描（防恶意注入 / 越权 / 信息泄漏）。DeerFlow 启发。
- **评估体系三步**——Refine Agent（v1.3.3）质量规则集的反哺闭环：真实案例长出规则 → 业务方当评委 → 晋升到生产回路。让质量规则不是静态写死的，而是从生产中持续生长。

## P2：养护（owner + 失效退役）——第五环

> 📖 **设计来源**：《AI 时代的组织应该是 GitHub 模式》（2026-07）「持续养护：明确 owner、审阅机制和回退权」+ FDE/GUIDE.md §5.12 能力资产管理——发布→发现→调用→评价四环缺「养护」：谁维护这项能力、谁能改、失效后怎样修正或退役。

**定位**：组织能力市场四环（发布/发现/调用/评价）管「能力流转」，但**没有管「能力存续」**——一项能力发布后，owner 是谁？失效了谁负责修？长期无人调用怎么办？这就是「养护」环。补上它，市场才完整（GitHub 模式里对应「仓库的 maintainer + issue 维护 + 归档」）。

### 交付

| 能力 | 说明 |
|------|------|
| **owner 声明** | 能力发布时强制声明维护人（复用 v1.3.1 Agent 身份码）——能力有主，改动有人负责。owner 记录同时承载 **trust 信誉分**（v1.3.4 新建，见待明确事项 #2） |
| **失效退役** | 长期无人调用 / 评价持续走低 / owner 主动下线 → 标记退役（不再被发现/调用，可恢复） |
| **养护记录** | 每次能力变更记录 owner + 变更原因（对接 decision-log evidence 字段）——养护可追溯 |
| **MCP `market_retire` tool** | 退役能力（强制 owner 确认） |

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/market/owner.ts` | 新建 | owner 声明 + 变更记录（对接身份码） |
| `engine/orchestrator/src/market/retire.ts` | 新建 | 失效判定（无人调用/评分走低/主动下线）+ 退役标记 |
| `engine/mcp/src/tools/market-retire.ts` | 新建 | MCP `market_retire` tool（强制 owner 确认） |
| `engine/orchestrator/src/__tests__/market-owner.test.ts` | 新建 | 单测（owner 声明 + 退役 + 恢复） |

### 验收标准（P2）

- [ ] 能力发布时强制声明 owner（无 owner 不可发布）
- [ ] 失效能力可退役（不再被发现/调用），可恢复
- [ ] 每次能力变更记录 owner + 原因（养护可追溯）
- [ ] MCP `market_retire` tool 可用（强制 owner 确认）
- [ ] **SKILL.md 登记本版 MCP tools（`market_publish` / `market_search` / `market_invoke` / `market_rate` / `market_retire` / `market_harvest_rule`）—— check-version.sh 工具数校验通过**
- [ ] `npm test` 全绿

> 🧠 **为什么补这一环**：市场四环管「能力流转」，养护环管「能力存续」——缺了它，市场里的能力会「只增不减」，长期无人维护的死能力污染检索结果（对应 GitHub 模式里无人维护的仓库会污染生态）。五环闭环 = 组织能力市场从「集市」升级为「会自我养护的树」。

## 🛡️ SkillScan 安全扫描器（DeerFlow 启发 · P2）

> 📖 **来源**：DeerFlow 安全扫描理念。第三方 Skill 安装前做静态安全扫描。

### 定位

L3 组织能力市场的安全门——市场允许第三方 Skill 发布，但发布/安装前必须过安全扫描，防止恶意 Skill 注入或越权。这是市场五环中「发布」环节的安全前置。

### 交付（P2）

- Skill 安装前静态扫描：注入检测（`eval` / `child_process` / 网络外联）+ 越权检测（访问 `.env` / SSH key / 系统目录）+ 敏感信息泄漏
- 扫描结果三态（SAFE / SUSPICIOUS / DANGEROUS）——复用 `@sofagent/skillopt` 的 `scanSkillSafety()`（v1.0.3 已有）
- ⚠️ **扫描引擎归属（防重复建设）**：`scanSkillSafety()` 是 skillopt 封装入口，核心扫描引擎与规则库在 `@sofagent/audit` 的 `skill-safety-{engine,rules,reporter}.ts`（skillopt 从 audit import）。集成层只做发布/安装双触发接线，不新写扫描逻辑
- DANGEROUS 拦截安装，SUSPICIOUS 警告但允许，SAFE 直接放行
- 扫描报告进审计日志

### 验收标准

- [ ] `scanSkillSafety()` 集成到 Skill 安装流程（发布 + 安装双触发）
- [ ] 三态判定正确（SAFE/SUSPICIOUS/DANGEROUS）
- [ ] DANGEROUS 被拦截，SUSPICIOUS 警告，SAFE 放行
- [ ] 扫描报告写审计日志

## 📊 评估体系三步——Refine 质量规则集的反哺闭环（P2）

> 📖 **设计来源**：范冰《前线部署工程师》方法论（2026-08-13 补充）+ ROADMAP v1.3.4 行「评估体系三步落地」。Refine Agent（v1.3.3）质量规则集有三个静态来源（builtin / fde_delivery / team_feedback），但缺「从生产案例动态生长」的通道。评估体系三步就是这个通道。

**定位**：让质量规则不是写死的，而是从市场调用和 Refine 循环的真实结果里持续提炼、评审、晋升。三步闭环 = 真实案例长出来 → 业务方当评委 → 接到生产回路上。

### 三步设计

| 步 | 能力 | 复用 | 输出 |
|---|------|------|------|
| **① 真实案例长出来** | 从市场调用日志（低分差评）+ Refine 循环结果（反复触发同类问题）提炼规则候选 | `parseFdeDeliveryReport()` 解析逻辑 | `QualityRule[]` 候选（source=team_feedback，待评审） |
| **② 业务方当评委** | 候选规则跑过 Benchmark 题库看评分是否提升 + 业务方 HITL 批准/驳回 | v1.3.1 Benchmark 评测 + HITL 通道 | 业务方签字的规则（evidence=Benchmark 报告 hash） |
| **③ 接到生产回路** | 批准的规则晋升到 `builtinQualityRules()`，下次 Refine 循环自动加载 | `engine/audit/src/decision-log.ts`（kind=EVOLUTION + evidence） | 晋升记录写 decision-log，规则进 builtin |

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/market/rule-harvest.ts` | 新建 | 第一步：规则候选提炼 |
| `engine/orchestrator/src/market/rule-jury.ts` | 新建 | 第二步：Benchmark + HITL 评审 |
| `engine/orchestrator/src/market/rule-promote.ts` | 新建 | 第三步：晋升 builtin + decision-log |
| `engine/mcp/src/tools/market-harvest-rule.ts` | 新建 | MCP `market_harvest_rule` tool（触发第一步） |
| `engine/orchestrator/src/__tests__/market-rule-cycle.test.ts` | 新建 | 单测（三步闭环） |

### 验收标准

- [ ] 市场低分差评 + Refine 反复触发的问题可被提炼为规则候选
- [ ] 候选规则可经 Benchmark 评测 + 业务方 HITL 评审
- [ ] 评审通过的规则晋升到 builtin，下次 Refine 循环自动生效
- [ ] 晋升全程记 decision-log（kind=EVOLUTION + evidence 三件套：Benchmark hash + 业务方签字 + 调用量数据）
- [ ] MCP `market_harvest_rule` tool 可用

> 🧠 **为什么补这一环**：Refine Agent 的质量规则集如果只有静态三来源，规则库会停滞——市场五环让能力流转起来，评估三步让规则也流转起来。两者合起来，组织的能力市场和规则市场都是「会自我生长的树」。
