## ✨ Refine Agent 完整版（FORGE 产品化第三刀）

> **设计来源**：FORGE 的 `fresh-eyes-driver.mjs`（2370 行）已验证"新鲜眼审查循环"可行性——审查发现问题 → 找另一个 agent 修 → 再审查 → 再修……循环直到质量收敛。Refine Agent 把这套能力产品化给企业。

### 与 Onboard Agent 的关系

| | Onboard Agent（v1.3.1+v1.3.2） | Refine Agent（本版） |
|---|---|---|
| **目标** | 节点从「不能用」到「能用」 | 节点从「能用」到「好用」 |
| **判据** | Ontology 本体结构（跑出来的对不对） | 质量规则集（跑出来的好不好） |
| **FORGE 原型** | release-gate-loop（发版门禁） | fresh-eyes-loop（新鲜眼审查） |
| **触发时机** | activate 后立即 | Onboard 收敛 PASS 后 |
| **循环引擎** | 自建 | **复用 Onboard 的 driver/judge/converge** |

两者串行：**Onboard 让它能干活 → Refine 让它干得好**。

### 五层（一次交付，复用 Onboard 引擎）

Onboard Agent 的 L1（工程判定）/ L3（定位）/ L4（修复）/ L5（收敛）是通用循环引擎，Refine Agent 直接复用，只换 **L2 判据层**：

| 层 | Onboard Agent | Refine Agent |
|:--:|--------------|--------------|
| L1 | crash/error/超时检测（复用） | 质量探测：跑一轮看输出规不规范 |
| **L2** | **Ontology 对比器（语义对错）** | **质量规则集判定（质量好坏）** |
| L3 | LLM 推理定位（复用） | 同 |
| L4 | 自动修复 + 审计兜底（复用） | 同 |
| L5 | 连续 N 轮 PASS 收敛（复用） | 同 |

### 质量规则集（Refine 的判据）

质量规则集不是凭空写的——来自三个来源：

| 来源 | 例子 | 怎么积累 |
|------|------|---------|
| **内置模板** | SKILL.md 工具描述必须带 example；输出不超过 500 字；few-shot 至少 2 条 | sofagent 自身开发经验固化 |
| **客户 FDE 回写** | 客户业务特定质量标准（如"金融场景必须带风险提示"） | FDE 离场时回写 delivery-report.md → 规则化 |
| **团队反馈放大** | 一个 Agent 踩过的坑广播成规则 | **本版协作协议的反馈放大机制** |

> 💡 **协同点**：质量规则集的第三个来源（团队反馈放大）正是本版 L2 协作协议的核心机制之一。这是两件事同版交付的深层原因——协作协议的反馈放大天然喂养 Refine Agent 的规则集。

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/refine-agent/refine-driver.ts` | 新建 | Refine 循环驱动（复用 Onboard driver，换 L2 判据） |
| `engine/orchestrator/src/refine-agent/quality-rule-set.ts` | 新建 | 质量规则集加载 + 匹配（内置模板 + 客户回写 + 团队反馈） |

| `engine/orchestrator/src/__tests__/refine-agent.test.ts` | 新建 | 单测（五层各一 + 与 Onboard 的串行验证） |

## 进化闭环升级（Benchmark 驱动的 Dream Cycle）

> 📖 **设计来源**：PenguinHarness `agent-optimization` Skill（v9）方法论。完整设计文档见 `~/Desktop/penguin-harness-ref/design-doc.md`。

### 定位

Refine Agent（本版 §Refine Agent）用质量规则集驱动优化。进化闭环升级把判据从「质量规则集」扩展为「Benchmark 评测结果」——不只看"输出规不规范"，更看"能力分数是否提升"。

### 核心循环（借鉴 agent-optimization 重新写成 sofagent 术语）

```
evidence（Benchmark 分数 + Trace）
  → hypothesis（哪个能力缺口导致失分）
    → Candidate（修改经验层）
      → evaluation（重跑 Benchmark）
        → strictly improves ? accept : rollback
```

### 关键规则

| 规则 | PenguinHarness 原版 | sofagent 适配 |
|------|---------------------|--------------|
| **严格提升才接受** | Candidate 分数严格 > Reference 才接受 | 同——Benchmark 分数不提升就回滚 |
| **快照+版本号回滚** | `snapshots/v<n>.tar.gz`，版本号只增 | 复用 sofagent git snapshot + Agent 版本号递增 |
| **污染检测** | 私有评测信息进入优化器 → 立即恢复 + 停止 | 同——rubric/Gold 不得进入优化器上下文 |
| **可证伪假设** | 优化前预测行为变化 → 验证 | 同——即使假设不成立但分数提升仍接受 |

### ⚠️ 优化范围收窄——方案 D 的灵魂

| 层 | PenguinHarness 可改 | sofagent 允许改 | sofagent 禁止改 |
|----|---------------------|----------------|----------------|
| L1 硬约束（SKILL.md） | ✅ 可改 | ❌ | **永远不可碰——审计铁律** |
| L2 决策约束（think.md） | ✅ 可改 | ✅ | |
| L4 经验层（knowledge/） | ✅ 可改 | ✅ | |
| 审计规则（A1-A23） | — | ❌ | **永远不可碰** |
| 回溯机制（git snapshot） | — | ❌ | **永远不可碰** |

> 💡 **为什么收窄**：PenguinHarness 的优化器可以改 Agent 的一切（AGENTS.md / Skills / config）；sofagent 的优化器只能改经验层（L2 think.md + L4 knowledge/），约束层（L1 SKILL.md + 审计 + 回溯）永远不可碰。这是「约束 Agent 行为」哲学的底线——如果优化器能改约束层，审计就失去了意义。

### 与 Dream Cycle 的融合

Dream Cycle（已有机制）：Agent 执行任务 → 审计发现偏差 → 沉淀经验到 think.md/knowledge/ → 下次执行更好。

进化闭环升级：Dream Cycle + Benchmark 驱动 → 不是等审计被动发现偏差，而是主动跑 Benchmark 找能力缺口 → 针对性优化经验层 → Benchmark 分数提升 → 确认优化有效。

| | Dream Cycle（当前） | 进化闭环升级（本版） |
|---|---|---|
| 触发 | 审计发现偏差 | 主动跑 Benchmark |
| 判据 | 审计规则（A1-A23） | Benchmark 分数（strictly improves） |
| 改什么 | think.md + knowledge/ | 同（只动经验层） |
| 验证 | 下次审计通过 | Benchmark 分数提升 |
| 反馈放大 | 单 Agent | **团队级（§协作协议广播）** |

### 涉及文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/refine-agent/optimization-loop.ts` | 新建 | evidence→hypothesis→Candidate→eval→accept/rollback 循环 |
| `engine/orchestrator/src/refine-agent/snapshot-manager.ts` | 新建 | Agent 级快照 + 版本号管理（复用 git snapshot） |
| `engine/orchestrator/src/refine-agent/contamination-guard.ts` | 新建 | 污染检测（rubric/Gold 不得进入优化器上下文） |
| `engine/orchestrator/src/__tests__/optimization-loop.test.ts` | 新建 | 单测（严格提升 + 回滚 + 污染检测 + 版本号递增） |

### 验收标准

- [ ] Benchmark 分数严格 > Reference 才接受 Candidate，否则 git snapshot 回滚
- [ ] Agent 版本号只增不减，不重用被拒绝的版本号
- [ ] 污染检测：rubric/Gold 进入优化器上下文 → 立即恢复 + 停止
- [ ] 可证伪假设：优化前预测行为变化 → 评估后验证（即使假设不成立但分数提升仍接受）
- [ ] **只动经验层**：Candidate 只修改 think.md + knowledge/，L1 SKILL.md / 审计 / 回溯不可碰
- [ ] **团队反馈放大**：一个 Agent 学到的优化经验，通过 §协作协议广播给全队

> 🧠 **与 Refine Agent 的关系**：Refine Agent 的质量规则集是"定性判据"（输出规不规范）；进化闭环升级增加"定量判据"（Benchmark 分数提升没有）。两者互补——Refine 先确保质量合格，进化闭环再驱动能力提升。

## RefinementEvent 强化（evidence 字段 · prime-agent 启发）

> 📖 **设计来源**：prime-agent (github.com/PrimeIntellect-ai/prime-agent, MIT) 的 Continual Harness RefinementEvent `{trigger, changes, evidence, outcome}` 结构化记录。

### 定位

v1.3.3 是进化能力集中落地的版本（Refine Agent + 进化闭环升级 + 团队反馈放大），进化动作（改 think.md / knowledge/ / 质量规则集）会频繁发生。每次进化必须带「触发证据」——哪条审计 FAIL / 哪个 Benchmark Case 失分——让进化可回放、可追责。

> 🔧 **进化链路写保护已移至 v1.3.0**：三处裸 writeFileSync 接入 atomic-write + mtime 检测是 v1.2.9 遗留技术债（风险是现在的），已由 v1.3.0「进化链路写保护（技术债回收）」承接。本版只做 evidence 字段（新能力，配合进化动作留痕）。

### 现状

sofagent 已有决策审计 `decision-log.jsonl`（v1.3.0 交付）——`emitDecision` 写 `{kind, moment, why, spec_ref}`。但「进化动作」没有独立的事件记录——Refine/进化闭环改了 think.md 还是 knowledge/，改了什么，为什么改，没有结构化留痕。

### 交付

决策审计新增 evidence 字段——进化动作必须附「触发证据」（哪条审计 FAIL / 哪个 Benchmark Case 失分）：

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/audit/src/decision-schema.ts` | 修改 | DecisionEntry 新增 `evidence` 字段（触发证据，可空） |
| `engine/audit/src/decision-log.ts` | 修改 | 写入时校验 evidence 格式（字符串数组） |
| `engine/orchestrator/src/refine-agent/optimization-loop.ts`（进化闭环新建） | 修改 | 每次进化动作 emitDecision 带 evidence（Benchmark Case 失分明细） |
| `engine/audit/src/__tests__/decision-log.test.ts` | 修改 | 补 evidence 字段用例 |

### 验收标准

- [ ] DecisionEntry 带 evidence 字段，进化动作必附触发证据
- [ ] 进化可回放：按 decision-log 能还原「为什么这么改」（证据链）
- [ ] `npm test` 全绿

> 🧠 **与进化闭环的关系**：进化闭环升级（Benchmark 驱动）是「改得更好」，evidence 是「改得有据」——每次进化可追责。写保护（v1.3.0）管「改得安全」，三者合起来才是完整的进化能力。
