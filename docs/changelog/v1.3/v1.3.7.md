## 一、SubAgent 完整沙箱执行环境

### 痛点

v1.3.0 的运行时审计是 **middleware 层**——包在 createReactAgent 外面，记录工具调用 + 审计日志。但 middleware 是**观测层**，不是**隔离层**。SubAgent 调用 `fs.writeFileSync` 时，middleware 能记录并告警，但**不能阻止文件被写入磁盘**——等审计 FAIL 时文件已经写了。

本版把审计从「记录+告警」升级为「**前置 allow/deny + 虚拟执行**」。

### 交付

| 组件 | 能力 | 对标 |
|------|------|------|
| **虚拟文件系统** | FilesystemBackend + virtualMode——SubAgent 写文件先写虚拟层，审批后才合并到物理磁盘 | bubblewrap / seatbelt |
| **网络出站白名单** | SubAgent 网络请求经白名单过滤，非白名单域名 deny | EnkryptAI Secure MCP Gateway |
| **工具调用中介** | 前置 allow/deny（非仅审计追踪）——高危工具调用在执行前拦截 | OpenWorker 权限模型 |
| **虚拟 key 凭证边界** | SubAgent 拿到的 API key 是虚拟 key，限速 + 限定 scope，不接触真实 key | LiteLLM 控制平面 |
| **AsyncSubAgent** | 远程 Agent Protocol 服务端——SubAgent 可在独立进程/容器运行 | Agent Protocol 标准 |
| **真·实时 A/B 双跑** | A/B SubAgent 在隔离环境同时执行，实时 diff 而非串行对比 | FORGE fresh-eyes 升级 |

### 沙箱与 v1.3.0 middleware 的关系

```
v1.3.0: createReactAgent → wrapToolCall middleware（记录+告警）→ 工具执行 → 物理磁盘
v1.3.7: createReactAgent → wrapToolCall middleware → 沙箱层（allow/deny + 虚拟执行）→ 审批 → 物理磁盘
```

v1.3.0 的 middleware **不删除**——它变成沙箱的「审计记录层」，沙箱是「执行隔离层」。两者叠加。

### 边契约「证据流 + 数据流」补全（从 v1.2.5 P6 拆入）

> 来源：v1.2.5 规划 P6「五类边契约形式化」。v1.2.5 瘦身时降级——权限流 + 失败流已在 v1.3.0 wrapToolCall 自然落地，剩余两类边随本版沙箱补全：
> - **证据流**：虚拟文件系统审批后才合并到物理磁盘（write → virtual → audit → approve → physical），每步输出留不可篡改审计记录——这正是"证据流"边契约的工程实现
> - **数据流契约**：虚拟 key 限速 + scope 约束 = 数据流边契约的显式化（SubAgent 拿到的凭证限定了它能访问的数据域，不再是隐式约定）

### 沙箱完整性自检与攻击面声明

> 📋 **2026-08-10 补充（安全基线 · 与 v1.4.1 ⑩ 训练安全基线对齐）**：沙箱是 v1.3.x 的安全核心组件，需要显式声明攻击面与防御措施——不声明 = 企业 IT 不敢用。

| 攻击面 | 防御措施 |
|--------|---------|
| **沙箱逃逸**（SubAgent 绕过虚拟 FS 直接写物理磁盘） | 启动时完整性自检（校验 FilesystemBackend hook 未被篡改）+ 运行时 fs 操作全部经虚拟层（monkey-patch fs 模块，绕过=进程级 deny） |
| **网络白名单绕过**（SubAgent 经 DNS 隧道 / ICMP 逃逸） | 网络出站经 network-gateway 全量拦截（不只 HTTP，含 DNS/raw socket）+ 白名单外域名 deny + deny 事件审计 |
| **虚拟 key 泄漏**（SubAgent 提取虚拟 key 向外发送） | 虚拟 key 限 scope + 限速（token bucket）+ key 不出现在 SubAgent 可见环境变量（host 边界注入）+ 日志脱敏 |
| **工具调用伪装**（SubAgent 伪造工具名绕过 tool-gate） | tool-gate 按工具唯一 ID（非名称字符串）判定——名称可伪造，ID 不可 |
| **沙箱资源耗尽**（SubAgent fork bomb / 磁盘填充） | 进程数限制 + 虚拟 FS 容量上限 + 超限 deny + 审计 |

**声明为后续版本职责**：
- OS 级硬隔离（bubblewrap/seatbelt）留 v1.3.9+——本版虚拟 FS 是应用层隔离，不防 kernel exploit
- 主 Agent 运行时策略强制留 v1.3.9——本版沙箱仅限 SubAgent

## 一点五、FORGE 审查循环自适应并发（driver 调参 · 2026-08-17 补充）

### 痛点

fresh-eyes-loop 24 个 perspective worker 串行执行（`FORGE_MAX_CONCURRENCY=1`），单轮 ~95 分钟。并发=1 是 run-12 的保守兜底（8GB 机器并发 3+ 即 OOM SIGKILL），但 16GB/32GB 机器被同一规则拖慢——固定值对高配机器是浪费。

### 设计：三级来源的自适应并发（优先级从高到低）

| 优先级 | 来源 | 行为 |
|--------|------|------|
| 1 | 环境变量 `FORGE_MAX_CONCURRENCY` 显式设置 | 用户显式意志，直接用，不覆盖 |
| 1 | `--max-concurrency N` CLI 参数 | 同上（后写者胜） |
| 2 | **自适应探测**（未显式设置时） | driver 启动时读 `os.totalmem()`，按预算表取值并打印推导过程 |
| 3 | 默认兜底 | 探测失败 → 1（现状，最保守） |

**自适应预算表**（按每 worker `--max-old-space-size=2048` 的 2GB heap 预算推导，为 OS + 系统进程留 ≥4GB 余量）：

| 物理内存 | 推荐并发 | 推导 |
|----------|---------|------|
| < 12GB（含 8GB） | 1 | 2GB×1 + 4GB 余量 = 6GB ≤ 8GB，并发 2 即 8GB 踩顶（run-12 死法） |
| 12-23GB | 2 | 2GB×2 + 4GB 余量 = 8GB，12GB 机器安全 |
| 24-47GB | 4 | 2GB×4 + 4GB 余量 = 12GB，24GB 机器安全 |
| ≥ 48GB | 6 | 上限 6——并发再高会撞 GLM API 速率限制，瓶颈从内存转移到 API 配额，单点等待抵消并行收益 |

> 💡 **并发上限 6 的第二重理由**：worker 是 LLM API 调用密集型（单 worker 50+ 次工具调用，每次都打 API），6 个并发 worker 的请求密度已接近订阅制 API 的舒适区上限；更高并发反而触发限流重试，总耗时可能不降反升。

### 交付清单

| 文件 | 改动 | 说明 |
|------|------|------|
| `FORGE/src/driver-base.mjs` | `resolveMaxConcurrency()` 函数 | 三级来源解析 + 预算表 + 启动日志打印 `[并发] 自适应: 物理内存 XX GB → N` |
| `FORGE/src/fresh-eyes-driver.mjs` | 接线 | 启动 banner 的 `FORGE_MAX_CONCURRENCY=1` 提示行改为自适应值展示 |
| `FORGE/src/release-gate-driver.mjs` | 同步接线 | 两个 driver 共用 driver-base（镜像 driver 漂移教训：修 A 忘 B 是必然） |
| `FORGE/SKILL/fresh-eyes-loop/SKILL.md` | 文档同步 | 「8GB 机器必须 FORGE_MAX_CONCURRENCY=1」改为「未显式设置时自动探测；8GB 机器自动取 1」 |
| `FORGE/SKILL/release-gate-loop/SKILL.md` | 文档同步 | 同上 |
| `engine/audit/src/__tests__/` 或 `FORGE/` 测试 | `resolveMaxConcurrency` 单测 | 预算表边界值（8/12/16/24/48GB）+ 三级优先级 + 探测失败兜底 |

### 运行时降级（OOM 保险丝）

自适应只解决「启动时选对值」；运行中仍可能因系统整体内存压力 OOM。driver 已有 heartbeat 死亡检测，补一层**熔断降级**：

- driver 捕获 worker 非正常退出（signal=SIGKILL 且 code=null，OOM 典型特征）→ 该批次剩余 worker 改串行，并在 LEDGER 记 `degraded-concurrency` 事件
- 连续 2 个批次触发降级 → 回退并发=1 并继续（不中止 run，只降速）——「宁可慢，不猝死」

### 与交付一「真·实时 A/B 双跑」的关系

本节是**近期可达**的调参提速（不动审查逻辑，零质量影响）；交付一的实时 A/B 双跑是**远期形态**（沙箱隔离后 A/B 物理并行）。两者不冲突：自适应并发先行落地，沙箱交付后 A/B 双跑直接复用本节的并发解析。

### 质量保障声明

- 审查 prompt / 熔断线（52 次工具预算）/ 报告格式**全部不动**——提速的是并行策略，不是审查深度
- 双盲机制保留：A/B worker 仍是独立子进程独立上下文，并发执行不改变其零上下文性质（进程隔离 ≠ 上下文共享）
- worker 分片模式（A 审 1-6 / B 审 7-12，24→12 个）**不在本版范围**——它以双盲降级换速度，需单独拍板，见「待明确事项」

## 三、ontology 生命周期状态：branch / trunk（GitHub 式协作底座 · 2026-08-16 新增 · 2026-08-17 增补 OKF 对齐）
