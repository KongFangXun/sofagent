## 一、SubAgent 完整沙箱执行环境

### 痛点

v1.3.0 的运行时审计是 **middleware 层**——包在 createReactAgent 外面，记录工具调用 + 审计日志。但 middleware 是**观测层**，不是**隔离层**。SubAgent 调用 `fs.writeFileSync` 时，middleware 能记录并告警，但**不能阻止文件被写入磁盘**——等审计 FAIL 时文件已经写了。

本版把审计从「记录+告警」升级为「**前置 allow/deny + 虚拟执行**」。

### 交付

| 组件 | 能力 | 对标 |
|------|------|------|
| **虚拟文件系统** | FilesystemBackend + virtualMode——SubAgent 写文件先写虚拟层，审批后才合并到物理磁盘 | bubblewrap / seatbelt |
| **网络出站白名单** | SubAgent 网络请求经白名单过滤，非白名单域名 deny | EnkryptAI Secure MCP Gateway |
| **工具调用中介** | 前置 allow/deny（非仅审计追踪）——高危工具调用在执行前拦截 | OpenWorker 权限模型 |
| **虚拟 key 凭证边界** | SubAgent 拿到的 API key 是虚拟 key，限速 + 限定 scope，不接触真实 key | LiteLLM 控制平面 |
| **AsyncSubAgent** | 远程 Agent Protocol 服务端——SubAgent 可在独立进程/容器运行 | Agent Protocol 标准 |
| **真·实时 A/B 双跑** | A/B SubAgent 在隔离环境同时执行，实时 diff 而非串行对比 | FORGE fresh-eyes 升级 |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/sandbox/filesystem-backend.ts` | 新建 | 虚拟文件系统层 |
| `engine/orchestrator/src/sandbox/network-gateway.ts` | 新建 | 网络出站白名单过滤 |
| `engine/orchestrator/src/sandbox/tool-gate.ts` | 新建 | 前置 allow/deny 拦截器 |
| `engine/orchestrator/src/sandbox/virtual-key.ts` | 新建 | 虚拟凭证管理 |
| `engine/orchestrator/src/sandbox/async-subagent.ts` | 新建 | AsyncSubAgent 远程执行 |
| `engine/orchestrator/src/__tests__/sandbox/*.test.ts` | 新建 | 沙箱全套测试 |

### 沙箱与 v1.3.0 middleware 的关系

```
v1.3.0: createReactAgent → wrapToolCall middleware（记录+告警）→ 工具执行 → 物理磁盘
v1.3.7: createReactAgent → wrapToolCall middleware → 沙箱层（allow/deny + 虚拟执行）→ 审批 → 物理磁盘
```

v1.3.0 的 middleware **不删除**——它变成沙箱的「审计记录层」，沙箱是「执行隔离层」。两者叠加。

### 边契约「证据流 + 数据流」补全（从 v1.2.5 P6 拆入）

> 来源：v1.2.5 规划 P6「五类边契约形式化」。v1.2.5 瘦身时降级——权限流 + 失败流已在 v1.3.0 wrapToolCall 自然落地，剩余两类边随本版沙箱补全：
> - **证据流**：虚拟文件系统审批后才合并到物理磁盘（write → virtual → audit → approve → physical），每步输出留不可篡改审计记录——这正是"证据流"边契约的工程实现
> - **数据流契约**：虚拟 key 限速 + scope 约束 = 数据流边契约的显式化（SubAgent 拿到的凭证限定了它能访问的数据域，不再是隐式约定）

### 沙箱完整性自检与攻击面声明

> 📋 **2026-08-10 补充（安全基线 · 与 v1.4.1 ⑩ 训练安全基线对齐）**：沙箱是 v1.3.x 的安全核心组件，需要显式声明攻击面与防御措施——不声明 = 企业 IT 不敢用。

| 攻击面 | 防御措施 |
|--------|---------|
| **沙箱逃逸**（SubAgent 绕过虚拟 FS 直接写物理磁盘） | 启动时完整性自检（校验 FilesystemBackend hook 未被篡改）+ 运行时 fs 操作全部经虚拟层（monkey-patch fs 模块，绕过=进程级 deny） |
| **网络白名单绕过**（SubAgent 经 DNS 隧道 / ICMP 逃逸） | 网络出站经 network-gateway 全量拦截（不只 HTTP，含 DNS/raw socket）+ 白名单外域名 deny + deny 事件审计 |
| **虚拟 key 泄漏**（SubAgent 提取虚拟 key 向外发送） | 虚拟 key 限 scope + 限速（token bucket）+ key 不出现在 SubAgent 可见环境变量（host 边界注入）+ 日志脱敏 |
| **工具调用伪装**（SubAgent 伪造工具名绕过 tool-gate） | tool-gate 按工具唯一 ID（非名称字符串）判定——名称可伪造，ID 不可 |
| **沙箱资源耗尽**（SubAgent fork bomb / 磁盘填充） | 进程数限制 + 虚拟 FS 容量上限 + 超限 deny + 审计 |

**声明为后续版本职责**：
- OS 级硬隔离（bubblewrap/seatbelt）留 v1.3.9+——本版虚拟 FS 是应用层隔离，不防 kernel exploit
- 主 Agent 运行时策略强制留 v1.3.9——本版沙箱仅限 SubAgent

## 一点五、FORGE 审查循环自适应并发（driver 调参 · 2026-08-17 补充）

### 痛点

fresh-eyes-loop 24 个 perspective worker 的并发当前是代码内固定值（`fresh-eyes-driver.mjs` 默认 2），8GB 机器上并发 3+ 即 OOM SIGKILL（run-12 死法），高配机器则被同一固定值拖慢——没有一个对所有机器都安全的值，也没有按机器自适应的机制。固定值对高配机器是浪费，对低配机器是风险。

### 设计：三级来源的自适应并发（优先级从高到低）

| 优先级 | 来源 | 行为 |
|--------|------|------|
| 1 | 环境变量 `FORGE_MAX_CONCURRENCY` 显式设置 | 用户显式意志，直接用，不覆盖 |
| 1 | `--max-concurrency N` CLI 参数 | 同上（后写者胜） |
| 2 | **自适应探测**（未显式设置时） | driver 启动时读 `os.totalmem()`，按预算表取值并打印推导过程 |
| 3 | 默认兜底 | 探测失败 → 1（最保守） |

**自适应预算表**（按每 worker `--max-old-space-size=1024` 的 1GB heap 上限 + 运行时峰值余量推导，为 OS + 系统进程留 ≥4GB 余量；heap 上限已由 v1.3.5 从 2048 降至 1024，若回调 2048 需重推本表）：

| 物理内存 | 推荐并发 | 推导 |
|----------|---------|------|
| < 12GB（含 8GB） | 1 | 1GB×1 + 4GB 余量 = 5GB ≤ 8GB；并发 2 在峰值叠加时仍有 OOM 风险（run-12 死法），保守取 1 |
| 12-23GB | 2 | 1GB×2 + 4GB 余量 = 6GB，12GB 机器留足峰值余量 |
| 24-47GB | 4 | 1GB×4 + 4GB 余量 = 8GB，24GB 机器安全 |
| ≥ 48GB | 6 | 上限 6——并发再高会撞 GLM API 速率限制，瓶颈从内存转移到 API 配额，单点等待抵消并行收益 |

> 💡 **并发上限 6 的第二重理由**：worker 是 LLM API 调用密集型（单 worker 50+ 次工具调用，每次都打 API），6 个并发 worker 的请求密度已接近订阅制 API 的舒适区上限；更高并发反而触发限流重试，总耗时可能不降反升。

### 交付清单

| `FORGE/src/fresh-eyes-driver.mjs` | 接线 | 启动 banner 的 `FORGE_MAX_CONCURRENCY=1` 提示行改为自适应值展示 |

### 运行时降级（OOM 保险丝）

自适应只解决「启动时选对值」；运行中仍可能因系统整体内存压力 OOM。driver 已有 heartbeat 死亡检测，补一层**熔断降级**：

- driver 捕获 worker 非正常退出（signal=SIGKILL 且 code=null，OOM 典型特征）→ 该批次剩余 worker 改串行，并在 LEDGER 记 `degraded-concurrency` 事件
- 连续 2 个批次触发降级 → 回退并发=1 并继续（不中止 run，只降速）——「宁可慢，不猝死」

### 与交付一「真·实时 A/B 双跑」的关系

本节是**近期可达**的调参提速（不动审查逻辑，零质量影响）；交付一的实时 A/B 双跑是**远期形态**（沙箱隔离后 A/B 物理并行）。两者不冲突：自适应并发先行落地，沙箱交付后 A/B 双跑直接复用本节的并发解析。

### 质量保障声明

- 审查 prompt / 熔断线（52 次工具预算）/ 报告格式**全部不动**——提速的是并行策略，不是审查深度
- 双盲机制保留：A/B worker 仍是独立子进程独立上下文，并发执行不改变其零上下文性质（进程隔离 ≠ 上下文共享）

## 二、场景驱动权限体系（原 v1.2.5 拆入）

### 交付

权限按「场景」（任务类型 × 数据域 × 动作风险等级）动态判定：

```
判定链：身份（v1.3.1）→ 场景匹配 → 风险等级 → 放行/deny/人工批准
```

| 维度 | 说明 | 示例 |
|------|------|------|
| 任务类型 | 代码开发 / 数据处理 / 报表生成 / 测试 | 代码开发场景可写 .ts 文件 |
| 数据域 | 代码 / 配置 / 审计数据 / 用户数据 | 用户数据场景禁写审计数据 |
| 动作风险等级 | 读（低）/ 写（中）/ 删（高）/ 外传（极高） | 极高风险 → 人工批准 |

**包含**：团队场景权限（v1.3.3 L2 协作）+ 市场调用权限（v1.3.4 L3 市场）+ 动态提权到期回收。

> 🧭 **设计轴：DSH 权限两旋钮正交分解（2026-08-15 DSH 教程蒸馏）**：权限体系按两个正交旋钮设计——**效果边界**（能碰到什么，由沙箱控制）× **决策通道**（能不能做，由审批控制），两者分离不混为一谈。三条硬约束：**fail-closed**（匹配不到场景/策略出错时默认 deny，不默认放行）、**守卫先于事件分发**（权限判定发生在工具执行之前，不是事后审计）、**最小权限**（每个场景只授予任务所需的最小工具面）。这套设计与 §一沙箱的关系：沙箱管「执行边界」（效果），本节管「决策通道」（审批）——两旋钮各司其职。

### 验收标准

- [x] 判定链完整：身份 → 场景匹配 → 风险等级 → 放行/deny/人工批准，每步可追溯（decision-log 留痕）
- [x] 场景定义三类维度（任务类型/数据域/动作风险）至少各 3 个预设场景（含示例表中的开发/数据/报表/测试）
- [x] 极高风险动作（删/外传）触发人工批准，无人审确认不执行（对齐 v1.3.5 人审语义）
- [x] 团队场景权限（v1.3.3）+ 市场调用权限（v1.3.4）+ 动态提权到期回收三合一
- [x] **fail-closed**：匹配不到场景或策略异常时默认 deny，不默认放行
- [x] 守卫先于事件分发：权限判定在工具执行前完成（allow/deny 前置，非事后记录）
- [x] `npm test` 全绿

## 三、ontology 生命周期状态：branch / trunk（GitHub 式协作底座 · 2026-08-16 新增 · 2026-08-17 增补 OKF 对齐）

### 定位

v1.3.6 给 workflow 加了 `merge_criteria`/`approver`（审阅协议字段），但 ontology 资产本身还缺一个「状态」维度：哪些实体是**已审阅合并进组织基线的树干资产**，哪些是**试验中的枝条**。本节补上这个状态机——GitHub 式协作底座在 ontology 层的落点。

> 🔗 **OKF 对齐增补（2026-08-17 · 谷歌 Open Knowledge Format v0.2）**：评估发现 sofagent 知识库与 OKF 天然同源（md+YAML frontmatter / 路径即 Concept ID / index.md+log.md 保留文件名约定完全一致 / Ed25519 身份码可映射 actor 约定）。本节按 OKF v0.2 标准补齐知识条目的信任与时效机制——spec 留档 `/Users/kongfangxun/WorkBuddy/Knowledge-Catalog/okf/SPEC.md`（官方仓库完整 clone），解读页已入 TencentDB wiki（wiki-33guguea）。边界：**只借鉴格式约定，不引入 OKF 运行时依赖**（OKF 是格式规范不是软件）；`stale_after` 采用绝对日期（非相对 TTL），字段名严格按 spec（注意得到处传播的 `valid_after` 是误记，spec 原文为 `stale_after`）。

### 交付

| 组件 | 能力 |
|------|------|
| **资产状态字段** | ontology 实体（object/entity/concept）加 `lifecycle` 字段：`trunk`（已合并进组织基线，稳定可复用）/ `branch`（试验中，待审阅） |
| **状态迁移** | `branch → trunk` 迁移走审阅门（对齐 v1.3.6 `approver` + 审计引擎硬证据）；`trunk` 回退走 git snapshot |
| **状态对齐** | 与 v1.3.4 能力市场五环状态（发布→发现→调用→评价→养护）对齐，避免两套状态并存——`trunk` 对应「已发布 + 养护中」，`branch` 对应「待发布/评价中」 |
| **能力地图展示** | ontology-view 区分 trunk/branch 展示——「森林能力地图」的基线资产一眼可辨，试验资产不误导复用 |
| **OKF ①type 必填** | knowledge/entities 与 concepts 的 frontmatter 补 `type` 必填字段（OKF 唯一强制字段）——create_entity/create_concept 写入时校验，缺 type 返回结构化错误 |
| **OKF ②信任+时效字段** | frontmatter 补 `status`（draft/stable/deprecated，OKF §5.4）+ `stale_after`（绝对日期，today≥stale_after 即过期，OKF §5.5）+ `verified: [{by, at}]`（OKF §5.2 三级信任：人审>机审>未审）；`generated: {by, at}` 用现有 created_at/updated_at 语义映射，actor 约定复用 Ed25519 身份码（human:&lt;id&gt; / process:&lt;id&gt; / agent/version 三态） |
| **OKF ③index 链接化** | knowledge/index.md 从纯权限表格升级为链接列表（保留权限列），agent 渐进披露——先读目录判断相关性再读正文，省上下文窗口 |
