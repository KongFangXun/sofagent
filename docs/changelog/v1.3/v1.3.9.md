## 一、官方 AST 规则引擎参考实现（sofagent-ruleset-ast）

### 背景

v1.2.9 已开放规则插件接口（`type: "plugin"` + `sofagent-ruleset-*` npm 包约定）。本版官方出第一个**语义级规则引擎示范**——用 TypeScript compiler / tree-sitter 做 AST 级规则，社区可照着写自己的引擎。

### 交付

| 组件 | 能力 |
|------|------|
| **AST 规则引擎** | 对提交的代码文件做 AST 解析 + 语义级规则匹配（如「禁止 `eval()`」「禁止硬编码密钥」） |
| **示范规则集** | 官方 `sofagent-ruleset-ast` 内置 5-10 条 AST 规则（对标审计规则在语义层的扩展） |
| **插件接入** | 走 v1.2.9 插件接口，与 git-diff 审计规则同管线（`ruleType: 'plugin'`） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/rules/src/ast/engine.ts` | 新建 | AST 规则引擎（TypeScript compiler API） |
| `engine/rules/src/ast/rules/*.ts` | 新建 | 示范 AST 规则集 |
| `engine/rules/src/ast/__tests__/*.test.ts` | 新建 | 单测 |

### 验收标准

- [ ] AST 引擎可解析 TS/JS 文件并匹配语义级规则
- [ ] 官方示范规则集 5-10 条可跑
- [ ] 走 v1.2.9 插件接口，与既有审计管线同构
- [ ] `npm test` 全绿

## 二、meta-harness 多 harness 编排（原 v1.5.0 前移）

### 背景

v1.3.7 给单个 SubAgent 沙箱。本版升级为**多 harness 统一编排**——多个 SubAgent（各自带沙箱）在一个 meta-harness 下协同运行 + 跨会话协作。

```
┌─ meta-harness（统一编排层）─────────────────────────┐
│  harness A（SubAgent + 沙箱）──┐                    │
│  harness B（SubAgent + 沙箱）──┼── 统一策略 + 共享审计  │
│  harness C（SubAgent + 沙箱）──┘                    │
└─────────────────────────────────────────────────┘
```

### 交付

| 组件 | 能力 |
|------|------|
| **多 harness 统一策略** | 策略在 meta-harness 层强制（对齐 Omnigent「策略强制在基础设施层」）——跨 harness 的状态追踪 + 动作前拦截 |
| **跨会话协作** | harness 间共享审计轨迹 + 决策记录（复用 v1.3.1 身份码 + v1.3.3 L2 协作协议） |
| **统一审计视图** | 多 harness 的审计日志聚合到同一视图（Dashboard 波次渲染扩展） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/meta-harness/orchestrator.ts` | 新建 | meta-harness 统一编排层 |
| `engine/orchestrator/src/meta-harness/policy-layer.ts` | 新建 | 跨 harness 策略强制层 |
| `engine/orchestrator/src/meta-harness/audit-aggregator.ts` | 新建 | 多 harness 审计聚合 |

### 验收标准

- [ ] 多 harness 在统一编排下运行（各自沙箱隔离，策略统一）
- [ ] 跨 harness 状态可追踪（动作前拦截，对齐 Omnigent 模式）
- [ ] 审计轨迹跨 harness 聚合可查
- [ ] 与 v1.3.3 L2 协作协议兼容（协作在 meta-harness 层运行）
- [ ] `npm test` 全绿

## 三、AI 工作明细（业务视角 · Startwork 启发）

### 定位

> 📖 **设计参考**：Startwork（startwork.im，企业 AI 管理平台）把「人与 AI 的对话自动整理成工作明细和看板」——业务视角的 AI 工作记录。sofagent 的 Dashboard 是**技术视角**（控制图波次渲染），本交付补**业务视角**的数据能力：企业客户可读的「AI 节点这周干了什么」。

**零新数据**——数据源全部已有/已排期：审计日志（v1.3.0）+ decision-log（v1.3.0）+ LLM Trace（v1.3.1），**只差聚合与查询**。

> 🔗 **节点实际耗时采集（2026-08-10 新增 · AIR C8 绩效量化输入）**：工作明细的「耗时」字段是 AIR C8 绩效量化引擎的直接输入（`年节省 = 日耗时 × 时薪 × 250`，见 `AIR.md` §3.2）。现状缺口：decision-log / runtime-audit 有判定结果，但**「节点跑了多久」没有明确的采集点**——按 Agent 工作明细里的「耗时」若只取 LLM Trace 的模型调用耗时，会漏掉工具执行 / 等待 / 重试的整节点耗时，C8 量化对不上 GUIDE 公式。本版补：
> | 组件 | 能力 |
> |------|------|
> | **节点级耗时采集** | 节点开始/结束时间戳 → 节点实际耗时（含工具执行 + 等待 + 重试），写入 worklog 聚合（不新开日志，复用 runtime-audit 记录的开始/结束时刻） |
> | **耗时口径标注** | worklog 查询区分「模型调用耗时」（LLM Trace）vs「节点总耗时」（含工具执行）——C8 消费总耗时，诊断消费调用耗时 |
> | **验收** | 按 Agent 工作明细可查节点总耗时（口径标注清晰），AIR C8 输入就绪 |

**边界（2026-08-09 拍板）**：本版做**数据罗列层**（聚合 + 查询 + 落盘），**Web 工作明细页放 v1.4.0**（v1.4.0 版本号重新启用，dashboard.html 已就绪——Web 页单独一版，本版已承载 AST 引擎 + meta-harness 两个大交付）：

| 层 | 内容 | 落点 |
|----|------|:--:|
| **① 数据罗列层**（主体） | worklog 聚合（审计 + decision-log + LLM Trace 三源合并）+ MCP `worklog_query` 数据口 + 落盘 `data/dashboard/worklog.json` | **v1.3.9** |
| **② 终端 ASCII 视图** | 复用 v1.2.3 渲染底座（开发/FDE 自用）——**尽力开发，能做出就做出** | v1.3.9 可选 |
| **③ Web 工作明细页** | `dashboard.html` 加「工作明细」页/区块——读 `worklog.json`（与现有 daemon-health.json 同模式），企业客户形态 | **v1.4.0** |

### 交付

**数据罗列层（本版）**：

| 查询能力 | 内容 |
|------|------|
| **按 Agent 的工作明细** | 某 Agent 在时间段内：执行了哪些任务（taskId）→ 调用了哪些工具 → 结果（PASS/FAIL/被审批拒绝）→ 消耗（token/耗时/成本） |
| **按 Workflow 聚合** | 整个 workflow 的节点执行情况：哪些节点在跑/跑完/失败/人工介入——业务进度视图 |
| **按周趋势** | 节点活跃度 / 成功率 / 成本趋势（复用 Dashboard 历史趋势底座） |
| **人工介入记录** | HITL 审批/纠正事件（谁批的、为什么）——「人参与 AI 工作」的可追溯查询 |

**展示层**：
- **终端 ASCII 列表视图**（本版，可选）：复用 v1.2.3 渲染底座（开发/FDE 自用）——能开发出来就开发出来
- **Web 工作明细页**（v1.4.0）：`dashboard.html` 新增「工作明细」区块，读本版落盘的 `data/dashboard/worklog.json`（聚合数据未生成时降级示例，对齐 ds-sample 模式）

**与 meta-harness 的关系**：meta-harness 的 `audit-aggregator`（本版二章）聚合多 harness 审计轨迹 → 工作明细查询消费聚合数据——**同一数据源的两个消费面**（meta 负责聚合，工作明细负责业务化）。单 harness 场景下直接消费单源审计，不依赖 meta-harness。

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/worklog/aggregator.ts` | 新建 | 工作明细聚合（审计 + decision-log + LLM Trace 三源合并，按 Agent/Workflow/周）+ 落盘 `data/dashboard/worklog.json` |
| `engine/mcp/src/tools/worklog-query.ts` | 新建 | MCP `worklog_query` tool（数据口——终端/Web/FlowHub 统一消费） |
| `engine/daemon/src/dashboard/worklog-view.ts` | 新建 | 终端 ASCII 列表视图（复用 v1.2.3 渲染底座，可选交付） |
| `engine/orchestrator/src/__tests__/worklog.test.ts` | 新建 | 单测（聚合正确性 + 数据源完整性） |

### 验收标准

- [ ] `worklog_query` 可查按 Agent 工作明细（任务/工具/结果/token/耗时/成本）
- [ ] 按 Workflow 聚合（节点状态 + 人工介入记录）
