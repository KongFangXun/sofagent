## 三、AI 工作明细（业务视角 · Startwork 启发）

### 定位

> 📖 **设计参考**：Startwork（startwork.im，企业 AI 管理平台）把「人与 AI 的对话自动整理成工作明细和看板」——业务视角的 AI 工作记录。sofagent 的 Dashboard 是**技术视角**（控制图波次渲染），本交付补**业务视角**的数据能力：企业客户可读的「AI 节点这周干了什么」。

**零新数据**——数据源全部已有/已排期：审计日志（v1.3.0）+ decision-log（v1.3.0）+ LLM Trace（v1.3.1），**只差聚合与查询**。

> 🔗 **节点实际耗时采集（2026-08-10 新增 · 绩效量化输入）**：工作明细的「耗时」字段是绩效量化引擎的直接输入（`年节省 = 日耗时 × 时薪 × 250`，见 GUIDE §4.3）。现状缺口：decision-log / runtime-audit 有判定结果，但**「节点跑了多久」没有明确的采集点**——按 Agent 工作明细里的「耗时」若只取 LLM Trace 的模型调用耗时，会漏掉工具执行 / 等待 / 重试的整节点耗时，量化对不上 GUIDE 公式。本版补：
> | 组件 | 能力 |
> |------|------|
> | **节点级耗时采集** | 节点开始/结束时间戳 → 节点实际耗时（含工具执行 + 等待 + 重试），写入 worklog 聚合（不新开日志，复用 runtime-audit 记录的开始/结束时刻） |
> | **耗时口径标注** | worklog 查询区分「模型调用耗时」（LLM Trace）vs「节点总耗时」（含工具执行）——绩效量化消费总耗时，诊断消费调用耗时 |
> | **验收** | 按 Agent 工作明细可查节点总耗时（口径标注清晰），绩效量化输入就绪 |

> 🔗 **进化曲线聚合（2026-08-17 新增 · self-evolution 五层谱系 · 自探索方向毕业）**：「做 1000 次任务后是否比第一次更强」产品化为可观测指标——worklog 聚合时顺带产出**进化维度**（不新开数据源，三源现成）：
> | 维度 | 数据源 | 回答什么 |
> |------|--------|---------|
> | 审计 PASS 率趋势 | history.jsonl 按周聚合 | 犯错率是否在降 |
> | 错题复发率 | instinct/failure-log 同类错误去重 | 同一个坑是否还在踩 |
> | AB 实验胜负曲线 | ab-test 晋升记录 | 进化产物是否真的更好 |
> | 首次通过率 | decision-log retry/escalate 占比 | 规划策略是否在瘦身（L2 层证据） |
>
> 谱系定位见 PHILOSOPHY §五「自进化的五层谱系」——反思（Reflection）与自进化的分界线在 update（永久保存），曲线是 update 生效与否的量化证据。验收：`worklog_query` 可按 Agent 查四维趋势；Web 曲线可视化归 v1.4.0 工作明细页同批。

**边界（2026-08-09 拍板）**：本版做**数据罗列层**（聚合 + 查询 + 落盘），**Web 工作明细页放 v1.4.0**（v1.4.0 版本号重新启用，dashboard.html 已就绪——Web 页单独一版，本版已承载 AST 引擎 + meta-harness 两个大交付）：

| 层 | 内容 | 落点 |

| **① 数据罗列层**（主体） | worklog 聚合（审计 + decision-log + LLM Trace 三源合并）+ MCP `worklog_query` 数据口 + 落盘 `data/dashboard/worklog.json` | **v1.3.9** |

## 四、ATTRIBUTION 归因引擎（P2 · v2.x 前移）

> 📖 **来源**：审计决策→业务指标的因果链追踪，依赖已交付的 v1.3.1 跨设备审计聚合数据积累。

### 定位

v1.3.1 交付了跨设备审计轨迹聚合，v1.3.9 交付工作明细数据层（§三 `worklog.json`）——这两者合起来恰好是 ATTRIBUTION 归因引擎的天然地基。审计记录 = 「Agent 做了什么」，工作明细 = 「业务产出是什么」，归因引擎 = 把两者用因果链接起来——回答「这个审计决策导致了多少业务指标变化」。

### 交付（P2）

- 因果链数据结构：`{decision_id, business_metric, delta, confidence, timestamp}`
- 工作明细（§三）的每条记录关联到审计决策（decisions.jsonl 的 decisionId）
- 归因查询接口：按 business_metric / 按 decision_id / 按 agentId 回溯因果链
- 归因报告：周报/月报自动生成「Top 5 高影响决策」+「Top 5 低效决策」

### 验收标准

- [ ] 因果链数据结构定义并落盘
- [ ] 工作明细记录可关联到 decisions.jsonl 的 decisionId
- [ ] 归因查询接口可用（按 metric / decision / agentId）

## 五、Dream Sandbox 沙盒审计（P2 · v2.x 前移 · Palantir AIP 启发）

> 📖 **来源**：Palantir AIP——Agent 操作先在平行空间模拟运行，人类审批后点「合并」才生效。

### 定位

v1.3.7 交付 SubAgent 完整沙箱（虚拟 FS + 网络白名单），v1.3.8 交付代理网关（唯一出入口 + 风险分级）——Dream Sandbox 是这两者的自然延伸：Agent 的操作不直接写主工作树，而是先写到一个平行 sandbox 分支，人类 review diff 后点「合并」才生效。约束从「事后审计」升级为「事前模拟 + 人工放行」。

### 交付（P2）

- 平行 sandbox 分支：Agent 操作写入 `dream-sandbox/<task-id>/`（复用 v1.3.7 沙箱底座）
- diff 预览：sandbox 分支 vs 主工作树的 git diff，人类可 review
- 「合并」MCP tool：`dream_merge`（强制人审，复用 v1.3.1 工具审批 always-ask 模式）
- sandbox 自动过期：未合并的 sandbox 分支 24h 后自动清理

### 验收标准

- [ ] Agent 操作默认写入 dream-sandbox 分支（不直接写主工作树）
- [ ] diff 预览可用（sandbox vs 主工作树）
- [ ] `dream_merge` 强制人审，未审不合并
- [ ] 未合并 sandbox 24h 自动清理

## 📊 MLflow agent 评估集成（从 v1.3.3 移入 · 2026-08-12）

> 📦 **移入说明**：本段原属 v1.3.3 范围（v2.x 前移），经 ROADMAP 核实 v1.3.3 核心交付为 6 件（L2 协作 + Refine + 主 agent + 入口路由 + 进化闭环 + evidence），MLflow 不在 ROADMAP v1.3.3 行内。本版（v1.3.9）同属"工程能力深化"批次，且 Benchmark 评测（v1.3.1）→ 进化闭环（v1.3.3）→ MLflow 标准化评估 的数据链在本版衔接更自然。
> 📖 **来源**：MLflow 50+ agent 评估指标 + LLM-as-Judge。FORGE 评估框架参考。

### 定位

v1.3.1 Benchmark 评测用自定义 0..100 评分，v1.3.3 进化闭环升级用 Benchmark 分数驱动优化。MLflow 集成为评估体系补**标准化指标库**——50+ 开箱即用的 agent 评估指标（task success rate / tool call efficiency / context utilization / latency / cost per task 等）+ LLM-as-Judge（用 LLM 评判 Agent 输出质量，补客观指标的不足）。让 Benchmark 评测从「自定义单一分数」升级为「多维标准化评估」。

### 交付

- MLflow agent evaluation 接入：Benchmark 评测跑完后，结果同步写 MLflow tracking（`mlflow.log_metric()`）

## 🌐 Agentic Browser / Playwright（从 v1.3.3 移入 · 2026-08-12）

> 📦 **移入说明**：与 MLflow 同批移入。Refine Agent（v1.3.3）跑质量规则集时部分场景需驱动浏览器验证 UI 行为，本版承接此能力落地。
> 📖 **来源**：DeerFlow 浏览器自动化能力。Agent 驱动浏览器做端到端操作，与「智能 E2E 测试 Agent」探索同源。

### 定位

Refine Agent 的端到端操作能力补充——跑质量规则集时，部分场景需要驱动浏览器验证 UI 行为（如「点击按钮后表单提交是否正确」）。Agentic Browser 让 Agent 闭环覆盖到 UI 层，不只停留在代码 diff。

### 交付

- Playwright MCP server 接入（`playwright_navigate` / `playwright_click` / `playwright_screenshot` / `playwright_assert`）
- Refine Agent 质量规则集可声明 `requires_browser: true`，执行时自动启用 Playwright
- 浏览器操作全程审计（与 wrapToolCall 运行时审计统一通道）

### 验收标准

- [ ] Playwright MCP 4 个核心 tool 可用（navigate/click/screenshot/assert）
- [ ] Refine Agent 质量规则集可声明 `requires_browser` 并触发浏览器执行
- [ ] 浏览器操作写运行时审计日志
