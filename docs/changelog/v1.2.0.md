### 编排引擎内嵌（双节点架构工具层拦截）

v1.1.x 解决了「文件系统层」和「MCP 协议层」的审计可见性——daemon 监控磁盘文件变更，MCP pipe 拦截 Agent 的文件编辑动作。但还有一个盲区：**Agent 平台自带的编排引擎（tool scheduler）**。

WorkBuddy / CodeBuddy / Cursor 这些 Agent 平台都有自己的工具调度层——决定「先调用哪个 tool、传什么参数、怎么处理返回值」。这层 sofagent 完全看不到。

v1.2.0 的方案：把 sofagent 的核心规则引擎内嵌成 Agent 平台的「tool 拦截器」（interceptor），而不是外部独立工具。架构上等价于 OpenClaw 的「orchestrator 层」从外部旁路变成内部插件。

**双节点架构对应**：
- **自动运行节点**（OpenClaw + sofagent 全栈）：OpenClaw 的 orchestrator 直接加载 sofagent 规则作为 tool pre-condition，每个 tool call 执行前过 sofagent 检查
- **个人增强节点**（第三方 Agent + sofagent）：通过 Agent 平台的 hook 机制（WorkBuddy 的 `<user-prompt-submit-hook>` / CodeBuddy 的 pre-tool-use hook）注入 sofagent 检查

**关键设计**：
- 规则引擎从 `@sofagent/audit` 抽出为独立包 `@sofagent/rules`（无 fs / git 依赖，纯函数）
- Agent 平台通过 hook 在 tool call 前调用 `rulesEngine.check({ tool, args, context })`
- 失败 → Agent 平台阻止 tool 执行，返回违规说明给 Agent
- WARN → Agent 平台允许执行但记录，可配置阈值转 FAIL

**与 v1.1.x 的关系**：
- v1.1.3 修好 daemon 物理可见性（plist + WorkingDirectory + PATH）
- v1.1.5 加 MCP pipe（Agent 编辑即时审计）
- v1.2.0 内嵌编排引擎（tool call 前置拦截，从「事后审计」升级为「事前拦截」——**范围限定：仅 sofagent 自派 SubAgent 的工具调用门禁；主 Agent 仍事后审计，完整运行时治理见 v1.4.0 SubAgent 沙箱**）

这是 sofagent 从「独立审计工具」变成「Agent 平台原生能力」的关键一跳。审计引擎不再是个外部旁路，而是 Agent 平台工具调度层的内置组件。

### 物理结构大重构（承接 v1.1.9 规划）

> 来源：v1.1.9 开发日志「交付四：产品叙事收敛」下的 v1.2.0 执行项。v1.1.9 完成叙事收敛（文档/定位），v1.2.0 落地物理结构重构——把散落各处的 Skill、安装脚本、发版工具链统一收口，并把 FDE 交付物从隐藏目录可见化、确立 Dashboard 定位。

#### Skill 收敛物理移动（v1.2.0 执行）

当前 Skill 散落 4 处（`/sofagent/skill/` + `/FDE/SKILL.md` + `/LOOP/SKILL.md` + `/agents/SKILL/`），用户不知从哪进入。v1.2.0 物理移动为统一入口：

```
/SKILL/                        ← 统一 Skill 入口（根目录）
  SKILL.md                     ← FDE Agent 主入口（用户看到的第一层 = 宪法 + FDE 身份合一）
  harness/                    ← 约束底座（所有 Agent 共享的闸门/铁律细节）
    engage.md / engage-fde.md / entry-gate.md / task-aware.md / loop-*.md ...
    data/                      ← 模板数据
  agents/                      ← FDE 内部 Sub Agent（FDE 的"下属"角色身份）
    audit/SKILL.md             ← 合规审计员
    engineer/SKILL.md          ← 工程师
    reviewer/SKILL.md          ← 审查员

/LOOP/                         ← 不动（开发工具定位，不在用户首屏）
  SKILL.md                     ← LOOP 开发循环 Skill（留在 LOOP/ 不进 /SKILL/）
  releaser/                    ← 发布工程师（归 LOOP——发版是开发循环最后一环）
  src/                         ← 运行时代码

/install.sh                    ← 提到根目录（v1.2.0）
```

**三层分离原则**：
- `/SKILL/SKILL.md` = **FDE Agent 主入口**（用户面对的唯一身份，含宪法+铁律）
- `/SKILL/harness/` = **约束底座细节**（所有 Agent 共享的闸门、任务流程、循环检查——主入口引用它们）
- `/SKILL/agents/` = **Sub Agent 角色身份**（FDE 内部的下属角色——audit/engineer/reviewer）
- `/LOOP/` = **开发工具包**（不进 /SKILL/——LOOP 是开发者用的自迭代工具，不是用户面对的 Agent 身份；releaser 归 LOOP 因为发版是开发循环的一环）

**搬迁路径**：

| 原位置 | → | 新位置 | 说明 |
|--------|---|--------|------|
| `/sofagent/skill/SKILL.md` + `/FDE/SKILL.md` | → | `/SKILL/SKILL.md` | 两者合并为 FDE Agent 主入口（宪法 + FDE 身份合一）|
| `/sofagent/skill/` 其余文件 | → | `/SKILL/harness/` | 约束底座细节整体搬（含 data/ 子目录 + 全部 .md 文件）|
| `/agents/SKILL/sofagent-fde` | → | 合并进 `/SKILL/SKILL.md` | FDE 主 Skill 源文件——与主 SKILL.md 合并 |
| `/agents/SKILL/sofagent-audit` `/agents/SKILL/sofagent-engineer` `/agents/SKILL/sofagent-reviewer` | → | `/SKILL/agents/audit` `/SKILL/agents/engineer` `/SKILL/agents/reviewer` | 3 个 FDE 内部 Sub Agent |
| `/agents/SKILL/sofagent-releaser` | → | `/LOOP/releaser/` | 归 LOOP（发版是开发循环最后一环）|
| `/LOOP/` 全部 | → | 不动 | 开发工具定位不变 |
| `install.sh` | → | `/install.sh` | 提升根目录 |

#### 两个用户入口（v1.2.0 落地）

| 入口 | 路径 | 场景 |
|------|------|------|
| ① install 安装 | `bash install.sh`（v1.2.0 移到根目录）| 企业/开发者直接 clone → 安装全栈 |
| ② skill 调用 | `@sofagent-fde`（WorkBuddy）/ seed prompt（其他平台）| 已装 Agent 平台的用户，通过 Skill 拉起 FDE Agent |

#### 三个安装包的边界（v1.2.0 落地）

| 安装命令 | 装什么 | 给谁 | 装 LOOP？ |
|---------|--------|------|:--:|
| `bash install.sh` | 底座 + FDE Skill + audit Skill | 企业用户 | ❌ |
| `bash install.sh --base-only` | 仅底座引擎（约束+审计+daemon+mcp） | 所有用户 | ❌ |
| `bash LOOP/loop-install.sh` | 底座(base-only) + engineer + reviewer Skill | 开发者 | ✅ |

> v1.2.0 收口：`FDE/fde-install.sh` 升格并入根 `install.sh`（FDE 成为默认模式），原纯底座脚本由 `--base-only` 开关替代。`loop-install.sh` 内部调 `install.sh --base-only` 复用底座逻辑，不误装 FDE。

**FDE 安装包不自动装 LOOP**——FDE 用户需要的是"能干活的人"，不是"自己迭代开发工具"。LOOP 是可选高级用法。

#### install.sh 提升到根目录（v1.2.0 执行）

主 install.sh 提升到根目录 `/install.sh`。v1.2.0 进一步将 `FDE/fde-install.sh` 合并进来，根 `install.sh` 成为唯一主安装器（默认 = FDE 模式，`--base-only` = 仅底座）。

#### LOOP 定位澄清：LOOP 只给 sofagent 自己用（文案收口）

LOOP 管理的是**代码**（写代码、改代码、审计代码），让外部用户用 LOOP 管理自己的项目风险太高、不可控。LOOP 不是通用自迭代工具，是 sofagent 自己的开发循环工具。真正的安全定制层是 **FDE**——FDE 输出的是文件/文档，用户可以安全地自定义、积累、迭代。

- LOOP/README.md 明确："LOOP 是 sofagent 项目的自迭代开发工具包"——不泛化为"任何项目"
- 强调 LOOP 的边界：它管理代码变更（写/审/测），给开发者用，不给终端用户用
- FDE 才是用户可自定义的层——通过 Skill 分层（引擎层 vs `/SKILL/custom/` 用户层）实现可持续定制

#### Skill 分层：解决用户自定义 vs 官方升级冲突（v1.2.0 设计 + 实现）

**核心设计：引擎层 vs 用户层分离**

```
/SKILL/
  SKILL.md                     ← 引擎层（官方维护，升级时覆盖）
  harness/                    ← 引擎层（同上）
  agents/audit|engineer|reviewer/  ← 引擎层（同上）

  custom/                      ← 用户层（用户自定义，升级时不动）
    engineer-overrides.md      ← 追加到 engineer 之后（类似 CSS !important）
    fde-overrides.md           ← 追加到 FDE 之后
```

**加载顺序**：引擎层先加载 → 用户层覆盖追加。升级时只覆盖引擎层，用户层不动。

**升级策略（v1.2.0 实现）**：

| 策略 | 行为 | 适用 |
|------|------|------|
| **安全升级**（默认） | 只覆盖引擎层；用户层不动；自动备份旧版到 `.backup/` | 90% 场景 |
| **强制覆盖**（`--force`） | 覆盖所有层（含用户自定义） | 用户明确要"重置到官方版" |
| **diff 合并**（`--merge`） | 对比引擎层 diff，自动合并用户层（Git 三路合并算法） | 高级用户 |

#### 发版工具链归入 LOOP（v1.2.0 执行）

发版是开发循环的最后一环。releaser Sub Agent 已经归 LOOP，但 releaser 调用的工具和 SOP 却散落在 `tools/` 和 `docs/verification/`，断裂了。发版流水线应整体归入 `LOOP/releaser/`，让 LOOP 成为完整的开发循环工具包：写代码 → 审计 → 审查 → 测试 → 发版 → 发布后审查 → 下一轮。

**关键认知**：LOOP 内部有两类东西，风险不同：
- **代码迭代引擎**（engineer/reviewer Sub Agent）：管理代码，高风险，sofagent-only
- **发版工具链**（releasing.md / acceptance-test.sh / bump-version.sh）：脚本+流程文档，用户跑了不会自动改代码，风险低，**可分享给用户**

**搬迁清单（v1.2.0 执行）**：

| 文件 | 从 | 到 | 类型 |
|------|-----|-----|------|
| `releasing.md` | `docs/verification/` | `LOOP/releaser/releasing.md` | 发版 SOP |
| `acceptance-test.sh` | `tools/` | `LOOP/releaser/acceptance-test.sh` | 验收测试 |

| `fresh-eyes-review.md` | `docs/verification/` | `LOOP/releaser/fresh-eyes-review.md` | 发布后审查 |

**留 tools/ 不搬**（日常质量门禁，不是发版专用）：`check-docs.sh` / `check-version.sh` / `check-test-count.sh` / `pre-push-check.sh` / `test-count.sh`

#### FDE 交付物可见化（v1.2.0）

> 背景：FDE 进场梳理的 workflow、ontology、知识库，当前全部落在 `.sofagent/` 隐藏目录里。用户装完 FDE、梳理完毕，打开 Finder 什么都看不到。FDE 的承诺是"梳理→挖掘→交付→离场"，但交付物不可见 = 用户感知不到价值。

**目标**：FDE 交付时，在用户项目里建一个**以企业名命名的可见目录**，落在用户项目根目录：

```
{企业名}/                            ← FDE §3 建档时确定，以此为根目录名
  交付手册/
    企业画像.md                       ← 基于 FDE/templates/enterprise-profile.md
    部署方案.md                       ← 基于 FDE/templates/deployment-plan.md
    运行规范.md                       ← 安装包自带 fde.md
    上手文档.md                       ← 安装包自带 quick-start.md
  nodes/                              ← AI 节点文档（人读 + 编排引擎读）
    节点A.md                          ← 基于 FDE/templates/nodes/node-template.md
    节点B.md
  skills/                             ← AI 节点 Skill（AI 读）
    节点A/SKILL.md                    ← 基于 FDE/templates/skills/skill-template/SKILL.md
    节点B/SKILL.md
  workflows/                          ← Workflow 定义
    节点A.yml
    节点B.yml
```

**根目录名是用户定的**——FDE 进场 §3 建档阶段跟用户聊的时候就确定了。四个子目录结构固定。

**这些文件是用户项目的一部分**，不写进 `.gitignore`——企业画像、节点文档、Skill、Workflow 是企业 AI 化的重要资产，应该进版本控制、团队共享。

> 注：`.sofagent/` 运行时目录保留作为真源与 Dashboard 数据源，可见 `{企业名}/` 为交付物副本，二者并存。

### 行业对标：gbrain / LLM Wiki / Palantir OAG

> 差异化铁律：吸收方法，不吸收定位。gbrain = 个人知识大脑（定位），sofagent = 约束中间件（定位）。

**gbrain（Garry Tan / YC）· Dream Cycle 对标**：
- gbrain 的 Dream Cycle：夜间扫描当天对话 → 实体检测/补全 → 引用修复 → 记忆整合（Compiled Truth 重写）
- sofagent 的 Dream Cycle：6 阶段管道（think.md → extract_facts → synthesize_concepts → atoms → skillopt 回灌 → log 周报）
- **方法吸收**：gbrain 的"Compiled Truth + Timeline"分离（上半部当前认知可重写 / 下半部证据链只追加）与 sofagent 的 Ledger-Views-Policy 同构——Ledger=证据链，Views=Compiled Truth，Policy=约束。验证了三层模型方向正确。
- **定位差异**：gbrain 是"个人知识大脑"（人/公司/事件），sofagent 是"Agent 行为约束"（审计/skill/经验）。gbrain 帮人记事，sofagent 管 Agent 干活。

**LLM Wiki（Karpathy）· 三层范式对标**：
- Karpathy 的 LLM Wiki：raw materials → wiki entries → spec norms（LLM 持续维护的知识编译层，取代 RAG 即时拼凑）
- sofagent 的 Ledger-Views-Policy：Ledger（原始记录）→ Views（派生视图）→ Policy（约束规则）
- **方法吸收**：LLM Wiki 的"知识编译"理念（不是每次查询从头检索，而是预编译维护稳定知识结构）已在 sofagent Dream Cycle 的 synthesize_concepts 阶段实现。
- **定位差异**：LLM Wiki 是"知识检索范式"（替代 RAG），sofagent 是"行为约束中间件"（审计+治理）。两者解决不同问题。

**Palantir OAG · Ontology 操作层对标**：
- Palantir Foundry 的 Ontology：企业级操作层（Object/Property/Action 统一模型，直接驱动业务逻辑）
- sofagent 的 Policy 层：约束规则层（A1-A21 审计规则 + config + Skill）
- **定位差异（本质不同）**：Palantir OAG 是"企业 OS"（集中式，数据全进平台），sofagent 是"分布式约束层"（数据主权在用户侧，MIT 可审计，第三方独立）。**不吸收 Palantir 的集中式定位**。

**sofagent 的差异化优势**：
1. 数据主权（`.sofagent/` 在用户本地，不进第三方平台）
2. 第三方独立（MIT 开源，审计逻辑公开可审查）
3. 平台中立（MCP 开放协议 + git diff/JSONL/Markdown 开放格式，不绑定任何 Agent 平台）
