# v1.1.7 开发日志 — Dream Cycle 6 阶段管道 + sensitivity

> 状态：规划中 · 孔放勋 · 2026-07-15
> 前置依赖：v1.1.6（conflict-check 已就绪）

## 背景

v1.1.6 能检测知识库的毛病了，但知识本身还是靠 daemon 两个老脚本（weekly-report / lessons-extract）散点生成。v1.1.7 用 gbrain 的 Dream Cycle 精简版（6 阶段 pipeline）替换它们，把知识沉淀从散兵升级为流水线。同时给 knowledge/ 加 sensitivity 字段，为后续联邦查询的安全过滤铺路。

### 设计输入：操作型本体论的读写回路

> 来自 Palantir 操作型本体论系列研报（2026-07）的启发。

Palantir 操作型本体论的核心是一个 5 节点闭环的**读写回路**：读（数据集成）→ 逻辑（规则编排）→ 写（事务回写）→ 反馈（持续学习）→ 治理（全链路审计）。传统知识图谱只覆盖前两节点——能查询，不能操作，不能反馈，不能治理。

sofagent 的 Dream Cycle 本质上是在做一个**迷你读写回路**：

| Palantir 回路 | Dream Cycle 对应 | v1.1.7 实现 |
|------|------|------|
| 读 | Ledger 层原始数据 | think.md + audit history（已有） |
| 逻辑 | 从原始数据提取模式 | extract_facts → extract_atoms → cluster_patterns（新增） |
| 写 | knowledge/ 写入 | synthesize_concepts → knowledge/ entities/（新增） |
| 反馈 | 持续学习回路 | skillopt_backfill → fde.md 优化（新增） |
| 治理 | 全链路审计 | conflict-check + sensitivity 过滤（v1.1.6 已有 + 本版增强） |

**关键差异**：Palantir 依赖集中式 Ontology OS + 重度物化索引。sofagent 走分布式路线——每个设备维护自己的 knowledge/，联邦查询按需获取。**我们不建中央本体，我们让每个 Agent 自己长出本体**。

## 交付一：Dream Cycle 6 阶段（P0）

gbrain 21 阶段的精简版——对约束沉淀真正有用的前半段：

```
extract_facts → extract_atoms → cluster_patterns
             → synthesize_concepts（喂 @sofagent/ontology）
             → skillopt_backfill（回灌自进化）
             → embed（向量化，供未来检索）
```

- `@sofagent/daemon`：stage 状态机替换 weekly-report / lessons-extract
- `@sofagent/ontology`：加 synthesize 接口
- `@sofagent/skillopt`：加 backfill 钩子

## 交付二：sensitivity frontmatter（P1）

entity/concept 的 frontmatter 新增 `sensitivity: public | internal | restricted` 字段。联邦查询时按 sensitivity 过滤结果。

## 交付三：knowledge-health inspector（P1，新增）

> 来源：外部笔记研读（个人 LLM Wiki 治理实践）+ v1.1.6 conflict-check 范式复用。

v1.1.6 的 `conflict-check` 管「项目文件矛盾/孤儿/死链」；本交付管「知识库健康」——Ledger-Views-Policy 三层知识目录的孤立、重复、断链、陈旧、缺源。与交付一（Dream Cycle 生成 fact/atom/concept）形成「生成 + 治理」闭环，是 Palantir 读写回路「治理」节点的补强。

- **文件**：`sofagent/daemon/src/inspectors/knowledge-health.ts`（与 `conflict-check.ts` 同形态）
- **注册**：`sofagent/daemon/src/inspectors/index.ts` 加 `'knowledge-health': { enabled: true, schedule: '@weekly' }`，与 conflict-check 同节奏，跑在外层 LOOP compliance 扫查
- **检查项**（适配 sofagent 知识目录）：
  1. 孤立页：`knowledge/` 中无任何其他 entity/concept/fde.md 引用的条目
  2. 重复页：标题或 normalized key 高度相似 / embedding 近邻的 concept（可复用交付一的 `embed` 产出）
  3. 断裂链接：`knowledge/` + `think.md` / `fde.md` 中 markdown/wikilink 指向不存在目标
  4. index 过旧：`index.md` / `log.md` 的 mtime 明显早于 `raw/` 或 `knowledge/` 最新源
  5. 来源缺失：concept/claim 无 `source:` frontmatter 或回指 `raw/` 的引用
- **行为**：fail-closed、只读（仅 `readdirSync`/`readFileSync`/`existsSync`）、输出 `InspectorResult`（finding 级别为 warning，非 critical——健康是建议性的）、**只建议不自动删**（与笔记②治理纪律一致，呼应 conflict-check 的 fail-closed 只读范式）
- **与 sensitivity 的关系**：巡检报告生成时按 `sensitivity` 过滤，restricted 条目不向未授权上下文泄露
- **测试**：`sofagent/daemon/src/inspectors/__tests__/knowledge-health.test.ts`（镜像 `conflict-check.test.ts`，8 case）
- **依赖**：无新增（复用 `fs`/`path`、既有 `InspectorResult` 类型、daemon 知识目录解析）

> 来源：原 changelog「LUI 感知」段落 concretized。用户要"看见"后端三件事在跑。

**A · 可感知产物（折入交付一/二/三验收）**：

- 文件：`sofagent/daemon/src/commands/knowledge-status.ts`（或并入现有 cli.ts，架构师阶段确认落点）
