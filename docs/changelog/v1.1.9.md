### Skill 收敛方向声明（v1.1.9 声明，v1.2.0 执行）

### LOOP 定位澄清：LOOP 只给 sofagent 自己用（v1.1.9 文案调整）

> 背景：孔老师纠正——LOOP 管理的是**代码**（写代码、改代码、审计代码），让外部用户用 LOOP 管理自己的项目风险太高、不可控。LOOP 不是通用自迭代工具，是 sofagent 自己的开发循环工具。真正的安全定制层是 **FDE**——FDE 输出的是文件/文档，用户可以安全地自定义、积累、迭代。

**文案调整方向**（v1.1.9 改文档，不改代码）：
- LOOP/README.md 明确："LOOP 是 sofagent 项目的自迭代开发工具包"——不泛化为"任何项目"
- 强调 LOOP 的边界：它管理代码变更（写/审/测），给开发者用，不给终端用户用
- FDE 才是用户可自定义的层——通过 Skill 分层（引擎层 vs `/SKILL/custom/` 用户层）实现可持续定制

**与 Skill 分层的关系**：Skill 分层不是为 LOOP 服务的（用户不会用 LOOP 改 Skill），是为 FDE 服务的——用户通过 `/SKILL/custom/` 追加自己的规则，官方升级时不动用户层。这才是孔老师说的"可持续定制平台"。

### Skill 分层：解决用户自定义 vs 官方升级冲突（v1.2.0 设计，v1.2.x 落地）

> 背景：孔老师提出——如果用户用 LOOP 改了 Skill 文件（加自定义规则），我们后续发了新版本也改了同一文件，用户升级时会冲突。

**核心设计：引擎层 vs 用户层分离**

```
/SKILL/
  SKILL.md                     ← 引擎层（官方维护，升级时覆盖）
  sofagent/                    ← 引擎层（同上）
  agents/audit|engineer|reviewer/  ← 引擎层（同上）

  custom/                      ← 用户层（用户自定义，升级时不动）
    engineer-overrides.md      ← 追加到 engineer 之后（类似 CSS !important）
    fde-overrides.md           ← 追加到 FDE 之后
```

**加载顺序**：引擎层先加载 → 用户层覆盖追加。升级时只覆盖引擎层，用户层不动。

**升级策略**（v1.2.x 实现）：

| 策略 | 行为 | 适用 |
|------|------|------|
| **安全升级**（默认） | 只覆盖引擎层；用户层不动；自动备份旧版到 `.backup/` | 90% 场景 |
| **强制覆盖**（`--force`） | 覆盖所有层（含用户自定义） | 用户明确要"重置到官方版" |
| **diff 合并**（`--merge`） | 对比引擎层 diff，自动合并用户层（Git 三路合并算法） | 高级用户 |

### 发版工具链归入 LOOP（v1.2.0 执行，v1.1.9 声明方向）

> 背景：孔老师指出——发版是开发循环的最后一环。releaser Sub Agent 已经归 LOOP，但 releaser 调用的工具和 SOP 却散落在 `tools/` 和 `docs/verification/`，断裂了。发版流水线应整体归入 LOOP/releaser/，让 LOOP 成为完整的开发循环工具包：写代码 → 审计 → 审查 → 测试 → 发版 → 发布后审查 → 下一轮。
>
> **关键认知**：LOOP 内部有两类东西，风险不同：
> - **代码迭代引擎**（engineer/reviewer Sub Agent）：管理代码，高风险，sofagent-only
> - **发版工具链**（releasing.md / acceptance-test.sh / bump-version.sh）：脚本+流程文档，用户跑了不会自动改代码，风险低，**可分享给用户**

## 背景

v1.1.8 把编排引擎从「只打印 YAML」升级到了「真正调度 Sub Agent 执行」，并交付了 A/B 原型（手动 `compose --run --label A/B` → `compare`）。但 A/B 测试还是手动的——人得记得去跑、去看结果、去 promote 赢家。

v1.1.9 补上这个缺口：daemon 自动定时触发 A/B 探索-利用循环，积累真实任务数据，自动 promote 表现更好的编排方案。同时交付 USB 完整运行时——把 sofagent 全栈打包进 U 盘。

> 🔴 **daemon A/B 调度器的核心价值**：v1.1.8 的 A/B 原型证明了「两种方案对比」可行，但需要人手动触发。v1.1.9 让它变成**后台自动运行**——daemon 定期用当前方案跑真实任务积累数据 → 自动切换候选方案跑 N 次 → compare → promote 赢家 → 再换新方案探索。这就是你说的「探索-利用」模式（explore-exploit），不是同一个任务跑两遍浪费 token。

### 安全：HMAC 内容签名 + 磁盘加密

**HMAC 防篡改**——`create-usb-key` 写入完成后，自动计算所有文件的 HMAC-SHA256 签名写入 `/.sofagent-signature`。daemon 每次启动先验签——签名不匹配 → 拒绝启动并记录安全事件。「不能阻止物理删除，但删了就废。」

**磁盘加密防失窃**——U 盘 knowledge/ 目录在写入时用 federation.json 中的 AES-256 密钥加密。daemon 启动后内存解密读写，U 盘文件系统上永远只有密文。U 盘丢失 = 拿到盘的人读不到任何知识。

| 攻击场景 | 防线 |
|------|------|
| 偷 U 盘插自己电脑看文件 | knowledge/ 全盘 AES 加密，无密钥不可读 |
| 删掉 federation.json 试图重置 | HMAC 签名不匹配，daemon 拒绝启动 |
| 往 U 盘拖入恶意文件 | 多余文件 → HMAC 签名不匹配 |
| 整盘格式化重写 | 签名文件消失 → daemon 检测不到 → 拒绝启动 |

## 交付二：daemon A/B 自动调度器（探索-利用模式，P1）

> 📐 技术依赖：v1.1.8 的 `orchestrator-compare.ts` `CONSECUTIVE_WINS_REQUIRED = 2` promote 机制 + T05 A/B 原型 + T06 自动候选方案 B/C/D

### 问题诊断

v1.1.8 的 A/B 是**手动的**——开发者得记得去跑 `compose --run --label A`、`compose --run --label B`、然后 `compare`。手动模式有两个问题：
1. **没人记得跑**：A/B 测试是「重要但不紧急」的事，人一忙就忘
2. **样本太少**：手动跑一两次就 compare，偶然性太大，不是统计意义上的 winner

v1.1.9 让 daemon **自动**做这件事——后台定期用当前方案跑真实任务积累数据，攒够 N 次后自动切换候选方案再跑 N 次，然后 compare 判定 promote。

### 探索-利用模式（不是同一个任务跑两遍）

用户澄清的核心设计（2026-07-21）：

```
阶段 1（利用）：
  当前方案 A 跑真实任务（不是测试任务，是企业日常使用的任务）
  → 每次任务的 PASS/FAIL/耗时/质量 指标写入历史日志
  → 积累 N 次（可配，默认 N=10）

阶段 2（探索）：
  daemon 自动生成候选方案 B/C/D（复用 v1.1.8 T06 的 --variants）
  → 选一个（轮询或随机）跑 N 次真实任务
  → 同样记录指标

阶段 3（判定 + promote）：
  compare A vs 候选方案的历史指标
  → 候选方案连续 CONSECUTIVE_WINS_REQUIRED=2 轮更好 → promote 为新当前方案
  → 候选方案不如当前 → 保留当前方案，换下一个候选探索

阶段 4（循环）：
  回到阶段 1，当前方案继续跑
  → 定期触发新一轮探索（@weekly 或 @daily cron）
```

**为什么不浪费 token**：跑的是企业**真实日常任务**，不是专门为 A/B 造的测试任务。方案 A 和方案 B 跑的都是有业务价值的真活，只是拆解策略不同。

### 实现拆解

#### T01：`ab-scheduler.ts`——A/B 调度状态机（新增，~200 行）

```typescript
// sofagent/orchestrator/src/ab-scheduler.ts

interface ABSchedulerState {
  currentPlan: string;          // 当前方案 ID（如 "A-step-by-step"）
  candidatePlan: string | null;  // 正在探索的候选方案 ID
  currentRunCount: number;       // 当前方案已跑次数
  candidateRunCount: number;     // 候选方案已跑次数
  threshold: number;             // 切换/promote 阈值（默认 10）
  exploreCandidates: string[];   // 待探索的候选方案队列（["B-domain", "C-risk", "D-tdd"]）
  history: PlanMetrics[];        // 历史指标（持久化到 .sofagent/ab-history.jsonl）
}

// daemon cron 触发（复用现有 @weekly/@daily 机制）
export async function runABScheduledTask(state: ABSchedulerState): Promise<ABSchedulerState> {
  if (state.candidatePlan === null) {
    // 利用阶段：当前方案继续跑
    return await runCurrentPlanAndAccumulate(state);
  } else {
    // 探索阶段：候选方案跑
    return await runCandidatePlanAndAccumulate(state);
  }
}

// 跑完后检查是否到阈值
export function checkThreshold(state: ABSchedulerState): ABSchedulerState {
  if (state.candidatePlan === null && state.currentRunCount >= state.threshold) {
    // 当前方案跑够 N 次 → 启动探索
    return startExploration(state);
  }
  if (state.candidatePlan !== null && state.candidateRunCount >= state.threshold) {
    // 候选方案跑够 N 次 → compare + 判定
    return judgeAndPromote(state);
  }
  return state;
}
```

## 交付三：控制图状态抽取（Graph Engineering 波次拓扑可视化 · 数据层，P1）

> 📐 来源：Graph Engineering 印证 ③「用户视角波次拓扑可视化」的数据底座部分。v1.2.x 文档里原 ③·1 里里程碑，提前到 v1.1.9——v1.1.9 是 daemon 可观测版本，后台 A/B 循环跑的是真实任务，但当前 `.sofagent/checkpoint/` + `LoopArtifacts` 是纯技术状态文件，人/调试者看不懂"现在卡在哪、哪个节点过了 audit、第几波"。本交付把控制图状态抽取成结构化 JSON，为 v1.2.x Dashboard 波次视图提供数据底座。

### 问题诊断

v1.1.8 编排引擎用 `@langchain/langgraph` StateGraph 实现 `START→engineer→audit→reviewer→human_confirm→END`，`audit` 节点即 ★Reality Anchor（真实 git diff A1-A19 作 guard edge），`FileCheckpointer` 快照到 `.sofagent/checkpoint/`。但：
1. **状态不可读**：checkpoint 是 LangGraph 内部序列化格式，人看不懂
2. **波次不显式**：graph.ts 当前串行，尚未有 DAG 波次概念，但 resume/retry 已产生"第几次跑/第几轮 guard"的隐含拓扑
3. **证据链散落**：audit 的 git diff 证据在各次运行日志中，无统一索引

v1.1.9 不引入新运行时，只做**数据抽取**——把已有 checkpoint + LoopArtifacts 翻译成人类/前端可读的结构化 JSON。

### 实现拆解

#### T01：`loop-state-extractor.ts`——控制图状态抽取（新增，~150 行）

```typescript
// sofagent/orchestrator/src/loop-state-extractor.ts

interface ControlGraphState {
  loopId: string;
  waves: WaveState[];             // 按 resume/retry 拆分的波次序列
  nodes: NodeState[];             // 每个节点的状态
  realityAnchorChain: Evidence[]; // audit 证据链（git diff 引用）
}

interface NodeState {
  name: "engineer" | "audit" | "reviewer" | "human_confirm";
  status: "pending" | "running" | "passed" | "failed" | "skipped";
  guardTriggered: boolean;         // guard edge 是否触发
  guardResult?: string;            // guard 判定结果（如 retryCount<3）
  enteredAt?: string;
  exitedAt?: string;
}
```
