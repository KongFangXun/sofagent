# v1.0.1 开发日志 — AI 知识库

> FDE 交付的第三样东西从散文件升级为结构化 AI 知识库——AI 节点自动积累经验，系统自动注入上下文，企业用越久 AI 越聪明。
>
> 已开发 · 孔放勋

---

## 背景

v0.99.9 完成概念先行（6 个文档写入 AI 知识库定义 + 架构定位）。v1.0.1 是代码实现版——一次性完成 AI 知识库的骨架创建、Ingest 自动生长、被动注入、Lint 体检闭环。

原计划分 v1.0.1（骨架）/ v1.0.2（Ingest）/ v1.0.3（Lint）三步走，讨论后合并为一个版本——三部分耦合度高，分开做反而增加管理成本。

### 设计依据

基于 Karpathy LLM Wiki 思想，适配 sofagent 架构。核心设计决策（v0.99.9 确认）：

1. **被动注入 > 主动查询**——不靠 Agent 自己决定查不查，加载链启动时自动注入 top-N 相关页（和 think.md 同机制）
2. **daemon 触发 Ingest**——Agent 平台没有 session 结束事件，靠 daemon 检测 task/logs 变化触发知识提取
3. **Lint 绑 loop-evaluate**——不支持 cron 定时，体检在 loop-evaluate 运行时顺带做
4. **数据层不进五层**——AI 知识库是 `.sofagent/knowledge/` 数据目录，不作为五层架构的第六层
5. **Agent 即搜索引擎**——不加向量数据库、不加 RAG pipeline、不加全文搜索。Agent 本身就是最强的语义匹配引擎——index.md 200 token 扫完就知道去哪找，结构化 frontmatter 让 Agent 读页面时不只是读文字而是在理解对象关系。如果未来有复杂查询需求，建一个 Knowledge Query Sub Agent 让它自己翻，比搭 pipeline 更简单且在纯 TS 架构内

## 交付内容（7 件事）

### 1. 目录骨架（install.sh 扩展）

install.sh 创建 `.sofagent/knowledge/` 目录结构：

```
.sofagent/knowledge/
├── index.md                 ← AI 自动维护的目录页（页面名 + 一句话摘要）
├── log.md                   ← 操作日志（Ingest/Query/Lint 追加时间戳）
├── entities/                ← 实体页（人、岗位、工作流节点、外部系统）
├── concepts/                ← 概念页（方法论、最佳实践、常见问题）
├── comparisons/             ← 对比页（问答产生的分析沉淀）
└── summaries/               ← 摘要页（从 evidence 层自动提取的摘要）
```

初始 `index.md` 模板（空知识库）和 `log.md` 模板（只有表头）由 install.sh 自动生成。

#### 实体关联（Ontology 第 1 步）

entities/ 页面从独立 Markdown 升级为关联图——frontmatter 加 `relations` 字段：

```yaml
---
# entities/供应商-华强电子.md
title: "华强电子"
type: "Supplier"
domain: "采购/供应商"
accessible-to: [AP-审批, AP-执行]
relations:
  has_many: [Payment-2026-001, Payment-2026-003]
  belongs_to: "采购/华南区"
constraints:
  credit_limit: 500000
---
```

Agent 查询实体时不只是拿到一段文字，而是拿到它的关联对象和约束边界。这为 v1.0.2 的 actions 定义和 v1.0.3 的约束验证打基础。

### 2. fde.md 加「AI 知识库维护规则」章节

在 `skill/data/fde.md` 中新增一章（受 ≤3200 字符总量约束，控制在 ~400 字以内）：

- **页面格式规范**：frontmatter 字段（title/category/created/updated/sources）、双向链接规范 `[[]]`、来源标注格式
- **Ingest 触发规则**：daemon 检测 task/logs 变化 → 触发知识提取 session → 新模式新建页，已有模式更新页，矛盾标注告警
- **注入规则**：session 启动时读 index.md → 关键词匹配上一个 session 的 task/logs → 注入 top-3 相关页摘要
- **Lint 规则**：loop-evaluate 运行时扫描——断链检测、矛盾标注、孤立页面发现、缺失概念提示

### 3. 加载链扩展：knowledge 被动注入

session 启动时的加载链顺序：

```
1. SKILL.md（宪法内联）
2. think.md（反思摘要）
3. fde.md（运行规范）
4. knowledge/index.md → top-3 相关页摘要  ← 新增
```

注入逻辑：
- 读取 `.sofagent/knowledge/index.md` 获取全部页面名 + 摘要
- 读取上一个 session 的 task/logs 关键词
- 关键词匹配 → 挑 top-3 页面 → 注入页面摘要（不是全文，控制 token 预算）
- 如果 index.md 为空（新装），跳过此步

**token 预算**：knowledge 注入不超过 500 token（约 index.md 200 token + 3 个页面摘要各 100 token）。加上前三层 ~3000 token，总加载链 ~3500 token，仍 < 窗口 5%。

### 4. daemon 触发 Ingest（知识提取 session）

daemon 现有逻辑：监控 think.md/fde.md hash 变化。新增分支：检测 task/logs/ 目录有新增文件。

触发流程：
```
task/logs/ 新增文件
  → daemon 检测到变化
  → 触发编排引擎跑一次「知识提取 session」
  → AI 读取最新 task/logs + 审计记录 + 评分变化
  → 提取模式：新建 entity/concept 页 or 更新已有页
  → 更新 index.md
  → 追加 log.md 条目
```

一个 session 可能同时更新 3-5 个 Wiki 页面。

**成本控制**：知识提取 session 是额外的 Agent 调用，有 token 成本。设阈值——task/logs 累积超过 N 条才触发一次提取，不做每条实时提取。

### 5. loop-evaluate 扩展 Lint

loop-evaluate 技能运行时，顺带执行知识库体检：

| 检查项 | 做什么 | 输出 |
|--------|--------|------|
| 断链检测 | `[[]]` 指向的页面名是否存在 | 列出断链 |
| 矛盾标注 | 同一概念在不同页面是否有冲突表述 | 列出矛盾对 |
| 孤立页面发现 | 没有其他页面链接到它的页面 | 列出孤立页 |
| 缺失概念提示 | 正文提到但没创建页面的概念 | 列出建议新建 |
| 过期标注 | sources 引用的 evidence 已过期 | 列出过期页 |

输出体检报告到 `.sofagent/knowledge/log.md`。

### 5.1 loop-check 轮次上限

当前 loop-check 只有步数比例检查点（60%），无绝对轮次上限。v1.0.1 加硬性兜底：超过 N 轮自动 closure → 交还人类。防止工具持续报错导致 Agent 无限循环消耗 Token。实现简单——loop-check 入口处计数器 +1，超过阈值跳过正常检查直接走 closure 逻辑。

### 6. knowledge-maintain.md（新 Skill）

新建 `skill/knowledge-maintain.md`——AI 节点跑知识提取 session 时加载的规则：

- 页面怎么写（frontmatter 模板、正文结构、来源标注）
- 双向链接怎么用（`[[]]` 语法、先查 index.md 确认目标存在）
- 什么时候新建 vs 更新（新模式新建，已有模式更新，矛盾标注不覆盖）
- index.md 更新规则（新建页必须同步加 index 条目）
- log.md 追加规则（每次操作追加时间戳 + 操作类型 + 影响页面）

≤90 行限制。

## 技术决策

1. **被动注入算法**：task/logs 关键词 → index.md 关键词重合度 → top-3 页摘要（≤500 token，重合度=0 则跳过）。纯关键词交集计数，不做 TF-IDF / 向量相似度。
2. **daemon 防抖**：task/logs 变化 → 标记「有待提取」→ 等 30 分钟无新变化 → 触发 Ingest。避免短时间多次触发成本爆炸。
3. **页面 frontmatter**：`title` / `category` / `created` / `updated` / `sources` / `tags`，entities 额外含 `relations: { has_many, belongs_to }` 和 `constraints`。

## 面向客户的描述（给 FDE 交付手册）

> AI 知识库是 AI 节点自己长的。每完成一个任务，系统自动从任务记录里提取经验，分类存成 Wiki 页面。下次 session 启动时，相关页面自动注入上下文——AI 不用自己决定查不查，系统自动喂。企业用越久，知识库越密，AI 节点越聪明。

> 🔐 **访问控制**：不是所有人都能看到所有知识。AI 节点只能看到自己 Workflow 职责范围内的数据——财务 Agent 看不到人事数据，运维 Agent 看不到财务数据。人类操作者可以看全部（审计透明），Agent 只看该看的（数据契约）。详见下方「知识库访问控制」章节。

---

### 知识库访问控制

Agent 读知识库的唯一入口是加载链第 4 层——在此执行 Workflow 域过滤。workflow.yml 中每个节点声明 `knowledge-domain: { include, exclude }`，不在范围内的页面不返回给 Agent。审计引擎新增 **A14 知识库越权**规则（hybrid 模式）——Agent 试图读取不在 own-domain 内的页面时告警。`--doctor` 第 9 项展示访问矩阵。人类操作者可 cat 所有 .md 文件（审计透明原则），Agent 只看该看的（数据契约原则）。

> 详细设计背景见 [ARCHITECTURE.md](../../ARCHITECTURE.md#知识库访问控制)。实现细节：`rule-a14-kb-cross-domain.ts`（10 tests）、`commands/doctor.ts` §9。

| 0 | 知行合一 | 说和做一致，声称必有证据 | 🆕 |
| 1 | 目标驱动 | 回到原始意图，不跑偏 | 4 |

| 3 | 成本意识 | 批量处理重复操作，简短回答不啰嗦 | 6 |
