# v0.97 开发日志

> 证据版本：纪律层证伪实验 + 审计规则扩展实现 + 编排引擎重构 + bash→TS 第二波
>
> v0.96 完成诚实收缩后，v0.97 是 sofagent 最重要的版本——**纪律层增量的生死验证**。同时完成审查吸收的 A9/A10/A11 代码实现、编排引擎精简重构、bash→TS 第二波迁移、概念精简和 HANDBOOK 重组。

## 概述

v0.97 的每个 P0 任务都来自前序版本的明确推迟或外部审查的硬性要求。三个来源：

1. **v0.96 推迟**：纪律层证伪实验 + bash→TS 第二波 + A9/A10/A11 实现
2. **两份外部审查共识**：非 OC 平台加载链实测 + 概念精简 + 编排引擎重构

v0.97 不做新功能。所有精力放在三件事上：证明纪律层有效（或诚实承认无效）、让代码更好维护、让编排引擎真正对接 FDE 场景。

## 一、P0：纪律层证伪实验（🔴 最高优先级）

> 来源：v0.96 §一推迟。ROADMAP v1.0 准入条件第一条。

### 实验设计

拒绝过度设计（v0.85 的 45 组方案已被审查一指出为「过度实验」）。采用审查一的建议：**2 组高质量实验 + 反转设计 + 盲评**。

```
实验组 A（n=5）：真实 sofagent 加载链（SKILL.md 内联宪法 + think.md + rules.md）
实验组 B（n=5）：裸 Agent（无任何约束层）

任务池：5 个陷阱任务（含「同名语义混淆」「越界修改」「盲改跳过」等高难度场景）

反转轮次：
  第一轮：A 组跑 Task 1→2→3→4→5，B 组跑 Task 6→7→8→9→10（相同难度，不同内容）
  第二轮：任务互换（A 组跑 Task 6→10，B 组跑 Task 1→5）
  目的：排除任务内容本身带来的 bias

盲评：评审者不知道哪个产出来自 sofagent 组，独立评分（纪律性 1-5）
```

### 实验条件

| 条件 | 说明 |
|------|------|
| 平台 | OpenClaw（唯一 100% 生效的平台——先在最有利条件下验证。非 OC 平台实测见 §二） |
| 模型 | DeepSeek V4 Flash（当前基准）+ GLM-5.2 + Claude（三模型交叉验证本版本不做，因为先要在一个模型上拿到明确结论） |
| 每个条件样本数 | n=5（总 2 组 × 5 任务 × 5 样本 = 50 组对照数据） |
| Task 2 异常复现 | sof-1 的 1/4 vs 裸 4/4——n≥8 确认是噪声还是系统性缺陷 |

### 自动化脚本

v0.94 已完成的脚本：
- `prepare-fixture.sh`：准备实验 fixture（陷阱任务 + 干净环境）
- `run-trial.sh`：运行单次试验（记录 task/logs + 产出文件）
- `aggregate.sh`：聚合结果（统计违纪次数 + 类型分布）

### 结论发表

**不管结果如何——诚实发表。** 

- ✅ **证实**：「纪律层在 OpenClaw 上将 Agent 违约率从 X% 降到 Y%，p < 0.05」
- ❌ **证伪**：「纪律层在 OpenClaw 上未产生统计学显著的纪律性增量，可能是以下原因：...」
- ⚠️ **部分证实**：「只在特定陷阱类型（如同名语义混淆）上有显著增量，通用场景无显著差异」

| 产出 | 存放位置 |
|------|------|
| 实验报告（含原始数据 + 统计分析） | `docs/experiments/v0.97-discipline-verification.md` |

## 二、P0：非 OpenClaw 平台加载链可靠性实测

> 来源：两份审查共识——「非 OC 平台加载链可靠性是整个项目的根基问题，而根基是裂的。」

### 实测设计

| 平台 | 实测次数 | 测量指标 |
|------|:--:|------|
| WorkBuddy | 30 次新会话 | think.md 加载率 / rules.md 加载率 / 闭合清单执行率 |
| Claude Code | 20 次新会话 | 种子指令生效率 / audit 可运行率 |
| Codex | 20 次新会话 | 同上 |
| Hermes Agent | 20 次新会话 | 同上 |

**总计 90 次实测**，覆盖 4 个平台。

### 加载链命中率统计方法

每次新会话：
1. 派一个简单任务（如「在 README.md 最后加一行空行」）
2. 检查 task/logs 是否记录了 think.md 的 Read 操作
3. 检查 Agent 是否执行了闭合清单
4. 记录：命中/部分命中/未命中

### 结论阈值

| 加载率 | 处理 |
|:--:|------|
| ≥ 70% | 保持当前方案，标注「实验性支持」 |
| 40-70% | 考虑将 think.md 关键内容内联进 SKILL.md，标注「有限支持」 |
| < 40% | 诚实标注「该平台仅宪法层生效」，放弃「跨平台」叙事中的「等值」暗示 |

> ⚠️ **预期**：基于 v0.60-v0.62 的历史数据（1/3 和 0/3），WorkBuddy 的加载率可能低于 40%。如果实测证实这一点，v0.97 必须做出叙事调整——把「跨平台纪律标准」改为「OpenClaw 完整治理 + 其他平台宪法层约束 + 审计工具跨平台」。

## 三、P0：审计 A9/A10/A11 代码实现

> 来源：v0.96 §三规则草案。审查二：「审计层没有覆盖 Agent 被攻击了的情况，只覆盖了 Agent 粗心。」

### A9 不纳注入（prompt injection 检测）

检测范围：Agent 生成的代码中是否包含已知注入模式。

**实现**：
- 纯文本正则匹配——不依赖语义分析，--silent 模式可跑
- 规则文件：`audit/src/rules/rule-a9-no-injection.ts`
- 测试文件：`audit/src/rules/rule-a9.test.ts`（≥8 个测试用例）

**检测模式清单**（初始版本）：
| 模式 | 正则 | 风险级别 |
|------|------|:--:|
| 指令覆盖 | `/ignore (all )?previous (instructions|prompts)/i` | 🔴 |
| 角色劫持 | `/(you are now|你现在是|你的新角色是) (DAN|jailbreak)/i` | 🔴 |
| 规则绕过 | `/do not follow (the |your )?(rules|guidelines|instructions)/i` | 🔴 |
| 输出劫持 | `/(ignore|forget) (everything|all) (above|before)/i` | 🔴 |

**检测范围**：git diff 中新增的代码注释和字符串字面量。

### A10 不引毒源（供应链检测）

检测范围：依赖文件（package.json / requirements.txt / Cargo.toml）的变更。

**实现**：
- 检测新增依赖是否指向非官方源（如 GitHub raw URL / 个人服务器）
- 检测版本号是否从语义化版本变成了指向特定 git commit
- 规则文件：`audit/src/rules/rule-a10-no-poison.ts`
- 测试文件：`audit/src/rules/rule-a10.test.ts`（≥8 个测试用例）

**v0.97 不维护恶意包名单**——那是独立安全服务的事。只检测「模式可疑的依赖变更」。

### A11 不滥资源（资源消耗检测）

检测范围：单次任务的文件操作规模。

**实现**：
- 纯 git diff 统计，--silent 模式可跑
- 规则文件：`audit/src/rules/rule-a11-no-abuse.ts`
- 测试文件：`audit/src/rules/rule-a11.test.ts`（≥8 个测试用例）

**阈值**：
| 检测项 | 阈值 | 判定 |
|------|:--:|:--:|
| 新增文件数 | > 50 | WARN |
| 单文件新增行数 | > 10,000 | WARN |
| 批量删除文件数 | > 20 | FAIL |

## 四、P1：编排引擎精简重构

> 来源：v0.96 §四编排引擎定位决策。两份审查共识——「编排引擎应该从 sofagent 核心拆出来，变成独立的可选项。」

### 重构范围

```
当前 engine.md（321 行）：
  - 点火条件（🔴 复杂任务）
  - 四级编排深度（L1-L4）
  - 三档自由度
  - AO compose 拆解
  - 渐进减薄
  - 信任等级四档
  - 闭环验收

重构后：
  sofagent/SKILL.md → 移除编排引擎点火条件
  sofagent-fde/SKILL.md → 嵌入编排引擎（精简版）

engage.md（编排引擎精简版，~120 行）：
  - 点火条件（FDE workflow 节点触发）
  - 两档拆解（拆 vs. 不拆）
  - AO compose 拆解（保留核心）
  - Agency Agent 模板匹配（引用 AO Compose 自带模板库）
  - think.md → 编排引擎反馈回路（新增）
  - 闭环验收

砍掉：
  - 四级编排深度 → 两档拆解
  - 三档自由度 → 删除
  - 渐进减薄 → 删除
  - 信任等级四档 → 删除（skillopt 替代）
```

### Agency Agent 模板匹配

**不自建模板库。** AO Compose 自带 Agency Agent 的几百个模板（数据分析型、文档生成型、代码审查型、客服回复型等）。编排引擎直接引用——不改模板、不加 wrapper、不建中间层。

```
编排引擎（engage.md）
  ↓ AO compose 拆解出子任务
  ↓ 根据子任务类型，匹配 Agency Agent 模板
  ↓ 注入模板到子任务上下文
  ↓ 子 Agent 按模板执行
  ↓ 任务完成 → think.md 反思
  ↓ 下次同一节点任务 → 反思驱动编排引擎微调拆解策略
```

**厚在治理，薄在复用**：编排引擎的代码只负责「何时拆、怎么拆、拆完谁做」——这是治理层。具体模板由 Agency Agent 提供——这是复用层。

### think.md → 编排引擎反馈回路（新增）

> 当前编排引擎每次拆解都是从零开始——不读 think.md 的反思记录。v0.97 新增反馈回路：

```
任务完成
  ↓
闭环反思（think.md 写入本次踩坑）
  ↓
下次同一 workflow 节点新任务
  ↓
编排引擎点火前先读 think.md（该节点的历史反思）
  ↓
根据反思调整拆解策略
  例：think.md 记录「上次拆分太细导致子 Agent 上下文不足」
  → 本次减少拆分粒度
  例：think.md 记录「Agency Agent 模板 X 在这个场景下容易出错」
  → 本次换模板 Y
```

| 文件 | 操作 | 说明 |

| `sofagent/SKILL.md` | 修改 | 移除编排引擎点火条件（🔴 复杂任务时不再点火编排） |
| `sofagent/engine.md` | **删除** | 321 行编排引擎 MD，内容重构后移到 engage.md |
| `sofagent/engage.md` | **新建** | 精简版编排引擎（~120 行），仅 FDE Skill 引用 |
| `sofagent-fde/SKILL.md` | 修改 | 嵌入编排引擎使用说明 + think.md 反馈回路 |

| `audit/src/task-orchestrate.ts` | **新建** | TS 重写编排引擎核心逻辑 + vitest 测试 |

## 七、P1：HANDBOOK 按场景重组

> 来源：v0.95 遗留项，v0.96 推迟。

### 当前结构问题

HANDBOOK 按功能模块组织（铁律章 / 编排章 / 反思章 / 审计章），用户不知道「装完之后该干什么」。

### 目标结构

按场景重组——让用户在任何时刻都能找到对应的行动指南。

```
HANDBOOK.md 新结构：
  §零 为什么 sofagent 选 Ralph 路线（v0.96 已写入）
  §一 第一次用：安装 → 验证 → 派第一个任务

  §三 日常使用：每次任务的纪律检查清单
  §四 出问题了：常见问题排查
    - Agent 不读 SKILL.md 怎么办
    - 审计报告不知道怎么看

  §五 深入定制：改 rules.md / 调审计阈值 / 加企业专属规则
  §六 给 FDE 部署者：workflow 梳理 → 编排引擎 → 交付清单
  §附录 铁律 + 审计规则速查表
```

## 最坏情况预案

如果纪律层增量在反转实验中**无法复现**（或统计不显著）：

1. **不压结论。** 诚实发表实验报告——包括所有原始数据、统计方法、可能的原因分析
2. **调整 v1.0 定位。** 从「纪律层被证实有效」调整为「纪律层在特定陷阱类型上有效（同名语义混淆），通用场景待验证」
3. **不影响审计层路线。** 审计工具（A1-A11）的价值不依赖纪律层增量——它是「事后检测」，纪律层是「事前约束」。「事后检测」在任何情况下都有独立价值
4. **v0.98 路线不变。** 审计闭环六步 + GitHub Action + 持续使用案例——这些工作在纪律层增量是真是假的情况下都可以推进
