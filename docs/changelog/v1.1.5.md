> 状态：规划中 · 孔放勋 · 2026-07-15

## 背景

v1.1.4 的 LOOP 能跑了，但 Agent 不知道「发版要做什么」。v1.1.5 把 `docs/verification/releasing.md` 的十二阶段 SOP 注入 Agent 上下文——Agent 不只是写代码，它知道怎么发版。

同时把 knowledge/ 暴露为结构化的 MCP resource，为后续联邦查询铺路。

## 交付一：releasing.md SOP 集成（P0）

Agent 按 releasing.md 全流程自动执行：

```
人类: "发布 v1.1.5"
  → 审查（阶段一）：Agent 跑独立审查 + 写 changelog
  → 开发（阶段二）：按 P0→P1→P2 修问题
  → 自测（阶段三）：build + test + shellcheck + acceptance-test
  → 审阅（阶段四-五）：code-review + 回归检查
  → 发版（阶段六-十一）：bump-version → git tag → push → gh release
```

人在节点：阶段一结束后确认 changelog 内容、阶段五独立检查报告确认、发版前最终确认（3 次 intervention）。

## 交付二：@sofagent/mcp knowledge resource + push target + list_capabilities（P1）

7 个 knowledge resource：`search_knowledge` / `read_entity` / `read_concept` / `list_entities` / `read_lessons` / `read_think_md` / `stats`。

## 交付三：WorkBuddy ↔ sofagent MCP pipe（P1）

**问题**：v1.1.3 之前 Agent（WorkBuddy / CodeBuddy / Cursor）的文件编辑动作不经过 sofagent——只有 `git commit` 才触发审计。这导致 Agent 编辑过程中产生的违规（A3 越界、A7 盲改、A11 debug 残留）要等到 commit 才被发现，那时已经写完一堆代码了。

**方案**：把 sofagent 的「文件变更审计」能力暴露为 MCP tool，让 Agent 平台主动把每次文件编辑事件喂给 sofagent：

```
Agent 编辑文件
  → Agent 平台（WorkBuddy / CodeBuddy）通过 MCP 调用 sofagent.audit_file
  → sofagent 即时跑 A3/A7/A11 等适用于单文件变更的规则
  → 返回审计结果给 Agent（WARN/FAIL + 具体规则）
  → Agent 在下一轮迭代中自我修正
```

**为什么放 v1.1.5**：v1.1.3 已修好 daemon 的物理可见性（plist 调用错误 + WorkingDirectory 错误 + PATH 残缺），daemon 现在能监控项目目录了。但 daemon 只解决「文件系统层」的可见性——Agent 编辑如果走 MCP 协议（而不是直接写磁盘），daemon 的 `fs.watch` 是看不到的。MCP pipe 补上这层。

**关键设计**：
- MCP tool `sofagent.audit_file(path, change_type, diff)` ——单文件即时审计
- 复用 `runFilesystemAudit()` 的规则引擎，只是触发源从 fs.watch 变成 MCP 调用
- 返回结构化结果（不返回原始 stdout），Agent 可直接解析
- A3「不改越界」需要 task 描述——MCP 调用方可选传 `task` 参数

**与 daemon 的关系**：两者互补。daemon 监控所有文件变更（包括非 Agent 的手动编辑），MCP pipe 只监控 Agent 通过协议触发的编辑。覆盖率：daemon 100% 项目文件，MCP pipe 100% Agent 编辑动作。

## 交付五：LOOP Sub Agent API Key 配置（P1 · 厂商无关）

**问题**：v1.1.4 的 LOOP 能跑，但 `loop-install.sh` 没有让用户输入 API key 的环节——用户装完后第一次跑 `loop --task` 才发现 engineer/reviewer 连不上 LLM，体验断裂。另外 v1.1.4 的 provider 解析硬编码 `OPENAI_API_KEY`，不支持「engineer 和 reviewer 用不同账号」这种常见场景（开发用便宜账号、审查用高质量账号分开计费）。

**方案**：三级 API key 回退 + 交互式配置向导 + LLM smoke test + custom provider 通用接入。

### 1. 三级 API key 回退（`resolveApiKey(role)`）

按角色解析优先级：
```
SOFAGENT_LLM_{ROLE}_API_KEY  >  SOFAGENT_LLM_API_KEY  >  OPENAI_API_KEY（兜底）
```

- **角色专用 key（高级用法）**：`SOFAGENT_LLM_ENGINEER_API_KEY` / `SOFAGENT_LLM_REVIEWER_API_KEY` —— engineer 和 reviewer 用不同账号可分别控制成本和限额
- **通用 key**：`SOFAGENT_LLM_API_KEY` —— 两个角色共用一个账号
- **兜底 key（默认推荐）**：`OPENAI_API_KEY` —— 所有 OpenAI 兼容 API 通用，入门最简路径

> ⚠️ **代码能力 ≠ 默认推荐**：三级 fallback 作为「能力」在代码里完整保留，但对外文档和向导的默认推荐是 `OPENAI_API_KEY` 一把梭——见末尾「设计修正」小节。

实现位置：`sofagent/orchestrator/src/loop/nodes.ts` `resolveApiKey(role)`。

### 2. custom provider 通用接入

新增 `custom:<model>` provider 配合 `SOFAGENT_LLM_BASE_URL` 使用，支持任意 OpenAI 兼容 API。用户用的模型不在预置列表（本地部署、企业内网、OpenRouter、Together AI 等），用 `custom` 即可接入——不硬编码任何厂商假设。

预置 provider（`deepseek`/`glm`/`kimi`）继续保留作为开箱即用选项，但**所有文档和向导文案改为厂商无关描述**（"性价比模型"/"推理能力更强的模型"，不绑定具体厂商）。

### 3. 交互式配置向导（`loop-install.sh` step [4/5]）

`bash LOOP/loop-install.sh` 新增第 4 步——装完底座后引导用户配置 LLM：

```
[4/5] 配置 LLM（交互式）...
  LOOP 需要 LLM 才能工作。engineer 和 reviewer 是两个 subagent——
  engineer 写代码（建议性价比模型），reviewer 审查（建议推理能力强的模型）。

  ── engineer（开发）配置 ──
  可选 provider: 1) deepseek 2) glm 3) kimi 4) custom 5) 跳过
  ...
```

- 检测到已有有效 `loop.env` 时自动跳过向导（不重复打扰）
- 写入 `loop.env` 并 `chmod 600`（API key 是敏感数据）
- 永久生效提示：将配置追加到 `~/.zshrc` 或 `~/.bashrc`

### 4. LLM smoke test（`loop-install.sh` step [5/5]）

配置完成后立即跑一次最小 LLM 调用验证 API key 有效性：

```
LLM 连通性测试：
  ✅ LLM 连通性 OK
```

失败时不阻塞安装（LOOP 仍可用），但明确告警 + 指出常见原因（key 错误 / 余额不足 / 网络不通 / provider 不支持）+ 指向 `loop.env` 供排查。

### 5. 附带修复的 bug

- `defaultRunReviewer` 中 `resolveLLMModelFor('engineer')` 应为 `'reviewer'`（v1.1.4 笔误，reviewer 读不到自己的角色配置）
- `defaultConfirmHuman` 中 reviewReport 重复打印两次（v1.1.4 笔误）
- `loop-install.sh` 步骤编号不一致（`[1/4]`/`[2/4]` 与 `[3/5]`/`[4/5]` 混用）

### 设计修正：默认路径从「三级 fallback」收敛为「OPENAI_API_KEY 一把梭」

**背景**：初版交付五把"角色专用 key > 通用 key > OPENAI_API_KEY"三级 fallback 作为**默认推荐**写到文档和向导第一选项。用户反馈戳中要害：

> "为什么我们直接全部用 OpenAI 的 API key 就好了？OpenAI API 格式的 key，这个现在不是世界上通用的吗？"

OpenAI API 格式（协议层 + key 格式）已是事实标准——DeepSeek / GLM / Kimi / OpenRouter / Together / vLLM / Ollama 全部兼容。90% 的用户只用一个 provider，一把 `OPENAI_API_KEY` 就能跑。把 power user 的分账需求摆在桌面上当默认推荐，是典型的过度设计。

**修正动作**：

| 文件 | 修正 |
|------|------|
| `LOOP/quick-start.md` | 第三步默认路径改为 `OPENAI_API_KEY` 一把梭；三级 fallback 降到「高级用法」小节 |
| `LOOP/README.md` | 快速开始同步改为 `OPENAI_API_KEY` 默认 + "一个 key 走天下"说明 |
| `LOOP/loop-install.sh` | step [3/5] env 模板默认启用 `OPENAI_API_KEY`，角色专用 key 注释掉；step [4/5] 向导 API Key 模式新增「统一 key（推荐）/ 分账号（高级）」二选一；smoke test fallback 顺序改为 OPENAI_API_KEY 优先 |

**代码逻辑不变**：`resolveApiKey(role)` 三级 fallback 保留——它没坏，只是不该作为默认推荐。现在三级 fallback 在代码里作为「能力」存在，在文档里作为「高级用法」呈现。

**澄清概念**：OpenAI 兼容的是**协议**（请求/响应 JSON schema），不是 key 互通。DeepSeek 的 key 只能调 DeepSeek endpoint，不会发到 OpenAI。但一把 `OPENAI_API_KEY` 环境变量 + 一个 `SOFAGENT_LLM_*` 指定的 provider，就能让 OpenAI SDK 自动把请求发到正确的 endpoint——这就是"一个 key 走天下"的本质。

**教训**：默认极简，复杂可选——而不是反过来。这是产品哲学，不是技术决策。

### 设计修正后的复查（2026-07-19 11:23）

修正完后系统性复查，发现并修复 3 个遗留问题：

| # | 问题 | 严重度 | 修复 |
|---|------|--------|------|
| 1 | smoke test 的 API key fallback 顺序是 `OPENAI_API_KEY > SOFAGENT_LLM_API_KEY > SOFAGENT_LLM_ENGINEER_API_KEY`，与 `nodes.ts` 的 `resolveApiKey(role)`（`SOFAGENT_LLM_{ROLE}_API_KEY > SOFAGENT_LLM_API_KEY > OPENAI_API_KEY`）相反 | P0 | smoke test 函数化 + fallback 顺序对齐 nodes.ts |

### 第二轮复查（2026-07-19 11:27）

用户要求"再检查一遍"，换了角度——构造实际 loop.env 文件 + 端到端模拟跑 smoke test，发现并修复 3 个问题：

| # | 问题 | 严重度 | 修复 |
|---|------|--------|------|
| 4 | smoke test 用 `result=$(node ... \| head -3) \|\| result="失败"`——pipe 吃掉 node 的 exit code，`\|\|` 永远不触发。失败判定完全依赖 grep 输出内容是否含 "error/401/invalid"，存在假阳（模型回复含 "error" 字样被误判失败）和假阴（API 失败但错误信息不含关键词被误判成功） | P1 | 改为 `local node_exit=$?` 捕获 node 退出码（在 pipe 前）+ EXIT_CODE\|OUTPUT 分隔符格式返回，判定逻辑用 exit code 而非 grep |
| 5 | smoke test 的 `providerUrls` 硬编码在 bash，`defaultModels` 缺失；`nodes.ts` 的 `LLM_PROVIDERS` 是另一份硬编码。两份列表不同步会出现 smoke test 过了但实际跑挂 | P1 | smoke test 补 `defaultModels` 对齐 nodes.ts；两处都加 `⚠️ 必须和 nodes.ts 同步` 约束注释 |
| 6 | `ENV_EXAMPLE` 变量定义但未使用（dead code） | P2 | 删除 |

**验证方式**：构造 5 个场景的 loop.env 文件（统一 key / 分账号 / 残留过期 OPENAI_API_KEY + 新角色 key / 含注释行 / 空配置）+ 抽取 smoke test node 脚本独立跑变量解析，全部通过。退出码判定逻辑用 4 个场景（exit 0/1/2 + 旧 grep 会误判的"no error all good"）验证。

**关键教训**：跨层一致性不能只看代码——要构造真实数据文件 + 端到端模拟跑。这次发现的 P1（pipe 吃退出码）光看代码看不出来，只有实际构造场景跑才能暴露。

### 关键教训

**「能修的全部修掉」原则**：原计划把 tag commit message 缺版本号当作「历史污点」保留，用户决定 retag——代码内容不变只是 tag 指向的 message 变，风险可控。retag 用 annotated tag（有独立 message）而非改 commit 本身，降低对历史的影响。knownKeys 漏 a18/a19 是典型的「新增规则后多处需同步」陷阱——本次已在 config-loader 加同步约束注释指向 runner.ts AUDIT_PRIORITY 权威源。
