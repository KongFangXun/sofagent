# v1.1.5 开发日志 — releasing.md SOP 集成 + MCP knowledge resource

> 状态：规划中 · 孔放勋 · 2026-07-15
> 前置依赖：v1.1.4（条件路由已就绪）

## 背景

v1.1.4 的 LOOP 能跑了，但 Agent 不知道「发版要做什么」。v1.1.5 把 `docs/verification/releasing.md` 的十二阶段 SOP 注入 Agent 上下文——Agent 不只是写代码，它知道怎么发版。

同时把 knowledge/ 暴露为结构化的 MCP resource，为后续联邦查询铺路。

## 交付一：releasing.md SOP 集成（P0）

Agent 按 releasing.md 全流程自动执行：

```
人类: "发布 v1.1.5"
  → 审查（阶段一）：Agent 跑独立审查 + 写 changelog
  → 开发（阶段二）：按 P0→P1→P2 修问题
  → 自测（阶段三）：build + test + shellcheck + acceptance-test
  → 审阅（阶段四-五）：code-review + 回归检查
  → 发版（阶段六-十一）：bump-version → git tag → push → gh release
```

人在节点：阶段一结束后确认 changelog 内容、阶段五审查报告确认、发版前最终确认（3 次 intervention）。

## 交付二：@sofagent/mcp knowledge resource + push target + list_capabilities（P1）

7 个 knowledge resource：`search_knowledge` / `read_entity` / `read_concept` / `list_entities` / `read_lessons` / `read_think_md` / `stats`。

## 交付三：WorkBuddy ↔ sofagent MCP pipe（P1）

**问题**：v1.1.3 之前 Agent（WorkBuddy / CodeBuddy / Cursor）的文件编辑动作不经过 sofagent——只有 `git commit` 才触发审计。这导致 Agent 编辑过程中产生的违规（A3 越界、A7 盲改、A11 debug 残留）要等到 commit 才被发现，那时已经写完一堆代码了。

**方案**：把 sofagent 的「文件变更审计」能力暴露为 MCP tool，让 Agent 平台主动把每次文件编辑事件喂给 sofagent：

```
Agent 编辑文件
  → Agent 平台（WorkBuddy / CodeBuddy）通过 MCP 调用 sofagent.audit_file
  → sofagent 即时跑 A3/A7/A11 等适用于单文件变更的规则
  → 返回审计结果给 Agent（WARN/FAIL + 具体规则）
  → Agent 在下一轮迭代中自我修正
```

**为什么放 v1.1.5**：v1.1.3 已修好 daemon 的物理可见性（plist 调用错误 + WorkingDirectory 错误 + PATH 残缺），daemon 现在能监控项目目录了。但 daemon 只解决「文件系统层」的可见性——Agent 编辑如果走 MCP 协议（而不是直接写磁盘），daemon 的 `fs.watch` 是看不到的。MCP pipe 补上这层。

**关键设计**：
- MCP tool `sofagent.audit_file(path, change_type, diff)` ——单文件即时审计
- 复用 `runFilesystemAudit()` 的规则引擎，只是触发源从 fs.watch 变成 MCP 调用
- 返回结构化结果（不返回原始 stdout），Agent 可直接解析
- A3「不改越界」需要 task 描述——MCP 调用方可选传 `task` 参数

**与 daemon 的关系**：两者互补。daemon 监控所有文件变更（包括非 Agent 的手动编辑），MCP pipe 只监控 Agent 通过协议触发的编辑。覆盖率：daemon 100% 项目文件，MCP pipe 100% Agent 编辑动作。

## 交付四：v1.1.4 审查修复延续（P1）

v1.1.4 发版审查发现的 8 个问题，v1.1.4 已修复 P0×2 + P1×2 + P2×4。以下项在 v1.1.5 持续推进：

### 1. maxTurns 可配置化（P1）

v1.1.4 硬编码 `DEFAULT_AGENT_MAX_TURNS = 20`（PRD Q1 决策）。v1.1.5 提取为 LOOP 配置项，收集实际数据后调整：
- 配置位置：`.sofagent/config.yml` 的 `loop.maxTurns`（默认 20）
- engineer 和 reviewer 可分别配置（reviewer 可能需要更少轮次）
- 收集指标：实际 invoke 的轮次分布，P50/P90 落在哪

### 2. warn-accumulator 文件级追踪（P2）

v1.1.4 修正了连续性判定（WARN 后有 PASS 中断），但「未处理」仍是粗粒度（末尾连续 N 条 WARN 即触发）。v1.1.5 做精确文件级追踪：
- 解析 WARN 记录的 `ruleResults[].details` 提取涉及文件
- 后续 history 记录中是否有对应文件的删除/修复 commit
- 真正判定「这条 WARN 涉及的文件至今仍在仓库」

### 3. USB federation 安全层（P1）

v1.1.4 基础版无签名校验（PRD Q4 决策），v1.1.5 加：
- HMAC 签名校验：`federation.json` 配 `.sig` sidecar 文件
- `detectSofagentUsb()` 读取后先验签，签名不匹配拒绝导入
- `exportToUSB()` 导出时自动生成签名
- schema 校验：按 `FederationConfig` 接口校验字段完整性
- `applyFederation()` 实现：nodes → `~/.sofagent/orchestrator/nodes/`、policies → `~/.sofagent/audit/policies/`

### 4. A18 评估提升为 defaultRules（P2）

v1.1.4 A18 在 extendedRules（需 `extendedRulesEnabled: true` 才生效）。垃圾文件检测应该是基线能力，不该藏在 config 开关里。v1.1.5 评估：
- 将 A18 从 extendedRules 移到 defaultRules（始终生效）
- 评估误报率：正规项目是否有 `a.txt` 这类合法文件（概率极低）

### 5. LOOP audit history 完整性（P2）

v1.1.4 已让 `defaultRunAudit` 三态（PASS/WARN/FAIL）都写 history。v1.1.5 验证：
- 实际 LOOP 运行时 history 是否真的三态都有记录
- warn-accumulator 在 LOOP 场景是否能正确识别「WARN 后有 PASS 清理」
- 端到端测试：构造 WARN → PASS 序列，验证 warn-accumulator 不误报

### 6. tools.ts 高危命令黑名单可配置（P2）

v1.1.4 硬编码黑名单（rm -rf /、fork 炸弹、curl|sh、mkfs、dd of=/dev/）。v1.1.5 评估：
- 黑名单是否需要可配置（企业可能有自定义高危命令）
- 是否需要 WARN 级灰名单（chmod 777、sudo 等，不阻断但告警）
- 正则模式是否需要单元测试 fuzzing（避免误伤边界情况）
