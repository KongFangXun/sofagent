## 一、训练推理服务（train serve · 部署后跑起来）

> 📋 **2026-08-10 补充（生命周期审查新发现）**：v1.4.4 只到"部署（model_register / model_switch）"——但**部署后谁拉起推理服务？** `model_register` 注册了权重，却没有"启动 vLLM / Ollama 服务并健康检查"的环节。缺了它，权重是"注册了但没跑起来"的死文件。

### 交付

| 组件 | 能力 |
|------|------|
| **train serve** | 启动推理服务：从权重目录拉起 vLLM / Ollama / OpenAI 兼容端点（复用 v1.3.2 `client_type: 'openai-compatible'` 插槽） |
| **健康检查** | 服务就绪探测（/health）+ 启动失败自动重试（对齐 v1.3.1 错误处理指数退避） |
| **服务生命周期** | 启动 / 停止 / 重启 / 状态查询——与 model_switch 联动（切模型时自动拉起新权重服务） |
| **serve 审计** | 每次服务启停记 `train_serve` 事件（谁启的、哪个模型、哪个节点在用） |

### 涉及文件（预估）

## 二、持续后训练（飞轮闭环的"持续"环）

> 📋 **2026-08-10 补充（生命周期审查新发现）**：「持续后训练」——非 FDE 路径下企业数据回流，让模型"越用越懂企业 workflow"——在 v1.4.1-1.4.4 没有落地点。训练引擎有了"训一次"（train-job），缺"定期增量训"（持续后训练）。

### 交付

| 组件 | 能力 |
|------|------|
| **增量训练任务** | 基于新回流数据（企业运行数据 / 人工纠正记录）定期触发增量训练——复用 train-job 编排（v1.4.1）+ 数据管道（v1.4.2） |
| **调度策略** | 触发条件：数据量达到阈值 / 定时（@weekly）/ 人工触发——对齐 daemon 定时任务模式 |
| **回退保护** | 增量训练后 eval 分数不低于基线 → 晋升；否则回退旧权重（复用 v1.4.4 产物注册衔接 + 回滚） |
| **飞轮数据源** | 复用 worklog（v1.3.9 节点耗时 + 人工介入记录）+ decision-log + llm-calls（v1.4.4 语料导出同源） |

> 🚧 **边界声明（2026-08-26 补）**：本版持续后训练 = **数据回流 + 触发策略 + 回退保护**（规则驱动的增量再训）。**不延伸至**：① 自然语言指令直接转权重更新（on-policy self-distillation）② 在线交互实时训练（online RL）——这两条是 continual learning 的权重级路线，属商业模型层范围，不在开源训练引擎内实现（训练引擎只提供数据回流管道与再训编排，权重级能力由商业层消费）。

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/daemon/src/tasks/continuous-training.ts` | 新建 | 持续后训练调度（daemon 定时任务，对齐 decision-memory @daily 模式） |
| `engine/orchestrator/src/train/train-continuous.ts` | 新建 | 增量训练编排（数据阈值 / 定时 / 人工触发） |
| `engine/orchestrator/src/__tests__/train-continuous.test.ts` | 新建 | 单测（触发条件 + 回退保护） |

### 验收标准

- [ ] 数据阈值 / 定时 / 人工三种触发方式可用
- [ ] 增量训练复用 train-job + 数据管道（不重复实现）

## 三、训练数据合规扫描（train compliance · 合规红线代码化）

> 📋 **2026-08-10 补充（合规缺口）**：v1.4.2 有"训练入口脱敏"（redactor 语义脱敏），但缺**合规扫描**——训练集进训练前的合规检查（个保法 / 敏感字段 / 数据来源标记）。合规红线（仅以脱敏聚合基准对外，不落个体级数据）需要一个代码化落点：**训练集进训练前先过合规闸**。
>
> 🔗 **与 v1.4.4 脱敏的边界**：两者用同一套检测能力（redactor 的 PII / 敏感字段红名单），但**流向不同**——v1.4.4 脱敏在**语料导出时**做（数据离开企业边界前，去掉可识别信息）；本版合规扫描在**训练管线入口**做（训练提交前，检查数据集是否可安全训练）。两道闸针对不同风险：导出闸防"泄漏出去"，训练闸防"不该训的数据进了训练"。检测能力共用，处置逻辑独立。

### 交付

| 组件 | 能力 |
|------|------|
| **合规扫描** | `train compliance <dataset>`——扫描训练集：个人可识别信息（姓名/手机号/身份证）/ 敏感字段（健康/财务）/ 企业专有名词——复用 v1.4.4 redactor 的红名单检测 |
| **合规报告** | 扫描结果 → 合规报告（发现项 + 严重度 + 处置建议：脱敏 / 剔除 / 人工确认）——写入训练集版本（v1.4.2） |
| **合规闸门** | 严重级发现 → 阻断训练提交（数据不处理完不让训）——对齐质量闸门模式 |
| **数据来源标记** | 训练集记录数据来源（企业提供 / 合成 / 公开语料）——合规可追溯 |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/train/train-compliance.ts` | 新建 | 合规扫描 + 报告 + 闸门 |
| `engine/orchestrator/src/train/dataset-version.ts` | 修改 | 记录合规扫描结果 + 数据来源标记 |
| `engine/mcp/src/tools/train-compliance.ts` | 新建 | MCP `train_compliance` tool |
| `engine/orchestrator/src/__tests__/train-compliance.test.ts` | 新建 | 单测（PII 扫描 + 闸门阻断 + 来源标记） |

### 验收标准

- [ ] `train compliance` 扫描 PII/敏感字段/企业专有名词（复用 redactor 检测）
- [ ] 合规报告写训练集版本（发现项 + 严重度 + 处置建议）
- [ ] 严重级发现阻断训练提交（数据不处理完不让训）
- [ ] 训练集记录数据来源（合规可追溯）
- [ ] `npm test` 全绿

## 五、训练产物归档与保留策略（磁盘治理 · 企业级标配）

### 定位

> 📋 **2026-08-10 补充（磁盘治理）**：训练跑多了会堆积大量历史 checkpoint 和旧训练集——一个 14B 模型的 checkpoint 几十 GB，跑十次几百 GB。v1.4.1 ⑤ 有 `train cleanup`（覆写销毁），v1.4.5 ④ 交付包含「权重清单（历史版本 + 回滚点）」——但**保留多少个回滚点？旧 checkpoint 留多久？过期谁清？** 没有定义。不补 = 磁盘逐渐塞满，手动清容易误删生产权重。

### 交付

| 组件 | 能力 |
|------|------|
| **保留策略配置** | `train-retention.json`：默认保留最近 N 个 checkpoint（默认 5）+ 当前生产权重 + eval 基线对应训练集 + FDE 交付包标记的回滚点——其余标记为可归档 |
| **自动归档** | daemon 定时任务（@weekly）：扫描超保留期的 checkpoint / 旧训练集 → 压缩归档到 `data/train/archive/` + 记审计（归档不删除，压缩冷存） |
| **过期清理** | 归档超过二次保留期（默认 90 天）→ `train cleanup` 覆写销毁（走 v1.4.1 ⑤ 覆写标准）|
| **空间预警** | 磁盘占用超阈值（默认 80%）→ 告警 + 建议清理（列出最大的可归档项）|

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/train/retention-policy.ts` | 新建 | 保留策略解析 + 归档标记 |
| `engine/daemon/src/tasks/train-archive.ts` | 新建 | 定时归档任务（@weekly）|
| `engine/orchestrator/src/__tests__/retention-policy.test.ts` | 新建 | 单测（保留策略 + 归档标记 + 过期清理） |

### 验收标准

- [ ] `train-retention.json` 保留策略可配（默认：最近 5 checkpoint + 生产权重 + eval 基线 + 回滚点）
- [ ] daemon @weekly 自动归档超期 checkpoint / 旧训练集（压缩冷存 + 审计）
- [ ] 归档超 90 天覆写销毁（走 v1.4.1 覆写标准）
- [ ] 磁盘超 80% 告警 + 清理建议
- [ ] `npm test` 全绿

## 七、进化引擎实证收口（自 v1.5.1 整版前移 · 2026-08-31 用户拍板）

### 四）技能进化提案审计与溯源（WikiSkill 机制收编 · Google Research arXiv:2608.27454）

> WikiSkill 三层架构（Raw 不可变轨迹/Wiki 永不回滚/Skills 可回滚）与 sofagent 的 history.jsonl+HMAC / 温故知新 / SKILL 体系同构，其消融实证（持久知识层 -15.0pt、推理时查知识库 -2.8pt）量化印证 sofagent「经验沉淀 + 约束层要轻」双哲学。本节收编其三个工程机制 + 门控闭环设计，行业印证详见 [DEVELOPMENT 九B](../../DEVELOPMENT.md#九b经验编译为持久知识wikiskill-印证)。

| 组件 | 能力 |
|------|------|
| **skill-impact 台账** | 技能进化每次提案的元数据/unified diff/验证分数/接受与否**程序化落账**（非 LLM 手写）——被拒提案不丢教训，Proposer 后续迭代查阅避免重复踩坑；与 LEDGER 记 run 互补，记的是「技能变更」这本账 |
| **PURPOSE 溯源** | SKILL.md frontmatter 增 `solves:` 字段——技能回链所解决的 pattern/问题（「为什么存在」），修改技能时先理解设计意图，而非对孤立 SKILL.md 盲目打补丁 |
| **门控量化** | 技能变更须过 eval 验证集、分数超历史最优才收编——接通 orchestrator 既有 eval 闭环与技能进化，进化引擎「过验证才发布」的最后一块 |
| **执行/进化上下文隔离** | 执行 Agent 与知识库隔离的显式约束——rollout 期禁查 Wiki（消融 -2.8pt：推理时查知识库反伤轨迹诊断价值），知识仅供进化者（Proposer/Maintainer）离线消费。落到 sofagent：任务执行中 history/lessons 只进不出，温故知新与 skill 进化提案都发生在任务边界之外，不塞运行时上下文 |

**涉及文件（预估）**：`engine/orchestrator/src/skill-evolution/`（台账与门控）/ `SKILL/` frontmatter 规范 / `docs/DEVELOPMENT.md` 九B 行业印证段。
