## 定位

> 商业产品层的多设备数据协同诉求：企业数据散落在**个人电脑（BYOD）**、**AI 节点设备**（Mac Mini 常驻）、**AI 模型一体机**（内置数据）上，平台要从这些设备读取数据做协同。**平台不直连设备**——设备侧必须有约束层承接：身份、授权、脱敏、审计、计量。本版把引擎层定位为多设备 Harness 中间层（承上启下：设备数据经治理后上平台，平台任务经治理后下设备）。
>
> **与 v1.4.7 平台接口版的关系**：v1.4.7 管「平台要的数据」（缺口/绩效/可见性/租户/账单——面向平台消费），v1.4.9 管「设备给的数据」（注册/心跳/授权读取/主动上行——面向设备供给）。两版合起来构成完整的平台-引擎-设备三层协同。
>
> **数据承接扩展**（2026-09-08 拍板）：一体机场景的第三类数据源——**模型网关 router**（基于开源项目自建，挡在千问等基座模型前面，过站流量含全部 session 上下文）。router 本体不在引擎开发范围（引擎内部另有 model-router.ts 调用侧路由，两者不冲突——一个是设备外置网关，一个是引擎内部路由），引擎交付**伴生 exporter 协议**：router 侧部署轻量 exporter，把过站 session/usage/路由决策按标准 schema 推给引擎，引擎承接后分拣→脱敏→数据集→蒸馏回流。至此设备数据三源齐备：G10 拉数据（平台发起）+ G11 推数据（设备发起）+ session 承接（router 伴生）。

| 设备类型 | 形态 | 引擎侧角色 |
|---------|------|-----------|
| **个人电脑（BYOD）** | 装用户侧 Agent（DSH / WorkBuddy），经 CLI + MCP 协同 | 任务执行端 + 数据源（经 G10 授权白名单读取） |
| **AI 节点设备** | Mac Mini 常驻一起跑 | 常驻执行节点：daemon 巡检 + 首部署 cron（G8）持续产出 + 计量出账 |
| **AI 模型一体机** | 内置模型 + 数据的盒子 | 本地推理 + 本地数据面（数据不出设备，只有脱敏后的结果/结论上行） |

## 一、设备注册/发现与心跳（G9 · MCP `device_register` / `device_list`）

### 扩展：设备侧健康巡检端点（商业平台机制对账 · 2026-09-08 排入）

> 📋 **背景**：商业平台机制文档 §9.2 安全表定义了「设备侧 AI 健康巡检协议」（对标 wemux health 端点），引擎侧零排期——随 G9（设备健康主题章）一并落地。心跳只回答「活着吗」，健康巡检回答「活得怎么样」。

- **`/health` 标准端点**：设备 daemon 暴露本地 HTTP 健康巡检端点（默认仅 loopback，绑定地址可配置）——返回结构化健康快照：引擎版本 / 模型可用性（注册表内逐模型可达探测）/ 磁盘水位 / 审计链尾部 HMAC 校验 / daemon 自身进程指标
- **巡检项分层**：`status: ok / degraded / down` 三态汇总 + 逐项明细（单项降级不整体误报 down）
- **与心跳的关系**：心跳（G9 主交付）携带健康摘要字段引用巡检结果——心跳管在线状态，巡检管健康状态，两者不合并
- **验收追加**：`/health` 返回结构化快照且三态判定可注入测试（单模型不可达 → degraded 而非 down）；loopback 默认绑定（外部不可达默认安全）

## 三、数据上行通道（G11 · 采集声明 opt-in → WAL 暂存 → 加密上行 → 审计计量）

### 定位

> G10 管「平台**拉**数据」（平台发起、白名单校验、拉取式读取），G11 管「设备**推**数据」（设备/节点侧发起、主动上报）。两类场景：① 一体机本地推理的**结果/结论上行**（原始数据不出设备，只有脱敏后的结论上平台）② AI 节点持续产出的**计量/心跳/审计摘要上行**（G8 首部署 cron 持续出账的云端回传）。地基已有八成——白名单授权（G10 同源）、WAL 断点续传（复用 `engine/orchestrator/src/durable/wal-writer.ts` / `wal-recovery.ts` 的 WAL 语义）、加密（AES-256-GCM v1.3.8）、审计（HMAC 链）、计量（worklog/cost）、设备身份（Ed25519 v1.3.1）——缺的是把这些散落能力补成**一等公民 tool 化**的上行通道。

### 交付

| 组件 | 能力 |
|------|------|
| **采集声明（opt-in）** | 设备配置声明「哪些数据可上行」（config.yml 采集清单：数据类别 + 频率 + 目的地，默认空 = 不上行，opt-in 模型与 G10 白名单同源） |
| **WAL 暂存** | 上行队列本地预写日志（复用 `engine/orchestrator/src/durable/wal-writer.ts` / `wal-recovery.ts` 的 WAL 语义，落 `wal.jsonl`）——断网/平台不可达时先落盘不丢，恢复后续传 |
| **断点续传** | 按 WAL 游标续传（offset + ack 确认，已确认段不重传） |
| **加密上行** | 出设备前 AES-256-GCM 加密（复用 v1.3.8 静态加密栈），平台侧验签解密 |
| **`device_data_push` MCP tool** | 上行通道 tool 化：手动/定时触发上行（daemon 定时器或 skill 侧显式调用），push 前过白名单校验 + 脱敏管线 |
| **审计留痕** | 每次上行进 audit history（谁/何时/推了什么/依据什么声明）——HMAC 链覆盖 |
| **计量进账** | 上行动作进 worklog + cost（上行数据量/次数进计量） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/core/src/device-upload-policy.ts` | 新建 | 采集声明解析 + 上行白名单判定（与 G10 device-data-policy 同源，默认空 = 不上行） |
| `engine/mcp/src/tools/device-data-push.ts` | 新建 | `device_data_push` tool（声明校验 → 脱敏 → 加密 → push） |
| `engine/daemon/src/upload-wal.ts` | 新建 | 上行 WAL 暂存 + 断点续传（复用 orchestrator `durable/wal-*` 的 WAL 语义；daemon 侧按 `long-tasks.ts` 同款「读 wal.jsonl、不跨包 import durable」纪律） |
| `engine/daemon/src/__tests__/upload-wal.test.ts` | 新建 | 单测（断网暂存 / 恢复续传 / 游标 ack / 越界拒绝） |
| `engine/core/src/__tests__/device-upload-policy.test.ts` | 新建 | 单测（空声明全拒 / 声明边界 / 目的地越界拒绝） |

### 验收标准

- [ ] 空采集声明设备对任何 push 请求返回拒绝（fail-closed）
- [ ] 声明内数据可上行、声明外拒绝

## 七、session 承接与 router 伴生（数据承接 · 2026-09-08 排入 · 自 v1.5.3 前移改写）

> 📋 **背景与拍板**：v1.5.3 原排「session 全量记录与蒸馏对接」以引擎自研 router 网关为前提；2026-09-08 用户拍板改向——**router 基于开源项目自建（非第三方托管），引擎不自研 router 本体**。引擎的职责是承接面：router 挡在基座模型前面收集的过站 session 是一体机最优质的训练数据源（真实业务对话 + 路由决策 + token 用量），引擎提供伴生 exporter 协议接住它。承接的数据**本地落盘**（数据主权铁律——记录不出企业边界），与 v1.5.3 原文「本地优先存储」语义一致。

## 八、敏感识别升级：检测器插槽 + 敏感度分类器 + NER 外挂协议（2026-09-08 排入 · 自 v1.5.3 前移 + 新编排）

> 📋 **背景**：现分拣闸（v1.4.6）是 5 组正则模式匹配，认不出「不含手机号/金额形态的客户名单」；现脱敏（v1.4.4 三类红名单）语义类靠人工录入实体名单。语义级识别需要模型推理——但引擎层纪律**只做管线不做模型推理**（分层架构：推理属模型层/企业侧）。解法：**插槽架构**——引擎建通用检测器接口与调度管线，内置正则检测器（零依赖默认档），外挂检测器（企业 NER 服务/Ollama 本地小模型/商业平台 NER API）经 endpoint 协议接入。敏感度分类器与 NER 脱敏**共用同一套检测器插槽**（一次建架构、两个消费面）。
>
> **可嵌入性（2026-09-08 补注）**：检测器插槽**设计为可独立消费的组件，不绑死在引擎进程内**——企业自建的模型网关/代理（如 LiteLLM 一类网关底座）可直接集成同一份分类器与检测器，在流量侧做 PII 过滤与敏感度分流。**网关侧与引擎侧共用一份规则定义，不各写一套**——避免判定口径分裂（同类教训见 v1.5.2 第九章双规则引擎统一）。注意分工：网关管「模型说了什么」（流量侧），约束层管「Agent 做了什么」（行为侧工具调用/git 变更/意图上下文），两者互补不替代。

## 十三、bugfix 修复批（已实施 · 2026-09-14）

> ⚠️ **本章为「已实施」修复批，非规划目标；上方一~十二章仍为规划态。** 本章逐条记录本轮 bugfix 批**已落地、当场可验证**的缺陷修复与门禁加固，写法为「问题 → 解决方案」，不含未实施项。

### 显式披露

> **自动演化路径恢复为行为恢复**：`isEvolveAvailable()` 原先探活 `evolve-gate`（全仓无此可执行）恒返回 `false`，把 native 默认路径整体挡死；修好探活即打开该路径，并暴露自指删除缺陷（`runEvolve` 曾把 `candidateDir`/`targetDir` 同传输入路径 ⇒ adopt 自指 copy 必 ENOENT 且 live 文件被删）。本版一并修掉。**属行为恢复：此前不可用 → 现可用**，发版入 CHANGELOG 索引时须并入本条。

### 行为恢复：自动演化路径

**问题**：探活面与调用面**对不上真实面却各自看起来正常**——探活 `evolve-gate`（全仓无此可执行）恒 false，调用 `skillopt-sleep`（外部兼容层真实名）；native 默认路径被恒 false 的探活整体挡死，**从未真正打开过**。打开后立即暴露一级数据丢失缺陷：`runEvolve` 把 `candidateDir`/`targetDir` 同传输入路径 ⇒ adopt 先 `rmSync(targetDir)` 再 `copyFileSync(candidateDir, targetDir)`，而两者同一路径 ⇒ **删源再拷已删的源** = `ENOENT` + **live 文件永久丢失**。

**解决方案**：
- 探活与调用**同源为单一常量** `LEGACY_GATE_CLI = 'skillopt-sleep'`；native 模式内置实现零外部依赖，`isEvolveAvailable()` 恒 true，不再因「外部 CLI 不在场」自降级（cli 模式仍真执行外部二进制看退出码）。
- `native-gate` adopt 改**无损替换** `replaceAtomically(src, dst)`：同路径 ⇒ no-op（不变式①）；异路径 ⇒ 先写**目标同目录**临时文件再 `renameSync`（同文件系统内原子替换，不变式②），消灭「目标已删、新内容未到」窗口。
- `runEvolve` 候选落 **staging 临时副本**（`mkdtempSync`）——技能目录只多出 `.gate-bak` / `.gate-history.json`；调用面加**防数据丢失锁**（L1 live 仍在 / L2 内容 ∈ {候选, 原文} / L3 adopt 后 `.gate-bak` 仍在），任一打破即 fail-loud 并尝试 `recoverLiveIfLost()` 从备份恢复。
- 顶层静态 `import { runNativeGate }` 替换原 `require('./native-gate')`——原写法在 vitest ESM 转换下不存在 ⇒ 该分支**直接抛错、从未被任何测试执行**（旧断言只查 `typeof === 'boolean'`，属零覆盖掩护，非「断言太弱」）；改静态 import 后回归锁才真跑。

### 门禁自愈（G-1 / G-2）

**问题**：`check-docs` 第 13 步接线断言**空转**——提取为空即静默跳过 ⇒ 恒绿（免费绿灯）；覆盖度行口径不统一、静默跳过不可见；发版窗口 `check-version` 非严格模式且 SOP 无 SKIP 逐条裁决步。

### P2-19 实测复核（与原始记载不符，以实测为准）

原记载为「链头锚点写入 fail-open ⇒ 需降级为至少 WARN 级用户可见输出」。**实测不支持该前提**——WARN 级告警**早已在位**，且读侧另有可见面；fail-open 亦非疏漏而是**刻意的设计取舍**。

**（i）降级告警已存在**（非待补项）：

- `engine/audit/src/audit-history.ts:499` — `} catch (e) {`
- `engine/audit/src/audit-history.ts:500-501` 注释原文：「fail-open：锚点写入失败不阻断审计主链路（与 appendHistory 既有取舍一致），仅告警——本次追加后尾部截断检测退化为「无锚点 = 跳过」的旧行为」
- `engine/audit/src/audit-history.ts:502` — `console.warn(\`[sofagent] 链头锚点写入失败（尾部截断检测本次不可用）: ${e instanceof Error ? e.message : String(e)}\`)`
- 同族另有 `engine/audit/src/audit-history.ts:601`：`console.warn(\`[sofagent] 链头锚点删除失败（请手动清理，否则可能误报历史截断）: …\`)`

即 `console.warn`（stderr，默认可见）已在位，「至少 WARN 级用户可见输出」这一要求**已满足**。

**（ii）读侧另有可见面，且「跳过」只针对文件不存在**：

- `engine/core/src/audit-history.ts:307-310` 注释原文：「finding-02 尾部截断防护——链头锚点校验（读侧）。… 判定顺序：**不可读 → unverifiable（黄）**；条数不足/锚位哈希不符 → tampered（红）」
- `engine/core/src/audit-history.ts:242-244` 注释原文：「锚点文件不存在时跳过，向后兼容。诚实边界：能同时重写 history.jsonl 与锚点文件的攻击者仍可伪造一致状态——锚点属防篡改证据强化而非密码学保证」

⇒ 锚点**存在但不可读**会落 `unverifiable`（黄，用户可见）；只有**文件不存在**（含本项 fail-open 后的退化态）才跳过，且这是为兼容锚点引入之前的历史而设。

**（iii）升 FAIL 会阻断审计主链**：该 `catch` 位于 `appendHistory` 的**追加路径内**——抛出即让**每次审计记录的写入**失败，等于以「丢审计留痕」换「锚点可用」，方向与「留痕优先」的核心取舍相反；且 fail-open 的退化是**有界**的（退回锚点引入前的旧行为，非静默数据丢失）。

⇒ 裁定：**不改本批**。若后续要提升该场景的可见性，方向应是读侧区分「锚点从未存在」与「锚点曾存在但已丢失」，而非把写侧改为 FAIL。
