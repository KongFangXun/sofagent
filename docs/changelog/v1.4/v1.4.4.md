## 一、训练语料导出三件套（规则 + 方法论 + 样本 · 训练信号）

> 🔗 **2026-08-10 归集**：原 v1.3.2「训练语料导出 MVE」+ 原 v1.3.6「训练语料导出三件套」合并为本章（MVE 与完整版同版交付，不再拆分）。依赖 v1.3.0 decision-log（已交付）+ v1.3.1 llm-calls/evaluation-log + v1.3.2 Trace 任务级轨迹（样本富矿）。

开源侧已有丰富的现成语料——GUIDE 方法论、SKILL 加载链、24 条审计规则、25+ 案例——本版把它们全部机器可读化，成为可喂给训练管线的训练信号：

| 语料 | 来源 | 交付 |
|------|------|------|
| **规则定义** | 24+3 条审计规则（TS 代码内聚） | 序列化导出（JSON/YAML 双格式）+ 版本化 + HMAC 签名 |
| **FDE 方法论** | `FDE/GUIDE.md`（五要素/三问判定/量化公式）+ SKILL 加载链 | 结构化导出（markdown → JSON 摘要 + 原文）+ **结构化锚点维护机制**（`<!-- METHODOLOGY: five-elements -->`，GUIDE 更新后重导即同步） |
| **带标签审计样本** | decision-log + llm-calls + evaluation-log + **runtime-audit** + **fde-session（FDE 服务轨迹 · 2026-08-23 新增第五源）** + Trace 轨迹 | 聚合导出（脱敏 + 按任务分组 + 标签）——**runtime-audit 含工具调用 + FAIL/PASS/HITL 判定，是 RL「行为 → 奖励信号」对应数据；fde-session 含 FDE 进场梳理的关键决策+理由（自举：训练自己的 FDE 模型的最佳语料，见 v1.4.1 训练 Agent 化）；Trace 轨迹提供任务级完整序列** |

**样本是训练信号里最值钱的部分**——真实的 FAIL/通过案例 = 带标签的「什么是对的」，对应 self-recording improvement（模型协作产生 trace → 用 trace 训练）。

### 规则 → reward/verifier 映射（样本到 reward 配方的最后一公里 · 2026-08-26 补）

> 📋 **2026-08-26 补充**：三件套导出了**样本**（什么行为被判 FAIL/PASS），但 RL 训练还需要 **reward 定义**（用什么函数给行为打分）。sofagent 的天然优势：24+3 条审计规则的判定逻辑本身就是机器可执行的 verifier——**规则导出（第一件）从「给人看的规则定义」升级为「可挂进训练循环的 reward 骨架」**。

| 组件 | 能力 |
|------|------|
| **规则 → reward 骨架导出** | 每条审计规则导出时附带 `reward_hint` 段：判定函数签名（输入=工具调用序列/产物文本，输出=PASS/FAIL 三态）+ 严重度权重 + 可判定性标注（机器可判 / 需人审 / 启发式） |
| **verifier 清单** | 规则导出附 `verifiers.json`——哪些规则可直接当 reward 函数（机器可判类）、哪些只能当训练后验收（需人审类）——训练管线按清单接线，不混用 |
| **与 RL 配方模板衔接** | reward 骨架 + v1.4.3 RL 配方模板（grpo/dapo/cispo）= 完整训练配置——商业侧「reward 配方」的开源对应物（开源导骨架，商业侧调权重） |

**边界（不做）**：本版只导「规则 → reward 骨架」的映射格式与清单，**不实现训练循环本身**（那是计算面，复用开源框架——v1.4.1 拍板的「轮子全复用」边界）；也不做自然语言指令直转权重（self-distillation 属商业模型层）。

### 通用脱敏管线（业务语义脱敏）

现役脱敏只有 A2 规则的**格式匹配**（AKIA / sk- / ghp_ / PEM 块）+ decision-log `sanitizeWhy`——企业业务语义脱敏（客户名/内部代号/API 响应体业务字段）无通用管线。本版新增 `engine/core/src/export/redactor.ts`：

- **规则配置**：`redact-rules.json`——正则 + 实体名 + 占位符映射（`{CUSTOMER_NAME}`, `{INTERNAL_CODE}`）
- **三类红名单**：格式类（复用 A2 检测）/ 语义类（实体名库，FDE 梳理辅助可录入）/ 结构类（API 响应体字段）
- **验收**：样本导出后 grep 原始企业专有名词 0 命中

### 合规红线（仅脱敏聚合，不落个体级数据）

| 红线 | 规则 |
|------|------|
| **不落个体级数据** | 样本导出仅脱敏聚合，可反推具体企业/具体请求的原始字段一律剥离 |
| **字段白名单** | 可导出：ruleId / ruleType / severity / token 数 / 耗时 / 失败码 / 脱敏后的文本模式 |
| **字段黑名单** | 禁止导出：原始 API 响应体 / 密钥类值 / 企业专有名词 / 用户可识别信息 / 未脱敏代码片段 |
| **导出审计** | 每次导出记 `corpus_export` 事件（谁导的、范围、签名）——导出行为本身受审计 |

### FDE 梳理 → 语料导出衔接（人工基准 = ground truth）

v1.3.2 FDE 梳理辅助产出的 workflow.yml 草稿 + 五要素 + 量化四字段，是企业 eval「访谈替代率」的人工基准（ground truth）——随语料导出（标记 `source: 'human-fde'`，人工基准样本）。

## 三、训练产物 → 模型注册自动衔接（训练闭环的最后一步）

> 📋 **2026-08-10 补充（架构审查新发现）**：训练引擎的「训练完成」和 v1.3.6 的「模型注册」是**断的**——训练完的权重产物不会自动进 `model_register`，差一个自动衔接动作。缺了它，训练引擎闭环不完整（train → eval → 部署 三环节断裂）。

### 交付

```
train job 完成（v1.4.1）
  → eval 通过（v1.4.2 阈值判定）
  → 权重产物打包（第二章目录规范）
  → 自动调 model_register（v1.3.6 ④，source: 'local-path'）
  → model_switch 挂载到 workflow 节点（灰度比例）
  → 全程 train_job + model_registry 审计留痕
```

| 组件 | 能力 |
|------|------|
| **训练产物注册器** | train done + eval pass → 自动调 `model_register`（幂等：同权重版本不重复注册） |
| **挂载建议** | 注册后给出 `model_switch` 建议（哪个 workflow 节点可挂载）——人工确认后执行（晋升强制人审，对齐 v1.3.5） |

> 🔗 **商业平台接口预留 G1（2026-08-17 补充）**：本版「训练产物 → 模型注册自动衔接」与商业产品层的 workflow 模板注册同类机制（商业平台接口规划 §9.1 G1）——商业平台跨企业 fork 需要 `workflow_export`/`workflow_import`（workflow 模板导出/导入 + 血缘追踪），挂靠本版的注册器模式扩展：**模型可注册，workflow 模板同样可注册**（模板元数据加血缘字段，记录「此模板来自哪个企业/哪个 fork」）。**本版先打通模型注册，workflow 模板注册随商业平台 SaaS 需要再补**。

## 五、决策因果链与先例检索（Semantica 启发 · 2026-08-29 排入）

> 🔗 **参照而非依赖**（2026-08-29 拍板）：Semantica（semantica-agi/semantica，Python/MIT/5.5k+ stars）的核心设计「决策不是日志行，是一等公民图节点」值得吸收，但其 Python 栈（gensim/FAISS/Oxigraph）与 sofagent 纯 TS 零重依赖定位冲突——**只参照设计，不引入依赖**。本版把 decision-log 从「完整性很强但无因果边」升级为可查因果链的结构。

### 定位

> decision-log.jsonl 的 HMAC 链保证**完整性**（防篡改），但决策之间没有因果关联——审查者看到的是一串孤立判定。Semantica 的 `CAUSED / INFLUENCED / PRECEDENT_FOR` 三种因果边映射到 sofagent：拦截决策引用触发它的路由决策、HITL 决策引用待审的上游决策。**审计叙事从「每条自证清白」升级为「决策链可追溯」**。

### 交付

| 组件 | 能力 |
|------|------|
| **决策因果边** | `DecisionLogEntry` 加可选字段 `causedBy?: string[]`（引用前序 decisionId）+ `causalType?: 'caused' \| 'influenced' \| 'precedent_for'`——写入时由触发链路带上（拦截→路由、HITL→待审项），HMAC 计算含新字段 |
| **因果链查询** | decision-query 扩展 `traceDecisionChain(id)`——沿 causedBy 回溯至根因，输出链式叙事（A 导致 B，B 触发 C 拦截） |
| **先例检索** | decision-query 扩展 `findSimilarDecisions(query)`——按 `DecisionWhy.tags + triggeredRule` 结构化匹配（不用向量，字段已有，零新依赖）；HITL 审批界面展示「历史类似决策 + 结果」 |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/audit/src/decision-schema.ts` | 修改 | 加 `causedBy` / `causalType` 可选字段（旧条目无此字段照常校验——向后兼容） |
| `engine/audit/src/decision-query.ts` | 修改 | 加 `traceDecisionChain` / `findSimilarDecisions` 查询 |
| `engine/audit/src/__tests__/decision-query.test.ts` | 修改 | 因果链回溯 + 先例匹配用例 |

### 验收标准

- [ ] 旧 decision-log（无 causedBy 字段）加载与链校验不破坏（向后兼容）
- [ ] traceDecisionChain 能回溯多级因果链并输出人类可读叙事
- [ ] findSimilarDecisions 按 tags + triggeredRule 匹配，HITL 场景可展示先例
- [ ] HMAC 计算涵盖新字段（链完整性不因 schema 扩展而弱化）
