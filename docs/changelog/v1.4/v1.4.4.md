## 一、训练语料导出三件套（规则 + 方法论 + 样本 · AIR 训练信号）

> 🔗 **2026-08-10 归集**：原 v1.3.2「训练语料导出 MVE」+ 原 v1.3.6「训练语料导出三件套」合并为本章（MVE 与完整版同版交付，不再拆分）。依赖 v1.3.0 decision-log（已交付）+ v1.3.1 llm-calls/evaluation-log + v1.3.2 Trace 任务级轨迹（样本富矿）。

AIR §5.3 冷启动自述「开源 GUIDE / SKILL / 24 条规则 / 25 个案例就是第一版现成语料」——本版把三类语料全部机器可读化：

| 语料 | 来源 | 交付 |
|------|------|------|
| **规则定义** | 24+3 条审计规则（TS 代码内聚） | 序列化导出（JSON/YAML 双格式）+ 版本化 + HMAC 签名 |
| **FDE 方法论** | `FDE/GUIDE.md`（五要素/三问判定/量化公式）+ SKILL 加载链 | 结构化导出（markdown → JSON 摘要 + 原文）+ **结构化锚点维护机制**（`<!-- METHODOLOGY: five-elements -->`，GUIDE 更新后重导即同步） |
| **带标签审计样本** | decision-log + llm-calls + evaluation-log + **runtime-audit 四源** + Trace 轨迹 | 聚合导出（脱敏 + 按任务分组 + 标签）——**runtime-audit 含工具调用 + FAIL/PASS/HITL 判定，是 RL「行为 → 奖励信号」对应数据；Trace 轨迹提供任务级完整序列** |

**样本是训练信号里最值钱的部分**——真实的 FAIL/通过案例 = 带标签的「什么是对的」，对应 self-recording improvement（模型协作产生 trace → 用 trace 训练）。

### 通用脱敏管线（业务语义脱敏）

现役脱敏只有 A2 规则的**格式匹配**（AKIA / sk- / ghp_ / PEM 块）+ decision-log `sanitizeWhy`——企业业务语义脱敏（客户名/内部代号/API 响应体业务字段）无通用管线。本版新增 `engine/core/src/export/redactor.ts`：

- **规则配置**：`redact-rules.json`——正则 + 实体名 + 占位符映射（`{CUSTOMER_NAME}`, `{INTERNAL_CODE}`）
- **三类红名单**：格式类（复用 A2 检测）/ 语义类（实体名库，FDE 梳理辅助可录入）/ 结构类（API 响应体字段）
- **验收**：样本导出后 grep 原始企业专有名词 0 命中

### 合规红线（对齐 AIR §6.7 Q7）

| 红线 | 规则 |
|------|------|
| **不落个体级数据** | 样本导出仅脱敏聚合，可反推具体企业/具体请求的原始字段一律剥离 |
| **字段白名单** | 可导出：ruleId / ruleType / severity / token 数 / 耗时 / 失败码 / 脱敏后的文本模式 |
| **字段黑名单** | 禁止导出：原始 API 响应体 / 密钥类值 / 企业专有名词 / 用户可识别信息 / 未脱敏代码片段 |
| **导出审计** | 每次导出记 `corpus_export` 事件（谁导的、范围、签名）——导出行为本身受审计 |

### FDE 梳理 → 语料导出衔接（人工基准 = C12 ground truth）

v1.3.2 FDE 梳理辅助产出的 workflow.yml 草稿 + 五要素 + 量化四字段，是 AIR C12 eval「访谈替代率」的 ground truth——随语料导出（标记 `source: 'human-fde'`，人工基准样本）。

## 三、训练产物 → 模型注册自动衔接（训练闭环的最后一步）

> 📋 **2026-08-10 补充（架构审查新发现）**：训练引擎的「训练完成」和 v1.3.6 的「模型注册」是**断的**——训练完的权重产物不会自动进 `model_register`，差一个自动衔接动作。缺了它，训练引擎闭环不完整（train → eval → 部署 三环节断裂）。

### 交付

```
train job 完成（v1.4.1）
  → eval 通过（v1.4.2 阈值判定）
  → 权重产物打包（第二章目录规范）
  → 自动调 model_register（v1.3.6 ④，source: 'local-path'）
  → model_switch 挂载到 workflow 节点（灰度比例）
  → 全程 train_job + model_registry 审计留痕
```

| 组件 | 能力 |
|------|------|
| **训练产物注册器** | train done + eval pass → 自动调 `model_register`（幂等：同权重版本不重复注册） |
| **挂载建议** | 注册后给出 `model_switch` 建议（哪个 workflow 节点可挂载）——人工确认后执行（晋升强制人审，对齐 v1.3.5） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/train/artifact-register.ts` | 新建 | 训练产物 → model_register 自动衔接 |
| `engine/orchestrator/src/__tests__/artifact-register.test.ts` | 新建 | 单测（eval pass → 自动注册 + 幂等） |

### 验收标准

- [ ] train done + eval pass → 自动调 `model_register`（权重产物）
- [ ] 幂等：同权重版本不重复注册
- [ ] 挂载建议给出（人工确认后 model_switch）
- [ ] `npm test` 全绿

## 四、多基座对比训练（train compare · 选型数据支撑）

> 📋 **2026-08-10 补充（训练引擎完善 · 阶段 2 选型前置）**：AIR-post-training §5 有两个待测对比——**Qwen3 vs R1-Distill**、**7B vs 14B**（eval 分数 ÷ 训练/部署成本 = ROI）。本版把「同一数据多基座并行训练 → 对比报告」做成引擎能力，选型不用手跑实验。

### 交付

| 组件 | 能力 |
|------|------|
| **对比训练** | `train compare --bases qwen3-8b,r1-distill-7b` → 同一数据并行提交多个 train job（同数据 hash / 同超参模板） |
| **对比报告** | 各基座 eval 分数 + 训练/部署成本 → ROI 排序（复用 v1.4.2 train report） |
| **GPU 调度** | 对比任务走 v1.4.3 GPU 队列（串行 or 预算并发） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/train/train-compare.ts` | 新建 | 多基座对比（并行提交 + 汇总） |
| `engine/orchestrator/src/__tests__/train-compare.test.ts` | 新建 | 单测（同数据多基座 → ROI 排序） |

### 验收标准

- [ ] `train compare` 同数据多基座并行提交（同 hash / 同模板）
- [ ] 对比报告含 eval 分数 + 成本 + ROI 排序
- [ ] 对比任务走 GPU 队列（不 OOM）
- [ ] `npm test` 全绿
