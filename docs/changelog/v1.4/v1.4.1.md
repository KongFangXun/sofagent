## 一、双栈架构决策（Node 控制面 + Python 执行面）

### 背景：Node/TS 后训练生态调研（2026-08-10 实测）

主流生产后训练框架（verl / TRL / NeMo RL / Oumi / open-instruct）在 2026 年**全部是 Python**（PyTorch + CUDA 生态决定，Node 无法绕过）。唯一纯 Node 方案：

| 方案 | 生态 | 硬约束 | 用途 |
|------|:---:|------|------|
| **@mlx-node/trl**（npm） | ✅ Node 18+ | **仅 Apple Silicon（M1+）Metal GPU**，SFT/GRPO/DPO + 内置 reward + checkpoint | **个人 Mac 阶段 0 验证**（reward 规则 → 收敛），不用于客户交付 |
| verl / TRL / NeMo RL / Oumi | ❌ Python | CUDA GPU（x86 + 4090 等） | **生产 + 客户交付（C13）**，不可替代 |

### 决策

**双栈不可避免，但用「Node 控制面 + Python 执行面」控制**——业界标准做法（NeMo RL 自己也是 Ray 控制面 + Megatron 训练后端）：

```
Node 控制面（本版全部）                        Python 执行面（外部框架）
  train submit ──→ spawn ──→ train.py（Oumi/verl/TinyZero 脚本）
  train 监控 ◄──── 日志流/事件 ──┘
  train 审计 / 沙箱 / 生命周期（Node 主场）
```

- **编排 / 审计 / 生命周期 / 沙箱全在 Node**（像 dag-runner 管 Agent 一样管 train job）
- **Python 只当被 spawn 的训练子进程**——接口 = 进程参数 + JSON 事件 + 日志流，双栈解耦
- **个人 Mac 阶段 0 用 @mlx-node/trl 纯 Node 跑通验证路径**（reward 规则 → 收敛），验证通过后再无缝换 Python 框架做生产——**阶段 0 不用碰 Python**，省掉学习成本

## 二、训练任务编排层（train-job 生命周期 · 引擎骨架）

### 痛点

没有编排层，Oumi 只是「客户自己会的工具」不是「我们交付的能力」——「提供训练管线」交付模式直接缺地基。与 dag-runner 管 Agent 同构：训练任务也是一种长任务。

### 交付

| 组件 | 能力 |
|------|------|
| **train submit** | 提交训练任务（数据路径 + 基座 + 算法 SFT/DPO/GRPO + 超参）→ 生成 train job 实例（trainJobId） |
| **train 监控** | 训练进度（step/epoch/loss/reward 曲线）实时可查——事件流从 Python 子进程回流 |
| **train 取消 / 重跑** | 任务可取消、可带 checkpoint 续跑（复用 v1.3.1 Durable Execution checkpoint 语义） |
| **train 生命周期** | queued → running → checkpointing → completed / failed / cancelled，状态机 + 幂等 |
| **checkpoint 管理** | 训练产物（checkpoint / LoRA adapter / 量化权重）目录规范 + 版本清单（衔接 C13 本地权重部署） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/train/train-job.ts` | 新建 | train job 数据模型 + 状态机 |
| `engine/orchestrator/src/train/train-scheduler.ts` | 新建 | 任务编排（提交/监控/取消/续跑）——spawn Python 子进程 + 事件回流 |
| `engine/mcp/src/tools/train-submit.ts` | 新建 | MCP `train_submit` tool |
| `engine/orchestrator/src/__tests__/train-job.test.ts` | 新建 | 单测（状态机 + 幂等 + checkpoint 续跑） |

### 验收标准

- [ ] `train_submit` 提交 → train job 状态机流转（queued → running → completed）
- [ ] 训练进度事件流回流（step/loss/reward 可查）
- [ ] 取消 / checkpoint 续跑可用（幂等，不重复消费）
- [ ] 训练产物目录规范落地（衔接 C13 权重部署）
- [ ] `npm test` 全绿

### 交付

```
workflow 节点（如「产线校准」）
  → 训练目标（预测校准参数？分类缺陷？）

```

## 八、训练语料导出三件套（从 v1.3.x 并入 · 完整版）

> 🔗 **2026-08-10 归集**：原 v1.3.2「训练语料导出 MVE」+ 原 v1.3.6「训练语料导出三件套」合并为本章（MVE 与完整版同版交付，不再拆分）。依赖 v1.3.0 decision-log（已交付）+ v1.3.1 llm-calls/evaluation-log + v1.3.2 Trace 任务级轨迹（样本富矿）。

AIR §5.3 冷启动自述「开源 GUIDE / SKILL / 24 条规则 / 25 个案例就是第一版现成语料」——本版把三类语料全部机器可读化：

| 语料 | 来源 | 交付 |
|------|------|------|
| **规则定义** | 24+3 条审计规则（TS 代码内聚） | 序列化导出（JSON/YAML 双格式）+ 版本化 + HMAC 签名 |
| **FDE 方法论** | `FDE/GUIDE.md`（五要素/三问判定/量化公式）+ SKILL 加载链 | 结构化导出（markdown → JSON 摘要 + 原文）+ **结构化锚点维护机制**（`<!-- METHODOLOGY: five-elements -->`，GUIDE 更新后重导即同步） |
| **带标签审计样本** | decision-log + llm-calls + evaluation-log + **runtime-audit 四源** + Trace 轨迹 | 聚合导出（脱敏 + 按任务分组 + 标签）——**runtime-audit 含工具调用 + FAIL/PASS/HITL 判定，是 RL「行为 → 奖励信号」对应数据；Trace 轨迹提供任务级完整序列** |

**样本是训练信号里最值钱的部分**——真实的 FAIL/通过案例 = 带标签的「什么是对的」，对应 self-recording improvement（模型协作产生 trace → 用 trace 训练）。

### 通用脱敏管线（业务语义脱敏）

现役脱敏只有 A2 规则的**格式匹配**（AKIA / sk- / ghp_ / PEM 块）+ decision-log `sanitizeWhy`——企业业务语义脱敏（客户名/内部代号/API 响应体业务字段）无通用管线。本版新增 `engine/core/src/export/redactor.ts`：

- **规则配置**：`redact-rules.json`——正则 + 实体名 + 占位符映射（`{CUSTOMER_NAME}`, `{INTERNAL_CODE}`）
- **三类红名单**：格式类（复用 A2 检测）/ 语义类（实体名库，FDE 梳理辅助可录入）/ 结构类（API 响应体字段）
- **验收**：样本导出后 grep 原始企业专有名词 0 命中

### 合规红线（对齐 AIR §6.7 Q7）

| 红线 | 规则 |
|------|------|
| **不落个体级数据** | 样本导出仅脱敏聚合，可反推具体企业/具体请求的原始字段一律剥离 |
| **字段白名单** | 可导出：ruleId / ruleType / severity / token 数 / 耗时 / 失败码 / 脱敏后的文本模式 |
| **字段黑名单** | 禁止导出：原始 API 响应体 / 密钥类值 / 企业专有名词 / 用户可识别信息 / 未脱敏代码片段 |
| **导出审计** | 每次导出记 `corpus_export` 事件（谁导的、范围、签名）——导出行为本身受审计 |

### FDE 梳理 → 语料导出衔接（人工基准 = C12 ground truth）

v1.3.2 FDE 梳理辅助产出的 workflow.yml 草稿 + 五要素 + 量化四字段，是 AIR C12 eval「访谈替代率」的 ground truth——随语料导出（标记 `source: 'human-fde'`，人工基准样本）。
