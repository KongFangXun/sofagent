# v1.4.0 开发日志 — SubAgent 完整沙箱 + 场景驱动权限 + 代理网关 + 数据静态加密 + Durable L3

> 📋 **规划中。** 前置依赖：v1.3.4（L3 组织能力市场）
> 状态：规划中 · 孔放勋 · 2026-08-02

## 背景

v1.3.x 完成运行时审计最小闭环（middleware 层）+ 多设备协同三刀（身份码 → L2 协作 → L3 能力市场）后，v1.4.0 是**执行层隔离的完整版本**——审计从「事后」+「middleware 运行时」扩展到「沙箱级策略强制」。同时补齐 Durable Execution L3（完整 WAL）。

四条主线：
1. **SubAgent 完整沙箱执行环境**：虚拟文件系统 + 网络白名单 + 工具中介 + 虚拟凭证
2. **场景驱动权限体系**：权限按场景动态判定
3. **代理网关硬边界**：SubAgent 所有外部请求经网关
4. **数据静态加密**：审计数据 age 加密落盘
5. **Durable Execution L3**：完整 WAL（write-ahead log）

> **范围限定**：v1.4.0 沙箱/权限/网关/加密**限定 SubAgent**，主 Agent 仍事后审计。主 Agent 的运行时策略强制留 v1.5.0+。

## 一、SubAgent 完整沙箱执行环境

### 痛点

v1.3.0 的运行时审计是 **middleware 层**——包在 createReactAgent 外面，记录工具调用 + 审计日志。但 middleware 是**观测层**，不是**隔离层**。SubAgent 调用 `fs.writeFileSync` 时，middleware 能记录并告警，但**不能阻止文件被写入磁盘**——等审计 FAIL 时文件已经写了。

v1.4.0 把审计从「记录+告警」升级为「**前置 allow/deny + 虚拟执行**」。

### 交付

| 组件 | 能力 | 对标 |
|------|------|------|
| **虚拟文件系统** | FilesystemBackend + virtualMode——SubAgent 写文件先写虚拟层，审批后才合并到物理磁盘 | bubblewrap / seatbelt |
| **网络出站白名单** | SubAgent 网络请求经白名单过滤，非白名单域名 deny | EnkryptAI Secure MCP Gateway |
| **工具调用中介** | 前置 allow/deny（非仅审计追踪）——高危工具调用在执行前拦截 | OpenWorker 权限模型 |
| **虚拟 key 凭证边界** | SubAgent 拿到的 API key 是虚拟 key，限速 + 限定 scope，不接触真实 key | LiteLLM 控制平面 |
| **AsyncSubAgent** | 远程 Agent Protocol 服务端——SubAgent 可在独立进程/容器运行 | Agent Protocol 标准 |
| **真·实时 A/B 双跑** | A/B SubAgent 在隔离环境同时执行，实时 diff 而非串行对比 | FORGE fresh-eyes 升级 |

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/sandbox/filesystem-backend.ts` | 新建 | 虚拟文件系统层 |
| `engine/orchestrator/src/sandbox/network-gateway.ts` | 新建 | 网络出站白名单过滤 |
| `engine/orchestrator/src/sandbox/tool-gate.ts` | 新建 | 前置 allow/deny 拦截器 |
| `engine/orchestrator/src/sandbox/virtual-key.ts` | 新建 | 虚拟凭证管理 |

| `engine/orchestrator/src/__tests__/sandbox/*.test.ts` | 新建 | 沙箱全套测试 |

### 沙箱与 v1.3.0 middleware 的关系

```
v1.3.0: createReactAgent → wrapToolCall middleware（记录+告警）→ 工具执行 → 物理磁盘
v1.4.0: createReactAgent → wrapToolCall middleware → 沙箱层（allow/deny + 虚拟执行）→ 审批 → 物理磁盘
```

v1.3.0 的 middleware **不删除**——它变成沙箱的「审计记录层」，沙箱是「执行隔离层」。两者叠加。

### 边契约「证据流 + 数据流」补全（从 v1.2.5 P6 拆入）

> 来源：v1.2.5 规划 P6「五类边契约形式化」。v1.2.5 瘦身时降级——权限流 + 失败流已在 v1.3.0 wrapToolCall 自然落地，剩余两类边随本版沙箱补全：
> - **证据流**：虚拟文件系统审批后才合并到物理磁盘（write → virtual → audit → approve → physical），每步输出留不可篡改审计记录——这正是"证据流"边契约的工程实现
> - **数据流契约**：虚拟 key 限速 + scope 约束 = 数据流边契约的显式化（SubAgent 拿到的凭证限定了它能访问的数据域，不再是隐式约定）

## 二、场景驱动权限体系（原 v1.2.5 拆入）

### 交付

权限按「场景」（任务类型 × 数据域 × 动作风险等级）动态判定：

```
判定链：身份（v1.3.1）→ 场景匹配 → 风险等级 → 放行/deny/人工批准
```

| 维度 | 说明 | 示例 |
|------|------|------|
| 任务类型 | 代码开发 / 数据处理 / 报表生成 / 测试 | 代码开发场景可写 .ts 文件 |
| 数据域 | 代码 / 配置 / 审计数据 / 用户数据 | 用户数据场景禁写审计数据 |
| 动作风险等级 | 读（低）/ 写（中）/ 删（高）/ 外传（极高） | 极高风险 → 人工批准 |

**包含**：团队场景权限（v1.3.3 L2 协作）+ 市场调用权限（v1.3.4 L3 市场）+ 动态提权到期回收。

## 三、代理网关硬边界（原 v1.2.5 拆入）

### 交付

SubAgent 所有外部请求经网关（唯一出入口）：

```
SubAgent → 代理网关 → {allow/deny + 风险分级 + 超阈值人工批准} → 外部服务
```

| 能力 | 说明 |
|------|------|
| allow/deny | 域名白名单 + 路径白名单 |
| 风险分级 | 低（GET 公开 API）/ 中（POST 业务 API）/ 高（写数据库）/ 极高（转账/删除） |
| 超阈值人工批准 | 极高风险请求暂停，等 human_confirm |
| 审计日志 | 所有请求 + 决策 + 结果落 JSONL |

### 与 §一沙箱的关系

沙箱是「SubAgent 侧」的隔离（虚拟文件系统 + 工具中介），网关是「外部侧」的隔离（唯一出口）。两者构成**双向边界**：

```
[SubAgent 沙箱] ←→ [sofagent 引擎] ←→ [代理网关] ←→ [外部服务]
```

## 四、数据静态加密（age）

### 痛点

`~/.sofagent/data/` 审计数据当前明文落盘。合规场景（尤其受监管行业）要求静态加密。

### 交付

使用 [age](https://age-encryption.org/)（现代文件加密工具）对审计数据加密落盘：

- 加密范围：`data/audit/` + `data/forge-runs/` + `data/checkpoint/`
- 密钥管理：本地 keypair（`~/.sofagent/keys/`），可选 passphrase 保护
- 透明读写：sofagent 引擎读写时自动加密/解密，用户不感知
- Dashboard 查看：通过引擎 API 读（自动解密），不直接读文件

## 五、Durable Execution L3：完整 WAL（write-ahead log）

### 背景

v1.3.1 交付了 Durable Execution L1（graph 状态恢复）+ L2（工具幂等性）。L3 是完整的事务级 WAL——所有工具调用**先写日志再执行**，类数据库事务机制。

### 与 L1+L2 的区别

| 层 | 机制 | 恢复粒度 | 版本 |
|----|------|---------|:----:|
| L1 | graph checkpoint | 节点级（恢复到中断节点） | v1.3.1 |
| L2 | 副作用登记簿 | 工具级（已执行的跳过） | v1.3.1 |
| **L3** | **WAL（write-ahead log）** | **事务级（全回放或全回滚）** | **v1.4.0** |

### WAL 工作流程

```
工具调用请求：
  1. WAL 先写 {taskId, tool, params, expectedSideEffects} 到 wal.jsonl
  2. 执行工具
  3. 成功 → WAL 写 {taskId, status:"committed", actualSideEffects}
  4. 失败 → WAL 写 {taskId, status:"aborted", reason}

崩溃恢复：
  1. 扫描 wal.jsonl
  2. committed 但未确认 → 验证副作用是否生效
  3. aborted → 回滚（调用 undo 函数或 git restore）
  4. 未完成 → 重新执行或跳过（按幂等策略）
```

### 为什么放 v1.4.0

v1.4.0 有**代理网关**——所有工具调用必经网关。WAL 写在**网关层**最干净：

```
SubAgent → wrapToolCall middleware → [沙箱层] → 代理网关[WAL 写入点] → 外部服务
```

v1.3.1 的 L1+L2 写在 middleware 层（观测层），v1.4.0 的 L3 写在网关层（执行层）。两层分离，职责清晰。

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/durable/wal-writer.ts` | 新建 | WAL 写入（append-only JSONL） |
| `engine/orchestrator/src/durable/wal-recovery.ts` | 新建 | WAL 崩溃恢复（扫描 + 回放/回滚） |
| `engine/orchestrator/src/durable/undo-registry.ts` | 新建 | 工具 undo 函数注册表（可逆操作回滚） |
| `engine/orchestrator/src/sandbox/network-gateway.ts` | 修改 | 网关层集成 WAL 写入 |

### 难度

⭐⭐⭐⭐（较高）。~1500 行+。难点不在 WAL 本身，而在 **undo 函数**——不是所有操作都可逆：
- ✅ 可逆：git 操作（git restore）、文件写入（删掉新写的）
- ⚠️ 部分可逆：PR 创建（关闭 PR）、飞书消息（撤回，2 分钟内）
- ❌ 不可逆：邮件发送、webhook 触发（已消费）
- 不可逆操作策略：WAL 标记 `irreversible: true` + 审计告警 + 不回滚（已发生的事实不篡改）
