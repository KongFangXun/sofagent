## 💰 成本审计（ccteam 启发 · 正交新维度 · WARN only）

> 📖 **来源**：ccteam——每会话追踪 token + 费用、每日预算上限、钱花完自动停工。sofagent 的 A1-A23 审的是 git diff **行为**（改了什么文件、有没有越权），完全不审**成本**。企业部署 Agent，「失控烧钱」和「越权改文件」是同等级风险。本版补这个盲区。

### 核心设计决策：WARN only，不拦截

成本超支**不阻断任务执行**——企业 Agent 跑着跑着超预算了，任务还得做完，不能因为"钱花完了"就中途扔了半截工作。

| 维度 | 做不做 | 理由 |
|------|:--:|------|
| 超支告警（WARN） | ✅ 做 | 让成本从不可见变可见，企业能知道"超了" |
| 告警推送（webhook/IM） | ✅ 做 | 超了要通知到人，对齐现有 PASS/WARN/FAIL 推送 |
| 超支拦截（FAIL/阻断） | ❌ 不做 | 超支不等于任务不该做——任务必须完成，账后算 |
| `--warn-as-error` 可选阻断 | ✅ 做 | 复用 v1.3.1 既有机制，企业自己选要不要 CI 阻断 |

**与训练预算控制（v1.3.6 train_budget）的区别**：训练是算力密集型长任务，超预算 SIGINT 暂停是合理的（训练可以存 checkpoint 接着跑）；运行时 Agent 任务一旦开始就有业务承诺，不能中途扔——所以运行时成本审计只告警不拦截，两个场景两套机制。

> 🔮 **演进方向（暂不排期）**：成本控制前移为「quota 事前门禁」——多轮长任务的每一轮开工前先查剩余配额再决定执行，验证过的回写才记 spend；本版的事后 WARN 是第一步，事前问路与 v1.3.7「守卫先于事件分发」同向，待 worklog 数据层成熟后评估。
> 🔮 **演进方向二（暂不排期）**：成本审计从「超支判定」升级为「turn 产出判定」——把每个计费 turn 的产出类型化（无产出消耗 / 暴露阻塞 / 有进展 / 完成主要结果），审计的不只是"超没超"，还有"这笔钱花的 turn 有没有产出"；记账要求"恰好一次"（验证过的回写才允许 spend，spend 后不得重复追加）。本版只做超支 WARN，产出判定待 worklog 采集的节点级数据足够支撑后评估。

## 🌐 商业模型层 商业侧定位（Sovereign AI 四层主权 · 2026-08-19 红杉 Neo-Lab 分享吸收）

> 📖 来源：红杉美国合伙人 Sonya Huang 创始人闭门分享（2026-08-18 流传视频转写）——「Every AI application company will become a neo-lab」+ Sovereign AI 四层主权框架。

### 四层主权与 sofagent 落点

红杉的 Sovereign AI 定义是「掌握对你产品最关键的那条智能链路的控制权」，拆四层——sofagent 每层都有落点，**商业模型层 是「模型适配 + 部署」两层主权的产品化**：

| 主权层 | 红杉定义 | sofagent 落点 | 状态 |
|--------|---------|--------------|------|
| 数据主权 | 领域私有数据自己说了算、不出企业边界 | ontology + 知识库 + 24 规则审计（数据不出企业）+ data_sovereignty_report | ✅ 已具备 |
| 模型适配主权 | 基于开源基座微调/LoRA/领域对齐，想改就改 | 训练引擎（v1.4.1-1.4.4）+ model_register / model_switch | 📋 排期 |
| 评测迭代主权 | 自有一套面向业务场景的评测体系，知道模型哪好哪坏 | Benchmark 评测 + define_acceptance/check_acceptance + MLflow 集成（v1.3.9） | 📋 排期 |
| 部署主权 | 推理放哪、何时升版本/回滚自己定 | 本地权重部署（v1.4.1）+ 灰度切换 + 审计全程留痕 | 📋 排期 |

### 三个直接印证的决策

- **「主权是光谱不是开关」**——红杉说绝大多数公司该待在中间档（开源基座微调 + 核心场景自有模型 + 长尾外调）。这与 sofagent 的「通用模型路由不自研——企业挂第三方 model router（LiteLLM/OpenRouter），只保留数据主权路由 + 注册/灰度/退役」完全同构（v1.3.6 已定）。商业模型层 就是中间档的产品化。
- **「先建评测集，再谈微调」**——红杉的落地顺序与 sofagent 的 Benchmark 先行 + define_acceptance 机器可判定验收一致：没有业务评测的微调全是瞎调。
- **「权重 ≠ 主权」**——红杉说「下个开源模型跑起来，除了部署啥也不会，和调 API 没区别」。sofagent 的部署主权 = 本地权重 + 审计 + 灰度切换 + 回滚——「能管住模型」才是主权，不是「能跑模型」。
- **「起步不需要几千 GPU 和几十博士」**——训练引擎定位轻量（LoRA/领域后对齐优先，v1.4.x 不做全参数预训练）；「套壳会陷同质化价格战」= 商业模型层 的价值主张。

> 💡 **「攻守一体 + 四能力闭环」= 一个 FDE**：约束层四能力（注入/审计/回溯/进化）全部有 plugin 落点——inject（注入）/ audit（审计）/ rollback（回溯）/ evolve（进化），这是叙事完整性的保证；再加 ontology（地图）+ commons（公地）+ gate（审阅门）+ daemon（养护）补齐仓库森林四要素 + GitHub 生态层；FDE 方法论 plugin（攻）是进场判断力。一个 DSH Agent 装齐「攻 + 守 + 进化 + 公地 + 养护」，就是一个 FDE——会进场梳理、会判定该不该上 AI、会算值不值、会审阅每次变更、会建能力地图、会发布/发现/调用能力、会越用越强、会 7×24 自巡检。FDE 不是「一个功能」，是「一套判断（fde_* tools）+ 一套基础设施（约束层家族）」；**plugin 家族拆好后，FDE 能力自动涌现**（与「协作底座是涌现不是构建」同一逻辑）。量化只带年薪问询框架（当前成本/AI 后成本/年节省/回本周期，年节省 = 岗位真实市场年薪 × AI 接管工时占比），薪酬基准属 商业模型层 不进开源。

> 💡 **「插件家族」比「单点大插件」更符合 DSH「万物皆插件」哲学，也更有商业纵深**：每个小 plugin 能单独被企业采用，渐进式落地（与 FDE「从最小工作单元切入、不搞流程大改造」同一套逻辑）。**协作底座是涌现不是构建**——审计（审阅门）+ ontology（地图）+ 回溯（剪枝）+ 注入（约束）+ 进化（越用越强）+ 公地（能力流通）+ 养护（daemon 巡检）挂进 DSH 后，DSH 生态里每个 Agent 自动获得「仓库森林」的运转机制，不需要一个「GitHub 式协作底座 plugin」。

**FORGE 侧的其他应用场景（2026-08-19 二次评估）**：

| 场景 | 机制 | 解决现在什么问题 |
|------|------|----------------|
| **监控协议升级：轮询 → 事件订阅** | DSH 会话事件流 + `notify_session`——driver 跑 DSH 时 phase 变化主动推送，监控端订阅而非 sleep 120 轮询 | 轮询的 120 秒盲区；监控 session 的 sleep 被 137 打断（2026-08-19 监控实录两次）；「推变拉」的下一步 |
