## 定位

> 商业产品层（商业平台接口规划 §9.1）需要 sofagent 预留的平台接口。v1.4.0/v1.4.2/v1.4.4 已分别覆盖 G3（`cost_query`）/ G5（DB/API 数据源）/ G1（模型注册器扩展），本版承载剩余四项——**G2 能力缺口查询 · G4 绩效数据导出 · G6 节点级可见性 · G7 多租户抽象层 v0**，外加 **G13 PR 生命周期接口**（2026-09-01 收编）与 **audit 专职面文档化**（第九章，2026-09-03 登记）。G2-G7 全部是「读数据 + 元数据」类接口，不改引擎执行内核；G13 是「提交-审阅-合并」动作面（写接口），补齐 PR 作为商业平台核心协同单位的一等公民地位。

## 一、能力缺口查询（G2 · MCP `workflow_gaps`）

### 定位

> 商业平台悬赏式 PR（§2.7）的发现接口——owner 想知道「哪棵树需要 PR、哪里缺人/缺能力」。依赖 v1.3.9 worklog（谁在跑什么）+ v1.3.7 ontology lifecycle（哪些是 trunk 基线、哪些是 branch 试验）。

### 交付

| 组件 | 能力 |

| **悬赏对接** | 缺口 → 可一键转悬赏式 PR（商业平台消费，owner 发起） |

## 六、审计留痕双层（存储架构 · Codex rollout-trace 启发 · 2026-08-22 排入）

### 定位

> Codex rollout-trace 把「raw bundle（原始事件流，writer 热路径只写不读）+ reduced state（语义规约缓存，供 replay/viewer 消费）」物理拆成两个 crate——与 sofagent「Ledger 原始不可变 + Views 派生」同构，但读端独立成层（热路径零负担）。本版评估审计历史（history.jsonl）读取端拆独立规约层，避免「写多读少」的单一文件性能瓶颈。**与审计存储 SQLite 迁移评估（ROADMAP 候选 v1.4.7）同批**——SQLite 若落地，规约层即 SQLite 查询面；若不落地，规约层独立存在。

### 交付

| 组件 | 能力 |
|------|------|
| **读端规约层** | history.jsonl 读取端拆出独立 reduce 层（按 agent/时间/规则聚合的派生视图），写路径不动（保持 append-only 热路径） |
| **查询接口** | 规约层暴露 `audit_query`（按 agent / 时间范围 / 规则 ID 过滤）——与 SQLite 迁移的查询能力目标一致，先以内存规约验证价值 |
| **PROV-O 导出器** | 薄导出层：`DecisionLogEntry → W3C PROV-O 三元组`（Turtle/JSON-LD），作为 audit-trail 导出选项之一——主链（HMAC jsonl）一字不动，只加标准格式出口供监管/合规对接（Semantica 验证：PROV-O 是合规框架普遍接受的提交格式） |

## 七、首部署确定性 cron job 包（G8 · 商业产品层前置 · 2026-08-24 新增）

### 定位

> **公司负责人拍板需求（2026-08-24）**：第一个客户部署就要有快速感知——部署完成即有一个**确定性**的定时任务在跑，客户第一天就看到产出，同时每次执行进入计量、账单周期持续出账。这是商业平台冷启动（§8.1 赋能服务 #1「FDE 部署包生成服务」）的引擎侧载体：**部署包生成时附带一个确定性 cron job，让客户「用起来」+「持续产生账单」**。
>
> 与同版「workflow 烧进 USB」互补：USB 是**物理交付载体**（插上即跑），cron job 是**定时交付形态**（部署即在跑）——一个解决「交付怎么落地」，一个解决「交付后怎么持续」。

### 交付

| 组件 | 能力 |
|------|------|
| **首部署模板库** | `daily-health` 预设模板（@daily 巡检 + 审计摘要 prompt）——客户部署即有一个看得懂的确定性任务在跑 |
| **一键创建命令** | `sofagent-daemon scheduler create --template daily-health`（scheduler 已支持 cron + 三档糖，缺的是「预设模板 + 部署即建」这一步） |
| **部署即建接线** | `install.sh` 安装完成后自动创建首部署 cron job（企业设备装完即见效，无需手工配置） |
| **账单周期聚合** | cost_query（G3 已交付）数据按周期聚合 → 月结账单数据（商业平台 §9.2 计量计费的数据源，每次 cron 执行进 worklog + cost） |

## 八、PR 生命周期接口（G13 · MCP `pr_submit` / `pr_review` / `pr_merge` · 2026-09-01 收编）

> 📋 **缺口 A（2026-09-01 对账定谳）**：商业平台核心协同单位是 PR（§2.2「所有工作都变成 PR」、§6.4 PR 三重身份是核心闭环——协同单位/审计对象/训练信号）。引擎侧现状：workflow schema 已有 `merge_criteria`/`approver` 审阅协议字段（v1.3.6）、有 `hitl_resolve`（异步人审决议 v1.3.7）、有 audit（24 规则）——但「PR 提交 → 审阅 → 合并/拒绝」的**动作面 MCP tool 不存在**。PR 三重身份里「审计对象 + 训练信号」两个人口都靠 PR 元数据进审计链，缺一等公民接口 = 商业平台协同飞轮的入口悬空。与 G2-G7 的「读接口」互补，本版补「写接口」。

### 交付
