## 一、能力缺口查询（G2 · MCP `workflow_gaps`）

### 定位

> 商业平台 悬赏式 PR（§2.7）的发现接口——owner 想知道「哪棵树需要 PR、哪里缺人/缺能力」。依赖 v1.3.9 worklog（谁在跑什么）+ v1.3.7 ontology lifecycle（哪些是 trunk 基线、哪些是 branch 试验）。

### 交付

| 组件 | 能力 |
|------|------|
| **`workflow_gaps` MCP tool** | 读 workflow 状态 + worklog 活跃度 + ontology lifecycle → 输出「缺人 / 缺能力 / 待升级」三类缺口清单 |
| **缺口判定规则** | ① 缺人：workflow 有节点但无活跃 session ② 缺能力：节点引用的 capability 未注册 ③ 待升级：branch 试验多次未晋升 trunk |
| **悬赏对接** | 缺口 → 可一键转悬赏式 PR（商业平台 消费，owner 发起） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/mcp/src/tools/workflow-gaps.ts` | 新建 | `workflow_gaps` tool |
| `engine/orchestrator/src/gap-analyzer.ts` | 新建 | 缺口判定逻辑（读 worklog + ontology lifecycle） |
| `engine/orchestrator/src/__tests__/gap-analyzer.test.ts` | 新建 | 单测（三类缺口判定） |

### 验收标准

- [ ] `workflow_gaps` 能输出三类缺口（缺人/缺能力/待升级），每类有具体节点定位
- [ ] 缺口清单可被 商业平台 消费转悬赏式 PR（输出 JSON 结构含 workflow_id + node + 缺口类型）
- [ ] 单测覆盖三类缺口判定边界（空 workflow / 全活跃 / 部分闲置）

## 二、绩效数据导出（G4 · MCP `contribution_query`）

### 定位

> 商业平台 DKP 价值轨（§七）的数据源——算每人/每 workflow 的贡献度。对齐 v1.4.5 FDE 训练交付包的量化四字段（当前成本 / AI 后成本 / 年节省 / 回本周期）。

### 交付

| 组件 | 能力 |
|------|------|
| **`contribution_query` MCP tool** | 读审计（git diff 证据）+ decision-log（判定记录）→ 按人/按 workflow 聚合贡献度 |
| **贡献度算法** | PR 合并数 × 权重（节点复杂度/节省小时数）——人和数字员工同标准 |
| **DKP 对接** | 输出贡献度 → 商业平台 换算 DKP（后台按 C7 基准映射薪酬参考） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/mcp/src/tools/contribution-query.ts` | 新建 | `contribution_query` tool |
| `engine/audit/src/contribution.ts` | 新建 | 贡献度聚合（读 audit history + decision-log） |
| `engine/audit/src/__tests__/contribution.test.ts` | 新建 | 单测（聚合正确性 + 人/数字员工同标准） |

### 验收标准

- [ ] `contribution_query` 按人/按 workflow 输出贡献度（含合并数、权重分、总计）
- [ ] 数字员工与人同一套贡献度算法（无身份差异）
- [ ] 输出可被 商业平台 换算 DKP（JSON 含 contributor_id + contribution_score）

## 三、节点级可见性元数据（G6 · workflow schema `visibility` 字段）

### 定位

> 商业平台 任务面/数据面分离（§2.8）——销售愿意开放「出 PPT/做方案」成 PR，但客户资料必须私有（防抢单）。workflow schema 加 `visibility` 字段，审阅门按此执行。

### 交付

| 组件 | 能力 |
|------|------|
| **`visibility` 字段** | workflow schema 节点级加 `visibility: open / private / result-only`——open 可悬赏参与；private 仅 owner+指定协作者；result-only 任务可见数据隐藏 |
| **审阅门联动** | merge_criteria 执行时检查 visibility——private 节点的 PR 仅 owner 可审，result-only 节点的 PR 完成者看不到底层数据 |
| **数据面隔离** | private/result-only 节点的数据不进入公开上下文（skill 下发时脱敏） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/workflow-schema.ts` | 修改 | schema 加 `visibility` 枚举字段（v1.3.6 标准格式扩展） |
| `engine/audit/src/merge-engine.ts` | 修改 | merge 时校验 visibility 权限 |
| `engine/orchestrator/src/__tests__/visibility.test.ts` | 新建 | 单测（三级可见性 + 审阅门联动） |

### 验收标准

- [ ] workflow schema 支持 `visibility` 三级枚举，v1.3.6 标准格式向后兼容
- [ ] 审阅门按 visibility 执行：private 节点 PR 仅 owner 可审，result-only 完成者看不到数据
- [ ] 单测覆盖三级可见性的权限边界

## 四、多租户抽象层 v0（G7 · `data/<tenant>/` 命名空间）

### 定位

> 商业平台 企业空间隔离（§9.2）的引擎层前置——先做**数据路径抽象**（`data/<tenant>/`），隔离策略随 SaaS 需要细化。动引擎内核，故放 v1.4.6（云 VM 执行面）之后评估。

### 交付

| 组件 | 能力 |
|------|------|
| **租户命名空间** | 引擎数据路径 `data/<tenant>/`——workflow/audit/log 按租户分目录 |
| **租户上下文注入** | 加载链注入 `tenant_id`（SKILL 约束层感知当前租户） |
| **隔离 v0** | 路径级隔离（不同租户不读对方目录）——不做云级隔离（v2.x） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/core/src/paths.ts` | 修改 | 数据路径函数加 tenant 参数（默认 `data/default/` 兼容单租户） |
| `engine/harness/src/index.ts` | 修改 | 加载链注入 tenant_id |
| `engine/core/src/__tests__/paths.test.ts` | 新建 | 单测（租户路径隔离 + 默认兼容） |

### 验收标准

- [ ] 数据路径支持 `data/<tenant>/`，默认 `data/default/`（单租户无感）
- [ ] 不同租户路径不交叉（隔离 v0）
- [ ] 单测覆盖租户路径生成 + 默认兼容
