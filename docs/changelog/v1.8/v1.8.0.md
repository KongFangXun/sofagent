## 定位

> 🔌 **判定底座 · DecisionChannel 真实实现**——阶段三第一版，回答「**判定怎么被用起来**」。v1.5.3 交付了 `DecisionChannel` 的**契约**（`judge(state, questions)` + 三原语语义 + 云端 provider opt-in 默认关），但当时留空——L1 判定层处于「只有接口没有实现，按 L0 兜底」的状态。本版用阶段一/二的产物**填上这个空**，让 L1 从兜底态变为真实可用态。**纪律不变**：通道而非依赖——引擎定义接口与编排，实现可被替换（用户自带实现或换基座，不动契约）。

## 一、DecisionChannel 实现落地（L1 判定层就位）

> **形态归属**：`[主干]`（判定·通道实现）｜ **不可拔**（通道契约与编排是判定层的接入面）

### 交付

| 组件 | 能力 |
|------|------|
| **默认实现接入** | 以 v1.6–v1.7 产出的判定底座作为 `DecisionChannel` 的**默认实现**（自研，随本仓开源），实现 `judge(state, questions) → typed answers + 概率` |
| **契约测试** | 按 v1.5.3 契约做可插拔替换测试：同一组问句下，换实现（默认实现 / 测试替身 / 用户自带实现）**契约行为一致**——实现可换，契约不动 |
| **L1 状态切换** | L1 判定层从「恒返回未就位 → 编排按 L0 兜底」切换为「实现就位 → 正常判定」；**保留未就位兜底路径**（实现加载失败 / 权重缺失时仍退回 L0，不留空窗、不静默降级为「全部放行」） |
| **云端 provider 纪律** | 云端判定 provider 仍**默认关闭**（用户 key opt-in）——本地优先、数据主权不破。打开时须显式配置且留痕 |
| **失败语义 fail-closed** | 判定通道调用失败 / 超时 / 输出类型不符 → **按 L0 兜底**（不静默放行、不静默阻断），失败原因可查 |
| **判定与留痕** | 判定结果（含概率与四态）落 decision-log，带 `routeReason` 语义可解释——与 v1.5.3 第七章验收项对齐 |
| **不占主模型槽位** | 判定调用不占用本地主模型推理槽位（行为锁，与 v1.6.2 同款断言） |

### 风险与前置假设

> ⚠️ **本版让判定第一次真正进入执行路径**——从「设计」变为「有行为」。因此本版起判定错误会产生**真实后果**。三条防线必须同时到位：① 兜底路径（失败退 L0）；② 建议非执法（判定不直接改变执行结果）；③ 确定性规则在前（既有 24–25 条规则判定面零改动）。
>
> ⚠️ **本版不带对外叙事**。判定已就位但权重分发通路未打通（v1.8.2），交付形态尚不完整——对外口径变化留给 v1.8.2。
