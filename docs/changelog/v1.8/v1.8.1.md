## 定位

> 🖥️ **判定底座 · 一体机推理接入**——阶段三第二版，回答「**判定在哪跑、跑得多快**」。判定底座要在客户的私有环境（一体机、离线节点、信创全封环境）里可用，且**不新增运行时组件**——跑在既有本地推理栈上。本版同时把路由层的**判定档（`decision-model`）**从「插槽已预留」接通为「真实可达」：判定任务由判定底座直接作答，**不经过生成模型**。

## 一、并行约束解码（一次前向出全部字段）

> **形态归属**：`[主干]`（判定·推理实现）｜ **不可拔**（判定吞吐与延迟的实现基础）

### 交付

| 组件 | 能力 |
|------|------|
| **并行约束解码** | 同一份 `state` 下的**全部问句一次前向出答案**（KV cache 广播 + 单次前向填充全部字段），而非逐问循环解码——这是判定模型相对生成模型的结构性优势，也是延迟能进入百毫秒级的前提 |
| **类型约束解码** | 解码过程**约束在声明的回答类型内**（choice 只能出候选项、score 只能出合法档位、noul 只能是概率）——从解码层保证「类型正确」，与 v1.6.0 的 schema 层限定构成双重保证（schema 层防越界，解码层防畸形） |
| **多问批处理** | 相互独立的问句可批量并行；**有依赖的问句串行**（依赖关系由问句集声明，不自动推断——自动推断会引入不可审计的隐式行为） |
| **本地推理栈协同** | 复用一体机既有本地推理栈（**零新增运行时组件**），与 v1.5.6 的本地并发槽位管理协同：判定请求走独立槽位通道，**不与主模型抢槽** |
| **离线可用** | 无网络环境下判定底座可正常加载与推理（权重本地留存，不联络外部服务）——信创全封场景的硬要求 |
| **延迟与吞吐落数** | 单次判定延迟、批量吞吐、并发下的延迟劣化曲线如实落数（作为 v1.9.1 四层性能标准的输入） |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/router/judge-runtime.ts` | 修改 | 并行约束解码 + 批量批处理 + 依赖串行 |
| `engine/orchestrator/src/router/slot-manager.ts` | 修改 | 判定独立槽位通道（不与主模型抢槽） |
| `engine/orchestrator/src/__tests__/judge-parallel.test.ts` | 新建 | 并行正确性 / 类型约束 / 槽位隔离 / 离线加载单测 |
| `docs/VALIDATION.md` | 修改 | 延迟与吞吐实测落数 |

### 验收标准

- [ ] 并行约束解码可用：同状态多问一次前向出全部答案（非逐问循环）
- [ ] 类型约束在解码层生效（畸形输出不可能产生，有单测）
- [ ] 独立问句并行、有依赖问句串行（依赖关系显式声明）
- [ ] 判定走独立槽位通道，**不占本地主模型槽**（行为锁）
- [ ] 离线环境可加载并推理（不联络外部服务，有断言）
- [ ] 延迟 / 吞吐 / 并发劣化曲线落数（进 `docs/VALIDATION.md`）
- [ ] `npm test` 全绿

## 二、路由判定档接通（`decision-model` 从插槽到可达）

> **形态归属**：`[主干]`（路由·判定档）｜ **不可拔**（路由档位是判定与执行的接缝）

### 交付

| 组件 | 能力 |
|------|------|
| **判定档接通** | `model-router` 的 `decision-model` 档从「类型已定义、分支已显式返回空」接通为**真实可达**——判定任务路由到该档后由判定底座作答，产出类型化答案 + 概率 |
| **判定档不进自动矩阵** | 该档**不参与「敏感度 × 复杂度」自动路由矩阵**——判定任务由上游显式请求（判定类任务发起时指定），避免判定任务被自动矩阵误路由到生成档 |
| **不落云端生成分支** | 判定档与拦截档（`block`）**绝不落到云端生成分支**（既有缺陷修复的回归锁——判定任务变成生成任务会既慢又错） |
| **判定档可观测** | 判定档的调用量 / 延迟 / 失败率 / 降级次数可观测（运维可见，数据本地不出门） |
| **与本地两档的分工声明** | 明确 `decision-model`（判定档）与 `local-executor`（本地执行档）/ `local-pipeline`（本地管道档）的分工边界：**判定档出判定，执行档出行为**——三者是任务形态区分，不是模型规格区分 |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/model-router.ts` | 修改 | 判定档接通 + 不进自动矩阵 + 观测字段 |
| `engine/orchestrator/src/loop/plan-node.ts` / `engineer-decide.ts` | 修改 | 判定档分支由「返回空」改为真实判定调用 |
| `engine/mcp/src/tools/router-slots.ts` | 修改 | 判定档可观测字段 |
| `engine/orchestrator/src/__tests__/model-router.test.ts` | 修改 | 判定档可达 + 不落云端的回归锁断言 |

### 验收标准

- [ ] `decision-model` 档真实可达（判定任务由判定底座作答，产出类型化答案）
- [ ] 判定档不参与自动路由矩阵（须上游显式请求）
- [ ] **判定档与拦截档绝不落云端生成分支**（回归锁断言在位）
- [ ] 判定档调用量 / 延迟 / 失败率 / 降级次数可观测
- [ ] 三档分工边界在文档在位（判定档出判定 / 执行档出行为，非规格区分）
- [ ] `npm test` 全绿

### 风险与前置假设

> ⚠️ **一体机硬件规格可能不足**。判定底座的底座规格与并行约束解码的显存/内存占用须与客户实际硬件对齐（本版落数的延迟曲线是选型依据）。若目标硬件跑不动，**退回串行解码**（延迟上升但功能可用），并把该形态明确标注为降级档而非静默降速。
