## 定位

## 一、三原语类型化（Choice / Score / Noul 的 typed answer 定稿）

> **形态归属**：`[主干]`（判定·类型契约）｜ **不可拔**（类型是判定面的根契约，拔掉则判定结果无法被审计消费）

### 交付

| 组件 | 能力 |
|------|------|
| **`Choice` answer** | 从候选项里做选择——输出选中项 + **全候选项概率分布**（不是只输出一个选项）。语义对齐既有 `fde_classify` 的「三选一」形态（🔄自动 / ⚡强化 / 👤暂不动），但把无概率的枚举升级为带分布的类型化答案 |
| **`Score` answer** | 按标准打分——输出分值 + **区间/不确定度**。语义对齐既有 `evaluate` / `evaluate_output` / `quality-judge` 的打分面，但把裸分值升级为「分值 + 可信区间」 |
| **`Noul` answer** | 给出某判断成立的概率——输出**真值概率**。语义对齐既有 `shouldAllow` 的布尔判定与 `fde_classify` 的三问布尔输入，但把 `boolean` 升级为概率 |
| **问题集限定** | 判定请求携带**限定回答类型的问句集**（问题与原语类型绑定，运行时不可越界）——保证输出「类型正确」，模型无法自作主张产出未声明类型（对齐 Jev 的「不编出选项 D」这一层保证） |
| **多问并行** | 同一份状态下的多个**相互独立**问题一次前向出全部答案（非逐问循环）——这是判定模型相对生成模型的结构性优势，schema 层须预留批量形态 |
| **与既有置信度并存** | 新类型与既有 `confidentiality` / `TriggerConfidence` / `'high'\|'med'\|'low'` 等枚举**并存不冲突**，映射口径落文档；既有 HMAC 链 schema 本版零改动 |

### 涉及文件（预估）

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/router/decision-primitives.ts` | 新建 | 三原语类型定义 + 问句集限定 + 批量形态 |
| `engine/orchestrator/src/__tests__/decision-primitives.test.ts` | 新建 | 类型构造 / 越界拒绝 / 批量形态单测 |
| `docs/ARCHITECTURE.md` | 修改 | 判定面新增三原语类型说明（与「判断与生成分离」章衔接） |

### 验收标准

- [ ] 三原语类型定义在位（choice 带分布 / score 带区间 / noul 带真值概率）
- [ ] 问句集限定生效：输出类型与请求问句类型不符时**拒绝**（fail-closed，非静默接受）
- [ ] 批量形态可用：同状态多问一次调用出全部答案（问题间不串扰）
- [ ] 与既有 `fde_classify` 三问布尔形态的**映射口径**写进文档（枚举 → 概率的迁移路径明确）
- [ ] decision-log / HMAC 链 schema 本版零改动（回归断言）
- [ ] `npm test` 全绿

## 二、24 条审计规则判据重述（从匹配逻辑到「判据 + 证据」）

> **形态归属**：`[主干]`（判定·判据集）｜ **不可拔**（判据集是训练目标本体）

### 交付

| 组件 | 能力 |
|------|------|
| **逐条重述** | 既有 24 条 git-diff 审计规则（v1.5.4 已扩至 25 条含 A24）逐条重述为「**判据**（要判断什么）+ **证据**（据什么判断）」两段式数据，与规则实现逐条对账，**不允许静默遗漏** |
| **判据 schema 校验器** | 加载时断言：判据字段齐全、证据字段可解析、类型与原语匹配；任一不满足 → **拒绝加载**（fail-closed），不降级为「跳过该条」 |
| **判据质量 lint** | schema 校验管**格式**合规，lint 管**质量**可用——**三条硬**判据 fail-closed：① **可判别性**（正负样例互不矛盾——同一样例同时出现在 `match` 与 `not_match` 即拒载该条并报红）② **可举证性**（证据字段须指向可复现的采集来源，以「人工判断」类自由文本充数即拒载）③ **概率来源可追溯**（概率须来自**输出分布的读数**；由模型生成出来的数字不构成概率——它测的是「自述与现实的差距」，与真实频率无因果关系，越训只会越像自述而非越准。来源不可追溯的判据**拒载**，因为它既不可校准也无法举证）。两条**软**判据只提示不阻断：④ **可校准性**（该判据能否给出概率目标而非只能二值——不能的进「硬标签清单」，训练侧不为其做校准）⑤ **判据重复度**（语义重复的判据提示合并）。软项产出**待修清单**，与 v1.5.17 验证器老化检测同族纪律——质量问题要暴露，但不阻断整批加载 |
| **正负样例继承** | 复用 v1.5.4 的 `match` / `not_match` 正负样例格式——**同一份样例既服务规则自测，又成为判据集的首批标注种子**（一份数据两用，不另起格式） |
| **判据面边界声明** | 明确本版判据面**只覆盖审计规则**（workflow / 本体数据 / 路由判定面的判据扩属 v1.9.1）；边界写进文档，防后续静默扩张 |

### 涉及文件（预估）

|------|------|------|
| `engine/orchestrator/src/router/criteria-schema.ts` | 新建 | 判据 schema + 加载校验（fail-closed） |
| `engine/orchestrator/src/router/criteria-quality-lint.ts` | 新建 | 判据质量 lint（三硬项 fail-closed + 两软项提示 + 待修清单） |
| `engine/audit/src/rules/criteria/`（目录） | 新建 | 24–25 条判据数据（与规则实现逐条对账） |

## 三、理念升级驱动的文档重构（触发条件与分层口径）

> **形态归属**：`[非功能]`（文档治理·重构）｜ —（重构不改能力边界，不涉可拔面）

文档的事实基础是**理念**，不是代码。代码变更只让某一段描述过时；理念升级会让一整批文档的**断言口径**同时失效——判定层接管后，「24 条审计规则各自判定」这句话本身不再成立（降为「判据声明 + 证据采集器」），而 SECURITY / ARCHITECTURE / audit README 三处都在说这句话。**只改被触发的那一处，等于把同一个事实分散在三处继续漂移。** 所以文档重构不是「有空再做的清理」，而是随触发它的那一版同批交付的交付面——它与本版第二章同源：判据重述改变了规则的文档口径，文档口径的重构就必须同批完成。

### 交付

**触发条件**（满足任一即触发重构评估，而非延后清理）：

| 触发 | 判据 | 处置 |
|------|------|------|
| 理念升级改变断言基础 | 新理念使既有文档的断言不再是当前事实 | 全站扫描该断言的**全部**承载面，同批改写 |
| 术语更名 | 术语 SSOT 变更 | 改名即刻全站扫描升级，不留新旧并存 |
| 版本线新增 | 版本数量级变化（施工期拆版等） | 版本叙事层重整：目录 / 索引 / 互引 |
| 分层预算触顶 | A / B / E 任一层无余量承载本批改动 | 先**归层**（把开发者参考面移出用户文档层），再考虑上限 |

**分层口径**（哪一层承载什么、按什么口径重构）：

| 层 | 承载什么 | 重构口径 |
|----|---------|---------|
| A 用户文档 | README（双语）/ CHANGELOG / SECURITY / ARCHITECTURE / ROADMAP 等 | 断言以**当前事实**为准；历史沿革下沉 changelog |
| B 开发者参考 | FORGE / playbook / agents / .github / engine hooks | 规则文档**只写规则**——不带版本号、行号与日期 |
| E 运维指南 | `docs/guides/**` | 操作口径优先；非核心文档按「零信息删除」压缩 |
| 历史事实区 | `docs/changelog/**` | **不计入预算**——它是重构的落点，不是重构的对象 |

**版本关系纪律**：

| 纪律 | 内容 |
|------|------|
| 不单独发版 | 重构附着在触发它的那一版交付里，与功能章同批验收 |
| 不改能力边界 | 本版标注为 `[非功能]` 的理由即此——重构前后能力面与可拔级别零变化 |
| 须过门禁 | 分层预算（`check-docs`）/ 锚点（`check-anchors`）/ 形态与章数（`check-forms`）——重构是这些守卫的输入，不受它们豁免 |
| 两条禁止 | 不得以重构为名删除仍起作用的断言；不得留下指向不存在章节的指针（指针目标必须可兑现） |

### 本版连带面

本版为该机制的首例：判据重述改变了 24 条规则的文档口径，连带重构同步落两处——[ARCHITECTURE](../../ARCHITECTURE.md) 落「审计规则面的判定化边界」（架构护栏 + 三维度增补），[SECURITY](../../../SECURITY.md) 落「24 条规则的判定化归属」（24 行逐条接管去向表）。两处一为**边界**（为什么只能加签不能代签）、一为**清单**（每条怎么触发），互引不重复。

- [ ] 触发条件与分层口径在文档在位（本章即其 SSOT）
- [ ] 本版连带重构执行完毕：24 条规则的文档口径在 ARCHITECTURE 与 SECURITY 两处同步重述，且互引可达
- [ ] 门禁全绿：`check-docs`（分层预算）/ `check-anchors`（指针可兑现）/ `check-forms` / `check-version`

## 四、判定底座的边界（做马鞍，不做马场）

> **形态归属**：`[主干]`（判定·边界声明）｜ **不可拔**（边界是能力声明的护栏——拔掉则判定面可静默扩张为应用面）

判定底座是**治理能力的载体**，不是**应用能力的容器**。判据的工作是把**已有判断**显式化并校准，不是**引入新场景**。这条区分必须在施工期第一版写死：边界先于能力落盘，后续每一版才有对照物——否则「顺手多做一个域」永远看起来比「先修判据质量」更像进展。完整边界陈述见 [ARCHITECTURE · 判定底座的边界](../../ARCHITECTURE.md#判定底座的边界做马鞍不做马场)，本章只落**版本级口径**（边界 SSOT 唯一，两处互引不重复）。

### 交付

| 组件 | 能力 |
|------|------|
| **四条边界判据** | ① **约束 vs 扩张能力**——既有判定面的判据已存在（只是隐式、未校准），底座做显式化与校准；为新场景从零造判定即越界 ② **判定面治理 vs 判定应用**——治理「判定怎么被做」，不决定「判定被用来做什么」 ③ **是否把判定变对外服务**——判定只在引擎内部被消费，不作为对外服务提供 ④ **是否承担模型提供者角色**——交付底座与通道且实现可替换，不承担模型性能承诺 |
| **边界外清单** | 逐条对应判据：浏览器动作与计算机使用 · 游戏 / 机器人 / 交易 / 媒体类判定 · SQL 方言扩展与多语言 SDK · 对外提供判定结果（判据 ③）· 通用模型托管（判据 ④）。**不做的事也要有落点**——不留「待评估」的模糊地带，模糊地带即日后的静默扩张入口 |
| **边界内六项落点** | 判据质量 lint（本版）· 数据采集点扩充与质量门（[v1.6.1](./v1.6.1.md)）· 中文零样本基线（[v1.6.2](./v1.6.2.md)）· 弃权语义独立化与校准上线前置门（[v1.7.1](../v1.7/v1.7.1.md)）· 判定面输入契约（[v1.8.0](../v1.8/v1.8.0.md)）· 静默失败监控与判定使用度量（[v1.9.1](../v1.9/v1.9.1.md)）。六项共同形态：**让既有判定更可信，而不是让系统能判更多东西** |
| **边界的三条理由** | ① 做应用会消耗治理资产（中立性不可事后追回） ② 做判定服务会破坏审计独立性（判定者与被判定者必须分离） ③ 边界是给客户看的（可写进验收标准的东西才可交付，信任不是可交付物） |
