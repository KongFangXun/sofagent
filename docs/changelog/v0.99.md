# v0.99 开发日志

> v1.0 前收尾：准入核查 + 外部反馈整理 + 文档终审 + FDE 完整链路跑通
>
> v0.98 完成审计独立化后，v0.99 不进新功能——只做 bugfix、文档终审、准入条件核查、外部 Beta 反馈整理。目标是让 v1.0 发布时没有任何未完成的 TODO 和未核对的宣称。

---

## 概述

v0.99 是 sofagent 在 v1.0 之前的最后一个版本。定位原则：

1. **不进新功能**。所有「要不要加 X」的讨论推到 v1.x。
2. **只做三件事**：修 bug + 对文档 + 核宣称。
3. **准入检查表是最高优先级**。9 条 v1.0 准入条件，每条必须打勾或诚实调整。

## 一、P0：v1.0 准入条件逐一核查

> 来源：ROADMAP v1.0 准入 9 条。

| # | 条件 | 核实方式 | 负责 |
|:--:|------|------|:--:|
| 1 | 纪律层增量在反转实验中被证实 | 核对 v0.97 实验报告 | v0.97 |
| 2 | 审计工具实现完整六步闭环 | 运行 `audit-root-cause.ts` + `audit-regression.ts` 端到端 | v0.98 |
| 3 | 纪律层上下文成本 ≤ 窗口 5% | verify.sh 输出验证（~3,000 token / 128K = 2.5%） | v0.96 |
| 4 | OpenClaw 预装 + AO compose + Agency Agent 全链路跑通 | install.sh --with-openclaw → 排一个复杂任务 → 验证编排引擎点火 → Agency Agent 模板匹配 | v0.98 |
| 5 | MCP server + 至少一个企业平台 webhook 跑通 | reporter.ts --webhook dingtalk → 验证群消息推送 | v0.98 |
| 6 | daemon 稳定运行 ≥ 30 天 | macOS + Linux 双平台 daemon 日志核查 | v0.99 |
| 7 | 至少 3 个外部用户 30 天使用数据 | 核对 EVIDENCE.md 的用户反馈 | v0.98-v0.99 |
| 8 | install → verify → 首次任务通过率 ≥ 90% | 干净环境 10 次安装测试，统计首次任务通过率 | v0.99 |
| 9 | 能力矩阵五个平台都有实测数据 | 核对 LIMITATIONS.md 平台能力表（v0.97 已补测） | v0.97 |

### 不及格的处理

如果某条准入条件无法满足，v0.99 做以下动作之一：
- **诚实调整 v1.0 定位**：比如「纪律层增量未充分证实」→ v1.0 定位从「纪律底座」改为「审计工具正式版 + 纪律层实验版」
- **降低准入门槛**：比如「3 个外部用户 30 天数据」做不到 → 调整为「1 个外部用户 30 天数据 + 5 个一次性测试用户」
- **推迟 v1.0**：如果准入条件大面积不及格，考虑 v1.0 推迟到 v1.0-rc1 并继续迭代

## 四、P1：FDE 完整链路跑通

> 来源：v0.97-v0.98 编排引擎重构 + MCP server + webhook 的集成验证。

### 端到端验证场景

模拟一个 FDE 部署者的完整流程：

```
1. 装环境
   mac 干净环境 → git clone sofagent → install.sh --with-openclaw
   → OpenClaw 预装成功 → sofagent Skill 加载成功 → 审计 CLI 可用

2. 梳理 workflow
   模拟企业场景：外贸报价流程
   → FDE 梳理出 5 个 workflow 节点
   → 识别 3 个 AI 可切入节点（客户需求理解 / 价格计算 / 报价单生成）

3. 编排任务
   → 对「价格计算」节点点火编排引擎
   → engage.md 拆解为子任务
   → AO Compose 匹配 Agency Agent 模板（数据分析型）
   → 子 Agent 执行

4. 任务执行 + 反思
   → 子 Agent 完成任务
   → think.md 反思：「本次价格计算用的是历史均价，未考虑客户特殊折扣」
   → task/logs 记录完整

5. 审计
   → sofagent-audit --diff → A1-A11 全量扫描
   → PASS / WARN → report

6. 反馈回路
   → 下次同一节点新任务
   → 编排引擎读 think.md：「上次价格计算忽略了特殊折扣」
   → 本次拆解加入「检查客户是否有特殊折扣」子任务

7. 推送到企业平台
   → 审计报告通过 webhook 推送到钉钉群
```

### 验证结果

| 步骤 | 预期 | 实际 | 状态 |
|------|------|------|:--:|
| 环境安装 | install.sh --with-openclaw 全自动 | ⏳ | |
| workflow 梳理 | FDE 十步流程可用 | ⏳ | |
| 编排引擎 | engage.md 点火 + AO compose 拆解 | ⏳ | |
| 模板匹配 | Agency Agent 模板正确匹配 | ⏳ | |
| 反思闭环 | think.md → 下次编排引擎 | ⏳ | |
| 审计 | A1-A11 全量扫描 | ⏳ | |
| webhook 推送 | 钉钉群收到审计报告 | ⏳ | |

## 五、P1：bus factor 缓解

> 来源：两份审查共识——「bus factor = 1 是到达 v1.0 的最大结构性障碍。」

### 目标（现实版）

| 指标 | 数值 |
|------|:--:|
| 外部 PR 合入 | ≥ 3 个（来自 ≥ 2 个不同贡献者） |
| 外部 Issue 提交 | ≥ 10 条（非作者） |
| Co-maintainer 候选人 | ≥ 1 个（至少合并过 1 个 PR） |
| GitHub star | — （不设目标——这不是指标，是结果） |

### 动作

1. 从 v0.97-v0.98 的外部反馈中主动邀请活跃贡献者
2. 为每个 P2 Issue 提供「怎么修」的指引（不是「你来修」——是「你看这里，改这里，跑这条命令验证」）
3. 在 CONTRIBUTING 中增加「我该从哪个 Issue 开始」的向导

### 如果做不到

在 v1.0 README 诚实声明：「当前单人维护。欢迎 Co-maintainer。在外部维护者稳定参与之前，v1.0 的定位是『高质量单人项目正式版』而非『社区驱动项目』。」
