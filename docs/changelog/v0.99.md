# v0.99 开发日志

> v1.0 前收尾：准入核查 + 外部反馈整理 + 文档终审 + FDE 完整链路跑通 + **放弃条件正式引入**
>
> v0.98 完成审计独立化和纪律层实验重跑后，v0.99 不进新功能——只做 bugfix、文档终审、准入条件核查、外部 Beta 反馈整理。目标是让 v1.0 发布时没有任何未完成的 TODO 和未核对的宣称。同时，两份独立审查均指出「没有放弃条件的 roadmap 是愿望清单」——v0.99 正式引入项目放弃条件。
>
> **🔴 v0.99 新增核心主题：放弃条件。** 不是悲观——是诚实。一个知道什么时候该停的项目，比一个永远在「下个版本」的项目更值得信赖。

---

## 概述

v0.99 是 sofagent 在 v1.0 之前的最后一个版本。定位原则：

1. **不进新功能**。所有「要不要加 X」的讨论推到 v1.x。
2. **只做三件事**：修 bug + 对文档 + 核宣称。
3. **准入检查表是最高优先级**。9 条 v1.0 准入条件，每条必须打勾或诚实调整。
4. **放弃条件是 v0.99 新增底线**。知道什么时候该停，比永远在「下个版本就正式」更值得信赖。

### 不及格的处理

如果某条准入条件无法满足，v0.99 做以下动作之一：
- **诚实调整 v1.0 定位**：比如「纪律层增量未充分证实」→ v1.0 定位从「纪律底座」改为「审计工具正式版 + 纪律层实验版」
- **降低准入门槛**：比如「3 个外部用户 30 天数据」做不到 → 调整为「1 个外部用户 30 天数据 + 5 个一次性测试用户」
- **推迟 v1.0**：如果准入条件大面积不及格，考虑 v1.0 推迟到 v1.0-rc1 并继续迭代

### Changelog 预写文件处理（v0.96 审查提醒）

> 来源：v0.96 第三轮审查——「预写 changelog 是反模式。它会在开发时产生 ''填空'' 而非 ''记录''，产生幸存者偏差（只写符合预写框架的内容）。」

**v0.99 做的事**：打开 v0.97/v0.98 的实际开发日志，逐条核对「预写的内容」和「实际开发了的内容」之间是否有差异。如果有差异，诚实标注「预写时计划了 X，实际开发了 Y」。如果差异大到预写框架完全失效——删掉预写内容，按实际开发结果重新写。

**关于预写文件本身**：v0.97/v0.98/v0.99 三个预写 changelog 文件**保留到开发完成后修改优化**，不提前删除。理由：作者习惯先定计划再做事，预写框架作为路线规划的具象化产物，有参考价值。开发完成后用实际结果替换预写内容，差异部分诚实标注。

**v1.0 的规则**：v1.0 起开发日志只在版本开发完成后写。ROADMAP 只写「方向」，changelog 只写「事实」。两个文件不互相抄。预写 changelog 的模式止于 v0.99。

### 端到端验证场景

模拟一个 FDE 部署者的完整流程：

```
1. 装环境
   mac 干净环境 → git clone sofagent → install.sh --with-openclaw
   → OpenClaw 预装成功 → sofagent Skill 加载成功 → 审计 CLI 可用

2. 梳理 workflow
   模拟企业场景：外贸报价流程
   → FDE 梳理出 5 个 workflow 节点
   → 识别 3 个 AI 可切入节点（客户需求理解 / 价格计算 / 报价单生成）

3. 编排任务
   → 对「价格计算」节点点火编排引擎
   → engage.md 拆解为子任务
   → AO Compose 匹配 Agency Agent 模板（数据分析型）
   → 子 Agent 执行

4. 任务执行 + 反思
   → 子 Agent 完成任务
   → think.md 反思：「本次价格计算用的是历史均价，未考虑客户特殊折扣」

   → sofagent-audit --diff → A1-A11 全量扫描

6. 反馈回路
   → 下次同一节点新任务
   → 编排引擎读 think.md：「上次价格计算忽略了特殊折扣」
   → 本次拆解加入「检查客户是否有特殊折扣」子任务

7. 推送到企业平台
   → 审计报告通过 webhook 推送到钉钉群
```

### 模型依赖单点故障声明（v0.96 审查发现）

> 来源：v0.96 外部审查阻断——「一个人类维护者离职项目还能用——代码在、文档在。但如果 DeepSeek V4 Pro 或 GLM-5.2 停止服务，项目失去修复 bug 的能力。这是比人类 bus factor = 1 更脆弱的结构性风险。」

**不是要解决的问题——是要被承认的结构性风险。** 在以下位置增加声明：

| 位置 | 内容 |
|------|------|
| README.md「作者说明」段 | 明确标注：代码由 AI 模型生成，作者做产品决策和终审，bug 修复依赖 AI 模型可用性 |
| CONTRIBUTING.md | 新增「项目维护模型」节——说清楚外部贡献者进入的是什么环境：AI 生成代码 + 人类审核 + 模型可用性风险 |
| LIMITATIONS.md | 新增一条已知局限：「模型依赖维护风险」——完整描述风险、缓解措施（当前无）、诚实承认 |

### 如果做不到

在 v1.0 README 诚实声明：「当前单人维护。欢迎 Co-maintainer。在外部维护者稳定参与之前，v1.0 的定位是『高质量单人项目正式版』而非『社区驱动项目』。」

### 6.5 sofagent-audit 独立 npm 包评估（v0.96 审查新增）

| 方案 | 收益 | 成本 |
|------|------|------|
| **拆** | 独立 npm 包 → 独立 star / issue / contributor / CI 生态。不绑定 sofagent 叙事，走「git diff 审计工具」独立赛道 | 双仓库维护、版本同步、npm publish 流程、文档分流 |
| **不拆** | 零额外工程成本。审计工具随着 sofagent 主仓库一起发版、一起宣传 | 审计工具的独立价值被 sofagent 叙事淹没。贡献者要理解整个 sofagent 才能改审计规则 |

**v0.99 不做决定——做评估。** 产出 `docs/decisions/audit-package-split-assessment.md`，写清楚：
- 拆或留的决策矩阵（技术/社区/维护三轴）
- 如果拆：拆哪些文件、npm 包名、版本策略、README 怎么写
- 如果留：如何让审计工具在主仓库里更容易被外部贡献者发现和修改

**判断标准**：如果 v0.98 的审计闭环跑通后 30 天内没有外部贡献者为审计工具提交 PR → 拆。有外部贡献 → 留（说明主仓库叙事已经足够吸引审计工具贡献者）。
