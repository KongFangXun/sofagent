### 四层防线攻防分析

| 层 | 做什么 | 谁负责 | 被攻破的后果 | 攻击者需要 |
|:--:|------|:--:|------|------|
| 1 | MCP server 只绑 localhost | sofagent | 无法从网络直接访问 MCP | 先攻破本机 |

| 4 | sensitivity frontmatter 过滤 | sofagent | `restricted` entity 不可读 | 伪造设备 identity + 突破加密 |

## 交付三：Prompt 注入 8 层防护体系（P1）

> 来源：《Agent 项目 Prompt 注入全链路防护体系》。核心原则：**模型提建议，系统控执行**——安全边界放在模型外面，不寄希望于模型听话。

当前 sofagent 安全内容散在多处（审计引擎 / 权限闸门 / HITL 节点），但缺系统性框架。8 层防护把零散能力串成体系，每一层都能映射到 sofagent 现有能力或待补能力：

| 层 | 防护内容 | sofagent 现状 |
|:--:|------|------|
| 1 | **指令分层隔离**——系统 > 用户 > 外部文档，外部内容加标签包裹 | ⚠️ 部分（SKILL.md 宪法层，但缺外部内容标签包裹） |
| 2 | **工具动态最小权限**——按任务类型动态收缩可调用工具列表 | ✅ 已有（Sub Agent 工具集零重叠设计，v1.1.0） |
| 3 | **工具参数后端强制校验**——模型只提建议，后端控执行 | ✅ 已有（审计引擎 git diff 硬证据，不依赖 Agent 配合） |
| 4 | **敏感数据不进 prompt**——必须用时走受控工具 + 脱敏 | ⚠️ 部分（sensitivity frontmatter v1.1.6，缺 prompt 级脱敏） |
| 5 | **RAG 召回可信分级**——官方 > 内部 > 用户上传 > 网页抓取，不可信内容默认标记 | ❌ 待补（知识库加载链无可信分级） |
| 6 | **输出结构化 + 执行前审核**——禁止自由自然语言直接触发执行 | ✅ 已有（entry-gate 风险分级 + HITL 确认） |
| 7 | **高危动作强制人工确认**——确认页展示完整参数（对象/范围/影响） | ✅ 已有（entry-gate 🔴 高风险 DB/外部 API/文件删除需审批） |
| 8 | **全链路日志 + 红队测试**——上线前变形攻击样本 + 上线后异常告警 | ✅ 已有（审计 history.jsonl + daemon WARN 累积报告 v1.1.4） |

**v1.1.8 新增实现目标**：补齐层 1（外部内容标签包裹）和层 4（prompt 级脱敏）+ 层 5（知识可信分级，与 v1.1.6 sensitivity 联动）。

## 交付四：编排引擎串行版——DeepAgents subagents 接入（P1）

> 📐 技术验证来源：`deepagents@1.11.0` 类型定义审计（2026-07-21）

### 问题诊断

v1.0.7 退役 ao（agency-orchestrator）时，迁移做了一半：
- ✅ ao 的文本生成 → 替换为 DeepAgents `createDeepAgent().invoke()`
- ❌ ao 的任务调度 → **没接入** DeepAgents 的 `subagents` 参数

结果：`composer.ts` 只用 deepagents 生成 YAML 文本（`tools: []` 空数组），`orchestrator-compare.ts` 的 `composeTask()` 说「使用 --run 执行」但 `--run` 从未实现。compose 出来的编排方案只打印不执行。

### v1.1.8 交付目标

把 DeepAgents 包自带的 Sub Agent 调度能力接上——compose 拆解 → 真正委派 Sub Agent → 审计卡关 → 结果聚合。

### 能力分级（基于 deepagents 类型定义审计）

| 能力 | deepagents 支持 | v1.1.8 实现 | 完整版目标 |
|------|:---:|:---:|:---|
| **串行委派**——主 Agent 把子任务交给 Sub Agent A，等它跑完再交给 B | ✅ `subagents` 参数 + `createSubAgentMiddleware` | ✅ 实现 | — |
| **同步并行**——主 Agent 一次发多个 task tool call，LangGraph React Agent 并行执行 | ✅ LLM 可在一次回复里发多个 tool_call，React Agent 并行调度；`filesValue` 提供文件状态自动合并 | ✅ 实现 | — |
| **异步并行**——Sub Agent 在远程 Agent Protocol 服务器上跑，不阻塞主 Agent | ✅ `AsyncSubAgent` + `createAsyncSubAgentMiddleware`（需远程服务器 + `graphId` + `url`） | ❌ 不做 | v1.4.0（需部署 Agent Protocol 服务端） |
| **沙箱隔离**——每个 Sub Agent 独立文件系统 / 网络白名单 | ✅ `FilesystemBackend` + `virtualMode` + `PermissionMode` | ❌ 不做 | v1.4.0（沙箱执行环境） |

> 💡 **关键发现**：deepagents 的同步 `SubAgent`（非 `AsyncSubAgent`）本身支持并行——主 Agent（LLM）可以在一次回复中发出多个 `task` tool call，LangGraph 的 React Agent 会并行执行这些 tool call。`filesValue`（ReducedValue）提供文件状态的自动合并机制，处理并行 Sub Agent 的文件写入冲突。**不需要远程 Agent Protocol 服务器就能实现同步并行**。

### 实现拆解

#### T01：`dag-runner.ts`——编排执行器（新增，~200 行）

接收 compose 输出的 YAML → 解析为 `SubAgent[]` 配置 → 调 `createDeepAgent({ subagents, tools, systemPrompt })`：

```typescript
// 伪代码
import { createDeepAgent, type SubAgent } from 'deepagents';
import { buildConstrainedSystemPrompt } from '@sofagent/harness';

export async function runDAG(taskDesc: string, workflowYaml: string): Promise<DAGResult> {
  // 1. 解析 YAML → SubAgent[] 配置
  const subagents: SubAgent[] = parseWorkflowYaml(workflowYaml, skillDir);

  // 2. 每个 SubAgent 注入四层约束加载链
  subagents.forEach(sa => {
    sa.systemPrompt = buildConstrainedSystemPrompt(skillDir) + sa.systemPrompt;
  });

  // 3. 创建编排 Agent
  const orchestrator = await createDeepAgent({
    subagents,           // ← 关键：之前代码这里是 []
    tools: ORCHESTRATOR_TOOLS,
    systemPrompt: ORCHESTRATOR_PROMPT,
  });

  // 4. 执行——主 Agent 自主决定何时委派给哪个 Sub Agent
  const result = await orchestrator.invoke({
    messages: [{ role: 'user', content: taskDesc }]
  });

  return { finalOutput: result, subagentCount: subagents.length };
}
```

#### T02：`composer.ts` 改造——接收企业 workflow 参考 + 返回结构化 SubAgent 配置（~80 行改动）

**输入端修正**（关键）：`composeWithDeepAgents()` 新增 `enterpriseWorkflowYaml` 可选参数。FDE 梳理好的企业 workflow 作为 compose 的参考上下文——compose 不再凭空生成通用拆解方案，而是基于企业真实业务流程生成编排方案：

```typescript
interface ComposeInput {
  taskDesc: string;
  enterpriseWorkflowYaml?: string;  // ← 新增：FDE 梳理的企业 workflow（可选，无则通用拆解）
}

interface ComposeResult {
  yaml: string;                      // YAML 文本（保留，给 --dry-run 预览）
  subagents: SubAgentConfig[];       // 结构化 SubAgent 配置（新增）
}

// compose 的 system prompt 增加参考上下文注入：
// 「以下是 FDE 梳理的本企业真实业务流程，请基于此 workflow 生成编排方案，
//   而非通用拆解。若 enterpriseWorkflowYaml 为空，退化为通用拆解。」
```

**为什么重要**：FDE 工具包的核心交付物是企业专有 Skill（含 workflow）。如果 compose 不接收企业 workflow，编排引擎跑出来的方案就是通用的，跟企业实际业务流程对不上——FDE 白梳了。

#### T03：`orchestrator-compare.ts`——实现 `--run` flag（~80 行改动）

`composeTask()` 新增 `--run` 分支：compose → 解析 → 调 `dag-runner.ts` 真正执行 → audit 卡关 → 输出结果。

#### T04：`parseWorkflowYaml()`——YAML → SubAgent 映射（~100 行）

解析 compose 输出的 YAML（`workflow.nodes[].agent` 字段映射到 builtin-agents），构建 `SubAgent[]`：

```yaml
# compose 输出的 YAML 格式
workflow:
  nodes:
    - id: impl-core
      agent: developer       # ← 映射到 ENGINEER_AGENT
      task: 实现核心逻辑
      depends_on: []
    - id: write-tests
      agent: qa-engineer     # ← 映射到 REVIEWER_AGENT
      task: 编写测试
      depends_on: [impl-core]
```

agent 类型映射表：

| YAML `agent` 值 | 映射到 | systemPrompt 来源 |
|-----------------|--------|-------------------|
| `developer` | ENGINEER_AGENT | agents/sofagent-engineer.md |
| `qa-engineer` | REVIEWER_AGENT | agents/sofagent-reviewer.md |
| `researcher` | FDE_AGENT（sustain 模式） | agents/sofagent-fde.md |
| `technical-writer` | 默认 general-purpose | deepagents 内置 |

#### T05：A/B 测试原型验证（~60 行）

基于现有 `orchestrator-compare.ts` 的 `CONSECUTIVE_WINS_REQUIRED = 2` 机制，新增 A/B 原型验证命令：

```bash
# 跑方案 A（当前拆解 prompt）
sofagent-orchestrator compose "任务描述" --run --label A

# 跑方案 B（换一种拆解 prompt）
sofagent-orchestrator compose "任务描述" --run --label B --alt-prompt

# 对比 → promote
sofagent-orchestrator compare --current logs/A --candidate logs/B
```

**v1.1.8 的 A/B 是串行双跑 + 事后对比**（非实时双跑）。实时双跑需要 v1.4.0 沙箱隔离——不然两个方案同时改同一批文件会互相踩。

#### T06：自动生成候选方案 B/C/D（~80 行）

A/B 测试的前提是有多个候选方案可选。v1.1.8 新增 `--variants` flag，compose 一次生成多种拆解策略的编排方案供对比：

```bash
# 一次生成 4 种拆解方案（A 默认 + B/C/D 变体）
sofagent-orchestrator compose "任务描述" \
  --enterprise-workflow fde-workflow.yaml \
  --variants A,B,C,D

# 输出：plans/A.yaml + plans/B.yaml + plans/C.yaml + plans/D.yaml
# 每个 YAML 可独立 --run 执行，事后 compare 对比
```

**4 种 prompt 变体策略**（基于同一企业 workflow，不同拆解角度）：

| 方案 | prompt 策略 | 适用场景 |
|------|------------|---------|
| **A（默认）** | 步骤拆解——按功能模块逐个实现 | 通用场景 |
| **B** | 领域驱动——按业务域聚合（数据层→逻辑层→接口层） | 复杂业务系统 |
| **C** | 风险优先——先做最不确定的部分验证可行性 | 探索型任务 |
| **D** | 测试先行——先写测试再实现 | TDD 场景 |

**实现**：在 `composer.ts` 的 system prompt 中增加 4 种策略模板，`composeWithDeepAgents()` 接收 `variant` 参数切换 prompt。所有方案都接收同一个 `enterpriseWorkflowYaml` 作为参考输入——变的是「怎么拆」，不变的是「拆什么」。

### 明确不做（划界）

| 不做 | 原因 | 哪个版本做 |
|------|------|-----------|
| 异步并行（AsyncSubAgent） | 需要远程 Agent Protocol 服务器 + graphId 配置，工程量超 v1.1.8 边界 | v1.4.0 |
| 沙箱隔离 | FilesystemBackend + virtualMode + PermissionMode，需深度改造 | v1.4.0 |
| DAG 循环依赖检测 | 拓扑排序校验 + 超时熔断，v1.1.8 依赖 LLM 自主排序 | v1.3.1 |
| 真·实时 A/B 双跑 | 两个方案并行实时对比需沙箱隔离 | v1.4.0 |
| **daemon A/B 自动定时调度器** | 需新模块——cron 触发 + 历史指标累积 + N 次阈值自动 promote + 方案轮换状态机（~200 行）。依赖 T05 A/B 原型先跑通，串行依赖不适合挤进已满的 v1.1.8 | **v1.1.9** |
| **探索-利用自动切换** | 方案 A 跑 N 次 → 自动换 B 跑 N 次 → compare → promote 赢家，需持久化计数器 + 方案轮换调度逻辑 | **v1.1.9** |
