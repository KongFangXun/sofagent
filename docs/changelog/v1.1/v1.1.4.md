# v1.1.4 开发日志 — LOOP 独立产品化 + 工具注入 + 条件路由 + 审计闭环加固

> 状态：已发版 · 孔放勋 · 2026-07-15 → 2026-07-19
> 前置依赖：v1.1.3（StateGraph + HITL 已就绪，但 engineer/reviewer 节点走 composer 零工具路径，只能说话不能干活）

## 背景

v1.1.3 的 LOOP 有两个结构性缺口：

1. **engineer/reviewer 走零工具路径**——DeepAgent 带着空 tools 数组上线，只能输出文字建议，**不能真的读写文件、跑测试、改代码**
2. **LOOP 代码混在 sofagent 包内**——用户装 sofagent 时被迫带上 LOOP 的所有代码，污染主包；用户想用 LOOP 也找不到独立入口

v1.1.4 同步解决这两件事：给节点装上手脚（工具注入），把 LOOP 升级为独立产品（用户按需安装）。

## 交付二：Workflow 模式 + 双模型 + 自动门控（P0）

> commit 9ce06fd / 5c74b8b / 91ec30b

### Workflow YAML 消费模式

外部编排平台（WorkBuddy 等）产出 `workflow.yml`，LOOP 引擎外层循环逐个执行子任务：

```yaml
workflow:
  name: "示例：新增审计规则"
  nodes:
    - id: T1
      task: "在 rules/ 下新建 rule-a20.ts"
    - id: T2
      task: "在 rules/index.ts 中注册 A20"
      depends_on: [T1]
```

每个子任务内部走完整 LOOP 闭环：engineer 写代码 → audit 审计 → reviewer 审查 → IS_PASS 判定 → 下一个子任务。

### 双模型支持

```bash
export SOFAGENT_LLM_ENGINEER=deepseek:工程模型  # 开发用便宜模型
export SOFAGENT_LLM_REVIEWER=glm:审查模型             # 审查用贵模型
```

`resolveLLMModelFor(role)` 在 `nodes.ts` 中按角色解析模型——engineer 和 reviewer 可以用不同模型，平衡成本和质量。支持 glm/工程模型/deepseek 三家（均兼容 OpenAI API 格式）。

### IS_PASS 自动门控

`LOOP_AUTO=1` 启用全自动模式，`parseReviewerPass` 解析 reviewer 输出的 `IS_PASS: YES/NO` 自动判定是否进入下一轮：

- 🔴 阻断项不修复 → IS_PASS: NO → 回 engineer 修复
- 🟡 告警项 ≤3 且无 🔴 → IS_PASS: YES → 进入下一子任务
- HITL 模式（默认）：每次审查后弹 y/n 等人工确认

## 交付三：LOOP 工具注入（P0）——给节点装上手脚

> 详见原 v1.1.3 设计——v1.1.4 实际落地。

engineer 和 reviewer 节点不再走 composer 的零工具路径，而是直接调用 `createDeepAgent` 并注入 sofagent 自有的工具集。

### 新增文件：`orchestrator/src/tools.ts`

定义 6 个工具，每个工具内嵌 A1-A17 约束：

| Tool | 对应能力 | 内置约束 |
|------|------|------|
| `read_file` | Read | A7 先读再改 |
| `write_file` | Write | A1 不碰敏感 · A3 不改越界 · A16 非授权文件 |
| `edit_file` | Edit | 同上 |
| `run_bash` | Bash | A6 不坏构建 · A11 不滥资源 · 高危命令黑名单（rm -rf /、fork 炸弹、curl\|sh、mkfs、dd of=/dev/） |
| `search_code` | Glob / Grep | — |
| `run_test` | npm test | A8 不逃验证 |

### 修改文件：`orchestrator/src/loop/nodes.ts`

- `defaultRunEngineer`：不再调 `spawnSubAgent`，直接 `createDeepAgent({ tools: [read, write, edit, bash, search, test], systemPrompt: buildConstrainedSystemPrompt(ENGINEER_AGENT), maxTurns: 20 })`
- `defaultRunReviewer`：同上，注入审查专用工具子集 + REVIEWER_AGENT

### 设计原则

- **tools 的 description 就是约束**——每个 tool 的 schema description 写清楚"什么能做、什么不能做"，模型读到 description 后自然遵守
- **约束底座完整性**：tool 执行前不额外做 hook 拦截（hook 留给 git commit 时触发），但在 prompt 中注入完整的 A1-A17 规则（通过 `buildConstrainedSystemPrompt` 的四层加载链）
- **兜底**：如果 `deepagents` 不可用或模型 API 不可达，优雅降级为旧路径（走 composer），在报告注明

## 交付六：审计闭环加固（P1）——垃圾文件事件驱动

> 背景（v1.1.3 发版期真实事件）：测试审计功能时在主仓库产生了 a.txt/b.txt/new-name.txt 三个垃圾 commit（message 为 "add"/"add a file"）。审计引擎 A3 正确检测到越界并判 WARN，但 WARN 放行后**无人跟进**，垃圾文件在 main 里躺了 1.5 小时才被人工发现。结论：审计的价值不在"检测"而在"闭环"——检测到但没人管，等于没检测。

### 新增规则 A18 垃圾文件检测

根目录（或任意非测试目录）新增匹配临时文件名模式的文件 → WARN（能力拐杖级，不阻断）：

- 模式：`^[a-z]\.(txt|md|js|ts)$`（单字母文件名）、`^(test|tmp|temp|foo|bar|aaa)[0-9]*\.`、`^(new|old)-name\.`
- 豁免：`test/`、`tests/`、`__tests__/`、`*.test.ts` 等正规测试路径
- ruleClass：`能力拐杖` → runner 优先级：**extended 层**（排在 A17 之后，按编号正序排列——A 组核心扩展优先于 E 组工程规范，各组内按编号升序）
- evidenceMode：`git-diff`
- 实现文件：`sofagent/audit/src/rules/rule-a18-junk-file.ts` + `index.ts` 注册 + `runner.ts` AUDIT_PRIORITY.extended 插入

### 新增规则 A19 commit message 质量

零信息量 commit message → FAIL（业务底线级，阻断）：

- message 长度 < 8 字符 → FAIL（如 "add"、"fix"、"test"、"update"）
- message 完全匹配黑名单词 → FAIL：`add`/`fix`/`test`/`update`/`change`/`wip`/`tmp`/`asdf`
- 理由：A3 靠 message 做越界对照——message 越空洞，A3 越形同虚设。message 质量是整个审计链的地基
- ruleClass：`业务底线` → runner 优先级：**critical 层**（排在 A4 之后——比 A4 稍轻但同属 critical 阻断级；排在 A3 之前是为了 message 不合格就直接阻断，不用再跑 A3 越界检测）
- evidenceMode：`git-diff`（仅从 `commitMsg` 参数判定，不读 diff 内容）
- 实现文件：`sofagent/audit/src/rules/rule-a19-commit-msg-quality.ts` + `index.ts` 注册 + `runner.ts` AUDIT_PRIORITY.critical 插入

### daemon WARN 累积报告

补上"检测→跟进"的闭环：

- daemon 定期扫描 `history.jsonl` 中 exitCode=1（WARN）的记录
- 连续 N 条 WARN 未处理（后续 commit 没有清理动作）→ 生成 `daemon-notice.md` 告警条目
- 周期汇总："本周 X 条 WARN，其中 Y 条涉及文件至今仍在仓库" + 文件清单
- 复用 v1.1.0 的 daemon 主动巡检框架，新增 WARN 分析器

## 交付七：daemon 可见性修复（P0）——v1.1.0 架构拆分遗留债务

> 背景：v1.1.3 发版审查期间诊断发现 daemon 自 v1.1.0 包结构拆分以来**从未真正运行过**——`~/.sofagent/daemon.log` 满屏 `❌ 不支持的参数 "--daemon"`，进程 exit code 78 持续崩溃重启。根因是拆包时 init.ts 的 plist 生成逻辑没同步更新，四个连锁问题导致 daemon 物理失效。

### 根因诊断（四个问题叠加）

| # | 问题 | 影响 |
|---|------|------|
| 1 | plist ProgramArguments 调用 `sofagent-audit --daemon start`（v1.1.3 已废） | daemon 持续崩溃，exit code 78 |
| 2 | `@sofagent/daemon` 包未 `npm link` | `sofagent-daemon` 命令全局找不到 |
| 3 | plist WorkingDirectory = `$HOME` | 即使跑起来也监控错目录（`$HOME` 而非项目目录） |
| 4 | plist PATH 残缺（开头多了冒号，node bin 目录缺失） | node 不在 PATH 里，daemon 启动即崩 |

### L0：当前项目 watch.yml 配置（即时生效）

`.sofagent/watch.yml` 的 paths 从默认 `src/ agents/ .sofagent/` 改为匹配 sofagent 仓库结构的 `sofagent/ agents/ tools/ docs/ FDE/ LOOP/ work模板市场/`。默认 paths 是通用项目的假设，sofagent 自身仓库不匹配。

### L1：init.ts 代码层修复

**修改文件**：`sofagent/audit/src/commands/init.ts`

1. **新增 watch.yml 生成**——`--init` 在生成 config.yml 后追加生成 watch.yml（调用 `generateWatchTemplate()`），之前只生成 config.yml 不生成 watch.yml，daemon 只能 fallback 到默认 paths
2. **plist ProgramArguments 修正**——`sofagent-audit --daemon start` → `sofagent-daemon start`，带 fallback 逻辑（找不到二进制就用 `node + 项目内 daemon/dist/cli.js`）
3. **plist WorkingDirectory 修正**——`$HOME` → `cwd`（init 时的项目目录）
4. **plist PATH 兜底**——`nodeBinDir` 失败时 fallback 到 `/usr/local/bin`，避免开头冒号
5. **步骤编号修正**——原代码 `[1/4] [2/4] [3/4] [4/4] [5/5]` 编号错误，改为 `[1/5] [2/5] [3/5] [4/5] [5/5]`
