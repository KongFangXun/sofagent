## 一、P0：代码硬伤止血（6 项）

> 来源：两轮评审交叉验证。VERSION 不一致和正则大小写 bug 是真 bug，其余是工程债。

### 1. VERSION 不一致（🔴 两轮评审交叉确认）

**问题**：`skill-safety-check.ts:22` 和 `verify-evidence.ts:13` 的 `VERSION = '0.92'`，但文件头注释和 package.json 是 v0.93。用户跑 `--version` 看到错误版本号。

**修复**：

```typescript
// skill-safety-check.ts:22
const VERSION = '0.92';  →  const VERSION = '0.94';

// verify-evidence.ts:13
const VERSION = '0.92';  →  const VERSION = '0.94';
```

### 2. license$/readme 正则大小写 bug（🔴 DeepSeek 发现）

**问题**：`rule-07-careful-modify.ts:26-27` 的 `LOW_RISK_PATTERNS` 没有 `i` flag：

```typescript
/license$/                    // 不匹配 LICENSE（大写）
/readme(\.\w+)?\.md$/        // 不匹配 Readme.md / README.MD
```

在 macOS 上（APFS 默认不区分大小写）没问题，但 **Linux CI 上会漏报大小写变体**。

**修复**：所有 `LOW_RISK_PATTERNS` 正则统一加 `i` flag。

### 3. verify-evidence 正则过宽（🟡 两轮交叉确认）

**问题**：`verify-evidence.ts:16-22` 的三个正则：

```typescript
const BUILD_PATTERN = /build.*(success|fail)|编译.*(成功|失败)|npm run build|make/i;
//                                                                       ^^^^
// "make sure""make a decision" 全部命中
const LINT_PATTERN = /lint|eslint|prettier|shellcheck/i;
//                   ^^^^
// "splinter""glint" 命中
```

**修复**：加词边界 + 限定上下文：

```typescript
const BUILD_PATTERN = /build.*(success|fail)|编译.*(成功|失败)|npm run build|\bmake\b\s+(build|all|install|clean)/i;
const LINT_PATTERN = /\b(lint|eslint|prettier|shellcheck)\b/i;
const TEST_PATTERN = /exit\.code|测试.*(pass|fail|通过|失败)|test.*(pass|fail)|✅.*pass|❌.*fail/i;
```

### 4. verify-evidence 不区分正负证据（🟡 DeepSeek 发现）

**问题**：`verify-evidence.ts` 只检查关键词出现，不区分"test passed"和"test failed"——两者都被算作"有测试证据"。

**修复**：`countMatches` 改为返回 `{ positive: number; negative: number }`，`negative > 0` 时降级为 WARN。

### 5. log-checker tsc\b 过于宽泛（🟡 DeepSeek 发现）

**问题**：`log-checker.ts:149` 的 `testPatterns` 包含 `/\btsc\b/`，日志中任意"检查 tsc 配置"都会被判定为"执行了构建"。

**修复**：改为 `/tsc\s+--noEmit/` 或 `/tsc\s+-p\b/`——只匹配真正的编译命令。

### 6. checkLogs 迭代中修改数组 + 三元死代码（🟡 两轮交叉确认）

**问题 A**：`log-checker.ts:39-60` 在 `for...of` 循环内向 `entries` push 新元素，两个职责（收集日志条目 + 展开文件引用）揉进一个循环。

**修复**：拆为两阶段——先收集所有日志条目，再遍历条目展开文件引用。

**问题 B**：`skill-safety-check.ts:192` 和 `verify-evidence.ts:82` 的三元表达式是死代码：

```typescript
// skill-safety-check.ts:192 —— 两个分支返回一样
const re = new RegExp(rule.pattern.source, rule.pattern.flags.includes('g') ? rule.pattern.flags : rule.pattern.flags);
// verify-evidence.ts:82 —— 写法冗余
const re = new RegExp(pattern.source, pattern.flags.includes('g') ? pattern.flags : pattern.flags + 'g');
```

**修复**：

```typescript
// skill-safety-check.ts —— 预编译正则到 RULES 定义时
export interface SafetyRule {
  regex: RegExp;  // 预编译，循环内直接 regex.test()
  ...
}
// 循环内：rule.regex.test(lines[lineNum]) —— 不再重建

// verify-evidence.ts —— 简化
const re = new RegExp(pattern.source, pattern.flags.includes('g') ? pattern.flags : pattern.flags + 'g');
// 改为：
const flags = pattern.flags.includes('g') ? pattern.flags : pattern.flags + 'g';
const re = new RegExp(pattern.source, flags);
```

## 二、P0：审计独立化——沉默审计模式（--silent）

> 来源：DeepSeek 评审 + GLM-5.2 评审合并。这是 v0.94 最核心的新增功能。

### 核心原则：三层证据策略

```
证据优先级: git-diff（硬证据） > Agent 日志（软证据） > 无证据（跳过）
```

git diff 本身就是客观证据——Agent 改没改文件、改了多少、改了什么内容，git 全知道。不需要 Agent 写一行日志。Agent 可以骗日志，骗不了 git。

### 背景

当前审计工具铁律 #1/#3 **完全依赖 Agent 自己写的日志**。Agent 不写日志 → 审计降级为 WARN → exit code 1 → 不阻断 CI。这等于默认允许 Agent 不写日志。

`--strict` 模式（v0.93 新增）解决了"不阻断"的问题，但没解决"检测能力降为零"的问题——无日志时铁律 #1/#3 什么都不查。

### 功能范围

```bash
# 现在的用法（需要 Agent 日志）
sofagent-audit --diff HEAD~1..HEAD --task "修复登录bug"

# 沉默模式（只跑纯 diff 规则，不需要 Agent 日志）
sofagent-audit --diff HEAD~1..HEAD --task "修复登录bug" --silent

# CI 模式（隐含 --strict + --silent，exit code ≥1 阻断）
sofagent-audit --diff HEAD~1..HEAD --task "修复登录bug" --ci
```

### evidenceMode 标注（DeepSeek 建议）

每条规则标注证据模式，让用户和 reviewer 一眼看到依赖什么：

| 规则 | evidenceMode | 说明 |
|------|:--:|------|
| #1 先读再用 | `hybrid` | 有日志走精确检查，无日志走 diff 推断 |
| #3 验证再干 | `hybrid` | 同上 |
| #7 谨慎修改 | `git-diff` | 纯 diff，零依赖日志 |
| #10 如实汇报 | `git-diff` | 纯 diff + commit message |
| R11 敏感文件 | `git-diff` | 纯文件名匹配 |
| R12 测试缺失 | `git-diff` | 纯 diff 路径匹配 |
| R13 低注释率 | `git-diff` | 纯 diff 内容分析 |

### 沉默模式下的 7 条纯 diff 规则

> 合并 GLM-5.2 和 DeepSeek 两轮评审。这 7 条**完全不依赖 Agent 日志**。

| 规则 | 看什么 | 判什么 | 严重性 | 对应铁律 | 来源 |
|------|------|------|:--:|:--:|:--:|
| **R1 无关文件批量改** | diff 文件数 > 10 且与 --task 匹配率 < 50% | "可能没读上下文就批量改" | WARN | #1 | GLM |
| **R2 源码改但测试没改** | src/ 变了但 `*.test.ts`/`*.spec.js` 没动 | "可能跳过了验证" | WARN | #3 | 两边 |
| **R3 TODO/FIXME 未声明** | diff 新增代码含 TODO/FIXME 但 commit message 没提 | "代码留了未完成标记但没说" | WARN | #10 | GLM |
| **R4 大体积删除** | 单文件删除 > 100 行且与 --task 无关 | "可能误删了不该动的代码" | WARN | #7 | GLM |
| **R5 commit 占位符** | commit 只有 "fix"/"update"/"wip" | 占位符（已有，强化） | WARN | #10 | 已有 |
| **R11 敏感文件触碰** | diff 含 `.env`/`*.pem`/`*.key`/`id_rsa`/`credentials.*` | 敏感文件被修改 | **FAIL** | 安全 | **DeepSeek** |
| **R12 超大 diff 低注释** | 新增 > 200 行且注释率 < 5% | "可能需要 reviewer 关注" | WARN | 质量 | **DeepSeek** |

> R11 是最硬的规则——敏感文件被碰直接 FAIL，不需要 --task、不需要日志、不需要任何上下文。纯文件名匹配。

### 现有规则 #1/#3 加 git-diff 回退分支（DeepSeek 方案）

不改规则核心逻辑，加双路径：

```typescript
// rule-01-read-before-write.ts 改造
export function checkRule01(ctx: AuditContext): RuleCheck {
  // 路径 A：有 Agent 日志 → 精确检查（现有逻辑）
  if (ctx.logEntries.length > 0) {
    return checkFromLogs(ctx);  // 现有逻辑不变
  }

  // 路径 B：无日志 → git diff 推断（新模式）
  // 弱信号：改了 A.ts 但引用 A.ts 的文件没改 → 可能没读上下文
  // 不报错只警告——git diff 只能证明「改了」，不能证明「没读」
  return checkFromDiffHeuristic(ctx);  // 调用 R1 规则
}
```

关键设计决策：**无日志时不报 FAIL，只报 WARN**。因为 git diff 只能证明「改了」，不能证明「没读」。

### --strict 与 --silent 的关系

| 模式 | 日志缺失时 | Agent 日志 | 纯 diff 规则 |
|------|:--:|:--:|:--:|
| 默认 | WARN（不阻断） | ✅ 跑 | ✅ 跑 |
| `--strict` | FAIL（阻断） | ✅ 跑 | ✅ 跑 |
| `--silent` | 跳过（不查） | ❌ 不跑 | ✅ 全跑 |
| `--ci` | = strict + silent | ❌ 不跑 | ✅ 全跑（exit ≥1 阻断） |

### 改造量估算

| 动作 | 代码量 |
|------|:--:|

| 改 index.ts 加 --silent/--ci 解析 | ~30 行 |

| 给所有规则加 evidenceMode 标注 | ~5 行 × 7 |
| **合计** | **~400 行** |

> 不需要大重构——现有每条规则已有独立函数，加分支即可。

## 五、P0：真实 Skill 加载链复现实验

> 回答评审核心质疑：prompt 前缀注入的 0% vs 100% 误伤率，在真实 Skill 加载链下还成立吗？

### 背景

v0.93 的 10 组对照实验中，sofagent 条件是 **prompt 前缀注入 4 条核心规则**，与真实 WorkBuddy 中加载的完整 SKILL.md + think.md + rules.md 加载链有本质差异。实验结果可能高估或低估真实效果。

### 实验设计

| 条件 | v0.93 实验 | v0.94 新增 |
|------|------|------|
| 裸 Agent | OpenClaw --local（无 sofagent） | 同左 |
| prompt 注入 | 手贴 4 条规则前缀 | 同左（作为对照组） |
| **真实加载链** | — | **WorkBuddy 中完整 sofagent Skill（SKILL.md + think.md + rules.md）** |

**任务**：复用 Task 1（camelCase → snake_case）——这是唯一出现强信号的任务。

**指标**：变量名误伤率 + 加载链命中率（通过 verify.sh 验证三层是否加载）

### 预期结果与决策

| 结果 | 含义 | 决策 |
|------|------|------|
| 真实加载链 ≤ prompt 注入的误伤率 | 完整加载链至少不差于前缀注入 | ✅ 继续推广 |
| 真实加载链 > prompt 注入的误伤率 | 完整加载链反而干扰了 Agent | ⚠️ 需排查加载链中哪个层导致干扰 |
| 加载链命中率 < 50% | Agent 根本没读到约束 | 🔴 加载链机制本身有问题，回到 LIMITATIONS |

> 独立轻量版——只装宪法层（4 底线 + 10 铁律），不装 daemon、编排引擎、审计工具。

### 交付物

- `sofagent-lite/install.sh`：独立安装脚本，自动探测 OpenClaw/WorkBuddy，其他平台打印宪法内容供手动粘贴
- `install.sh --lite` flag（主仓库）：与完整版共享同一套安装脚本，加 flag 跳过 daemon/编排/审计
- 独立发布到 SkillHub + ClawHub（`sofagent-lite` 产品入口）

### 为什么保留在 ROADMAP 里

- FDE 驻场快速部署（30 秒挂纪律底线，后续按需升级）
- 个人开发者轻量使用（只想要行为约束，不想要复杂体系）

## 六、P0：sofagent-fde Skill（从 P1 升级）

> 评审共识 + 作者确认：中小企业 AI 落地唯一可行路径是 FDE 驻场部署。

### 为什么升 P0

传统中小企业没有技术团队维护 Agent。**FDE 进去部署 → 交付 → 撤离**是唯一可行的落地模式。sofagent-fde Skill 是 FDE 工程师的标准化工具箱——不是给老板看的，是给部署者用的。

### 使用者画像澄清

| 角色 | 是谁 | 看什么 |
|------|------|------|
| **部署者**（FDE 工程师 / 企业 IT / 技术骨干） | 跑安装脚本、配 hook、写企业专属 Skill | sofagent-fde SKILL.md + install.sh + 审计工具 |
| **买单者**（企业老板） | 看效果、批预算 | 只看 FDE 交付的「部署方案书」和「运行时报告」 |
| **无感用户**（企业员工） | 正常用 Agent 干活，不知道 sofagent 存在 | 无 |

> sofagent-fde 面向**部署者**，不面向买单者。老板的无感是目标，不是问题。

### 交付物

- `sofagent-fde/SKILL.md`：十步完整流程（进场→平台盘点→工作流深挖→AI节点识别→价值量化→出方案→部署交付→交付物清单→速采模板→离场检查）
- **企业专属 Skill 生成**：部署时为每个需要定制的节点创建企业专属 Skill（注入行业术语、业务规则、数据源）
- **工作流检查点**：sub-agent 完成→先过验证→再流到下一步，默认 10% 抽检率，高敏感节点 50-100%
- `sofagent-fde/references/`：案例库（电池研发 / 电商运营）
- 三大交付物：部署方案书（给老板）、知识库（给 IT）、运行时（给 Agent）

## 六点五、P1：6 个子 Skill 检查点

> 子 Skill 是产品形态，不是功能特性——需要持续维护。

### 检查范围

sofagent 主 Skill 由 6 个 .md 文件组成：SKILL.md（主入口）+ engine.md / entry-gate.md / task-aware.md / task-closure.md / loop-check.md（5 个子 Skill）。

### 每个子 Skill 检查项

| 检查项 | 标准 | 为什么 |
|------|------|------|
| 行数 ≤ 90 | 每个 ≤ 90 行 | Agent 不会迷路（DEVELOPMENT §一 原则） |
| Gotcha 章节完整 | 每个有「最常踩的坑」节 | Gotcha 比功能介绍有价值（ARCHITECTURE 写作原则） |
| 文件路径引用有效 | 引用的脚本/Skill 路径存在 | 防止 v0.62 扁平化后遗留的死引用 |
| 与主 SKILL.md 一致 | 子 Skill 的铁律编号与宪法一致 | 防止多个版本迭代后编号错位 |

### 为什么放 ROADMAP 而不是做完就忘

子 Skill 体系和 sofagent Lite / sofagent-fde 一样是**产品形态**。每次版本迭代都可能新增/修改/删除子 Skill——这不是一次性任务，是每个版本都要跑一遍的维护检查。放 ROADMAP 提醒"每版检查"。
