> ao compose 迁移到 DeepAgents。A/B 测试运行器从 mock 升级为真实模型 API——自迭代闭环打通。
>
> 待开发 · 孔放勋

## 背景

v1.0.5 审查发现两个问题：
1. launcher.ts 仅 68 行 thin wrapper，compose 仍走 `execFileSync('ao', ['compose'])`，DeepAgents 一行没写
2. **A/B 测试运行器 `simulateAgentRun()` 是 mock**——直接返回 testCase.expected，导致 candidate 和 current 永远打平，自迭代闭环断了

v1.0.6 解决两件事：compose 迁移到 DeepAgents + A/B 运行器接真实模型 API。

## 交付内容（3 件事）

### 1. DeepAgents compose 实现

用 `createDeepAgent()` 替换 orchestrate-compare.ts 中的 `execFileSync('ao', ['compose'])`：

```typescript
// 之前（v1.0.5 及以前）
const output = execFileSync('ao', ['compose', taskDesc], { timeout: AO_TIMEOUT });

// 之后（v1.0.6）
const agent = await launch(orchestratorAgent);
const result = await agent.compose(taskDesc);
```

**实现要点**：
- compose agent 的 systemPrompt 基于 workflow.yml 的节点定义
- 输出格式与 ao compose 一致（YAML 工作流定义）
- ao 仍作为 fallback——deepagents 未安装时自动降级到 `execFileSync('ao', ...)`
- `@deprecated` 标注从"v1.0.5 移除"修正为"v1.0.6 迁移核心逻辑，ao 降为 fallback"

### 2. Sub Agent 状态管理基础

为 Sub Agent 加上最基本的运行状态跟踪：

| 能力 | 实现 |
|------|------|
| Agent 注册表 | 从 `.sofagent/subagents/` 加载 YML 定义（v1.0.4 已有 registry.ts） |
| 运行状态 | 记录启动/活跃/停止时间戳到 `.sofagent/subagents/runtime.json` |
| 基本心跳 | launcher.ts 的 Agent 实例定期写 `lastActive` 到 runtime.json |

**不做的**：
- ❌ Agent 间消息传递（推到 v1.1）
- ❌ LangGraph 状态图（推到 v1.1）
- ❌ 长任务规划（推到 v1.1）

### 3. A/B 真实运行器：模型 API 直跑（方案 B）

v1.0.5 的 `ab-runner.ts` 中 `simulateAgentRun()` 是 mock——直接返回 expected，A/B 永远打平。v1.0.6 替换为真实模型 API 调用。

**设计思路**：Skill 优化的本质是 prompt 质量对比——candidate 和 current 的区别是 Skill 文件内容不同，不是工具链路不同。用最小 Agent（模型 + Skill prompt）就够区分，不需要完整编排引擎。

**改动文件**：`ab-runner.ts`

```typescript
// 之前（v1.0.5 mock）
async function simulateAgentRun(testCase, _agentPath) {
  return { ...testCase.expected }; // 永远满分
}

// 之后（v1.0.6 真实运行）
async function runMinimalAgent(testCase, skillPath) {
  // 1. 读 Skill 文件内容作为 system prompt
  const skillContent = readFileSync(skillPath, 'utf-8');
  // 2. 组装消息：system = skillContent, user = testCase.input
  // 3. 调模型 API（GLM/DeepSeek，复用 daemon 的 API 接入）
  // 4. 解析输出为结构化结果
  // 5. 返回给 scoreCase 评分
}
```

**关键设计**：

| 维度 | 规格 |
|------|------|
| 模型 | 复用 daemon 已有的 API 接入（GLM-5.2 / DeepSeek） |
| 温度 | temperature=0.3 固定，减少随机性 |
| 重试 | 单次 60s 超时，失败重试 1 次，再失败返回零分 |
| 公平性 | candidate 和 current 用相同的调用顺序，同一 testCase 先跑 current 再跑 candidate |
| 降噪 | 每个 testCase 跑 1 次（后续 v1.0.7 可扩为 3 次取平均） |

**eval/types.ts 补充**：TestCase 加 `input` 字段（任务描述），当前只有 `expected`。

**TestCase 示例**：
```yaml
- id: fde-onboard-01
  input: "梳理一个电商客服团队的工作流，识别 AI 节点"
  expected:
    deliverable: "workflow.yml + AI 节点清单"
    key_sections: ["渠道分析", "意图分类", "AI 节点", "人机协作"]
    constraint_check: true
```

**自迭代闭环打通后的完整链路**：

```
Agent 跑任务 → loop-evaluate 评分 → scoring.md（✅ v1.0.1）
  → daemon 检测阈值 20 条 → 24h 防抖（✅ v1.0.4）
    → skillopt-run 生成 candidate（✅ v1.0.4）
      → A/B 对比：candidate vs current 各跑 testCase 集（🆕 v1.0.6）
        → 连续胜出 ≥2 → promote 替换（✅ v1.0.5 逻辑在）
```

**不做的**：
- ❌ 工具调用（模型不调外部 API，纯 prompt 对比）——v1.0.7 接 DeepAgents 后可加
- ❌ 多轮推理（单次调用，不是 Agent loop）——同上
- ❌ 多次采样取平均——v1.0.7 可扩
