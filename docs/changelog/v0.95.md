### 0.2 审计：8 项 A 编号（五层，不对称但每条独立）

> 为什么不是 10 项？A4「不断锁定」是「不删配置」的子集（lock 文件就是配置文件），A7「不坏入口」和 A8「不毁构建」在 SMB 出事路径上是同一件事。硬拆成两条，用户读到会问"删 package-lock.json 到底触发哪条？"——overlap 制造困惑。五层不用硬凑成每层两项，边界层和入口层各 1 项不丢人，反而诚实。

| 层 | ID | 名称 | 查什么 | 怎么查 | 判定 |
|---|:---:|---|---|---|:---:|
| 安全 | A1 | 不碰敏感 | 敏感文件被碰 | 文件名匹配 `.env` `*.pem` `*.key` `id_rsa` `credentials.json` | **FAIL** |
| 安全 | A2 | 不泄密钥 | diff 内容含密钥字符串 | 正则 `AKIA[A-Z0-9]{16}` / `-----BEGIN [A-Z ]*PRIVATE KEY-----` / `sk-[a-zA-Z0-9]{48}` | **FAIL** |
| 边界 | A3 | 不改越界 | 改了任务范围外的文件 | 全量 diff 文件 vs `--task` 声明的文件清单（无清单则跳过） | **WARN** |
| 追溯 | A4 | 不删配置 | 关键配置/lock 文件被删 | diff 含 `D` + 文件名白名单（`.gitignore` `tsconfig.json` `Dockerfile` `Makefile` `deploy.yml` `*.lock` `package-lock.json`） | **WARN** |
| 追溯 | A5 | 不瞒真相 | commit message 含占位词 | 正则 `wip\|todo\|fix me\|placeholder\|xxx` | **WARN** |
| 入口 | A6 | 不坏构建 | 构建/入口配置被破坏性改 | diff 含构建文件（`vite.config` `webpack.config` `rollup.config` `tsconfig` `package.json`）且删除行 > 5 | **WARN** |
| 过程 | A7 | 不存盲改* | 改了没读 | 依赖 Agent 日志，`--silent` 降级跳过 | **WARN** |
| 过程 | A8 | 不逃验证* | 改了没验证 | 依赖 Agent 日志，`--silent` 降级跳过 | **WARN** |

`* A7/A8 需要 Agent 写入 task/logs`，`--silent` 模式降级跳过（同 v0.94 双路径回退逻辑）。

> ⚠️ **A3 实现要求——中英文映射**：文件路径匹配需支持 Unicode。`git diff --name-only` 原样输出中文路径，但当前正则只匹配 ASCII 文件名，中文路径（如 `src/工具/`）会漏检。实现时用 Unicode-aware 正则或走 basename 精确匹配（同 v0.92 #1 检测加固方案）。来源：DeepSeek 双视角评审（「R1 中文匹配失效」）。

## 一、P0：审计配置化（.sofagent/config.yml）

> 来源：DeepSeek PR #2。不同项目的低风险文件不同——Java 项目不关心 package.json，Python 项目不在乎 tsconfig.json。

### 背景

v0.94 前 `LOW_RISK_PATTERNS`、`testPatterns`、规则阈值全部硬编码在 TypeScript 源码里。团队接入需要改源码 + 重新编译——这在企业部署中不可接受。

### 设计

```yaml
# .sofagent/config.yml
audit:
  low_risk_patterns:
    - package-lock.json
    - yarn.lock
    - "*.generated.*"
    - "docs/**"
  test_patterns:
    - "npm test"
    - "npm run test"
    - "pytest"
    - "go test ./..."
  careful_modify_threshold: 0.2  # 超过 20% 无关文件 → WARN
  strict_mode: false             # 默认不强制写日志
```

### 加载优先级

1. 项目根目录 `.sofagent/config.yml`（最高）
2. 用户目录 `~/.sofagent/config.yml`
3. 内置默认值（当前硬编码值，作为 fallback）

### 收益

- FDE 部署者可为每个企业定制审计规则（不碰源码）
- 不同语言项目可用不同配置（Java/Python/Go 各一份）
- 为 v0.96 GitHub Actions 模板打基础

| **LIMITATIONS** | 做不到什么、为什么做不到 | ❌ 不该重复 ROADMAP 的规划、不该展开设计理由 |

**emoji 清理规则**（来源：评审二「emoji 比代码多」）：

## 八点七、双读者模型：给人看的 vs 给 AI 看的

> 来源：作者洞察（非评审吸收）。
>
> **核心命题**：在 AI 时代，GitHub 上的文档有两类读者——**人类**（扫一眼做决策）和 **AI/模型**（检索后整理给向它提问的用户）。未来 AI 读 GitHub 一定比人多。

### 问题：当前文档没有区分两类读者

README 同时在服务两类读者，但没有分层——人类需要"30 秒做决策"的入口，AI 需要"可被结构化检索"的深度内容。两类需求混在一起，结果是人类嫌长（420 行），AI 觉得信息密度不够。

### v0.95 文档分层原则

| 层 | 面向谁 | 写什么 | 代表文档 |
|---|---|---|---|
| **决策层** | 人类（30 秒做决定） | 是什么 + 能不能用 + 怎么开始 + demo | README（≤60 行核心区） |
| **检索层** | AI（深度检索后总结给用户） | 设计决策 + 权衡 + 已知局限 + 完整架构 | ARCHITECTURE / HANDBOOK / DEVELOPMENT / Skill 文件 |
| **证据层** | 双方（人类核实 + AI 引用） | 实测数据 + 实验设计 + 评审报告 | EVIDENCE / CHANGELOG / docs/changelog/ |

### 具体动作

| # | 动作 | 理由 |
|---|------|------|
| ① | README 砍到 ≤60 行核心区（§8.4 已规划），实验数据/架构图/设计哲学全移走 | 人类决策层——30 秒看到 Quick Start + demo + badge |
| ② | ARCHITECTURE 保留完整深度（不砍），加结构化 frontmatter（关键词标签） | AI 检索层——模型能快速定位"为什么用 git diff""Ralph 范式是什么" |
| ③ | 每份文档开头加一行 `> 面向：[人类决策 / AI 检索 / 双方证据]` 标签 | 让人类和 AI 都知道这份文档该不该读 |
| ④ | Skill 文件（.md）保持给 Agent 读的 ≤90 行标准——Agent 是 AI 读者，不是人类读者 | Skill 拆分（§8.1）本质上就是"给 AI 读的文档要做 AI 能消化的粒度" |

> 💡 **双读者模型与 §8.3 文档去重的关系**：去重不是单纯砍内容，是**把内容分到正确的读者层**。审计 git diff 的理由，人类层（README）一句话够了，AI 层（ARCHITECTURE）要完整展开——因为 AI 要能向提问的用户解释"为什么 sofagent 选择 git diff 而不是 LLM 语义分析"。

## 八点八、AI Loop 叙事：10 天 17 版本是证据，不是灾难

> 来源：作者洞察（非评审吸收）。对评审"迭代太快=不稳定"判断的正面回应。

### 评审的判断 vs 实际的含义

| 评审视角 | 传统软件标准 | AI Loop 标准 |
|---------|------------|-------------|
| "v0.47 → v0.94，一个月 20+ 个版本" | ❌ 不稳定，频繁重构定位 | ✅ **这本身就是 sofagent 价值的证据** |
| "v0.85 整版重构定位、v0.91 文档瘦身 47%" | ❌ 自己的纪律不够稳定 | ✅ 两个模型自循环 loop，快速迭代本身就是实验产物 |

### 核心论点

10 天迭代 17 个版本——在传统软件工程里是灾难信号。但在 AI Loop 语境下，这恰恰是 sofagent 价值主张的**活体验证**：

## 八点九、知识库底层引擎：RAGFlow → Graphify

> 来源：作者决策（非评审吸收）。

### 背景

ARCHITECTURE §多设备记忆管理 和 ROADMAP v2.x「企业 Agent 知识库」中原推荐 RAGFlow 作为知识库底层检索引擎。经评估，[Graphify](https://github.com/safishamsi/graphify) 更适合 sofagent 的 SMB 定位。

### 为什么换

| 维度 | RAGFlow | Graphify |
|------|---------|---------|
| 检索方式 | 向量检索 RAG（embedding 相似度） | 知识图谱（tree-sitter AST + 图遍历） |
| 部署重量 | 重——需向量数据库 + embedding 模型 | 轻——基于 AST 解析，无外部依赖 |
| OpenClaw 支持 | 需适配 | 原生支持 |
| SMB 适用性 | 偏重——大企业级场景 | 轻量——SMB 快速部署 |
| 精确度 | 语义近似（有幻觉风险） | 结构精确（AST 节点关系） |

### 处理

- ARCHITECTURE.md §多设备记忆管理：RAGFlow → Graphify，补一句轻量/SMB/OpenClaw 原生支持的理由
- ROADMAP.md v2.x 知识库条目：同步替换
- 不搞三档分法（Graphify for SMB / RAGFlow for Mid / Google Knowledge Catalog for Enterprise）——sofagent 就是针对 SMB 的，一个引擎够了

## 八点十一、Repo 结构决策：保持 monorepo，不拆 lite/FDE

> 来源：作者决策（2026-06-28）。同步讨论铁律 10→6 后 lite 的审计约束纳入。

### 背景

v0.95 后 sofagent 有三个变体：完整版（`sofagent/`，代码项目）、lite（`sofagent-lite/`，SKILL.md + install.sh）、FDE（`sofagent-fde/`，SKILL.md + references/）。曾考虑将 lite 和 FDE 拆为独立 GitHub repo。

### 决策：保持 monorepo，独立 README 入口

| 选项 | 结论 | 理由 |
|------|:----:|------|
| lite/FDE 拆独立 repo | ❌ 不拆 | FDE 仅一个 SKILL.md（15KB）+ references/，lite 仅 SKILL.md（2KB）+ install.sh（1KB），内容量撑不起独立 repo。铁律更新需同步三处，维护成本 > 收益 |
| 保持 monorepo | ✅ 采用 | `github.com/KongFangXun/sofagent/tree/main/sofagent-fde` 本身就是独立入口。每个子目录加独立的 README 入口说明。需要独立宣传时再考虑 fork 或拆 repo |

### lite 的审计约束

lite 是纯 Skill（无代码/CI/运行时），但 8 项审计（A1-A8）要作为**Agent 行为约束**写入 lite 的 SKILL.md：

- Agent 虽然没跑 audit 代码，但 SKILL.md 里的审计规则告诉 Agent「你应该遵守这些」
- lite 用户（个人开发者）靠 Agent 自觉遵守，不像完整版靠 git diff 机器判定
- 不引入 E1-E4 扩展项——lite 场景不需要测试覆盖率/注释率等工程规范约束

## 十、Ralph 范式洞察吸收（哲学层 × 工程层）

> 来源：Geoffrey Huntley「everything is a ralph loop」(2026-01-17 ghuntley.com/loop)、「人与Agent」系列 5 期（2026-06-28）、Ralph vs Hermes 双范式对比、Human in/on/out of the loop、无身份 Agent、CloudTag Agent、多 Agent 组织形态。

### 核心发现：sofagent 是 Ralph 范式的治理层

6 篇笔记从六个角度在论证同一个底层命题——Agent 的记忆该长在哪里？Ralph 的回答是文件系统，Hermes 的回答是 Agent 内部。sofagent 选了 Ralph 路线，但文档里没说出来。

Ralph 路线的六个工程后果（与 sofagent 一一对应）：

| Ralph 原则 | sofagent 对应 | 状态 |
|:--|------|:--:|
| Agent 失忆，文件不失忆 | SKILL.md + task/logs + think.md 三层文件外化 | ✅ |
| git 是唯一地面真相 | sofagent-audit 优先信任 git diff，Agent 日志是辅助 | ✅ |
| 单一窄化反馈水管 | --silent 模式纯 git diff 判定，确定性 exit code | ✅ |
| 循环退出必须客观可验证 | 8 项审计（A1-A8）全部是机器可判定标准 | ✅ |
| 新鲜上下文 + 持久化状态分离 | 三层加载链（新鲜注入）+ task/logs（持久化状态） | ✅ |
| 从人审AI到AI审AI | 审计工具是第一步；v0.96 审计闭环是第二步 | ⏳ |

Ralph 原帖（ghuntley.com/loop）关键引用：

> "Ralph is monolithic. Ralph works autonomously in a single repository as a single process that performs one task per loop." — Geoffrey Huntley, 2026-01-17

> "It's important to watch the loop as that is where your personal development and learning will come from. When you see a failure domain – put on your engineering hat and resolve the problem so it never happens again." — Geoffrey Huntley

sofagent 的审计工具就是「watch the loop」的机器版——人不用盯着 Agent 跑了，审计报告告诉你哪一步出了问题。
