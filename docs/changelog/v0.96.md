## 概述

v0.96 的哲学基础来自 2026 年上半年两条独立但交汇的技术线：

**线一：Geoffrey Huntley 的 Ralph 循环**

> "Everything is a Ralph Loop" — ghuntley.com/loop, 2026-01-17

Ralph 循环的核心不是技术（一行 bash），而是范式：**把模型当作随机过程而非员工，用循环驯化随机性**。每一轮 Agent 都是失忆的婴儿，记忆不在模型里，在文件系统里。git 是唯一的地面真相。

Huntley 的原始代码只有 5 行：

```bash
while :; do
    cat PROMPT.md | claude-code
done
```

但它的设计深度远超代码量：Stop Hook 拦截退出信号、新鲜上下文每轮刷新、持久化状态通过文件传承、「完成承诺」必须是客观可验证的标准。

**线二：「人与 Agent」系列五期 + CloudTag + Hermes 对比**

五期从五个角度追问同一个问题——Agent 的记忆该长在哪里？

1. Ralph 循环：记忆长在项目文件里（Agent 失忆，文件不失忆）
2. Hermes Agent：记忆长在 Agent 内部（终身陪伴，自我进化）
3. Human in/on/out of the loop：人机契约的三种形态，本质是 OODA 决策环上 Decide 环的归属
4. 多 Agent 组织：记忆长在共享文件 / 队长 Agent / 对话历史——三条路对应三种组织形态
5. 无身份 Agent：终极形态——身份有成本，状态最贵，HTTP 无状态设计支撑互联网三十年

CloudTag (Anthropic)：65% PR 由 Agent 创建，每个频道有独立记忆和权限——这是 Ralph 范式在 Anthropic 内部的生产级验证。

**两条线的交汇点就是 sofagent 的定位**：

> sofagent 不是「又一套 Agent 框架」——是 Ralph 范式的治理层。Ralph 让 Agent 能跑起来并且不跑偏，sofagent 让跑完之后有据可查。

## 二、P1：审计闭环六步——从单次判定到持续改进

> 来源：OpenAI Tax AI 案例（FDE 研报笔记 2026-06-27）+ Ralph 循环的「watch the loop」哲学

### 当前状态

sofagent-audit 只做到了「检测→报告」，相当于 OODA 决策环的 O-O-D（观察→判断→决策），缺少 Act（行动）。具体说：

```
当前（四步缺一）：  git diff → 逐条规则匹配 → PASS/WARN/FAIL → （停在这里）
目标（完整闭环）：  git diff → 逐条规则匹配 → PASS/WARN/FAIL → 行动
                    ↑                                                      │
                    └──────────── 分类归因 ←── 根因分析 ←──────────────┘
```

### 六步闭环设计

借鉴 OpenAI FDE 团队 Tax AI 项目的持续改进闭环：

```
检测（git diff 扫描改动）
  ↓
分类（规则匹配：安全/边界/追溯/入口/过程）
  ↓
根因（为什么这次 FAIL 了？同类问题之前出现过吗？）
  ↓
改进（规则本身的阈值需要调吗？Agent 的行为模式需要改吗？）
  ↓
回归（改进后重新审计同一批 diff，确认旧问题不重犯）
  ↓
上线（规则更新 + threshold 调整 + .sofagent/config.yml 版本化）
```

### 工程实现

| 步骤 | 产物 | 技术 |
|------|------|------|
| 检测 + 分类 | 现有功能 | 已完成（v0.94） |
| 根因 | `audit-root-cause.ts` | 聚合本月审计历史，按规则/文件/Agent 三个维度归因 |
| 改进 | `config-suggestion.json` | 基于根因分析自动建议阈值调整 |
| 回归 | `audit-regression.ts` | 用历史 diff 重跑更新后的规则 |
| 上线 | git commit config.yml | 配置变更进入版本控制 |

## 四、P1：OODA × 审计 = 人机契约可视化

> 来源：「人与Agent」系列第三期——Human in/on/out of the loop + OODA 模型

### 当前审计输出的不足

审计工具输出的是 PASS / WARN / FAIL，但没有告诉用户「现在你需要做什么」。

```
当前:  ⚠️ A3 不改越界: 3 个文件不在任务范围内
改进:  ⚠️ A3 不改越界: 3 个文件不在任务范围内
      [on the loop] 建议人工审核这 3 个文件的改动是否必要
```

### 设计

在每条审计结果后追加 `[in the loop]` / `[on the loop]` / `[out of the loop]` 标签：

| 审计结果 | OODA 位置 | 人需要做什么 |
|------|------|------|
| FAIL | in the loop | 必须人工处理——审计不能替你决策 |
| WARN | on the loop | 通知到人，由人判断是否需要介入 |
| PASS | out of the loop | Agent 自己过了，人不需要参与 |

这不只是 UI 美化——它把审计工具从一个「检测器」升级为「决策助手」，让 FDE 工程师或企业 IT 一眼知道哪些需要自己动手。

## 五、P2：审计历史聚合 + 反馈回路

> 来源：FDE 笔记——「FDE 的反馈回路：现场经验→产品迭代」+ Ralph 的「watch the loop」

`scripts/audit-summary.sh`（v0.95 已规划，v0.96 实现）：

- 输入：一个月内的所有审计输出
- 输出：
  - 本月触发最多的 3 条规则（该调阈值了？）
  - 被标记最多的 5 个文件（设计有问题？）
  - 趋势图：FAIL/WARN 比例是否在改善

本质是在做 Huntley 说的「watch the loop and resolve failure domains」——只是用脚本替代了人盯着终端。
