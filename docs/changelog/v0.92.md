## 一、P0 修复（安全硬伤 — 必须修）

### 1. execSync 命令注入（🔴 安全）

**问题**：`sofagent-audit/src/diff-parser.ts:22` 和 `rule-10-honest-report.ts:27` 中，用户输入的 CLI 参数直接拼接到命令字符串。

注入机制：

| 调用 | 机制 | 风险 |
|------|------|------|
| `execSync('git diff ${range}')` | Node.js `execSync` 对字符串参数**会** spawn shell（`/bin/sh -c`） | `range = "HEAD~1..HEAD; rm -rf /"` → shell 会执行 `rm`。**这是真正的 shell 注入。** |
| `execFileSync('git', ['diff', range])` | `execFileSync` **不** spawn shell——直接调用 git 二进制，参数作为数组传递 | `range` 中的 `;` 只是 git 的参数，git 报 invalid ref 而非执行命令。**安全。** |

> `execSync(string)` 确实 spawn `/bin/sh -c`。`execFileSync(file, args[])` 才不经过 shell。

**额外风险**：即使换了 `execFileSync`，`range` 参数仍可注入 git flag（如 `--output=/etc/passwd` 或 `-c core.gitProxy='evil'`）。**必须加参数格式校验。**

**修复**：
| 文件 | 方案 |
|------|------|
| `diff-parser.ts:22,57` | ① 参数格式校验：`range` 只允许 `[a-zA-Z0-9~^.\-]` 字符，拒绝其他字符并报错退出；② 改用 `execFileSync('git', ['diff', '--name-status', range])` 传参数数组，彻底避免 shell spawn；③ 同样替换 line 57 的 `git diff ${range} -- "${path}"` → `execFileSync('git', ['diff', range, '--', path])` |
| `rule-10-honest-report.ts:27` | 改用 `execFileSync('git', ['log', '-1', '--pretty=%B'])`，无用户输入无需校验 |
| 所有 `execSync` 调用 | 全局搜索，一律改为 `execFileSync` + 参数数组 |

### 3. 铁律 #1 检测可靠性边界（🔴 设计债）

**问题**：铁律 #1「先读再用」的检测逻辑——在 Agent 写入的 MD 日志文件中用正则寻找文件名，再用子字符串匹配（`readFile.includes(fileName)`）——误报率预估 35-50%，漏报率预估 30-40%。

核心缺陷：
- 文件名子串匹配：`config.ts` 匹配 `tsconfig.json`（假阳性）
- 缺乏操作语义：日志中"提到"了文件名 ≠ Agent "读取"了文件
- 正则只匹配特定扩展名：`Makefile`、`Dockerfile` 等无扩展名文件漏报

**修复**（分三步）：
| 步骤 | 文件 | 改动 |
|------|------|------|
| **第一步（v0.92）** | `rule-01-read-before-write.ts` | ① 子串匹配 → 精确文件名匹配（比对 `path.basename`）；② 正则扩展支持无扩展名文件（`Makefile`、`Dockerfile`、`.env`）；③ 仅匹配日志中 Read 操作条目（不是整篇日志的任意文件名引用） |
| **第二步（v0.92）** | `LIMITATIONS.md` | 标注检测可靠性的诚实边界：「铁律 #1 检测基于 Agent 任务日志的正则匹配，预估误报率 X%、漏报率 Y%（v0.92 实测后填入）。并非 100% 可靠——Agent 可在日志中伪造读取记录。」 |
| **第三步（v0.93+ 规划）** | — | 结构化日志方案：task/logs 从自然语言 MD → JSONL 格式（操作类型 + 文件路径 + 时间戳），让审计工具做精确匹配而非启发式猜测 |
