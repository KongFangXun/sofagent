## 背景

v1.2.0 完成了物理结构重构。v1.2.1 有三个核心交付：

1. **数据目录重构**：将散落在 `.sofagent/` 的 669 个运行时数据文件统一迁移到 `data/` 可见目录——用户能直接打开、Dashboard 能直接消费、备份只需拷贝一个目录。这是 v1.2.2 Dashboard 的前置基础设施。

3. **SubAgent 可见性 L2**：worker 内部可观测，Dashboard 实时面板的数据前置。

1. **ToolGate 出口已接好但没人用**——`createToolGate()` + `toolGate` 单例都 export 了，但 `loop/nodes.ts` 只用 `ENGINEER_TOOLS`，没调 gate。门锁挂在门框上了，开门没拧钥匙。
2. **custom/ 目录骨架就位但加载链没声明**——`custom/README.md` 写了加载顺序，但 `SKILL.md` 加载链没提 custom/，`file-deploy.sh` 也不处理 custom/ 目录。用户写了规则但 Agent 不会自动加载。

v1.2.1 补这两个闭环，外加 custom/README 从"说明书"升级为"操作手册"。

### P3 · SubAgent 可见性 L2（worker 细粒度埋点）

**背景**：v1.2.0 的 FORGE fresh-eyes-driver 已实现 L1 可见性（轮次/步骤级，driver 编排层）。但 worker（SubAgent）内部是黑盒——A 正在读哪些文件、B 正在改哪行、token 消耗实时变化，driver 在 worker 退出前完全不可见。这是 Dashboard 实时面板（v1.2.2 L3）的数据前置缺口。

**三层可见性架构**（L1 已交付，L2 本版本，L3 在 v1.2.2）：

| 层 | 粒度 | 数据源 | 状态 |
|----|------|--------|:----:|
| **L1 driver** | 轮次/步骤完成 | `progress.jsonl` + `status.json` | ✅ v1.2.0 已交付 |
| **L2 worker** | 工具调用序列 + 模型推理心跳 | `sub-progress-A.jsonl` + `sub-progress-B.jsonl` | 🔧 v1.2.1 |
| **L3 Dashboard** | 实时面板（进度条 + 工具流 + 成本曲线） | 聚合 L1+L2 数据渲染 | 📋 v1.2.2 |

**设计**：利用 deepagents 的 middleware 机制，写一个 `ProgressMiddleware`，挂在每次工具调用（`sf_read`/`sf_write`/`sf_edit`/`ls`/`glob`/`grep`）和模型推理事件上，往 worker 自己的 `sub-progress-<role>.jsonl` 追加微事件：

```jsonl
{"ts":"...","role":"A","tool":"read","target":"README.md","phase":"start"}
{"ts":"...","role":"A","tool":"read","target":"README.md","phase":"end","duration":120}
{"ts":"...","role":"B","tool":"edit","target":"tools.ts","phase":"start","lines":"+3/-1"}
{"ts":"...","role":"B","event":"llm-chunk","tokens":523}
```

**Dashboard 能看到的实时信号**（v1.2.2 消费 L2 数据）：
- **工具调用流**：A 读了 README → grep CHANGELOG → B 改了 tools.ts 第 45 行...
- **实时成本**：usage.jsonl（已有）+ sub-progress token 事件 → 成本曲线
- **双 agent 心跳**：最后一条 sub-progress 时间戳判断是否卡死

**文件清单**：

| 文件 | 改动 | 说明 |
|------|------|------|
| `FORGE/src/progress-middleware.ts` | 新建 | DeepAgents middleware：挂工具调用前后 + LLM 流式 chunk 事件 |
| `FORGE/src/fresh-eyes-driver.mjs` | 修改 | `runWorker()` 创建 agent 时注入 ProgressMiddleware，传入 `roundDir` + `role` |
| `FORGE/src/__tests__/progress-middleware.test.ts` | 新建 | 单测：工具调用写事件 / LLM chunk 写事件 / 错误不阻断主流程 |

#### LangGraph + Harness 数据流分层

**架构原则**：Graph（LangGraph StateGraph）是执行层，Harness（MD/JSONL 数据写入器）是数据层。

```
LangGraph 编排层（结构化状态）
├── plan → engineer → audit → reviewer（节点间通过 checkpoint 传递状态）
└── 每个节点产出结构化结果（taskId / diff / auditResult...）

     ↓ 数据写入器

Harness 数据层（人类可读 + Dashboard 可消费）
├── think.md     ← engine/think 从 audit 结果生成反思
├── task/logs/   ← 节点完成时写入（log-checker / verify-evidence / cost-baseline）
├── history.jsonl ← audit 节点写入 21 条规则结果
├── data-sovereignty/ ← v1.2.2 新增：从 LLM 调用事件写入
└── daemon-health.json ← daemon 健康状态（本版本新增）
```

**关键**：Graph 不做数据格式化——它只传递结构化字段。数据写入器（think-generator / log-checker / health-reporter）负责把 Graph 产出转成 Dashboard 可消费的格式。这个分层 v1.2.1 已部分实现（ProgressMiddleware L2 事件写入），v1.2.2 的 DataSovereigntyRecord 挂到 LLM 调用后即可补齐。

**trust-but-verify 教训**：工程师用 mock 跑单元测试全绿（IS_PASS: YES），但 QA 跑真实 CLI 端到端通过率仅 14.3%——mock 绕过了真实审计引擎，掩盖了 golden set 与 audit 规则不匹配。逐条读 21 个 `rule-*.ts` 重写后 14.3% → 100%。

**关键设计决策**：
1. **A2/A9 占位符方案**：golden set 的 fail 用例需含假密钥/injection 文本，但字面串会触发 A2/A9 扫源码本身 → commit hook 拦截。解法：YAML 用 `{{SK_PREFIX}}`/`{{INJ_PHRASE}}` 占位符，`loadGoldenSet()` 运行时替换，映射值用 base64 编码存储。源码安全 + audit 检测有效。
2. **convertAuditResult 三态**：exitCode 0=PASS, 1=WARN, 2=FAIL（原版把 WARN 当 FAIL 是 bug）
3. **DiffFile 接口**：实际代码用 `lines` 字段（unified-diff 行数组带 +/- 前缀），非 PRD 假设的 `added/deleted`
