# v1.2.2 开发日志 — 数据主权审计 + 混合模型路由 + FDE Dashboard 原型 🔧

> ⚠️ **本文档为开发规划，尚未实现。** 以下所有代码、接口、文件路径均为设计稿，`engine/` 下尚无对应代码。
> 状态：规划中（未开发） · 孔放勋 · 2026-07-25
> 前置依赖：v1.2.0（物理结构大重构）+ v1.2.1（custom/ 闭环 + ToolGate 接入）

## 背景

v1.2.0 完成了物理结构重构，v1.2.1 补了 custom/ 闭环和 ToolGate 接入。但有一个企业采购的**硬阻塞项**一直没解决：

**企业最大的恐惧：我的数据去了哪？**

当前 sofagent 的所有 LLM 调用都走云端大模型 API。企业不知道：
1. 云端到底调用了什么？
2. 本地到底执行了什么？
3. 数据到底有没有走？走了哪儿？是否安全？
4. 每一次的任务到底是什么？

已有客户反馈：**硬件客户的代码出现在了 AI 的输出中**——证明数据进了大模型训练集。沙盒也拦不住，因为只要走 API key，数据就一定被大模型拿去训练。

v1.2.2 将解决这个问题，两个核心交付：
- **混合模型路由**：Harness 按任务复杂度路由到云端/本地，敏感数据不出内网
- **数据主权审计**：4 维审计追踪（云端调用 / 本地执行 / 数据流向 / 任务记录），每次调用都被监控和审计

这两个交付是 v3.x 分层模型架构的**前置基础设施**——没有路由层和审计追踪，v3.x 的三层模型就是空中楼阁。

## LUI 感知

用户通过 Agent 对话感知：「我问 Agent 能不能帮我整理绩效数据——它告诉我'这个任务涉及敏感数据，已路由到本地模型执行，数据未出内网'。我打开 Dashboard，看到今天的审计报告：云端调用 3 次（都是通用知识查询），本地执行 12 次（全部业务数据），数据流出 0 次。我心里踏实了。」

## 交付项

### P0 · 数据主权审计追踪（DataSovereigntyAudit）

**问题**：当前 LLM 调用无审计追踪。Agent 调了什么大模型、传了什么数据、返回了什么——全是黑盒。企业无法回答"我的数据安全吗"这个问题。

**设计**：每次 LLM 调用和工具调用都记录 4 维审计日志：

```typescript
interface DataSovereigntyRecord {
  // 维度 1：云端调用了什么？
  cloudCall: {
    timestamp: string;           // ISO 8601
    provider: string;            // 'openai' | 'anthropic' | 'deepseek' | 'qwen' | ...
    model: string;               // 'gpt-4o' | 'claude-3-5-sonnet' | ...
    endpoint: string;            // API endpoint URL
    tokenCount: { input: number; output: number };
    purpose: string;             // 'planning' | 'translation' | 'reasoning' | 'code-gen'
  };

  // 维度 2：本地到底执行了什么？
  localAction: {
    type: 'file-read' | 'file-write' | 'tool-call' | 'model-inference';
    target: string;              // 文件路径 / 工具名 / 模型名
    description: string;         // 人可读描述
    auditResult: 'PASS' | 'WARN' | 'FAIL';  // Harness 审计结果
  };

  // 维度 3：数据到底有没有走？走了哪儿？
  dataFlow: {
    direction: 'outbound' | 'inbound' | 'local-only';
    sensitivity: 'public' | 'internal' | 'restricted' | 'confidential';
    fields: string[];            // 涉及的数据字段（脱敏后记录）
    destination: 'cloud-api' | 'local-model' | 'local-file' | 'local-tool';
    redacted: boolean;           // 是否已脱敏
  };

  // 维度 4：每一次的任务到底是什么？
  taskContext: {
    taskId: string;              // 唯一任务 ID
    parentTaskId?: string;       // 父任务（编排链路）
    userIntent: string;          // 用户原始意图（脱敏摘要）
    workflowId?: string;         // 关联的 workflow
    agentRole: string;           // 'engineer' | 'reviewer' | 'audit' | 'fde'
  };
}
```

### P1 · 混合模型路由层（ModelRouter）

**问题**：所有任务都走云端大模型，敏感数据不得不出内网。需要路由层把任务分发到不同模型。

**设计**：在 orchestrator 的工具调用层插入路由节点，根据任务类型和数据敏感度选择执行模型。

```typescript
interface ModelRoute {
  // 路由决策
  target: 'cloud-strong' | 'cloud-fast' | 'local-executor' | 'local-pipeline';
  
  // 决策依据
  reason: 'complex-reasoning'    // 复杂推理 → 云端 32B+
      | 'simple-translation'     // 简单翻译/摘要 → 云端快速模型
      | 'workflow-execution'     // workflow 执行 → 本地 7B
      | 'fixed-pipeline'         // 固定管道 → 本地 0.5B
      | 'sensitive-data';        // 敏感数据强制本地
  
  // 数据安全级别
  sensitivity: 'public' | 'internal' | 'restricted' | 'confidential';
}

class ModelRouter {
  // 输入：用户自然语言 Prompt + 当前任务上下文
  // 输出：路由决策（走哪个模型）+ 标准化任务指令（如果走本地）
  route(prompt: string, context: TaskContext): ModelRoute {
    // 1. 数据敏感度检查（sensitivity frontmatter + 文件内容扫描）
    // 2. 任务复杂度评估（prompt 结构分析）
    // 3. 路由决策
  }
}
```

**路由规则**：

| 数据敏感度 | 任务类型 | 路由到 | 说明 |
|---------|---------|--------|------|
| public | 任意 | cloud-fast | 公开信息，走快速模型 |
| internal | 简单（翻译/摘要） | cloud-fast | 内部信息但非敏感 |
| internal | 复杂（推理/规划） | cloud-strong | 内部信息但需大模型推理 |
| restricted | 任意 | local-executor (7B) | 敏感数据，不出内网 |
| confidential | 任意 | local-pipeline (0.5B) | 最高级别，只在管道层处理 |

**Prompt → 标准化任务指令翻译**（云端大模型负责）：

```
用户: "帮我把这月的绩效数据按部门汇总"
     ↓ 云端大模型翻译
{
  "task": "aggregate_and_render",
  "group_by": "department",
  "source": "local://performance_202607.xlsx",
  "template": "monthly_report_v3",
  "output": "local://report.md"
}
     ↓ 路由到本地 7B 执行（数据不出内网）
```

**本地模型服务**：通过 Ollama API 调用本地模型（`http://localhost:11434/api/generate`）。v1.2.2 只做路由 + 调用接口，不做精调（精调是 v3.x）。

**配置**：`.sofagent/config/model-router.json`

```json
{
  "cloud": {
    "strong": { "provider": "openai", "model": "gpt-4o" },
    "fast": { "provider": "deepseek", "model": "deepseek-chat" }
  },
  "local": {
    "executor": { "provider": "ollama", "model": "qwen2.5:7b", "endpoint": "http://localhost:11434" },
    "pipeline": { "provider": "ollama", "model": "qwen2.5:0.5b", "endpoint": "http://localhost:11434" }
  },
  "policy": {
    "restrictedForcesLocal": true,
    "confidentialForcesPipeline": true,
    "fallbackOnLocalFailure": "cloud-strong"
  }
}
```

### P3 · Skill 分层升级策略实现

| 策略 | 行为 | 实现位置 |

### P4 · Graph Engine 基础设施

> 理论基础：Carlos E. Perez·[From Loop Engineering to Graph Engineering?](https://engineering.zooz.com/intuitionmachine/from-loop-engineering-to-graph-engineering-d3ebeb08511c)（四类失效+grounding）+ Addy Osmani·Loop Engineering + 行业五层工程化框架。详见 [ARCHITECTURE §Graph Engineering 视角](../../ARCHITECTURE.md#graph-engineering-视角控制图--stategraph)。

**④ Planner 节点**：START → `plan` → engineer。LLM 把复杂任务拆成子任务列表存入 `LoopGraphState.artifacts.subtasks`，engineer 逐个子任务执行。不新建包——扩展 `graph.ts` + 新增 `plan-node.ts`。

**⑤ 降级路由链**：扩展 `routeAfterAudit`——adit FAIL 后不再只 retry → pass：
```
engineer → audit → FAIL
→ 第 1 次：retry engineer（现有）
→ 第 2 次：自动降级任务范围（"先做最小可行版本"）
→ 第 3 次：标记低可信 + 继续（不 blocked）
→ 超限：人工确认
```
`LoopGraphState` 新增 `degradationLevel` 字段。

**⑥ engineer-decide / engineer-execute 分层**：把 engineer 节点拆为两层——`decide`（LLM 层，云 32B，判定"改什么"→输出结构化决策）＋ `execute`（代码层，确定性执行：文件编辑/git 暂存/diff）。与 ModelRouter 对接——decide 走云，execute 走本地。

**Dashboard Graph Engine 状态卡片**：Dashboard 首页新增 Graph Engine 状态卡片（当前活跃的 Org Graph 节点 + Work Graph 任务数）。
