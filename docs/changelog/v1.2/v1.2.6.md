## 🔗 激活链 Phase 2 前半：映射表 + 注册扩展

### 定位

v1.2.5 Phase 1 完成了企业 Agent 注册（车厢造好挂上去了）。v1.2.6 让 workflow-parser 和 registry 认识企业 Agent 类型——为 v1.2.7 的 StateGraph 构建打基础。

### 交付

| 文件 | 改动 | 说明 |
|------|------|------|
| `engine/orchestrator/src/workflow-parser.ts` | 修改 | 扩展映射表支持 `agent: enterprise` 类型 |
| `engine/orchestrator/src/registry.ts` | 修改 | `SubAgentDefinition` 增加 hitl / hitlConfig / knowledgeDomain 字段 |
| `engine/orchestrator/src/__tests__/workflow-parser.test.ts` | 修改 | 新增 enterprise agent 映射测试 |

### 关键改动

**workflow-parser.ts**：当前映射表写死 4 个内置 Agent。新增 `enterprise` 类型，通过 `listAgents()` 动态查找注册的 YML（而非写死映射）。enterprise 节点查找失败时报错（不静默降级）。

**registry.ts**：`SubAgentDefinition` 接口新增 `hitl` / `hitlConfig` / `knowledgeDomain` 字段（全部可选，向后兼容）。同步扩展 `loadDefinition()` 解析逻辑，确保 YML 写入的新字段能被读回。

### 2A · workflow.yml 格式对齐（activate ↔ workflow-parser 共用 schema）

**背景**：实测发现两个解析器对同一份交付物期望不同 YAML 结构——`activate` 期望平铺格式（顶层 `name` / `nodes[]`），`workflow-parser` 期望嵌套格式（`workflow:` 根节点）。同一份 workflow.yml 无法同时喂给两个解析器，导致企业 Agent 注册了但编排读不到。

**交付**：`activate.ts` 读取层兼容嵌套格式（`const wf = doc['workflow'] ?? doc`），统一为嵌套格式标准；写入侧仍产嵌套。`FDE/GUIDE.md` 明确 workflow.yml 标准格式（嵌套 `workflow:` 根节点），避免 FDE 交付物与引擎期望格式漂移。

**验收**：同一份嵌套格式 workflow.yml 能同时通过 `activate` 和 `parseWorkflowYaml` 解析；activate 对平铺旧格式仍向后兼容。

### 2B · SOFAGENT_LLM 环境变量打通（编排执行前置修复）

**背景**：`resolveLLMModel()` 只认 `SOFAGENT_LLM`，为空时直接 return null 无警告。用户配了 `SOFAGENT_LLM_A` / `SOFAGENT_LLM_B`（FORGE 审查用）+ API key，但编排主链路永远跑不通——`subagent run fde` 返回"编排引擎未返回结果"。

**交付**：`resolveLLMModel` / `resolveApiKey` 增加 `SOFAGENT_LLM_A` / `SOFAGENT_LLM_B` 回退。`SOFAGENT_LLM` 显式设置时优先级不变（显式 > A/B 回退）。

**验收**：仅设 `SOFAGENT_LLM_A` + `SOFAGENT_LLM_A_API_KEY`（不设 `SOFAGENT_LLM`）时，`resolveLLMModel(null)` 返回模型实例。

## 🔌 MCP 交付链路修补

### 定位

MCP 覆盖度审计发现 13 个应 MCP 化而未做的缺口 tool，用户已拍板版本归属。v1.2.6 承接其中最紧急的四项——它们都是「能力已在、只差 MCP 暴露」的交付链路修补：两个是只读查询（实现现成），两个闭合激活链的断点。

### 交付（4 个 tool）

| tool | 所属包 | 一句话 |
|------|--------|--------|
| `daemon_status` | daemon | 查 daemon 运行状态：heartbeat、健康报告、推送队列/重试失败数、联邦 peers 概要。实现现成（`readHealthFile` / `checkDaemonHealth` 已导出）。**只读查询，不含 start/stop 进程控制** |
| `list_agents` | orchestrator | 列出已注册 SubAgent（含企业 Agent），闭合 ACTIVATE→ORCHESTRATE 发现入口。实现现成（`registry.listAgents`） |
| `list_concepts` | mcp | 列出全部 concept，与 `list_entities` 对称（实现位于 mcp-server.ts，照抄 toolListEntities 读 knowledge 目录模式） |
| `hitl_resolve` | orchestrator | 对 awaiting_human 挂起的 HITL checkpoint 写入人工决策（approve/reject）并续跑，闭合编排人工确认环 |

### 安全边界（用户已背书）

1. daemon 类 tool 只做**只读查询**——start/stop 等进程控制永不 MCP 化（防恶意 Agent 滥用）
2. 联邦 peers 只在 `daemon_status` 内含**只读概要**——pair/unpair 配对操作不 MCP 化

## Deployment Sizing 表格（README 企业 IT 参考）

**交付**：README 新增 Deployment Sizing 三档表格（个人/中型/企业级），明确 CPU/内存/磁盘/并发 Agent 数量，企业 IT 问"几核几 G"能直接答。

**三档规格**：
- 个人（1-3 Agent）：1 核 / 512 MB / 500 MB
- 中型（5-10 Agent）：2 核 / 1 GB / 2 GB

**数据来源**：各包 dist 实测（daemon 1.2M / mcp 340K / audit 1.2M / orchestrator 1.1M / core 1.0M），运行时数据实测（~94 MB），daemon 心跳 5min 间隔 + maxRetries=3。
