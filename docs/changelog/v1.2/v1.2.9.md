## 交付一：🔧 FORGE Driver 短任务化（P0 · 核心架构改造）

### 问题诊断

v1.2.5-v1.2.8 的 FORGE driver 实跑反复暴露同一个根因：**LLM 在 30-100 次工具调用的长循环中不可控**——不收敛、碎片文本、幻觉、需要三层熔断兜底。这不是某个模型的缺陷，是当前 LLM 能力天花板。

### 实现

v1.2.9 从架构层面解决：**把每个步骤拆成独立短 worker，每个 worker 只做一件事、调 5-8 次工具、30 秒内完成。** driver 编排层负责串行/并行调度，worker 落在 LLM 舒适区内。

- **fresh-eyes-loop**：a-check/b-check 各 12 个独立 perspective worker（12 × A + 12 × B = 24 文件），并行执行
- **release-gate-loop**：acceptance 按 scenario 分片（12 片），f-fix 按问题拆分
- **preModelHook 三级阈值**（run-12 增强）：TOKEN_SOFT 60k / TOKEN_HARD 100k，基于 token 估算而非纯消息条数
- **effectiveHardLimit 跨闭包修复**（run-07 发现）：变量从 stateModifier 闭包提到 agent 定义前的共同作用域

### 验收标准

- `FORGE/src/fresh-eyes-driver.test.mjs`：新增并行多 worker 调度测试
- fresh-eyes-loop run-12：2 轮 clean stop，P0=0 P1=0 P2=0
- release-gate-loop run-07：verdict=PASS

### 明确不做

- 不改 LangGraph recursionLimit（25 已够用，短任务化后 5-8 次调用远在舒适区）
- 不做 prompt caching（API 侧优化，不影响架构）

## 交付二：⏸️ Checkpoint/Resume worker 级（P0）

### 实现

v1.2.8 已有 checkpoint/resume 基础设计。v1.2.9 结合短任务化落地：断点粒度从"每轮"细化到"每个 worker"。

```json
{
  "round": 1,
  "workers": {
    "a-check-p1": { "status": "done", "output": "check-a-p1.md" },
    "a-check-p2": { "status": "pending" }
  },
  "completedWorkers": ["a-check-p1"],
  "pendingWorkers": ["a-check-p2", ..., "b-check-p12"]
}
```

- `--resume` 参数 + loadResumePoint 断点恢复逻辑
- 损坏容错：resume-point.json 损坏时从头开始，不崩溃

### 验收标准

- `FORGE/src/driver-base.test.mjs`：断点写入/读取/损坏容错测试

## 交付三：🏠 PM2 守护进程（P1）

### 实现

driver 不应该跑在 WorkBuddy session 里——session 过夜清理会杀后台进程。PM2 提供：被杀自动重启 + 日志持久化 + 开机自启。

PM2 + Checkpoint 联动：driver 崩溃 → PM2 自动重启 → `--resume` 读取断点 → 从最后一个未完成 worker 续跑。

### 涉及文件

| 文件 | 说明 |
|------|------|
| `FORGE/ecosystem.config.mjs` | PM2 配置（两个 driver 的启动配置） |
| `tools/forge-pm2-start.sh` | PM2 启动脚本（封装常用命令） |
| `FORGE/SKILL/fresh-eyes-loop/SKILL.md` | 监控协议新增 PM2 启动方式 |

## 交付四：🔗 激活链 Phase 3 后半（P1 · HITL + 审计集成 + 异常处理）

### 实现

v1.2.8 让 dag-runner 能跑企业 Agent。v1.2.9 补上三个关键运行时能力：

- ⚡ **HITL 中断**：节点执行到此处暂停 → 向用户展示方案 → 等待确认 → 继续/终止
- **自动审计**：每个节点执行后自动触发审计，审计 FAIL → 暂停工作流 + 通知用户
- **异常兜底**：异常写入 exceptions 队列，根据节点配置决定重试 or 跳过

## 交付九：🧠 FORGE 上下文预算管理（P1）

### 问题诊断

FORGE worker 跑长任务时上下文膨胀——工具调用越多、工具输出越长，prompt_tokens 从 30K 膨胀到 100K+ 直至 OOM。学习 ClaudeCode 上下文管理机制后，评估 5 项技术中 3 项可落地。

### 实现

| 层 | 做什么 | 文件 | 说明 |
|----|--------|------|------|
| L1 工具输出截断 + 渐进式磁盘加载 | 超长输出按步骤预算截断 + 完整版写磁盘 | `tool-output-budget.mjs` | `truncateToolOutput` 新增 `diskPath` 参数；截断标记附文件路径，agent 可 sf_read 完整版 |
| L2 小模型总结 | 审查类步骤超阈值输出用 LLM 总结 | `tool-output-budget.mjs` | `summarizeToolOutput` + `createSmartTruncator`；模型从 `FORGE/models/glm-5.2.mjs` 动态读取；失败 fallback L1 截断 |
| L3 动态 token 裁剪 | preModelHook 基于 token 估算激进修剪 | `fresh-eyes-driver.mjs` | `estimateTokens`（chars/4 粗估）+ TOKEN_HARD=100K 激进裁剪到 12 条 |

**向后兼容**：所有新参数（`diskPath` / `diskDir`）可选，不传时行为与 v1.2.8 完全一致。三个 driver 的 import 均为 named import，无需改动。

**预埋 API**：`createSmartTruncator` / `summarizeToolOutput` 当前未被 driver 调用——预留给后续版本接线。
