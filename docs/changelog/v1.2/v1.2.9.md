## 🔧 FORGE Driver 短任务化（核心改造）

### 定位

v1.2.5-v1.2.8 的 FORGE driver 实跑反复暴露同一个根因：**LLM 在 30-100 次工具调用的长循环中不可控**——不收敛、碎片文本、幻觉、需要三层熔断兜底。这不是某个模型的缺陷，是当前 LLM 能力天花板。

v1.2.9 从架构层面解决：**把每个步骤拆成独立短 worker，每个 worker 只做一件事、调 5-8 次工具、30 秒内完成。** driver 编排层负责串行/并行调度，worker 落在 LLM 舒适区内。

### 改造范围

**fresh-eyes-loop**（当前 6 步 → 拆成 28+ 个短任务）：

| 当前步骤 | 当前行为 | 改造后 |
|---|---|---|
| a-check | 1 个 worker 跑 12 视角（30-100 次调用） | **12 个独立 worker**，每个 1 视角（5-8 次调用），并行执行 |
| b-check | 同上 | **12 个独立 worker**，同上 |
| a-consolidate | 合并 2 份大报告（需 32000 token） | 合并 **24 份小报告** → findings.md + result.md（输入更结构化） |
| b-fix | 1 个 worker 按全部 P0/P1 分片修复 | **按问题拆分**：每个 P0/P1 一个独立 fix worker（已有 sharded 机制，优化粒度） |
| b-audit | driver 步骤（不变） | 不变 |
| a-verify | 1 个 worker 验证全部修复 | **按修复拆分**：每个修复一个独立 verify worker |

**release-gate-loop**（当前 8 步，部分步骤已短小）：

| 当前步骤 | 工具调用 | 改造后 |
|---|---|---|
| acceptance | 20-50 次 | 按 scenario 分片（已有 acceptance-test 148 场景，可按维度拆） |
| regression | ≤5 次（已有 precheck） | **不变**——已在舒适区 |
| coverage | ≤5 次（已有 precheck） | **不变** |
| consolidate | 10-20 次 | **不变**——输入已结构化 |
| verdict | ≤5 次 | **不变** |
| f-diagnose | 5-10 次 | **不变** |
| f-fix | 10-20 次 | 按问题拆分（与 b-fix 同策略） |
| f-audit | driver 步骤 | 不变 |

### 设计原则

1. **发散性保留**——每个视角 worker 仍是完整 ReAct agent，有 grep/cat/自由探索能力。不是脚本喂 context，是把窗口从 12 视角缩小到 1 视角。
2. **并行执行**——12 个视角 worker 互不依赖，driver 用 `spawnParallel`（已有）并行调度。
3. **独立容错**——1 个 worker 崩溃不影响其他 11 个（allSettled 模式，已有）。降级占位机制已有。
4. **无需三层熔断**——5-8 次工具调用在 LangGraph recursionLimit 25 的舒适区内，不需要软/硬/降级三层防线。
5. **checkpoint 自然适配**——断点粒度从"每轮"细化到"每个 worker"，被杀后精确续跑未完成的 worker。

## ⏸️ Checkpoint/Resume（断点续跑）

### 定位

v1.2.8 开发期间 driver 多次被宿主环境杀死（session 过夜清理、OOM SIGKILL）。driver 被杀后已完成的轮产物全部有效，但重跑只能从零开始。

v1.2.8 已规划 checkpoint/resume 方案。v1.2.9 结合短任务化落地：断点粒度从"每轮"细化到"每个 worker"，driver 被杀后精确续跑未完成的 worker。

### 设计

```
短任务模式下断点：
  resume-point.json
  {
    "round": 1,
    "workers": {
      "a-check-p1": { "status": "done", "output": "check-a-p1.md" },
      "a-check-p2": { "status": "done", "output": "check-a-p2.md" },
      "a-check-p3": { "status": "pending" },   // ← 被杀时还没跑完
      ...
      "b-check-p12": { "status": "pending" }
    },
    "completedWorkers": ["a-check-p1", "a-check-p2"],
    "pendingWorkers": ["a-check-p3", ..., "b-check-p12"]
  }

断点续跑：
  driver --resume --target vX.Y.Z
    → 读 resume-point.json
    → 跳过 completedWorkers
    → 只跑 pendingWorkers
```

### 交付

| 文件 | 改动 | 说明 |
|------|------|------|
| `FORGE/src/driver-base.mjs` | 修改 | saveResumePoint / loadResumePoint（v1.2.8 设计的增强版：worker 级断点）|
| `FORGE/src/fresh-eyes-driver.mjs` | 修改 | `--resume` 参数 + 断点恢复逻辑 |
| `FORGE/src/release-gate-driver.mjs` | 修改 | 同上 |
| `FORGE/src/driver-base.test.mjs` | 修改 | 断点写入/读取/损坏容错测试 |

> 基础设计参见 v1.2.8 checkpoint/resume 开发 prompt，v1.2.9 扩展为 worker 级粒度。

## 🏠 PM2 守护进程（本地长驻方案）

### 定位

driver 不应该跑在 WorkBuddy session 里——session 过夜清理会杀后台进程。也不能走云端——项目约束不允许。

PM2 是 Node.js 的生产级进程管理器，提供：
- **被杀自动重启**——进程异常退出时 PM2 自动拉起
- **日志持久化**——stdout/stderr 写入文件，不依赖 session
- **开机自启**——`pm2 startup` 注册系统服务

### 设计

```bash
# 启动 driver（PM2 守护）
pm2 start FORGE/src/fresh-eyes-driver.mjs \
  --name "forge-fresh-eyes" \
  --node-args="--experimental-vm-modules" \
  -- --target v1.2.9 --max-rounds 10

# 查看日志
pm2 logs forge-fresh-eyes

# 被杀后自动重启（PM2 默认行为）
# driver 退出码 0（正常结束）→ PM2 不重启
# driver 退出码 1（崩溃）→ PM2 自动重启 + checkpoint/resume 续跑

# 开机自启
pm2 startup
pm2 save
```

### PM2 + Checkpoint 联动

```
driver 被 session 杀死
  → PM2 检测到进程退出（非 0 退出码）
  → PM2 自动重启 driver
  → driver --resume 读取断点
  → 从最后一个未完成 worker 续跑
```

### 运行时行为

```
每个 🔄 节点：自动执行，结果写入 State + entity
每个 ⚡ 节点：执行到此处暂停 → 向用户展示方案 → 等待确认 → 继续
每个节点执行后：自动触发审计
审计 FAIL：暂停整个工作流，通知用户
异常：写入 exceptions 队列，根据节点配置决定重试 or 跳过
```
