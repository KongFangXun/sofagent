### P1 · skillopt 自动触发 + 失败清单驱动

**设计**：连续 3 次同类失败 → 自动触发 skillopt。每个 Skill 失败时记录失败场景 + 原因 + 正确做法，以负面样本驱动优化。

> **🔴 接口现状（实测）**：skillopt 包当前**没有** `optimize()` 函数（现有导出仅 skillopt-integration / skill-safety-check / backfill）。下方示例中的 `skillopt.optimize(...)` 是**本版本需要新建的核心 API**，不是已有接口。

```typescript
// ⬇ optimize() 为本版新建 API（skillopt 当前无此函数）
if (failurePattern.repeatedCount >= 3) {
  await skillopt.optimize({
    skillId: failurePattern.skillId,
    failureMode: failurePattern.description,
    source: 'auto-trigger',
  });
}
```

### P2 · conflict-check CLI + 联邦蒸馏

**设计**：独立 CLI 供用户手动检查 + 联邦蒸馏。

```bash
sofagent audit conflict-check [--fix]
sofagent audit federation-distill --peers device-a,device-b
```

**🔒 安全约束**：`federation-distill` 跨设备搬运知识，须走**已认证的配对通道**（参照 USB 配对机制），**禁止在明文/未加密通道传输知识原文**；合并产物仅含去重后的派生视图，原始 Ledger 不出本机（与 SECURITY.md「明文存储 + 多设备不隔离」P1 风险对齐，不新增暴露面）。

> **🔴 复用关系（实测，必读）**：
> - **矛盾检测逻辑已存在**：`engine/daemon/src/inspectors/conflict-check.ts`（L2 @weekly 自动巡检）已实现 `checkConflict()`。CLI 版**必须复用**该逻辑，不要重写第二套矛盾判定。
> - **联邦基础设施已存在**：`engine/daemon/src/federation/`（`merge.ts` / `query-router.ts` / `peers.ts` / `channel.ts` / `offline-fallback.ts`）是完整的联邦查询/合并模块。`federation-distill` 的 CRDT 合并**必须基于** `federation/merge.ts`。
> - **CLI 入口现状**：audit 包没有 `src/cli/` 子目录，bin 指向 `dist/index.js`（即 `src/index.ts`）。新建 `src/cli/` 子目录后，须在 `index.ts` 的命令分发里挂载这两个子命令。

> **⚠️ 分层风险**：audit 是底层包，daemon 是上层包。若 CLI 直接 import `@sofagent/daemon` 会形成「底层→上层」反向依赖。**推荐方案**：把 `checkConflict` / `federation/merge` 的核心纯函数下沉到共享位置（或 audit/core 包），daemon inspector 与 audit CLI 各自引用；或由调用方把函数作为参数注入 CLI。开发前须先定这个边界。

### P2b · Graph Engine Checker 扩展 + 受控循环升级（ROADMAP Graph Engine 表已承诺 → 定为 P2）

> **优先级说明**：此项在 ROADMAP「v1.2.x Graph Engine 进化路线」表中已明确列入 v1.2.4（②Checker 扩展 / ⑥受控循环），属已承诺交付，故定为 **P2** 而非 P3。降级预案：时间不足时仅交付 Checker 三节点（⑧），受控循环升级（⑨）降为可运行骨架 + TODO。

**⑧ 多类型 Checker 图节点**：当前 audit 节点只做文件系统审计。新增三个 inline Checker 作为独立图节点（在 audit 之后、reviewer 之前）：
- `format-checker`：输出是否符合预期 schema（JSON/Markdown/表格字段完整性）
- `fact-checker`：引用的文件/数据源是否真实存在、内容是否匹配
- `source-validator`：信息来源可信度评分（内部 trusted vs 外部 unverified）

Checker 发现的失败模式自动喂给 P1 skillopt 失败清单。

**⑨ 受控循环升级**：当前 engineer→audit→FAIL→engineer 是单一重试圈。升级为三种循环模式：
- "补信息后继续"：audit 发现证据不足→不直接 FAIL→回到 plan 补子任务
- "降级通过"：audit WARN 时不是直接过，标记后 reviewer 带警告展示
- "循环守卫"：每种循环有独立 `maxRetries` + `degradationThreshold` + `humanHandoffTrigger`
扩展 `buildLoopGraph` 条件边 + `LoopGraphState` 新增循环守卫字段。

### P0b · 进化引擎接通 eval（知识进化核心）

> **定位调整**（2026-07-28 孔老师拍板）：eval + ab-test 的 golden set / CLI / 持久化等引擎层基础设施已移到 v1.2.1（P0b），作为 v1.2.2 Dashboard 的前置数据管道。v1.2.4 只保留**进化引擎接通**部分——think-generator 读 eval failures 生成反思条目，这是「知识进化」的核心闭环。

**背景**：v1.2.1 已交付 eval golden set + CLI + 持久化（`data/eval/latest.json` + `history.jsonl`）。v1.2.4 的工作是**消费这些数据**——think-generator 读 eval 失败用例，自动生成反思条目写入 think.md，驱动 Skill 优化。

**交付**：
- `engine/think/src/think-generator.ts`：**复用 v1.2.1 P0b 已交付的 `generateThinkFromEval(opts?)`**（L253，无需修改）
  - 读 `data/eval/latest.json` 的 `failures` 数组
  - 为每条失败用例生成 think.md 反思条目（格式：`## {timestamp} eval 失败: {testId}\n- #期望/实际/得分/教训`）
  - latest.json 不存在或 failures 为空时静默跳过
  - 幂等检查（复用 isDuplicateEntry 逻辑）

**数据流**：
```
eval CLI 跑 golden set
    ↓ 写 data/eval/latest.json (failures 数组)
daemon @daily L1 巡检 → 检测 latest.json 变更 → 调用 generateThinkFromEval()
    ↓ 读 failures → 生成反思条目
    ↓ 写 data/think.md (append-only)
harness 加载链第 3 层消费 think.md → 约束 Agent 行为
```

**触发条件 + 幂等（开发前必定）**：
- **检测什么**：比对 `data/eval/latest.json` 的 mtime 与上次已处理的 mtime（记录在 `data/eval/.last-think-processed` 标记文件）。仅当 mtime 更新**且** `failures` 数组非空时才触发。
- **幂等保证**：`generateThinkFromEval()` 内部已有 `isDuplicateEntry` 逻辑（按 testId 去重），但 daemon 侧仍须用上述标记文件避免每天无意义重跑——latest.json 没变就不调用。
- **失败处理**：latest.json 不存在 / 解析失败 / failures 为空 → 静默跳过（severity: info，不告警），不阻塞 L1 其余巡检。
