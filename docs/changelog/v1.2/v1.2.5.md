## 背景

v1.2.5 是 v1.2.x 的收官大版本——从单设备约束升级到多设备协同。L2（团队协作协议）让多 Agent 协作有序化，L3（组织能力市场）让 Skill/Agent/流程在企业内自由流通。同时落地 ATTRIBUTION 归因引擎和网关边界。

这是 v1.2.x 里规模最大的版本，建议拆 2-3 个 PR 分批合并。

## LUI 感知

用户通过 Agent 对话感知：「我有两台 AI 节点，设备 A 在写代码，设备 B 在跑审计。Dashboard 上看到两台设备的控制图并排显示，跨设备审计轨迹聚合在一起。Skill 市场里能看到设备 A 的 engineer Skill 被设备 B 调用了 12 次，评分 4.2/5。系统告诉我'设备 A 上周有 3 次审计干预避免了潜在 bug，预估挽回损失约 2 小时返工时间'——审计不只是拦住错误，还能告诉我拦住的价值。」

## 交付项

### P0 · L2 团队协作协议

**问题**：多 Agent 并行时缺乏协作规则——谁先做、冲突怎么办、状态怎么共享。

**设计**：五大机制

| 机制 | 干什么 |
|------|--------|
| 共享态 | 多 Agent 共享当前工作上下文（通过 `.sofagent/shared-state/`） |
| 意图广播 | Agent 开始任务前广播意图（"我要改 src/index.ts"），避免撞车 |
| 触发反应 | Agent A 完成某动作后，自动触发 Agent B 的后续动作 |
| 冲突消解 | 复用 v1.2.3 的冲突消解策略，扩展到跨 Agent 场景 |
| 反馈放大 | 一个 Agent 的学习成果快速传播给其他 Agent |

**文件清单**：

### P2 · L3 组织能力市场

**问题**：Skill/Agent/流程在企业内散落，没有统一的发布→发现→调用→评价机制。

**设计**：

```
发布：Agent A 把自己擅长的 Skill 发布到能力市场
发现：Agent B 搜索"谁擅长做绩效汇总"
调用：Agent B 调用 Agent A 的 Skill（带身份验证）
评价：调用后打分 + 反馈，高频高价值自然胜出
```

### P5 · ATTRIBUTION 归因引擎

**问题**：审计能告诉你 Agent 违规了，但不能告诉你哪次正确的审计干预带来了业务价值。

**设计**：在多设备、多客户、长时间尺度上追踪审计决策→业务指标的因果链。

```
审计干预 "拦截了 engineer 删除 test 文件"
    → 因果链追踪
业务价值 "避免了测试覆盖率下降 → 避免了潜在 bug 逃逸 → 估算挽回 2h 返工"
```

### P6 · Graph Engine 边契约形式化 + Anchor 配置

**⑩ 五类边契约形式化**（行业共识）：当前 sofagent 只显式实现了数据流（`artifacts`）和控制流（`routeAfter*`）。v1.2.5 将五类边全部显式化为可审计的配置对象：
- **数据流**（现有）：`artifacts` 对象在节点间传递——已有
- **控制流**（现有）：`routeAfterAudit`/`routeAfterHuman` 条件路由——已有
- **权限流**：Sub Agent 工具调用前检查权限边界（`ScenePermissions`）
- **证据流**：每步输出 → audit 审计结果 → history.jsonl 不可篡改记录
- **失败流**：降解路径 + 重试次数 + 最终状态（blocked/human/degraded）

**⑪ Anchor 配置**（防自洽幻觉）：冻结验收标准配置：
```yaml
anchor:
  audit_rules: A1-A11,A14-A19  # 不可篡改
  acceptance_test: acceptance-test.sh  # 外部冻结脚本
  human_confirm: required  # human_confirm 不可跳过
  max_self_iterations: 3  # 防止无限自改
```

**Dashboard 归因视图对接**：P5 ATTRIBUTION 归因引擎用 Graph Engine 的状态变化追踪审计决策 → 业务价值因果链。
