# 阶段四：审查体系合并更新（含最终确认）

> **目的**：从本轮所有产出物中提取新发现，系统性升级四份审查文档。
>
> 审查体系运作原理（A/B/C 清单 / 模式提取 / 防膨胀 / 校准逻辑）见 [审查体系指南](../../guides/review-system.md)。
>
> **与阶段三分工**：阶段三步骤三 只管「增量」（新功能对应的新场景/新维度随开发实时加）；本阶段管「体系」（A/B/C 分类 → 四份文档归并/压缩/校准）。两阶段先后动同一批文件，边界以此为准——阶段三不加体系性改动，阶段四不重复增量补齐。

## 步骤四 细则：瘦身三判据 + 归并配额（2026-08-16 硬化 · v1.3.4/v1.3.5 连续上调教训 · v1.3.9 归并配额强化）

> **病根**：「先瘦身再上调」写了两版，实际执行率接近零——上调成了默认动作，警戒线橡皮图章化（v1.3.4 审查原话："上调线和新增量同版发生"）。v1.3.9 再教训：三判据「全否」判断过于宽松，执行者直接上调不动归并——「防膨胀只是说说」。本细则把瘦身从口号变成**可测量、可强制**的硬门槛。

**上调警戒线前，必须依次过三判据 + 归并配额（都满足才准上调）：**

| 判据 | 问什么 | 实测手段 | 是=动作 |
|------|--------|---------|---------|
| ①冗余判据 | 有没有维度做的事已被自动化工具覆盖？ | 逐新增维度比对 check-version / check-test-count / check-anchors 的扫描范围 | 有 → 删该维度或降为工具引用一行 |
| ②重叠判据 | 有没有 ≥2 个维度在做同一主题？ | `grep -oE "^#### [0-9]+" 后标题关键词聚簇`（≥3 个同类=强归并候选） | 有 → 归并进最大维度，子项合并 |
| ③增长性质判据 | 新增行是新审查面还是同模式的第 N 次重复？ | 每个新增维度回答"这个检查上个版本是否做过类似的事" | 重复 → 扩展旧维度子项，不新增编号 |
| **④归并配额判据（v1.3.9 新增 · 硬门槛）** | 本版真实归并了几处？新增行数是否 ≤ 归并释放行数？ | 记录归并清单（被并维度号 + 内容实际移入处 + git diff 可查的行数净减）+ 计算净增行数 | **新增 N 维 → 本版必须先真实归并 ≥N 维**；净增行数 > 警戒线余量 → 继续归并消化，消化不了移下一版 |

**归并配额判据的强制语义（v1.3.9 新增）**：

1. **1:1 对销**：本版新增 1 个维度编号，必须先完成 ≥1 次真实归并（删/并既有维度，行数净减）。新增 3 维 → 归并 ≥3 维。**只调警戒线不归并 = 本步骤不合格，禁止上调**。
2. **真实归并 ≠ 注释压缩**：被并维度的**检查内容**实际移入目标维度（bash 块/子项真实合并，`git diff` 可查），不是删注释/改措辞凑数。
3. **警戒线余量检查**：上调后的净增行数必须 ≤ 警戒线余量（当前行数到新警戒线的距离 ≥ 实际净增）。净增行数 > 余量 → 内容必须继续瘦身，否则**移下一版**——不允许「上调一个更大的数来装下全部新增」。
4. **聚簇假信号排除**：关键词聚簇（HMAC/tool 类通用词）≠ 真重叠——HMAC×4 可能是不同子系统各自独立（USB/审计链/决策日志/密钥强度），「新功能审查面×4」是同模式不同内容（历史版本锚点必须留）。归并前先读被并维度内容确认真重叠，再动手。
5. **归并释放行数入账**：执行模板记录「本版归并清单（维度号 → 并入处 → 净减行数）」，作为上调的依据与下一版对账的基础。

**连续上调禁令**：同一警戒线**连续两个版本上调 = 第三版禁止上调**，必须先完成 ≥1 次真实归并（删/并维度，行数净减）才解锁。执行记录写进 checklist 头部对账注。

**同版二次上调冻结（2026-08-18 补 · v1.3.6 一日四连调教训）**：三判据管「能不能上调」，不管「一版调几次」——v1.3.6 的 B 层预算一天被动小步跟涨 4 次（8880→8940）、checklist 警戒线 1500→1540，警戒线在「铁律上调不删内容」与「防膨胀」之间被磨成橡皮筋。**同一版内同一警戒线第 2 次上调即触发当版冻结**：追加内容必须靠真实归并消化，消化不了移下一版——禁止第 3 次上调。

**编号查重纪律（2026-08-16 双 107 事故补）**：新增维度前 `grep -cE "^#### N\." ` 确认编号未占用——v1.3.5 曾把新维度编成 107 与 v1.3.4 的 107 撞号（当时最大已是 109），违反"新编号=当前最大+1"自身纪律。查重一行命令，先跑再加。

**维度脚本编写三铁律（2026-08-17 release-gate run-08 补——7 FAIL 中 5 个是脚本缺陷，driver 白跑）**：① 显式收尾（`echo ✅/❌`，禁「期望无输出/exit 1」退出码语义——driver 只看 exitCode，grep 无命中与循环尾判假都返回 1 必误判）② 禁写死 CLI 参数签名与计数数字（版本演进必漂——动态对账或可达性验证）③ 改 checklist 的 commit 前最后跑 check-docs（B 层预算会被净增顶破）。完整版见 regression-checklist.md 头部「维护公约」。

**执行模板（每版阶段四填一次，附在步骤四 产物后）**：

```
[瘦身判据记录 vX.Y.Z]
①冗余：检查了 N 个维度，M 个已被工具覆盖（列出）→ 处置：…
②重叠：聚簇「关键词」×K（列出维度号）→ 真重叠 J 处 / 假信号（通用词/历史锚点）K-J 处 → 归并：…
③增长性质：新增 K 维中 J 维属新审查面 / K-J 维属模式重复 → 重复的处置：…
④归并配额：新增 N 维 → 本版真实归并 M 处（清单：维度号 → 并入处 → 净减行数，git diff 可查）；M≥N ✓/✗；净增 X 行 vs 警戒线余量 Y → 余量充足 ✓ / 不足→继续归并或移下版
结论：[净增 X 行 / 净减 X 行]；警戒线 [不动 / 上调 A→B，理由：归并 M 处 + 三判据全否 + 净增 ≤ 余量]
```

## fresh-eyes-review 风格守护自检（步骤五 必跑）

```bash
# 1. 行数守护：不超过 440 行（v1.4.1 阶段四上调 410→425：校准笔记 +1 节（11 条 C 类校准），真实新校准非冗余非清单化——同 v1.4.0「400→410 校准笔记 +1 节」先例；v1.4.1 阶段十二上调 425→440：发版期校准笔记 +1 节（阶段十~十二实录 6 条——发布流水线/分发链教训，真实新校准同先例））
WC=$(wc -l < FORGE/playbook/fresh-eyes-review.md)
[ "$WC" -gt 440 ] && echo "🔴 行数膨胀（$WC > 440）——检查是否在加精确检查项" || echo "✅ 行数正常（$WC）"

# 2. 反清单化守护：不应出现精确检查命令（fresh-eyes-review 是留白式直觉审查，不是 checklist）
CMD_COUNT=$(grep -cE '(grep|bash|npm|wc -l|test -)' FORGE/playbook/fresh-eyes-review.md || echo 0)
[ "$CMD_COUNT" -gt 5 ] && echo "🟡 命令引用偏多（$CMD_COUNT 处）——确认都是举例而非检查项" || echo "✅ 命令引用适度（$CMD_COUNT 处）"

# 3. 视角数守护：当前 16 个常规视角（v1.3.1 从 12 扩到 16，commit 157c6eb9），新增需谨慎
# v1.4.1 精度修复：原 `grep -c '^### '` 把规则子节（审查校准/工程防线/文档治理）误计为视角，
# 预存在假阳性（恒报 19）——改为只数真视角标题（「视角N [n]：」模式），动态对账不产生假信号。
VIEWS=$(grep -cE '^### .*视角[一二三四五六七八九十]+ \[' FORGE/playbook/fresh-eyes-review.md)
[ "$VIEWS" -ne 16 ] && echo "🟡 视角数变化（当前 $VIEWS，基线 16）——确认是刻意调整" || echo "✅ 视角数稳定（$VIEWS）"
```

> 💡 **什么时候 `git diff` 显示无变更也是正常的**：如果所有预料外发现都属于"可精确描述的具体问题模式"，它们全部进了 regression-checklist，fresh-eyes-review 本版本无需更新。零变更 = 审查体系稳定，不是遗漏。

## 最终确认（原阶段七 · 审查体系收口）

> **定位**：审查体系合并更新（上方步骤一~五）完成后的收口确认（原独立阶段七并入）——脚本管「数字对账」，人管「语义覆盖」。

| # | 步骤 | 验证方式 |
|:--:|------|------|
| 一 | **跑一致性门禁**：`bash tools/check/check-review-system.sh`——脚本自动核对六组声称值 vs 实际值（checklist 头部/正文维度数、编号查重、双文档行数警戒线、checklist 自校验段警戒线同步、acceptance 场景数与编号唯一性、S 编号交叉引用闭环、fresh-eyes 行数、check-version 分母自洽） | 脚本全绿（RC=0）；FAIL 项按输出逐条修复后重跑 |
| 二 | **审查体系闭环确认**：regression 维度 → acceptance 场景 → fresh-eyes 5 方向（数字漂移/搬迁残留/叙事不一致/静默失效/假绿假阳性）三者形成闭环——脚本管「数字对账」，人管「语义覆盖」：三份文档读一遍，确认覆盖链完整、无维度指向已不存在的场景方向 | 对照三份文件人工确认 |

> 审查文档自身也会过时——脚本管得住「声称 N ≠ 实际 N」这类数字漂移，管不住「维度内容过时」；后者靠步骤二的人工通读。`acceptance-test.sh` 的场景数和覆盖范围必须与 changelog 功能点对齐。
>
> 📌 脚本产出是**清单不是结论**：每个 ❌ 都附文件+行号+声称值 vs 实际值，修复动作归本阶段人工执行（或回阶段三做体系更新）。
