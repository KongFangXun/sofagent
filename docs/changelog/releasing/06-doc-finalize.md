# 阶段六：开发日志定稿 + 文档收尾

> 🔴 **前置闸门（防跳阶段）**：阶段六开工前必须确认**阶段三~五已按 SOP 完成**——
> - 阶段三（fresh-eyes-loop 质量循环）：草稿产物存在 / driver verdict 产出（若应跑）——见 [03-quality-loop.md](./03-quality-loop.md) 步骤完成判据

## 开发日志标准结构

> **章节顺序铁律**（阶段一~二起遵守，定稿时复核）：合并版本（新功能 + BugFix 同版）时**新功能在前、BugFix 在后**。用户读 changelog 第一眼看到的应该是「这个版本带来了什么新价值」，不是「修了哪些坑」。BugFix 放前面会让用户觉得这只是个补丁版，掩盖了新功能的价值传达。背景段的两行概述同理——先写新功能一句话，再写 BugFix。

定稿时照抄以下骨架（开发期间作为活文档持续追加，此时归位）：

```markdown
# vX.Y.Z 开发日志 — {一句话主题}（{启发来源}）

> ✅ 已开发 · {交付日期}
> 前置依赖：{上一版本能力}
> 交付：{N 项} · **{M} tests across {K} packages 全绿** · {其他门禁全绿项}
> {设计文档/灵感来源链接，可选}

## 背景

{两行概述：本版主线 + 交付件协同关系}

## 发布检查清单（汇总）

> 发版门禁总表——与各交付章节内的「验收标准」是两个层次：
> - **验收标准**（章节内）= 功能层面：这个交付件做没做到
> - **发布检查清单**（此处）= 发布层面：能不能发版（npm test / check-version / npm publish / git tag）

### 通用
- [ ] `npm run build` exit 0
- [ ] `npm test` 全绿（{M} 测试）
- [ ] `check-version.sh` 全绿
- [ ] `check-test-count.sh` 全绿
- [ ] `acceptance-test.sh` 全绿
- [ ] `check-docs.sh` 全绿 + 各层余量核对（超标先查分层口径/冗余，再上调预算——机制见下方「文档精简与优化机制」节）

### 质量循环
- [ ] fresh-eyes-loop verdict=PASS（或 clean stop）
- [ ] release-gate-loop verdict=PASS

### 版本号
- [ ] SSOT 版本号，N+ 文件同步
- [ ] 文档头日期统一
- [ ] ROADMAP 版本头更新
- [ ] 🔴 发版状态三件套核对：`docs/WIKI.md` 状态表「当前版本/下一版」+ 尾部维护规则行、`docs/ROADMAP.md`「现在在哪」节、`docs/HANDBOOK.md`「近期版本新功能速览」节——三处版本号与 SSOT 一致，无旧版残留（历史叙述除外）。曾出现只更新 WIKI 头部、状态表和尾注漏更，同文档三处版本打架

## 文档精简与优化机制（check-docs 相关）

> 🔴 **超标处理三原则**：`check-docs.sh` 任何层超标时，**先查口径、再查冗余、最后才上调预算**——禁止无脑上调。曾出现 A 层余量只剩十几行，根因是分层错位（包级开发者文档混入用户文档层），修正口径后余量恢复，无需上调预算。

**① 先查分层错位（最常见根因）**：统计口径是否混入"性质不符"的文档——
- 包级开发者文档（`engine/*/README.md`、`tools/README.md`）不应占 A 层（用户文档）预算——A 层 find 已排除，新增目录文档时先判断归属
- 持续增长型文档（`FORGE/lessons/` 经验沉淀）不应设硬上限——已排除出 B 层，由 F 软检查约束
- 判定标准：这份文档的读者是「用户」还是「开发者/内部」？后者 → 从用户层移出（改 check-docs.sh 的 find 排除并加注释）

**② 再查冗余（内容层）**：
- 活文档历史版本新能力段堆叠（check-docs 3b 自动检查，警告项）——「新能力段只留最新版，旧版去 CHANGELOG」
- 跨文档重复主题 / 完全相同句（用 dup-check 脚本扫 >40 字符相同句）
- 已闭环的占位桩 / 历史 stub 泄漏到公共 API（grep `stub|占位|TODO.*交付` 排查）

**③ 最后才上调预算（铁律）**：确属真实内容增长（非错位非冗余）→ 上调 LIMIT_* 并在注释记录「为什么涨 + 涨多少」（超标上调不删内容，但必须给理由，不留模糊地带）

**F 软检查配套（只提示不阻断，不计 ERRORS）**：
- `F-lessons`：FORGE/lessons 总量 >3000 行 → 提示整理。触发点：F 提示 或 **每 3 个发版周期（季度级）**。整理动作：归并同根因（只留一条 + 互相引用）/ 归档已泛化条目至 `FORGE/lessons/archive/` / 教训去考古（去日期去 run 编号）——详见 [FORGE/lessons/index.md 维护公约](../../../FORGE/lessons/index.md)
- `F-pkg`：包级 README 合计 >1500 行 → 提示精简

**发版时必做**：`check-docs.sh` 全绿 + 目测各层余量——**A/B 层余量 <100 行时预警**（下一版大概率继续加文档，提前规划精简或口径修正，避免发版中途被预算卡住）

## Release Notes（GitHub Release 发布用）

> 面向用户的发布说明——开发日志正文给开发者看，Release Notes（本段 + GitHub Release body）给用户看。
> **结构 SSOT = 上一版实际发布物**（`gh release view v上一版 --json body` 动态拉取）——本节范本快照仅供追溯，**每版发布前必须重新拉取上一版对照**，禁止按本节文字直接生成（范本段与实际发布物的结构差异曾在发布前才暴露）。已知结构基线（v1.4.5，2026-09-06 发布后回写）：定位句 + TL;DR (EN) + 五 H2（⚡ Install/Upgrade → 🔨 核心变更 → ✅ 质量验证 → ⚠️ 破坏性变更 → 🔗 深入了解）+ 尾链——与 v1.4.4 同构（范本快照回写项首次执行）。曾出现发布物漏质量验证表与标题主题短语被作者退回——范本对照不可省。
> 🔴 **铁律：发布时禁止把 changelog 内嵌段直接复制当 GitHub body**——本段是格式规范源头，GitHub body 由 [09-publish.md 三道工序](./09-publish.md) 生成；两处同源同构，但生成动作在阶段九，此段只定义标准。

### 格式规范（对照 v1.3.7 逐要素）

**① Title（release name）**：`vX.Y.Z — {emoji 主题短语}`
- 1-2 个核心交付的 emoji + 名词短语（v1.3.7：`v1.3.7 — 🏰 SubAgent 完整沙箱与场景驱动权限`）
- 主题短语与 body 首行定位句呼应（v1.3.7：title「沙箱与权限」↔ 首行「第一次在真正隔离的环境里」）
- ❌ 禁止裸版本号——历版均为「版本号 — 主题」惯例

**② Body 五要素**（v1.3.7 逐项，缺一不可）：

```
{首行定位句：一句话故事，承接上版讲本版主线 + 1 个类比锚点。无标题行，直接开始}

## 🔨 核心变更
### {emoji} {功能领域 1}
- {变更点 1}（含技术锚点：tool 名/API 名/机制名）
- {变更点 2}
### {emoji} {功能领域 2}
- ...
### 🔒 BugFix（上版遗留）        ← 有 bugfix 时必加末节
- {P0/P1 修复要点}

## ⚠️ 破坏性变更
- {真实列出：MCP 工具数变化（列新 tool 名）/ 枚举扩展 / Schema 变化}
- {确实没有才写「无」——工具数变化和枚举扩展不算「无」，必须列出}

## ✅ 质量验证
| 检查项 | 结果 |
|------|:--:|
| npm test | {N} tests 全绿 ✅ |
| acceptance-test | {N}/{N} 场景全绿 ✅ |
| shellcheck | 零 error ✅ |
| check-version | {N}/{N} 全绿 ✅ |
| 回归检查 | {N} 维度 ✅ |
| release-gate | verdict=PASS ✅ |
| fresh-eyes | {N} 视角审查闭环 ✅ |

📖 [详细开发日志](./docs/changelog/vX.Y.Z/vX.Y.Z.md)
```

**v1.3.7 范本数据**（生成时对照）：title 主题短语 2 个 emoji 词 · 首行定位句 1 段 · H2 共 3 个（核心变更/破坏性变更/质量验证）· H3 小节 8 个（7 功能 + 1 BugFix）· 每小节 2-3 条 bullet · 质量表 7 行（表头 1 + 数据 7）· 尾链相对路径 `./docs/changelog/v1.3/v1.3.7.md` · body 总行 59 行。

### Release Notes 体例铁律（以 v1.3.7 为标准校准，仅约束此段与 GitHub body）

| # | 铁律 | 说明 |
|---|------|------|
| N1 | **Title + Body 要素齐备**：title 主题短语 → 首行定位句 → TL;DR (EN) → H2 ⚡ Install/Upgrade（新装 curl / 升级 npx --doctor / GitHub Action 三块）→ H2 🔨 核心变更（分 H3 功能小节）→ H2 ✅ 质量验证表（在破坏性变更之前）→ H2 ⚠️ 破坏性变更 → H2 🔗 深入了解（CHANGELOG/HANDBOOK/Discussions/npm 四行表）→ 尾链。**节序与要素以上一版实际发布物为 SSOT**，缺一不可（曾出现漏质量验证表 + 漏标题主题短语被退回；曾出现按旧范本漏 Install/深入了解节——发布前必须跑工序三对照） | 用户能扫到安装/故事/变更/验证三要素 |
| N2 | **H3 小节内 bullet 单层**——每节 2-3 条，禁止三级展开；body 总长 ≤ 60 行 | 细节属于开发日志正文 |
| N3 | **破坏性变更禁止轻率写「无」**——MCP 工具数变化 / 枚举扩展 / 新导出必须列出（曾出现工具数变化写了「无」） | 用户升级靠这个 |
| N4 | **首行定位句是故事不是功能列表**——承接上版 + 本版主线 + 一个类比锚点；功能细节放 H3 小节 | 用户秒懂本版干了什么 |
| N5 | **H3 小节标题带功能领域 emoji**（`### 🏰 SubAgent 完整沙箱`）——emoji 在领域名最前，语义化（🛡️ 安全/🔐 权限/⚙️ 基建/📊 计量/🔒 bugfix） | 范本八节全带 emoji |
| N6 | **标题三层不重复**——changelog H1（动词化故事，不带 emoji）≠ release title（名词化主题短语，带 emoji）≠ H3 小节（交付名，带 emoji）。同一交付名只出现在 H3 小节标题，不逐项罗列进 H1/title | 曾出现 H1 与 note 逐项逐字复读 |
| N7 | **质量验证表固定 7 项**（npm test / acceptance-test / shellcheck / check-version / 回归检查 / release-gate / fresh-eyes）——不可增减、顺序固定 | 信任信号标准化 |
| N8 | **changelog 内嵌「## Release Notes」段 = GitHub body 同源**——本阶段（六）写入，阶段九发布时按三道工序生成并自检（title 主题/定位句/H2 骨架/7 项表/尾链五对照），发布前禁止凭记忆手写简化（曾出现生成 prompt 时手写简化 title 丢主题短语） | 发布物与开发日志同步 |
| N9 | **定位句长度带硬上限**——首行定位句 ≤ 220 字符（含 emoji 与空格；常规版 140-210 区间）。生成后必跑 `gh release view vX.Y.Z --json body -q '.body' \| head -1 \| awk '{print length($0)}'` 实测，超 220 拆 H3 小节承载，不允许首行堆三个主句 | 首行扫一眼能读完 |
| N10 | **BugFix 节标题逐字固定**——`### 🔒 BugFix（上版遗留）`，括号补语不可省（曾出现简写漂移省略补语）。内嵌段与 GitHub body 双处同查：`grep -E "^### 🔒" changelog 与 gh release body`，任一处缺补语即视为漂移 | 读者知道这是补账不是本版功能 |
| N11 | **里程碑 🎉 前缀仅限 vX.Y.0**——`🎉 vX.Y.Z — ...` 格式只有次版本位为 0 的里程碑版可用，且 emoji 前缀在版本号前（不在短语尾部）；常规版一律 `vX.Y.Z — {emoji 短语}`，尾部不加装饰后缀。混用即漂移 | 版本等级一眼可辨 |

### 体例铁律（防止跨版本漂移）

| # | 铁律 | 反例（禁止） |
|---|------|------------|
| 一 | **标题一句话主题**——不罗列功能清单 | title 逐项罗列 10 项功能名 |
| 二 | **开头 blockquote ≤ 4 行**——只放状态/前置/交付数+测试数/来源链接，不塞实现进度 | 开头 5-15 行把波次拆分/包级测试数全搬上来（与文末实现纪要重复） |
| 三 | **交付清单速览表必须有**——让读者一眼看到全貌 + 优先级 + 章节跳转 | 大量章节平铺无速览表，读者要扫完全文才知道交付了什么 |
| 四 | **章节带优先级前缀**（P0/P1/P2）——读者一眼看出核心 vs 配套 | `## 一、{交付名}`（无优先级，不知是不是核心） |
| 五 | **每个交付都必须有验收标准**——用 `- [x]` 勾选格式，100% 覆盖 | 一半章节有验收、一半没有（体例分裂） |
| 六 | **子段按「问题诊断/实现/涉及文件/验收」四段式**——按需用，不用的不强行加，但顺序固定 | 交付 A 用四段式、交付 B 只有「实现」、交付 C 裸文字（同文档三种体例） |
| 七 | **规则口径单一事实源**——A1-A23 + E1/E2/E4 共 26 条注册（E3 并入 A11），生效 24 条（17 默认 + 7 扩展）。全文用同一套口径 | 多种计数口径并存双重计数，读者不知该信哪个 |
| 八 | **BugFix 表格独立成段**——不套「问题诊断/实现」四段式 | BugFix 用 Bug/处理方式两列表格即可，不硬套 |
| 九 | **emoji 风格全版本统一**——速览表与章节标题的 emoji 必须一致（同名同 emoji）；一个版本内要么全带要么全不带，不允许混用；emoji 放交付名最前面（`## 一、🔧 {交付名}` 非 `## 一、{交付名} 🔧`） | 部分交付有 emoji、部分没有（同版本混用，扫目录视觉断裂） |
| 十 | **发布检查清单段必须有**——发版门禁总表（npm test / check-version / acceptance-test / npm publish / git tag），与章节内「验收标准」是两个层次 | 只有章节内功能验收，没有发版门禁总表（读者不知这版能不能发） |
| 十一 | **Release Notes 段必须有**——面向用户的发布说明（核心变更 / 新功能 / 破坏性变更），与开发日志正文（给开发者）是两个读者层 | 开发日志写得很细，但用户升级时看不到「这版破坏性变更是什么」 |

**强制项**：文件命名三段式 `vX.Y.Z.md` · 速览表不可省 · 验收标准 100% 覆盖 · 发布检查清单段不可省 · Release Notes 段不可省 · 测试数与 CHANGELOG/ROADMAP/LIMITATIONS/evidence 一致 · 规则口径全文统一。

## 红项自动修复批（操作步骤红项的处置协议）

操作步骤一~九产生的红项分两类，处置方式不同：

- **确定性红项（可自动修复，按 [`auto-converge-protocol.md`](./auto-converge-protocol.md) 修复批协议执行）**：测试数声称漂移（check-test-count 红 → 跑 `sync-test-count.sh` 或按 SSOT 修文档，谁的测试谁同步）/ 版本号残留（check-version 红 → 按 bump 中断恢复清单补漏）/ 命名不一致 / U+FFFD 乱码字符 / 文档预算超标（check-docs 红 → 按「调预算不删内容」纪律上调 LIMIT 并对账）/ 发版日期漂移（跑同步脚本）。修完复跑对应检查至 EXIT=0 再 commit。
- **叙事性红项（停手问作者，不自动修）**：结构缺失要补写内容（Release Notes 段缺/速览表缺/发布检查清单缺——内容需要作者意图）/ ROADMAP 取舍类决策（条目移出/合并/删除）/ 交付描述与实际实现冲突（可能暴露开发期问题）。这类「怎么写」依赖作者拍板，自动写 = 编造意图。

**判别口径**：红项的修复动作是否只需要「对齐既有 SSOT 数字/格式」——是 = 确定性（自动修）；需要「产生新内容或做取舍」 = 叙事性（停手问）。修复批红线上同款适用：禁止为让 check 变绿而删内容/删检查项。

## 发版日期同步脚本（步骤三）

```bash
TODAY=$(date -u +%Y-%m-%d)

# 1. 找到 bump 写入的旧日期（从 package.json 的首次提交日期推断）
OLD_DATE=$(git log --format="%ci" -1 --diff-filter=A -- package.json | grep -oE "[0-9]{4}-[0-9]{2}-[0-9]{2}" | head -1)
# 如果找不到，手动指定：OLD_DATE="YYYY-MM-DD"

# 2. check-version.sh 的 EXPECTED_DOC_DATE 改为今天
sed -i '' "s/EXPECTED_DOC_DATE=\"[0-9-]*\"/EXPECTED_DOC_DATE=\"$TODAY\"/" tools/check/check-version.sh

# 3. 批量更新文档头日期（旧日期 → 今天，只改 > vX.Y 开头的文档头行）
grep -rl "^> v[0-9].*· ${OLD_DATE}" --include="*.md" . \
  | grep -v "docs/changelog/" \
  | grep -v "docs/evidence/" \
  | xargs sed -i '' "s/· ${OLD_DATE}/· ${TODAY}/g" 2>/dev/null || true

# 4. 验证
bash tools/check/check-version.sh   # 期望：日期一致项全绿
```

> bump 详细指南（13 类位置 + package-lock 同步 + npm 铁律）见 [FORGE/playbook/version-bump.md](../../../FORGE/playbook/version-bump.md)。
> 文档同步详细指南（LIMITATIONS 覆盖 + 归属原则 + D6 闭环）见 [FORGE/playbook/doc-sync.md](../../../FORGE/playbook/doc-sync.md)。

## 按需文档

| 文档 | 什么时候更新 |
|------|------|
| `README.md` | FDE 完成度变化、效果证据更新、**新功能入口（新增能力段 + changelog 链接）** · **新能力段只留最新版本——旧版直接删不堆叠** · 每版开发完成后顺手优化 README 表达/结构/视觉 |
| `README.en.md` | **与 README.md 同步**——badge 自动改，但新能力段 + 测试数 + 规则数需手动同步（英文版易漏）· 同样只留最新版本新能力段 |

> 🔴 **README 头部禁止版本状态播报行**（2026-09-06 拍板）：不得在 README 头部（badges 与「这是什么」之间）添加「🚀 vX.Y 已发版 / ⏳ 待发版」式 blockquote 状态行——版本历史归 CHANGELOG 天然可查，头部状态行是冗余且过时即错（曾堆叠 v1.4.4/v1.4.5 两段，2026-09-06 已清）。README 头部结构固定为：badges → 语言切换 → 「这是什么」。版本动向的读者动线走 badge（Version-vX.Y.Z）→ CHANGELOG 链接，不走状态行。
>
> **README 新能力段写入后必须语义交叉核对**（核对紧贴写入时机）：逐项对照 README.md/README.en.md「vX.Y 新能力」段与 CHANGELOG/changelog/vX.Y/vX.Y.Z.md 交付清单——新能力段每项都是**本版本真实交付**（非上版本残留），且本版本所有核心交付**均已出现在新能力段**。check-version.sh 只校验版本号字面一致，无法检测语义错配（如新能力段写着上一版内容）——此项必须人工执行。
>
> 🔴 **README 新能力段替换安全步骤（防误删）**——用脚本按标题范围替换时曾出现**删除范围超预期**导致整段误删。替换必须三步走：
> ① **替换前 diff 预览删除范围**：`python3 -c` 定位起止 index 后先打印将删除的段落（或 `git diff --stat` 前后对比），确认边界正确（起止锚点要精确到「目标段结尾的下一节标题」，不是任意 ## 标题）
> ② **替换后验证关键段存在**：`grep -c "关键段标题"` 逐个确认（README: 为什么选/Why choose、Evidence、Docs 导航表、LICENSE 等结构段不能被吞）
> ③ **中英结构对称检查**：`grep -c "^## " README.md README.en.md` 两侧标题数一致（如 11:11 对称——不对称 = 有段被误删/误加）
>
> **测试数口径规则（防多处打架）**：所有文档写测试数必须**带口径标注**——`workspace 口径`（引擎 12 包，check-test-count SSOT）vs `全量口径`（引擎 + DSH 插件 + OpenClaw 插件）。曾出现 WIKI/ROADMAP/changelog 三处口径打架。写法统一：`全量 N（workspace M/12 包）`；纯 engine 语境用 workspace 口径并写清「12 包」。
| `ARCHITECTURE.md` | 架构决策或设计思路有变更 · 13/12 包口径一致性（13=npm 发布总数，12=有 test script） |
| `DEVELOPMENT.md` | 开发流程有变更 · 正文测试数声称同步（grep `XX 测试`，bump 后数字会过时） |
| `LIMITATIONS.md` | 新发现的局限或旧局限被消除 · 已知问题标注修复版本落点（写具体 vX.Y.Z，不写「未来版本」） |
| `HANDBOOK.md` | 用户使用习惯、FAQ 有变化 · 「已经能替你干的事」版本号 + 新能力列表 · 「现在还干不了的事」移除本版交付项 |
| `ROADMAP.md` | 五步更新（见上） |
| `CHANGELOG.md` | 新增版本索引条目（版本历史唯一权威入口） |
| `THANKS.md` / `docs/evidence/` | 效果证据与案例更新时——**证据强度分级标注**：公开可查（PR/issue/复现命令可验证）> 用户自报（脱敏第三方报告）> 自测自报（作者环境实测），标注跟着案例走；只维护最强少数案例，弱证据不进入对外叙事（防止自测当实证） |

## ROADMAP 同步手册（步骤五）

> **定位**：每次发版后 ROADMAP 必须同步更新，随阶段六步骤五一同执行、同 commit 收编——无独立 pass/fail 闸门（阶段五 release-gate 是闸门，本节是手册）。

### 两条核心纪律

1. **单向流动**：探索方向（想到了没排期）→ 版本规划表（已排期 📋）→ 迭代历程表（已交付 ✅）。条目只往一个方向走，**绝不重复出现**在两个段。
2. **交付即移出**：版本一旦发版，立刻从「版本规划表」移到「迭代历程表」——规划表里不留已交付版本的任何痕迹。

### 操作清单（每次发版必做）

**① 本版从规划表移到迭代表**

| 动作 | 细节 |
|------|------|
| 版本规划表 | 删除本版那一行（整行删，不留「已交付」标注） |
| 迭代历程表 | 本版加一行（逐行，不合并——最近三个大版本内的都逐行） |

**② 「现在在哪」段更新**

| 动作 | 细节 |
|------|------|
| 标题 | `## 现在在哪：vX.Y.Z（已交付）`——**版本号 = 当前 SSOT 版本**（check-version 校验标题前两段 = SSOT，跨大版本时写「下一版号」会撞 FAIL）。下一版方向写进叙事段，不写标题 |
| 叙事段 | 本版「已于 YYYY-MM-DD 交付」一句话总结 + 下一版规划方向 |

**③ 探索方向表清理**

| 情况 | 动作 |
|------|------|
| 本版交付了探索方向里的某条 | **整条删除**（不残留「已交付」标注） |
| 某条探索方向已排进版本规划表 | **整条删除**（不残留「见版本规划表」标注） |
| 某条写「vX.Y 后期」等模糊版本号 | 落具体版本（写进对应 changelog）**或**去掉版本号保留探索 |
| **某条判断无用（主动淘汰）** | **整条删除**——三问判定：① 与信任层主线（审计/回溯/注入/进化/沙箱/网关）相关吗？② 三个月内有人需要吗？③ 被生态（DSH）或商业侧取代了吗？三问全否 → 删。**不等「毕业」，主动淘汰**（探索方向只进不出会摊薄注意力） |

**④ 版本号 + 日期**

| 动作 | 细节 |
|------|------|
| ROADMAP 顶栏 | 版本号 + 日期更新（`> vX.Y.Z · YYYY-MM-DD`） |
| 已交付范围 | 「已交付版本（v1.0.0~vX.Y.Z）」更新到本版 |

**⑤ 迭代表瘦身（老版本合并）**

> 迭代表是「产品演进脉络」，不是「全量版本日志」。全量日志在 CHANGELOG。

| 规则 | 动作 |
|------|------|
| **最近一个大版本**（如 v1.3.x） | **逐行保留**（当前读者最关心） |
| **倒数第二、三个大版本**（如 v1.2.x、v1.1.x） | **各合并成 1 行**——一句话主题 + 3-4 个关键里程碑版本号 + 指向 CHANGELOG |
| **更早的大版本**（如 v1.0.x） | 同上，1 行概述 |

**合并行格式**（示例）：
```markdown
| **v1.2.x**（10 版） | **激活链全线打通 + 约束层叙事统一 + 三个入口产品**：v1.2.0 物理重构 → v1.2.5 激活链 Phase 1 → v1.2.7 编排增强 → v1.2.9 三入口 + 叙事重构（详见 [CHANGELOG](../../../CHANGELOG.md)） |
```

**警戒线**：迭代表超过 10 行就该考虑合并最老的那个大版本。

### 体检清单（每次发版后顺带做）

> 这些问题不会每次都出现，但积累几版就会冒出来。每次发版花 5 分钟扫一遍。

| # | 检查项 | 怎么查 | 修法 |
|:--:|--------|--------|------|
| 一 | **重复表/章节** | 同一信息是否出现在两个地方（如规划表 + 里程碑拆分表） | 删冗余，保留唯一权威源 |
| 二 | **散落方向章节** | 是否有 `## 中期方向` / `## 远期方向` 等独立章节与探索方向表重叠 | 并入探索方向表，删散落章节 |
| 三 | **跨文档死链** | 仓库内相对链接已由 check-docs（死链扫描）+ check-anchors（锚点校验）自动覆盖，**人工只补查两类**：① 自动门禁豁免区（archive/ 等）内的链接 ② 外链（ROADMAP 现状全为内链，此条为防御性预留） | 修路径或删链接 |
| 四 | **已交付版本混入规划表** | 规划表里有没有本版或更早的版本 | 移到迭代表（或合并） |
| 五 | **「已交付范围」过期** | 「已交付版本（v1.0.0~vX.Y.Z）」是否更新到本版 | 更新版本号 |
| 六 | **模糊版本号** | 探索方向表里有没有「vX.Y 后期」「未来版本」等模糊措辞 | 落具体版本或去掉版本号 |
| 七 | **U+FFFD 替换字符** | `grep -c $'\xef\xbf\xbd' docs/ROADMAP.md`（期望 0） | 定位并修复编码损坏 |
| 八 | **新增前未 grep 同类** | 新增检查项/生成器/脚本前，`grep -rn <功能关键词> tools/ engine/scripts/` 确认无同类实现 | 有同类则增量扩展，不新建 |
| 九 | **同类文件 ≥3 未抽库** | 同类前缀文件 ≥3 个（如 gen-* 系列）仍各自复制公共逻辑 | 抽公共库（tools/lib/ 等），各文件只留差异面 |

### 反例（禁止的做法）

| 反例 | 为什么禁止 |
|------|-----------|
| 规划表保留已交付版本并标「已交付」 | 违反「交付即移出」——规划表是「还没做的」，不是「做完了的」 |
| 迭代表几十行全逐行 | 老版本占版面，读者要滚很久才到「未来」——该合并 |
| 探索方向表标「见版本规划表」 | 违反单向流动——排进规划表了就整条删，不残留指引 |
| 同一版本列在规划表 + 里程碑拆分表 | 重复——只保留一张权威表 |
| 删了版本但留了引用它的锚点链接 | 死链——删版本前先 grep 引用 |
