## 一、施工期收口判据（能不能进 V2.0）

> **形态归属**：`[主干]`（交付·收口判据——本版为**判据与收口动作**）｜ —

### 交付

| 检查项 | 判据 |
|--------|------|
| **阶段一（判据与数据）** | 判据 schema 定稿且逐条对账无遗漏；数据集三元组可校验；零样本基线已落数 |
| **阶段二（模型与校准）** | 训练回路可复现；**ECE 达阈**；三态对照落数且判定质量与概率可信度**双达阈** |
| **阶段三（接线与分发）** | DecisionChannel 实现在位（默认 + 可替换）；一体机离线推理可用；权重分发通路打通且 sha256 校验 fail-closed |
| **阶段四（消费与收口）** | 既有判定面收敛完成（三原语补概率）；假概率正名完成；三类判据域在位；**四层性能标准落数** |
| **口径** | 对外无「未达阈却已宣称」的能力项（逐项核对） |

### 收口结论的两条分支

| 分支 | 条件 | 动作 |
|------|------|------|
| **可进 V2.0** | 四阶段全部达阈 | 全站口径对齐后进 V2.0 形态宣告 |
| **不可进 V2.0** | 任一阶段未达阈 | **在施工期内增补细版**（见 §三 弹性机制），**不带着未达阈项进 V2.0** |

- [ ] 未达阈项有明确的增补版本安排（不是「后续优化」这类无主语表述）
- [ ] 对外能力项与 `docs/VALIDATION.md` 落数**逐项一致**（无宣称超出证据的能力）

## 三、版本弹性机制（后续开发量剩余的处置方式）

> **形态归属**：`[非功能]`（排期纪律——**本版首次落盘**）｜ —

### 机制

| 情形 | 处置 | 理由 |
|------|------|------|
| **阶段内开发量超出预期** | 在**该阶段内增补细版**（如 `v1.7.3` / `v1.7.4`），不挤进后续阶段 | 阶段内主题一致、依赖连续，增补成本最低；跨阶段挤压会破坏「每版可独立验收」的前提 |
| **出现新识别的工作面** | 在阶段之间**插入新阶段**（如 `v1.10.x`），并保持原四阶段编号不变 | 编号稳定便于引用；插入而非重排可避免全仓版本号重写 |
| **V2.0 时点** | **不锁死在 v1.9.2 之后**——V2.0 在「四阶段收口达阈」时点到来，之前不停留 | 形态宣告的时点由**达阈状态**决定，不由版本号决定；形式上成立却内容未达阈时宣告，等于把叙事跑在实现前面 |
| **单版内容上限** | 每版内容以「**可独立验收的交付单元**」为界，不以「章数」硬凑 | 颗粒度细化的目的就是让每版能独立停、独立验 |
| **不允许** | 把多个阶段的工作挤进一版；或为了「按计划进 V2.0」而放宽达阈标准 | 前者破坏可验收性，后者破坏证据链 |

### 验收标准

- [ ] 弹性机制写入 ROADMAP 与 changelog 目录说明（后续版本增补有据可依）
- [ ] 已增补 / 已插入的版本记录在册（版本号不复用、不重排）
- [ ] V2.0 时点表述统一为「四阶段收口达阈时」（非「v1.9.2 之后」）
- [ ] `docs/changelog/README.md` 记录阶段与版数关系

### 风险与前置假设

> ⚠️ **弹性机制可能被滥用为「无限延后」**。约束是：每次增补细版**须有明确的未达阈项或新识别工作面作为依据**，并在 changelog 中记录增补理由——「感觉还没做完」不构成增补依据。
>
> ⚠️ **本版仍不改对外产品身份**。身份切换是 V2.0 的动作，本版只把口径铺平。若本版提前宣告身份，会让 V2.0 失去「一次定义到位」的意义（P18 拍板：形态成立时点 = V2.0，不设中间成立点）。
