## 二、发现清单（按优先级）

### P0（严重 / 阻塞）

**P0-1 — changelog 锚点与场景语义错配，EXEMPT 判定依据不可信**
- **文件**：`docs/changelog/v1.5/v1.5.8.md`（经 `coverage.md` 映射表暴露）
- **具体证据**：
  - 「一、进化准入判据」→ 锚 `S1`，而 `S1 = Fresh install（--install-hook）`，二者无语义对应关系；
  - 「发布检查清单（汇总）」→ 锚 `S476`，而 `S476 = v1.5.7 章五·可拔契约行为锁`，二者无语义对应关系。
- **影响**：v1.5.8 的两个关键章节（进化准入判据、发布检查清单）疑似未被任何有效场景覆盖，`machineVerdict=EXEMPT` 建立在错配锚点之上，构成**假豁免 / 假覆盖**风险——闸门可能将未验证的核心交付当作已豁免放行。
- **独立复核意见**：该判定为“高置信度疑似”，因 coverage 审查者在报告中自陈“未展示终稿正文”。按 fail-closed 原则，证据不足时不得放行；建议先核对 `coverage.md` 的模块↔场景映射表原文：**若证伪则降级为 P2；若证实则必须修复后方可放行**。

> **本次 consolidate 对 P0-1 的裁决**：维持 P0。阻塞不因上游 acceptance/regression 全绿而解除——三层验收面向不同，覆盖缺口不被测试通过所抵消。

- **建议**：发版前人工核对版本头描述与 v1.5.8 实际内容，修正后回填。

**P1-2 — README quick 规则数口径漂移**
- **文件**：`README.md`（quick 规则数段落）
- **证据**：regression 维度 110 → `⚠️ README quick 规则数口径漂移`
- **建议**：对齐规则数口径至 SSOT（与 acceptance 场景 476 的 `core 308→310` 口径联动核查，避免与 `CURRENT_RULE_KEYS` 新增数打架）。

**P1-3 — v1.5.8 changelog 交付性模块 8/8 全 EXEMPT，缺机器验收**
- **文件**：`docs/changelog/v1.5/v1.5.8.md`
- **描述**：8 个模块全部 `machineVerdict=EXEMPT`。其中「定位」「与后续版本的依赖」属说明性章节，豁免合理；但「一、进化准入判据」「二、三层晋级判据」「三、经验池接训练管道」「四、出题考核器」「五、RL 训练治理」「发布检查清单（汇总）」含实质交付 / 治理承诺，现有证据无法证明其被任何非豁免场景覆盖。
- **建议**：对交付性模块补可执行场景，或在 `coverage.md` 逐条登记豁免类型（文档叙事 / 未来版本 / 人工验证 / 不适用）+ 依据来源 + 验证人。

**P1-4 — 发布检查清单被整体豁免，闸门缺清单闭环证据**
- **文件**：`docs/changelog/v1.5/v1.5.8.md` →「发布检查清单（汇总）」
- **描述**：发布检查清单是发版闸门的直接输入，不应与普通叙事章节等同豁免；当前标记 `EXEMPT` 且锚到无关场景 `S476`，意味着清单项缺少逐项执行证据、责任人与时间戳对账，存在漏检风险。
- **建议**：将清单拆解为可执行断言（或至少保留逐项人工核对记录），每项可追溯至场景编号 / 验证命令 / 核对记录。修复前不建议依赖该清单放行。
