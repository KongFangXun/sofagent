## 一、P0：代码硬伤止血（6 项）

### 1. VERSION 不一致

`skill-safety-check.ts` 和 `verify-evidence.ts` 的 `VERSION = '0.92'`，但 package.json 是 v0.93。修复：统一更新为 `'0.94'`。

**根因**：版本号手动散落在多个 TS 文件中，发版时只改了 package.json 没改源码常量。

### 2. license$/readme 正则大小写 bug

`LOW_RISK_PATTERNS` 没有 `i` flag：`/license$/` 不匹配 `LICENSE`（大写），`/readme(\.\w+)?\.md$/` 不匹配 `Readme.md`。macOS（APFS 不区分大小写）没问题，Linux CI 上漏报。

**修复**：所有 `LOW_RISK_PATTERNS` 正则统一加 `i` flag。

**教训**：跨平台正则必须显式声明大小写策略——依赖文件系统的默认行为是隐患。

### 3. verify-evidence 正则过宽

`/make/` 匹配了 "make sure""make a decision"；`/lint/` 匹配了 "splinter""glint"。

**修复**：加词边界 `\b` + 限定上下文：
```typescript
const BUILD_PATTERN = /build.*(success|fail)|编译.*(成功|失败)|npm run build|\bmake\b\s+(build|all|install|clean)/i;
const LINT_PATTERN = /\b(lint|eslint|prettier|shellcheck)\b/i;
```

### 4. verify-evidence 不区分正负证据

只检查关键词出现，不区分"test passed"和"test failed"——两者都被算作"有测试证据"。

**修复**：`countMatches` 改为返回 `{ positive: number; negative: number }`，`negative > 0` 时降级为 WARN。

**教训**：证据检测必须区分正负——"提到了测试"和"测试通过"是两回事。

### 5. log-checker tsc\b 过于宽泛

`/\btsc\b/` 匹配日志中任意"检查 tsc 配置"。改为 `/tsc\s+--noEmit/` 或 `/tsc\s+-p\b/`——只匹配真正的编译命令。

### 6. checkLogs 迭代中修改数组 + 三元死代码

`log-checker.ts` 在 `for...of` 循环内向数组 push 新元素——两个职责（收集日志条目 + 展开文件引用）揉进一个循环。

**修复**：拆为两阶段——先收集所有日志条目，再遍历条目展开文件引用。同时清理三元表达式死代码，正则改为预编译。

## 二、P0：审计独立化——沉默审计模式（--silent）

> v0.94 最核心的新增功能。来源：两轮评审合并。

### 核心原则：三层证据策略

```
证据优先级: git-diff（硬证据） > Agent 日志（软证据） > 无证据（跳过）
```

git diff 本身就是客观证据——Agent 改没改文件、改了多少、改了什么内容，git 全知道。Agent 可以骗日志，骗不了 git。

### 功能范围

```bash
# 沉默模式（只跑纯 diff 规则，不需要 Agent 日志）
sofagent-audit --diff HEAD~1..HEAD --task "修复登录bug" --silent

# CI 模式（隐含 --strict + --silent，exit code ≥1 阻断）
sofagent-audit --diff HEAD~1..HEAD --task "修复登录bug" --ci
```

### evidenceMode 标注

每条规则标注证据模式：

| 规则 | evidenceMode | 说明 |
|------|:--:|------|
| #1 先读再用 | `hybrid` | 有日志走精确检查，无日志走 diff 推断 |
| #3 验证再干 | `hybrid` | 同上 |
| #7 谨慎修改 | `git-diff` | 纯 diff，零依赖日志 |
| #10 如实汇报 | `git-diff` | 纯 diff + commit message |
| R11 敏感文件 | `git-diff` | 纯文件名匹配 |
| R12 测试缺失 | `git-diff` | 纯 diff 路径匹配 |
| R13 低注释率 | `git-diff` | 纯 diff 内容分析 |

### 沉默模式下的 7 条纯 diff 规则

> 这 7 条**完全不依赖 Agent 日志**。

| 规则 | 看什么 | 判什么 | 严重性 | 对应铁律 |
|------|------|------|:--:|:--:|
| **R1 无关文件批量改** | diff 文件数 > 10 且与 --task 匹配率 < 50% | "可能没读上下文就批量改" | WARN | #1 |
| **R2 源码改但测试没改** | src/ 变了但 `*.test.ts`/`*.spec.js` 没动 | "可能跳过了验证" | WARN | #3 |
| **R3 TODO/FIXME 未声明** | diff 新增代码含 TODO/FIXME 但 commit message 没提 | "代码留了未完成标记但没说" | WARN | #10 |
| **R4 大体积删除** | 单文件删除 > 100 行且与 --task 无关 | "可能误删了不该动的代码" | WARN | #7 |
| **R5 commit 占位符** | commit 只有 "fix"/"update"/"wip" | 占位符（已有，强化） | WARN | #10 |
| **R11 敏感文件触碰** | diff 含 `.env`/`*.pem`/`*.key`/`id_rsa`/`credentials.*` | 敏感文件被修改 | **FAIL** | 安全 |
| **R12 超大 diff 低注释** | 新增 > 200 行且注释率 < 5% | "可能需要 reviewer 关注" | WARN | 质量 |

> R11 是最硬的规则——敏感文件被碰直接 FAIL，不需要 --task、不需要日志、不需要任何上下文。纯文件名匹配。

### 现有规则 #1/#3 加 git-diff 回退分支

不改规则核心逻辑，加双路径：有 Agent 日志 → 走精确检查（现有逻辑）；无日志 → git diff 推断（弱信号 WARN）。

关键设计决策：**无日志时不报 FAIL，只报 WARN**。因为 git diff 只能证明「改了」，不能证明「没读」。

### --strict 与 --silent 的关系

| 模式 | 日志缺失时 | Agent 日志 | 纯 diff 规则 |
|------|:--:|:--:|:--:|
| 默认 | WARN（不阻断） | ✅ 跑 | ✅ 跑 |
| `--strict` | FAIL（阻断） | ✅ 跑 | ✅ 跑 |
| `--silent` | 跳过（不查） | ❌ 不跑 | ✅ 全跑 |
| `--ci` | = strict + silent | ❌ 不跑 | ✅ 全跑（exit ≥1 阻断） |

## 三、P0：LogFormat 可插拔接口

```typescript
interface LogReader {
  extractOperation(content: string): string;
  extractFileReferences(content: string): string[];
}

class MarkdownLogReader implements LogReader { /* 当前实现 */ }
class JSONLLogReader implements LogReader { /* v0.94 新增 */ }
```

`checkLogs()` 根据日志文件扩展名自动选择 reader（`.jsonl` → JSONLLogReader，`.md` → MarkdownLogReader）。

**收益**：审计工具核心弱点改善（启发式正则 → 结构化字段匹配），为 v0.95 配置化打基础。

## 五、P0：真实 Skill 加载链复现实验

> 回答评审核心质疑：prompt 前缀注入的 0% vs 100% 误伤率，在真实 Skill 加载链下还成立吗？

### 背景

v0.93 的 10 组对照实验中，sofagent 条件是 **prompt 前缀注入 4 条核心规则**，与真实 WorkBuddy 中加载的完整 SKILL.md + think.md + rules.md 加载链有本质差异。

### 实验设计

| 条件 | v0.93 实验 | v0.94 新增 |
|------|------|------|
| 裸 Agent | OpenClaw --local（无 sofagent） | 同左 |
| prompt 注入 | 手贴 4 条规则前缀 | 同左（对照组） |
| **真实加载链** | — | **WorkBuddy 完整 sofagent Skill** |

**任务**：复用 Task 1（camelCase → snake_case）。**指标**：变量名误伤率 + 加载链命中率。

### 预期结果与决策

| 结果 | 含义 | 决策 |
|------|------|------|
| 真实加载链 ≤ prompt 注入 | 完整加载链至少不差于前缀注入 | ✅ 继续推广 |
| 真实加载链 > prompt 注入 | 完整加载链反而干扰了 Agent | ⚠️ 排查加载链哪个层导致干扰 |
| 加载链命中率 < 50% | Agent 根本没读到约束 | 🔴 加载链机制本身有问题 |

## 七、P0：sofagent-fde Skill

> 中小企业 AI 落地唯一可行路径是 FDE 驻场部署。

### 使用者画像

| 角色 | 是谁 | 看什么 |
|------|------|------|

- 三大交付物：部署方案书（给老板）、知识库（给 IT）、运行时（给 Agent）
