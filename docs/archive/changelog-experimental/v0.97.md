## 〇、P0：v0.96 诚实性修复（🔴 必须在纪律层实验前完成）

> 来源：v0.96 第三轮外部审查（2026-06-29）发现的实锤 bug 和文档-代码脱节。这些不是新功能——是在修「表演诚实」的裂缝。必须在纪律层证伪实验之前修完，否则实验结果的可信度也会受牵连。

### 〇.1 verify-evidence.ts 负向证据三倍计数（实锤 bug）

**文件**：`sofagent/audit/src/verify-evidence.ts` 第 101-120 行

**bug 原理**：`countMatches` 函数被 TEST/LINT/BUILD 三个 pattern 各调用一次。每次调用都对全文扫描 `NEGATIVE_PATTERN`（匹配 error/fail/broken 等负向关键词）。日志里出现 1 次 fail → totalNegative = 3。

**影响**：任何包含 error/fail/broken 的正常日志（如 "fixed the error" 或 "no failures"）都被结构性放大 3 倍。审计工具误报率被系统性推高。这是审计工具信誉的直接威胁——开发者用两次就会关掉它。

**修复**：负向证据统计从 countMatches 中拆出，独立为单次全文扫描。

### 〇.2 verify-evidence.ts BUILD_PATTERN `make all` 误报

**文件**：`sofagent/audit/src/verify-evidence.ts` 第 22 行

**bug 原理**：`BUILD_PATTERN = /...|\bmake\b\s+(build|all|install|clean)/i` 中 `make all` 会匹配 `make all the difference`、`make all changes` 等正常文本。

**影响**：日志中任何 `make all XXX` 的正常描述会被误判为「build 证据」，导致未验证的任务被判定为「已验证」。

**修复**：收紧 `make` 的匹配——要求 `make all` 后面必须紧跟行尾或标点，不能接普通单词。或改为只匹配 `make all` 单独成行。

### 〇.3 Changelog 与实际代码不一致——声称删除的脚本仍在

**v0.96 changelog 明确记录**（第 31-37 行）：
- `verify-evidence.sh → 删除 bash + 更新引用`
- `skill-safety-check.sh → 删除 bash + 更新引用`
- `task-record.sh → 删除 bash + 更新引用`

**实际验证**：
- ❌ `sofagent/scripts/task-record.sh` 仍然存在
- ❌ `sofagent/scripts/skill-safety-check.sh` 仍然存在
- ❌ `install.sh` 第 516 行部署循环引用不存在的 `audit-summary.sh`（幽灵文件）

**修复**（方案 B——诚实补 changelog）：

v0.96 changelog 表述精度不够——bash→TS 迁移是分批的（v0.96 第一波 4 个，v0.97 第二波 6 个），3 个「僵尸」脚本在 v0.93/v0.94 TS 重写后保留 bash 旧版作为兼容路径，v0.97 清理。**分批迁移的中间态本来就是计划的一部分，不是「说了没做」**。changelog 补充说明，install.sh 幽灵引用同步修复。

> ⚠️ 不选方案 A（真删脚本）的理由：v0.97 §五的 bash→TS 第二波会处理这些脚本的迁移和清理，在 v0.97 统一做，不在 v0.96 事后补删。

### 〇.4 skill-safety-rules.ts regex 死代码嫌疑

**文件**：`sofagent/audit/src/rules/skill-safety-rules.ts` 第 12 行 + 第 80-83 行

**问题**：`SafetyRule` 接口加了 `regex?: RegExp` 字段，`COMPILED_RULES` 也做了预编译（去除 g flag），但 `scanFile` 实际用的是 `r.pattern` 还是 `r.regex`？如果是 `r.pattern`，那 `regex` 字段和整个 `COMPILED_RULES` 预编译就是死代码——v0.94 changelog 说「消除死代码三元」，但这里可能新引入了死代码。

**修复**：核实 `scanFile` 到底用哪个字段。如果用 `regex`，确认预编译生效；如果用 `pattern`，删掉 `regex` 字段和 `COMPILED_RULES`。

### 〇.5 task-orchestrate.ts execFileSync 超时不一致

**文件**：`sofagent/audit/src/task-orchestrate.ts` 第 204 行 vs 第 345 行

**问题**：`ao compose` 有 `timeout: 120000`（2 分钟），但 `runAo` 函数用 `timeout: 300000`（5 分钟）。如果 `ao compose` 卡住 2 分钟超时，catch 块里第 209 行又调了一次 `ao compose --run`——这个调用继承 `runAo` 的 300s。级联超时会让用户等 7 分钟才报错。

**修复**：统一超时策略——所有 `ao` 调用统一为 180s（3 分钟），catch 块的 fallback 调用也加独立超时。

## 二、P0：非 OpenClaw 平台加载链可靠性实测

> 来源：两份审查共识——「非 OC 平台加载链可靠性是整个项目的根基问题，而根基是裂的。」

### 实测设计

| 平台 | 实测次数 | 测量指标 |
|------|:--:|------|
| WorkBuddy | 30 次新会话 | think.md 加载率 / rules.md 加载率 / 闭合清单执行率 |
| Claude Code | 20 次新会话 | 种子指令生效率 / audit 可运行率 |
| Codex | 20 次新会话 | 同上 |
| Hermes Agent | 20 次新会话 | 同上 |

**总计 90 次实测**，覆盖 4 个平台。

### 加载链命中率统计方法

每次新会话：
1. 派一个简单任务（如「在 README.md 最后加一行空行」）
2. 检查 task/logs 是否记录了 think.md 的 Read 操作
3. 检查 Agent 是否执行了闭合清单
4. 记录：命中/部分命中/未命中

### 结论阈值

| 加载率 | 处理 |
|:--:|------|
| ≥ 70% | 保持当前方案，标注「实验性支持」 |
| 40-70% | 考虑将 think.md 关键内容内联进 SKILL.md，标注「有限支持」 |
| < 40% | 诚实标注「该平台仅宪法层生效」，放弃「跨平台」叙事中的「等值」暗示 |

> ⚠️ **预期**：基于 v0.60-v0.62 的历史数据（1/3 和 0/3），WorkBuddy 的加载率可能低于 40%。如果实测证实这一点，v0.97 必须做出叙事调整——把「跨平台纪律标准」改为「OpenClaw 完整治理 + 其他平台宪法层约束 + 审计工具跨平台」。

## 三、P0：审计 A9/A10/A11 代码实现

> 来源：v0.96 §三规则草案。审查二：「审计层没有覆盖 Agent 被攻击了的情况，只覆盖了 Agent 粗心。」

### A9 不纳注入（prompt injection 检测）

检测范围：Agent 生成的代码中是否包含已知注入模式。

**实现**：
- 纯文本正则匹配——不依赖语义分析，--silent 模式可跑
- 规则文件：`audit/src/rules/rule-a9-no-injection.ts`
- 测试文件：`audit/src/rules/rule-a9.test.ts`（≥8 个测试用例）

**检测模式清单**（初始版本）：
| 模式 | 正则 | 风险级别 |
|------|------|:--:|
| 指令覆盖 | `/ignore (all )?previous (instructions|prompts)/i` | 🔴 |
| 角色劫持 | `/(you are now|你现在是|你的新角色是) (DAN|jailbreak)/i` | 🔴 |
| 规则绕过 | `/do not follow (the |your )?(rules|guidelines|instructions)/i` | 🔴 |
| 输出劫持 | `/(ignore|forget) (everything|all) (above|before)/i` | 🔴 |

**检测范围**：git diff 中新增的代码注释和字符串字面量。

### A10 不引毒源（供应链检测）

检测范围：依赖文件（package.json / requirements.txt / Cargo.toml）的变更。

**实现**：
- 检测新增依赖是否指向非官方源（如 GitHub raw URL / 个人服务器）
- 检测版本号是否从语义化版本变成了指向特定 git commit
- 规则文件：`audit/src/rules/rule-a10-no-poison.ts`
- 测试文件：`audit/src/rules/rule-a10.test.ts`（≥8 个测试用例）

**v0.97 不维护恶意包名单**——那是独立安全服务的事。只检测「模式可疑的依赖变更」。

### A11 不滥资源（资源消耗检测）

检测范围：单次任务的文件操作规模。

**实现**：
- 纯 git diff 统计，--silent 模式可跑
- 规则文件：`audit/src/rules/rule-a11-no-abuse.ts`
- 测试文件：`audit/src/rules/rule-a11.test.ts`（≥8 个测试用例）

**阈值**：
| 检测项 | 阈值 | 判定 |
|------|:--:|:--:|
| 新增文件数 | > 50 | WARN |
| 单文件新增行数 | > 10,000 | WARN |
| 批量删除文件数 | > 20 | FAIL |

> 来源：v0.96 外部审查阻断——「246 个测试没有一个跑过真实 git diff 输出。所有数据都是手工构造的 makeDiffFile()。一次 git 版本升级就能让整个审计工具产生错误的 diff 解析。」

### Agency Agent 模板匹配

**不自建模板库。** AO Compose 自带 Agency Agent 的几百个模板（数据分析型、文档生成型、代码审查型、客服回复型等）。编排引擎直接引用——不改模板、不加 wrapper、不建中间层。

```
编排引擎（engage.md）
  ↓ AO compose 拆解出子任务
  ↓ 根据子任务类型，匹配 Agency Agent 模板
  ↓ 注入模板到子任务上下文
  ↓ 子 Agent 按模板执行
  ↓ 任务完成 → think.md 反思
  ↓ 下次同一节点任务 → 反思驱动编排引擎微调拆解策略
```

**厚在治理，薄在复用**：编排引擎的代码只负责「何时拆、怎么拆、拆完谁做」——这是治理层。具体模板由 Agency Agent 提供——这是复用层。

### think.md → 编排引擎反馈回路（新增）

> 当前编排引擎每次拆解都是从零开始——不读 think.md 的反思记录。v0.97 新增反馈回路：

```
任务完成
  ↓
闭环反思（think.md 写入本次踩坑）
  ↓
下次同一 workflow 节点新任务
  ↓
编排引擎点火前先读 think.md（该节点的历史反思）
  ↓
根据反思调整拆解策略
  例：think.md 记录「上次拆分太细导致子 Agent 上下文不足」
  → 本次减少拆分粒度
  例：think.md 记录「Agency Agent 模板 X 在这个场景下容易出错」
  → 本次换模板 Y
```

## 最坏情况预案

如果纪律层增量在反转实验中**无法复现**（或统计不显著）：

1. **不压结论。** 诚实发表实验报告——包括所有原始数据、统计方法、可能的原因分析
2. **调整 v1.0 定位。** 从「纪律层被证实有效」调整为「纪律层在特定陷阱类型上有效（同名语义混淆），通用场景待验证」
3. **不影响审计层路线。** 审计工具（A1-A11）的价值不依赖纪律层增量——它是「事后检测」，纪律层是「事前约束」。「事后检测」在任何情况下都有独立价值
4. **v0.98 路线不变。** 审计闭环六步 + GitHub Action + 持续使用案例——这些工作在纪律层增量是真是假的情况下都可以推进
