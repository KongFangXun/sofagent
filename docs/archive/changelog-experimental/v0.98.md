## 概述

v0.98 的定位来自三条线的交汇：

1. **两次各 100 次对照实验的结论（作废）**。v0.97 + v0.98 两次实验都证明：纪律层在运行时的行为约束效果无法通过实验验证——不是"有效但不够强"，而是"实验方法本身无法测量"。与其第三次再跑同样的实验，不如承认现实：**sofagent 的核心价值从事前约束转向事后审计 + FDE 企业部署**。v0.98 的架构重组就是这个判断的直接产物。

2. **产品架构重组：审计引擎升为主产品**。实验结论作废 → 产品核心从事前约束转向事后审计。具体重组：lite 删除 + 宪法内联 SKILL.md → rules.md 升级为 fde.md（企业规范）→ think.md 由审计引擎基于 git diff 自动生成 → 编排引擎留主产品（与审计引擎形成运行时闭环）→ FDE 从独立 Skill 改为根目录文档 → OpenClaw 重定义为必装执行引擎（不再是"平台之一"）。这是 sofagent 定位最大的一次调整。

3. **v1.0 定位转向 FDE 部署底座**。v0.98 的架构重组直接改变了 v1.0 的目标——从"Agent 工作验收工具正式版"转向"FDE 部署底座"。三条主线：① 快速帮 FDE 实现 workflow ② 任意节点部署+执行 ③ MCP webhook 推送审计结果。准入条件从偏纪律层验证（9 条）换成偏 FDE+workflow+MCP（6 条）。

## 一、P0：审计闭环六步——从单次判定到持续改进

> 来源：v0.96 §二设计，v0.97 推迟（当时没有真实数据）。v0.97 实验数据因方法缺陷不可用，v0.98 用日常使用数据跑审计闭环。

### 六步闭环

```
检测（git diff 扫描改动）
  ↓
分类（规则匹配：A1-A11 逐条判定）
  ↓
根因（为什么这次 FAIL 了？同类问题之前出现过吗？）
  ↓
改进（规则阈值需要调吗？Agent 行为模式需要改吗？）
  ↓
回归（改进后重新审计同一批历史 diff，确认旧问题不重犯）
  ↓
上线（规则更新 + threshold 调整 + config.yml 版本化）
```

### 工程实现

| 步骤 | 产物 | 技术 |
|------|------|------|
| 检测 + 分类 | 现有功能 | v0.94 已完成 |
| 根因 | `audit/src/audit-root-cause.ts` | 聚合审计历史，按规则/文件/Agent 三个维度归因 |
| 改进 | `audit/src/config-suggestion.json` | 基于根因分析自动建议阈值调整 |
| 回归 | `audit/src/audit-regression.ts` | 用历史 diff 重跑更新后的规则 |
| 上线 | git commit config.yml | 配置变更进入版本控制 |

### 根因分析三个维度

| 维度 | 分析内容 | 输出示例 |
|------|------|------|
| 按规则 | 哪条规则触发最多？误报率如何？ | 「A3 不改越界：本月触发 23 次，其中 8 次经人工确认是误报（误报率 35%），建议调整路径匹配规则」 |
| 按文件 | 哪些文件反复被标记？ | 「src/config.ts：本月被 A3 标记 7 次——该文件可能是公共配置，建议加入白名单」 |
| 按 Agent | 哪个模型/配置下的 Agent 违规最多？ | 「审查模型 + 无 sofagent：A7 盲改率 42%。审查模型 + sofagent：A7 盲改率 12%。建议所有 Agent 启用 sofagent」 |

### 前置条件

- 从日常使用中积累了至少 30 天的审计数据（v0.97 实验数据因方法缺陷不可用，但在日常使用中仍有积累）
- 审计数据量 ≥ 100 条任务日志（有足够样本做统计分析）

## 三、P1：GitHub Action 模板

> 来源：ROADMAP 探索方向「CI/CD Gate」+ 审查一建议。

### 功能

一个 GitHub Action 模板文件，任何仓库放到 `.github/workflows/sofagent-audit.yml` 即可启用：

```yaml
name: sofagent-audit
on: [pull_request]
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Run sofagent-audit
        run: |
          npm install -g sofagent-audit
          sofagent-audit --diff origin/main..HEAD --ci --strict
```

### 设计原则

- **零配置**：默认行为就是最佳实践（`--ci --strict`）
- **exit code 驱动**：FAIL (exit 1) → PR 被 block；WARN (exit 2) → PR 可以合并但有标注
- **README badge**：通过后 README 显示绿色 badge
- **不绑定 sofagent 核心**：审计 CLI 独立运行，不需要 OpenClaw，不需要安装 sofagent Skill

### 产物

| 文件 | 说明 |
|------|------|
| `.github/workflows/sofagent-audit.yml` | Action 模板（放在 sofagent 仓库自身，也作为示例） |
| `docs/github-action.md` | GitHub Action 使用指南 |

## 三.5、P0：纪律层实验重设计

> 来源：两份独立审查的共识——「v0.97 实验失败后没有重跑就直接发了版，v1.0 准入条件 #1 处于未知状态。纪律层增量是真是假这个问题不能在 v1.0 前留白。」

### v0.97 实验的三根刺

| # | 缺陷 | 修复方案 |
|:--:|------|------|
| ① | SKILL.md trigger 条件匹配可能导致 skill 从未被激活 | 用 `@skill:sofagent` 显式触发，不依赖自动激活 |
| ② | 任务设计缺乏 scope creep 空间 | 设计真正有越界机会的任务（如「改一个函数时顺便重构另一个文件」） |
| ③ | bare/sofagent 切换用 rename 过于脆弱 | 用环境变量 `SOFAGENT_ENABLED=0/1` 控制，不动文件系统 |

### v0.98 重跑结果

| 参数 | 值 |
|------|------|
| 平台 | OpenClaw `agent --local` |
| 模型 | 工程模型 |
| 任务数 | 5 个（T1-T5） |
| n | 10（每组每任务） |
| 总计 | 100 次对照 ✅ 全部完成 |
| PASS 率 | 100/100（含 7 个幽灵 PASS——见报告缺陷一） |
| scope creep | 0/100 |
| victims | 0/100 |
| B 组 sofagent 激活 | 37/50 日志有激活痕迹 |

### 结论：作废（实验无法证实也无法证伪）

100 次对照全部 PASS，但**这个结果无法回答"纪律层有没有用"**——因为三个缺陷叠加使数据不具备判决力：

| # | 缺陷 | 影响 |
|:--:|------|------|
| ① | 评分脚本幽灵 PASS（7/100）：diff 为空也判 PASS | 7% 数据无效 |
| ② | workspace 交叉污染：B 组 think.md 累积了跨试验记录 | T1 的 B 组数据受序列效应影响 |
| ③ | 任务设计仍缺乏 scope creep 空间（和 v0.97 同根因） | 0/100 越界——无法测出差异 |

v0.97 三根刺的修复结果：① trigger ✅ 修复（37/50 激活）② scope creep ❌ 未修复（0/100 越界）③ rename 未改且引入新污染。净改善为零。

**v1.0 定位调整**：纪律层实验作废——不是"纪律层无效"，而是"实验方法无法测量"。v1.0 定位从"Agent 工作验收工具"转向"FDE 部署底座"。

> 📄 完整报告：[docs/evidence/anti-cases/004-discipline-experiment-inconclusive.md](../../evidence/anti-cases/004-discipline-experiment-inconclusive.md)

### 下一步：不再重跑同样的实验

v0.97 跑了 100 次，v0.98 又跑了 100 次，两次都因任务设计问题无法得出结论。第三次不会有不同结果。换赛道——从"实验室对照"转向"日常使用观察"（审计闭环六步）。如果要再跑实验（v0.99+），必须满足：任务涉及 3+ 文件联动修改 + 评分修复零 diff=FAIL + workspace 每次全新 git clone。

## 六、🔴 产品架构重组（v0.98 核心转身）

> 来源：v0.97 + v0.98 两次各 100 次对照实验都证明——纪律层在运行时的行为约束效果无法通过实验验证。与其第三次再跑同样的实验，不如承认现实：**sofagent 的核心价值从事前约束转向事后审计**。

### 6.1 决策背景

| 轮次 | 实验结论 | 教训 |
|------|------|------|
| v0.97 | 100 次对照，三根刺（trigger / scope creep / rename） | 实验设计有缺陷 |
| v0.98 | 100 次对照，修了 trigger（37/50 激活），但 scope creep 仍然 0/100，外加评分幽灵 PASS + workspace 污染 | **任务太简单测不出差异，不是纪律层无效，是实验无法区分** |

两轮实验的共同结论：**靠运行时纪律层约束 Agent 行为这条路，没有可测量的证据支撑。**

### 6.2 新架构：从「三层加载链」到「两个独立产品」

| 维度 | 变化前（v0.97 及以前） | 变化后（v0.98） |
|------|------|------|
| **核心叙事** | 三层加载链（SKILL→think→rules） | 两个独立产品 + 宪法层内联 |
| **宪法（4底线+6铁律）** | SKILL.md 内联 + lite 独立产品 | **内联到审计引擎 SKILL.md 顶部**，lite 删除 |
| **think.md** | Agent 自觉写（实测 2/50 才写） | **审计引擎自动生成**（基于 git diff 硬证据） |
| **rules.md** | 用户自定义偏好 | **改名 fde.md**，FDE 工程师写企业约束 |
| **审计引擎** | sofagent 的一个模块 | **sofagent 的核心**（git diff → 检测 → 生成 think.md） |
| **编排引擎** | sofagent 通用功能 | **留主产品**（与审计引擎形成运行时闭环） |
| **sofagent-fde/** | 独立 Skill 目录 | **改为根目录 `FDE.md` 大文档**（人读 + Agent 读） |
| **sofagent-lite/** | 独立产品 | **删除**（OpenClaw 自带约束机制，独立宪法 skill 多余） |

### 6.3 产品边界（重组后）

```
产品1：sofagent（审计引擎 = 唯一主产品）
  ├ SKILL.md（宪法层内联 + 审计引擎 + 编排引擎）
  ├ 审计引擎（A1-A11 规则，纯 git diff，不依赖 Agent 配合）
  ├ think.md（审计后自动生成/更新，不再靠 Agent 自觉）
  ├ 编排引擎（读 think.md 反馈，优化任务拆分策略）
  ├ daemon（可选，session 结束触发审计）
  ├ webhook / GitHub Action
  └ 引导："宪法有用？复制到你 Agent 的约束文件里"
      ├ OpenClaw → ~/.openclaw/rules.md
      ├ Claude Code → CLAUDE.md
      ├ Cursor → .cursorrules
      └ 其他 → 各自约束文件

产品2：FDE.md（根目录大文档，不再是独立 Skill）
  ├ 十步 FDE 实施流程（梳理企业 workflow → 定义 AI 节点 → 部署交付）
  ├ FDE.md（企业专属约束，FDE 工程师写，不是用户自己写）
  ├ workflow.yaml（FDE 产出，编排引擎输入）
  ├ 外部参考：n8n-workflows 模板库（行业流程参考）
  └ workflow 模板补充（v0.99 细化）：BPMN 2.0 标准 / Coze / Dify
```

### 6.4 编排引擎归属决策（留主产品）

**决策：编排引擎留主产品（审计引擎），不挪 FDE。**

编排引擎和审计引擎是同一个运行时闭环的两个半圆：

```
运行阶段（每台设备上持续循环）：
  ┌→ AI 节点的任务进来
  │   编排引擎决定怎么拆（读 think.md 历史经验）
  │   Agent 执行
  │   审计引擎检查 git diff → 生成/更新 think.md
  └→ think.md 反馈给编排引擎 → 下次优化拆法

部署阶段（FDE，一次性）：
  梳理 workflow → 定义 AI 节点 → 生成 workflow.yaml → 装设备 → 实施
```

FDE 是闭环外面的"实施者"——实施完就走，不参与日常循环。把编排引擎挪到 FDE 等于把闭环劈成两半。

### 6.5 workflow 产出格式（新增）

FDE 梳理完企业 workflow 后，产出的不只是一个 .md 文档——需要能被编排引擎消费的机器可读格式。

| 阶段 | 格式 | 产出者 | 消费者 |
|------|------|--------|--------|
| FDE 梳理时 | Markdown 表格（人读） | FDE 工程师 | 企业负责人 + FDE 自己 |
| 交付时 | **workflow.yaml**（人可编辑） | FDE 工程师 | 编排引擎输入 |
| 运行时 | **DAG JSON**（机器产机器读） | 编排引擎 | OpenClaw 执行 |

**workflow.yaml**：**Agent 在 FDE §六 自动生成**（不是 FDE 工程师手写）。Agent 全程参与 FDE 对话，记录了每个节点的五要素 + AI 分类，到 §六 时自动输出 yaml。FDE 工程师只需 review 和微调。定义 AI 节点（类型🔄/⚡、输入源、输出目标、审计频率、企业 Skill 需求）。编排引擎的输入。

**DAG 执行图**：编排引擎读 workflow.yaml + think.md 历史经验后，展开为具体执行步骤的 JSON。给 OpenClaw 跑。

> ⚠️ DAG JSON 的确切 schema 取决于 OpenClaw `ao compose` 的标准输出格式。v0.98 在概念层面定义分层（yaml → DAG），schema 细化在 v0.99 实现。

### 6.6 rules.md → FDE.md

| 维度 | 变化前 | 变化后 |
|------|------|------|
| 文件名 | `rules.md` | `FDE.md` |
| 谁写 | 用户自己 | **FDE 工程师**（老板说需求 → FDE 翻译成约束） |
| 定位 | 用户自定义偏好（回复风格、模型偏好） | **企业运行规范**（合规要求、数据脱敏、审计频率、行业约束） |
| 内容来源 | 用户自学后填 | FDE 梳理 workflow 时沉淀 |

模板结构保留（模型偏好 / 行为规则 / 阈值 / 企业合规），内容升级。

### 6.7 think.md 生成机制

| 方案 | 做法 | 可靠性 | v0.98 采用 |
|------|------|:----:|:----:|
| 现状 | Agent 自觉写 | ❌ 2/50 才写 | 废弃 |
| A | 审计引擎跑完后基于 git diff 自动生成 | ✅ 高 | ✅ 主方案 |
| B | daemon 监听 session 结束事件触发生成 | ⚠️ 中 | ✅ 可选增强 |

## 四、P1：部署层 bash→TS 决策 + install.sh 模块化

> 来源：bash→TS 迁移第三波（v0.96 规划，v0.97 推迟）。

### 决策背景

部署层脚本（install.sh / uninstall.sh / verify.sh / cleanup.sh / lite/install.sh）共 2,458 行。特点是：
- 需要在**安装 Node.js 之前**就能运行（否则 chicken-and-egg）
- 需要零依赖（bash 是所有 macOS/Linux 的默认 shell）
- 不涉及复杂逻辑（主要是 cp / mkdir / chmod / echo）

### 决策

**部署层保留 bash bootstrap，不迁 TypeScript。**

理由：
1. bash 在部署场景下是唯一可依赖的运行时——你不能假设目标机器有 Node.js
2. 部署脚本的逻辑足够简单——不涉及类型安全的风险
3. 保留 bash 和 Rust/C 项目保留 `Makefile` 一样——是 bootstrap 层，不是核心逻辑层
4. 迁移成本高（2,458 行 bash 重写为 TS + 引入 Node.js 依赖 + 处理 chicken-and-egg 问题）但收益低

### 执行

- 部署层脚本封存——不再做大改动，只做 bugfix
- 在 LIMITATIONS.md 标注「部署层永久保留 bash bootstrap」
- bash 重复代码债（§七 代码审计发现）——接受为已知技术债，不单独建 bash 基础设施

### install.sh 模块化拆分

> 来源：两份独立审查共识——「install.sh 941 行是定时炸弹。每次版本都在修 install.sh 的 bug（v0.47 装不上、v0.90 三个 P0 安装断裂、v0.97 幽灵引用 audit-summary.sh）。继续打补丁不可持续。」

| 模块 | 职责 | 预估行数 |
|------|------|:--:|
| `lib/platform-detect.sh` | 平台探测（OpenClaw / WorkBuddy / Claude / Codex / Hermes） | ~80 |
| `lib/file-deploy.sh` | 文件部署（cp 到目标目录） | ~120 |
| `lib/daemon-register.sh` | daemon 注册（launchd / systemd） | ~100 |
| `lib/post-install.sh` | 安装后检查（verify 触发 + smoke test） | ~80 |
| `install.sh` | 主入口（组装 + 参数解析 + 错误处理） | ~200 |
| **合计** | | **~580**（从 941 减 38%） |

**设计原则**：每个模块独立可测（`source lib/xxx.sh && 函数名 参数` 能独立跑）。不引入新的依赖（仍只用 bash built-in）。主入口只做组装，不做逻辑。

### 本节标题更新

> v0.97 原标题「部署层 bash→TS 决策 + 执行」→ v0.98 更新为「部署层 bash→TS 决策 + install.sh 模块化」。

### MCP 推送层 POC：100 行概念验证（v0.96 审查新增）

> 来源：v0.96 第三轮审查——「五层架构展望中后三层（MCP推送层/协同层）目前零代码、零原型、零验证。''先有理论框架再找工程对应''容易造空中楼阁。」

**定位**：不是实现 MCP 推送层的完整功能——是用 ~100 行代码证明「文件变化 → 推送」这个方向在工程上可行。如果 POC 跑不通，就从架构文档里诚实拿掉 MCP 推送层。

| 验证内容 | 技术 |
|------|------|
| 监听 `.sofagent/task/logs/` 目录新增文件 | `fs.watch`（Node.js 内置） |
| 读取新 task/logs 文件，提取摘要 | 现有 log-reader 接口 |
| 通过 webhook 推送到钉钉群 | 内置 `fetch` + 群机器人 webhook |
| 验证：修改一个文件 → agent 记录日志 → 钉钉群 3 秒内收到消息 | 端到端手动触发 |

**通过标准**：手动触发 → 钉钉群收到消息。不用自动化测试，不用处理异常路径。就一条 happy path——证明链路通。

**如果 POC 失败**：诚实标注 MCP 推送层从「规划」改为「探索」，从架构文档中移出五层架构图（降为三层的当前形态：纪律→执行→审计）。
