## 第二部分：AI 知识库概念先行

### 为什么要做 AI 知识库

FDE 交付给客户三样东西：交付手册 + AI 节点（三层实体）+ 知识库。第三样目前是几个散文件（think.md + scoring.md + task/logs），既没结构也不能自己生长。

升级为 AI 知识库——AI 节点在干活过程中自动积累的结构化知识系统。基于 Karpathy LLM Wiki 框架适配 sofagent 架构。

### 关键设计决策（经讨论确认）

| 决策点 | 选择 | 理由 |
|--------|------|------|
| think.md 边界 | **不动**——加载链反思层，独立运作 | think.md 是被动注入的短期教训，AI 知识库是长期记忆，职责不重叠 |
| Query 机制 | **被动注入**（非主动查询） | Agent 主动查询服从率存疑（铁律服从率强措辞下才 72%）。改为加载链启动时自动注入 top-N 相关页——和 think.md 同机制，服从率从「存疑」变「必然」 |
| Ingest 触发 | **daemon 检测 task/logs 变化** | Agent 平台没有 session 结束事件，只有文件监控。daemon 检测到变化 → 触发编排引擎跑知识提取 session |
| Lint 时机 | **loop-evaluate 运行时顺带跑** | ROADMAP 明确「不支持 cron 定时」。Lint 绑已有组件，不做独立定时器 |
| 架构定位 | **数据层，不进五层** | 五层是功能引擎层，AI 知识库是数据目录。硬塞进五层维度不匹配——就像把「数据库」当成微服务架构里的一个「服务」 |

### 三层架构

```
┌─────────────────────────────────────────────────┐
│                  Schema（规则层）                  │
│  fde.md 加一章"AI 知识库维护规则"                   │
├─────────────────────────────────────────────────┤
│               AI 知识库（Wiki 层）                  │
│  .sofagent/knowledge/                             │
│  index.md + entities/ concepts/ comparisons/      │
├─────────────────────────────────────────────────┤
│               Raw sources（证据层）                │
│  task/logs/ + scoring.md + 审计记录（只读）         │
└─────────────────────────────────────────────────┘
```

### think.md vs AI 知识库边界

| | think.md（反思层） | AI 知识库（沉淀层） |
|:--|:--|:--|
| 注入机制 | 加载链被动注入 | 加载链被动注入（top-N 相关页） |
| 内容 | 单次任务的反思教训 | 跨任务的模式、最佳实践、对比 |
| 结构 | 扁平时间线 | Wiki 页面 + 双向链接 |
| 生命周期 | 旧了压缩 | 持续积累，越用越值钱 |

## 第三部分：verify.ts 代码重构

### 背景

v0.99.8 双审查（审查模型 + 工程模型）发现 `sofagent/audit/src/verify.ts` 达 1257 行，可维护性差。原计划 v1.1 拆分，讨论后决定提前到 v0.99.9——因为 AI 知识库的 Lint 检查（v1.1）也要挂到 verify 流程，不拆后续更难动。

### 拆分方案

按检查类别拆为 4 个模块 + 1 个入口 + 1 个工具模块：

```
sofagent/audit/src/
├── verify.ts          → 入口（main + quick 模式 + banner/summary），~250 行
├── verify/
│   ├── types.ts       → CheckStatus / CheckItem / VerifyResult / Args 接口定义
│   ├── utils.ts       → tryExec / commandAvailable / countChars / readFileContent 等工具函数
│   ├── verifier.ts    → Verifier 类（checkPass/Fail/Warn + outputJson/Summary）
│   └── checks.ts      → §1-§11 检查函数（runAllChecks + runQuickChecks）
```

### 拆分原则

1. **纯文件移动 + import 调整**——不改任何业务逻辑
2. **407 tests 必须全绿**——拆分后行为完全等价
3. **bin 入口不变**——`sofagent-verify` 命令行为不变
4. **verify-evidence.ts 的 `--help` 引用不变**

## 第四部分：行业笔记落地 + Skill 摘要优化

### 背景

v0.99.9 开发过程中，对 7 项行业洞察做了判断和分类——哪些立刻做、哪些进 ROADMAP、哪些是 v2.x 探索。同时发现 Skill 文件描述段存在信息架构问题：摘要写了步骤 = Agent 会照着摘要偷懒跳过正文。

### Skill 摘要信息架构优化（4 文件）

**原则**：摘要只写两件事——什么时候触发 + 解决什么问题。任何「怎么做」的内容留在正文，迫使 Agent 读。

| 文件 | 改前 | 改后 |
|------|------|------|
| `SKILL.md` | "能约束行为、拆解任务、沉淀教训" | 去掉功能列表，只留问题域 |
| `FDE/SKILL.md` | "走完四阶段十二步（进场→挖掘→交付→离场）" | 去掉步骤流程，只留触发条件 |
| `engage.md` | "两档拆解（拆 vs. 不拆）" | 去掉方法描述 |
| `loop-evaluate.md` | "复盘、评分、沉淀" | 去掉功能列表，改为触发条件 |

### 7 项行业笔记落地分配

| # | 笔记 | 落地位置 | 版本 |
|---|------|---------|------|

| 1b | 后置测验（可选维度） | ROADMAP v1.x | v2.x 探索 |
| 2 | 三层时间尺度循环 | ARCHITECTURE「三层循环」节 | 叙事已写入，中层 v1.1 / 外层 v2.x |

| 4 | Lingua Word 短词锚定 | ROADMAP v1.x | v1.0 前 A/B 实验 |

| 6 | 共享记忆三模式 | ARCHITECTURE v2.x + ROADMAP v2.x | v2.x 占位 |
| 7 | 7-Entry Checklist | ROADMAP v1.x | v1.x 占位注释 |

### 关键决策记录

1. **think.md 模板强制但不做 gate 检查**——强制 gate 会导致 Agent 用垃圾内容填模板（"做了什么：改了bug。踩了什么坑：没有。"），信噪比暴跌。模板强制（如果写就按模板）+ 审计标⚠️但不阻断
2. **审批超时降级 + 防橡皮图章不做**——这是企业级 BPM 功能，不是 Agent harness 层的职责。sofagent 用户大部分是单人或小团队，不会有「审批者」角色
3. **后置测验默认关闭**——每次任务让人答题成本太高，只有高风险任务才开启
