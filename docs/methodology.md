## 这个项目是怎么做出来的？

说到底是场实验——AI 模型们能不能在迭代中互相校验，写出一个像样的技术产品？

作者代码写得很糟糕，所以换了一种方式：DeepSeek V4 Pro 和 GLM-5.2 各自写代码，也各自审对方的代码——两个模型都在写、都在审、都在改。作者也不跳出这个循环，坐在中间跟着一起滚：定约束、看产出、做终审。整个项目在「模型 A 写 → 模型 B 审 → 模型 A 改 → 再审」的循环里打磨出来。

大力出奇迹的代价是 token 消耗是正常写代码的 3-5 倍，烧 token 换项目产出与质量保证。好处是人不需要碰代码——设计决策、经验积累、方向判断，这些是人能做的。至于这种模式能不能稳定复现，说实话还不知道——所以这既是项目，也是实验。

## 双轮评审（GLM-5.2 + DeepSeek V4 Pro）

v0.93 起，每个版本发布前接受两轮独立评审：

- **GLM-5.2**：关注完整性、可交付性、用户体验
- **DeepSeek V4 Pro**：关注工程质量、安全、可维护性

两轮评审合并去重后形成问题清单，按 P0/P1/P2 排程落地。这个流程本身就是在验证 sofagent 想做的事——GLM 定框架 → DeepSeek 写实现 → GLM 审查 → DeepSeek 修复 → 下一轮。

## 一个诚实的注脚：实验做不通的部分

> 注：本文保留历史术语「纪律层」，对应 v0.98 后改称的「约束底座」。

v0.97 和 v0.98 各跑了一次 100 次对照实验，想验证「纪律层在运行时到底有没有用」。两次都因为任务设计太简单（0/100 越界）、评分幽灵 PASS、workspace 污染等问题，**结论无法采用**。

这件事的直接产物是 v0.98 的架构重组：承认运行时约束这条路没有可测量证据支撑，产品核心从事前约束转向事后审计。10 天 17 个版本的迭代速度确实是真的，但「模型互审能写出好产品」和「纪律层能约束 Agent 行为」是两件事——前者是这个项目本身，后者是产品的核心命题，后者至今没有实验证据。
