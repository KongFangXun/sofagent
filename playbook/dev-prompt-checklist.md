# dev-prompt-checklist.md · Dev Prompt 交付前自检手册

> **定位**：A0 证据闸门 `check-dev-prompt.sh` 的"人脑补充层"。
> 脚本查"引用的东西存不存在"（路径 / 函数名 / 目录），本清单查"**写法对不对、全不全、新不新**"——那些脚本结构上拦不住的思维盲区。
>
> **使用方式**：`check-dev-prompt.sh` 零 ❌ 后，逐条过本清单。发现命中 → 修 prompt → 回跑脚本确认无回归。
>
> **嵌入位置**：`docs/changelog/releasing.md` 阶段十二 步骤 41（开发 Prompt 校验循环）。
>
> **来源**：发版前评审实证（5🔴 / 5🟡 / 7🔵，双人背书）——详见 `~/Desktop/<版本>-dev-prompt-review-<日期>.md`。

## 一、三类根因（为什么 AI 生成的 dev prompt 会出错）

### ① 凭记忆写"事实"（占本次 5🔴 的 4 条）

LLM 写 prompt 时，对"文件在哪、函数叫什么、行号是多少"是**凭概率补全**，不是查表。它"记得"的大概率是训练语料里见过的类似项目结构，不是你这个仓库的真实结构。

**高危对象**（写进 prompt 就必须验证）：

| 对象 | 验证命令示例 | 本次踩中的条目 |
|------|------------|--------------|
| 文件路径 | `ls engine/audit/src/rules/shared/patterns.ts` | 🔴-3 / 🔴-5 / 🟡-8 |
| 函数签名 | `grep -n "export function buildConstrained" engine/` | 🔴-4 |
| 行号 | `grep -n "defaultRules" engine/audit/src/rules/runner.ts` | 🔴-1 / 🔴-2 |
| 数组 / 变量名 | `grep -n "BASELINE_RULE_KEYS" engine/core/src/` | 🔴-3 |

**口诀**：写进 prompt 的每一句"事实"，写之前先 grep 一下。成本 10 秒，收益干掉一半阻断级问题。

### ② 只写"造什么"，没写"插哪"（占本次 2 条）

AI 详细描述新组件长什么样，但**不追"系统怎么知道要跑它"**。它默认开发者会自己摸清注册机制——但开发者照 prompt 做，不读源码。

**自查问题**：对每个新组件问一句——
> "如果开发者只做我写的这些，这东西会**自动生效**吗？"

答案为"不会，还得在某处登记一下" → 那个"登记处"必须写进 prompt。

本次实例：A20-23 写了规则对象，没写进 `defaultRules` 数组 → 默认配置下静默不生效。

### ③ 时间快照失真（占本次 1 条）

prompt 是**快照**，代码在动。写 prompt 时某个 bug 还没修，等交付时已经修完了。把"已完工"当"待开发"交给开发者 → 重复施工甚至覆盖好代码。

**处理**：prompt 里固定留一个 **"已完成区"**。交付前扫一遍 `git log --oneline -20`，把已落地的条目移进去标"仅回归验证"。

## 二、交付前 7 条自查（逐条打勾）

> 建议：把 7 条印在脑子里，过完 `check-dev-prompt.sh` 零 ❌ 后，**逐条过一遍**。命中即修。

- [ ] **1. 引用真实性**：每个文件路径 / 函数签名 / 行号，我都 grep 验证过真实存在、且签名一致？
      （脚本查"存不存在"，你补查"签名对不对、行号准不准"）

- [ ] **2. 注册点 / 挂载点**：每个新规则 / 新功能 / 新文件，我都写明了"注册/挂载到哪个数组、入口或配置项"？
      （反问：开发者只做这些，它会自动生效吗？）

- [ ] **3. 改造代码的"保留声明"**：凡是要开发者"重写/改造"现有代码的地方，我标明了"哪些部分保持不变"？
      （给 diff 或只贴改动行，别给"整段替换"——否则尾部逻辑会被一起删掉）

- [ ] **4. 已完成区剥离**：prompt 里有没有"其实已经做完了"的条目？移进"已完成区"标"仅回归验证，勿重复实现"？
      （对照 `git log --oneline -20` 扫一遍）

- [ ] **5. 强动词名副其实**："复用 / 调用 / 读取"是不是真的能直接调用？还是其实只是"参考其思路"？
      （若函数签名错配、格式不兼容，改"参考（不直接调用）"）

- [ ] **6. 修正批回写完整性（三方对账防半拉子）**：凡是往 prompt 里合入「审查修正 / 定谳结论 / 已销案合并」，是否把**同一结论在 prompt 内的所有落点**同步回写了？
      （典型病：基线表说「未定谳」而文末清单说「已定谳」；待拍板清单合并删行后，正文「见清单第 N 条」引用错位。自查法：合并/修正任何条目后，grep 该条目关键词（如「定谳」「清单第」）扫全 prompt，逐处核对指向；修正批收尾必须能列出本批触碰的全部段落清单，列不全 = 没查过 = 未收口）

- [ ] **7. 大版本深检六项（minor 版 / 含 breaking 必跑；patch 版可选）**：prompt 深检实证——check-dev-prompt.sh 只拦「文件存在性」，以下六类结构性错误它拦不住，均有一轮 5 处真问题的实锤：
      ① **章节数机械对账**：prompt 产任务章数 == devlog `## ` 章数（含元章声明——「与后续版本的依赖」这类不产任务的章也要显式标注，防对照困惑）
      ② **验收搬运对账**：devlog 每章验收 `- [ ]` 逐条 grep prompt（用 node 脚本机械比对，不靠肉眼）
      ③ **「不存在的东西当已存在写」**：devlog 引用的枚举值/常量/字段逐个查源码（实锤：`COVERAGE` 不在 DecisionKind 12 值枚举内，运行时校验会抛「非法 kind」）
      ④ **移除/改名面全枚举**：凡「移除 X」条目，`git grep` X 的**全部落点**（导出面/测试/README/@public 基线 JSON——实锤：曾发生移除面残留事故（更名期旧名多处残留，基线漏改 = 门禁红））
      ⑤ **基线数字时效**：devlog 排期快照数字（工具数/文件数/枚举数）逐个当轮重测（实锤：「77th tool」实为 105th；两族字面量 28/9 → 31/17 漂移）
      ⑥ **ROADMAP 行交叉对账**：ROADMAP 版本行能力条目逐条在 devlog+prompt 找落点（ROADMAP 是对外承诺面，漏项 = 承诺无载体）
      发现问题**先修 devlog（SSOT）再同步 prompt**——只修 prompt 不修源头，下个 session 读 devlog 重新踩坑。

## 三、`check-dev-prompt.sh` 已知盲区（未来增强方向）

脚本当前覆盖：文件路径存在性 / 函数定义存在性 / 目录存在性 / 快照标记行数对账，外加四类
「本就应当尚不存在」的归类（📋 待新建 · 📋 待归档 · 📋 迁移改名目标）与 🗑 已退场
（文档声明该模块已移除）。以下是**结构上拦不住**、需本清单人工补的：

| 盲区 | 说明 | 人工补查方式 |
|------|------|------------|
| 函数签名准确性 | 函数存在，但参数列表是虚构的 | grep 函数定义，对照 prompt 里的调用 |
| 行号引用 | "L180-211" 可能已漂移 | grep 锚点字符串定位真实行号 |
| 注册点 / 数组归属 | 新规则没写进哪个数组 | 反问"会自动生效吗" |
| 已完成区剥离 | 脚本不知道哪些已完工 | 对照 git log |
| 交叉引用一致性 | 章节号、§ 引用、内部链接 | 通读 + grep 章节号 |
| 修正批回写完整性 | 合并/修正条目后，同结论的其他落点未同步（基线表 vs 定谳清单自相矛盾、清单合并后「见第 N 条」错位） | 自查第 6 条：grep 关键词扫全 prompt 逐处核对 |
| "复用"可行性 | 强动词背后的函数是否真能直调 | 读目标函数实现确认 |
| 文件类型白名单外 | 提取只认 `.ts/.sh/.mjs/.json/.yml`——`.md` / `.tsx` / `.html` / `.yaml` / `.jsonl` 等**完全不判**（实测：`.jsonl` 34 条全指向运行时日志、`.tsx` 6 条全指向从未落地的 `engine/dashboard/`）⇒ 扩白名单必须逐类配「运行时/产物」规则，否则用一批假红换一个盲区 | 涉及这些类型的路径手查 |
| 表格行动词归属 | 判定域 = 「以动作词**开头**的单元格 + 引用所在单元格」；行内没有这样的单元格时**只**看引用自己那一格。动词写在格的**中段**（如「推送失败 → 移入 `x/`」）不再算数——该类行的表格引用会归为「不存在/错位」，需人工判断是否其实是目标位置 | 表格里既写路径又写动作叙述的行，核对动词属于哪一格 |
| 归位 / 箭头归类看词序 | 归位族（归档 / 移至）与箭头目标（`→` 右侧）只放行**目标**；「归档 `X` 至 `Y`」里 X 也是动词后项，会被一并放行 | 归档 / 迁移条目人工确认哪一侧是「源」 |

> ⚠️ **历史档案口径**：版本严格低于根 `package.json` 版本的 `docs/changelog/v*/*.md`，
> 漂移只计 🕘 不构成失败（冻结档案是发布时点快照，模块迁移后必然漂移）。对**正在发版**
> 的那份日志恒为严格口径（版本相等不算历史）；给历史档案补 `--strict` 即按 ❌ 判。

> 若未来要把其中某项自动化（如"签名准确性"可做 AST 比对），优先做 **②注册点** 和 **④已完成区** ——这两项最易自动化、收益最高。

## 四、改造代码时的"保留声明"规范

本次 🔴-2（runner 重写漏尾部 → P0 回归）是最典型教训：伪代码只贴了要改的循环，开发者照抄会把尾部降级逻辑一起删掉。

**规范**：

1. **能给 diff 就给 diff**，不要给"整段替换"的伪代码。
2. 若必须贴整段，**明确写一句**："以上仅为 XX 分支改造；下方 L180-211 的尾部逻辑（列出要点）必须原样保留。"
3. 涉及"移动 / 重构"时，澄清**哪些维度不变**。例：移规则到另一【层】≠ 改其【类】，阻断行为可能零改变——要点明，避免开发者误以为"移动即改变行为"。

## 六、施工后复核与回报纪律（prompt 的另一半）

> **定位**：前五节管「prompt 写得对不对」；本节管「拿到 prompt 之后怎么执行与怎么回报」。
> **来源**：v1.5.3 bugfix 收尾两批实证（约 8 处前提失效 + 2 处口径错位 + 1 处卡线被迫放弃 + 1 处对外动作误判）。

### ① 前提复核（施工前必做 —— 本次最高频失效模式）

prompt 里的**因果假设**（"为什么这是问题"）与引用路径一样会错，且错得更贵：按错误前提施工 = 白做，甚至反向施工。

| 实证：prompt 说的 | 实测 |
|---|---|
| 台账条目失效 ⇒ 文件"重新进入判定面" ⇒ 可能由绿转红（免费的覆盖扩张） | 该台账**不 gate 扫描面**（只服务漂移报告）⇒ 预期整个反了 |
| 「v1.5.x 各版 tools 数未记」⇒ 断笔在此 | 已记；真断笔在 v1.5.1 行与 v1.4.6 计数 |
| 「`--quick` 占 README 首屏主推位」⇒ 让位 | README 无此推荐 ⇒ 无需改；改了反而是凭空新增 |
| 「某模块零生产引用」⇒ 删掉即可 | 已有 inspector 消费 |
| 「某插件 0 处 flags 是正确设计」⇒ 后人勿补 | 实际有 `featureGates` 三档 |
| 「某收录徽章疑为假」⇒ 删或改 PR 态 | 实为真（PR 已 merged、目标仓全文含本仓名） |

**纪律**：每条条目的**判据**在动手前独立复核一次；**前提不成立 ⇒ 停手报告**（**不得**按错误前提施工，**不得**为凑"符合预期"的结论而软化）。回报时把「前提与实测不符」单列，它本身就是最高价值产出。

### ② 回报口径标注（计数 / 对账类结论必标三项）

同一批数据换口径就是另一个数；分歧表面像"谁算错了"，实际是标签不同。

- **统计时点**：改前 / 改后（实证：修复后对账自报的 `99/35/3` 实为"修复前"口径，正确为 `98/34/2`）
- **统计范围**：文件集筛选条件（实证：一份盲区计数用了未排除 `__tests__/`、`*.test.ts`、`*.d.ts` 的文件集，比门禁扫描面多 441 个文件 ⇒ 三数全部不可比、不可登记）
- **不可互算**：两种口径的数并列时**显式声明"不可互算"**（禁拼合第三写法）

### ③ 对外动作：先判可行性，再决定"谁做"

别把能自动化的活推给人（实证：`npm deprecate` 被误判为"需 2FA OTP、须维护者执行"，实测**直接可跑**）。判据：**先查鉴权模式 / 试跑一次**，再落到"我能做 / 必须人做"；移交给人时必须附**完整可粘贴命令 + 可逆方式**。

### ④ 卡线资产主动腾位（发版期设"归并窗口"）

`playbook/acceptance-test.sh`（4499/4500）与 `playbook/regression-checklist.md`（1949/1950）**只剩 1 行** ⇒ 任何新增都要"净零体操"，或被迫放弃改动（实证：一批的场景账本补记只能塞进既有长注释行以保净零；另一批因卡线而**放弃**了删除动作）。**建议**：发版期主动设归并窗口腾位，而非每批被动应对。

### ⑤ 发版判据的表述纪律（禁把"有存量命中"写成"全绿"）

门禁存在"已知存量命中"时**不得**表述为"全部通过"——实证：`check-archaeology` 有 1 处存量命中，且其设计是**有命中即 exit 1**，正确表述是「**N 道 rc=0 + M 道已知待清**」，否则该判据永久不可用或掩盖真红。

### ⑥ 门禁新判据必须带「失效模式分析 + 探针证据」

新增门禁 / 断言时，除证明"能转红"外必须回答**"它什么时候会假绿 / 假红"**——实证：

- 新加的"豁免台账自证"断言**自身**含 fail-open 边界（不能判定时静默降级放行，恰是它要防的那个病）⇒ 被独立复验抓出后返工；
- `search/code` 对超大 README（1.8MB）返回 0 命中 = 假阴性 ⇒ 判据须改用 blob 全文；
- `execFileSync` 默认 `maxBuffer` 1MB ⇒ 大文件静默失败。

**每条探针必须留三样**：构造方式 + 真实输出（含退出码）+ 还原确认（工作区干净）。
