# fresh-eyes 校准档案（维护者文档）

> **定位**：fresh-eyes 审查体系的通用注意事项集——记录「有这些问题需要注意，不要再犯」。
>
> **读者**：审查工具的维护者（driver / 管道 / 门禁脚本的改者）与报告判读者（consolidate / verify 阶段）。
> **worker 不加载本文件**——审查者的输入是留白式视角 prompt，规则堆进 prompt 会锚定注意力、压缩直觉。
>
> **增长纪律**：持续往里补充问题，**只写「问题 + 防御」，不写版本号、日期、run 编号**——读者要的是「注意什么」，不是「哪天发现的」。条目消化成熟（收口进 checklist / 门禁脚本 / SOP）后移入文末索引，一行留档。

---

## 审查校准规则（报告可信度判别）

- **碎片不是报告**——LLM 最后一条消息可能是思考碎片（非空但无结构），报告提取必须过质量门控（≥300 字符或含 `##` 标题行），不达标按降级处理
- **「空 findings」≠「干净」**——停止条件必须校验每轮 worker 是否正常退出；findings 全丢了也会显示为空
- **降级轮的 finding 不可信**——worker 降级只读部分文件，降级标记的 finding 须人工核实后再定级
- **证据纪律双向**——臆造报告靠证据密度判别：finding 每条都能定位到文件行号、grep 可复验，经不起复验的"证据"是碎片上下文编的；反向同理，关闭误报也须附「文件:行号 + 实测证据」，口头关闭不算数
- **P0/P1 证据三件套**——每条 P0/P1 finding 必附「文件:行 + 复验命令 + 原始输出」，缺件的降 P2 或删；深度审查视角易过度自信，此条对深度视角尤其重要
- **语义层/数字层分工**——数字对账（测试数/工具数/版本号）是 check 门禁的面，LLM 视角只报行为语义漂移（描述的行为 ≠ 实现的行为、时态错位、图与文不符）；发现不浪费在数字层
- **消费出口**——报告收尾须分级落桶：进当版 bugfix 批 / 进后续版本规划 / 记录不修（已披露+有缓解）；发现只有被消费才有价值，不落桶的报告只是一堆问题清单
- **确定性判定的不让 LLM 解读**——grep 退出码、编号连续性、WARN 分级这类能正则判定的，LLM 解读必出错；解析 shell 日志先剥 ANSI + 理解格式约定
- **「上轮遗留」先 grep 当前仓库复验**——旧报告清单可能把已修项标未修
- **同族发现按修复动作去重**——跨视角同根因信号合并为一条 finding，不按视角数膨胀；派发多视角时预判撞车对
- **观察项分级纪律**——「确认不修（已披露+有缓解）」不进结果清单；「待证实」留待下轮复验再分类
- **正面交叉确认留档**——多视角正面确认的已知好实践要让审查者知晓，防误报
- **豁免类开关固定检查**——隐藏安全开关只存在于代码注释即成审计盲区：豁免类环境变量开关必须全仓 grep 并核对文档披露
- **终态零信任**——P0 清零须披露末轮采样深度不足的残余风险（末轮短轮次靠前几轮交叉验证支撑时必须说明）；「已修复」清单逐条实物复验——修复链不含的项就是没修
- **降级披露双信号**——碎片率（产物太短）与空响应率（模型没回内容）是不同信号，降级披露两者都要报
- **元规则：防误报校准的隐性代价**——「占位≠缺陷」「环境限制≠缺陷」「中间态默认 SKIP」持续加码 precision，漏报无声无息不进任何报告；校准加防误报条目时，须自问「这条会不会把真阳性一起压掉」
- **碎片线索不升级**——截断的工具碎片只作交叉佐证；「跨工具对比缺失」这类单侧碎片线索不单独升 P1
- **「待实测」先实测再定级**——静态通读标「待实测确认」的结论，须在隔离 SOFAGENT_DATA 下用可跑夹具实测后才能升 P1；不据交付物中无法就地复现的状态定级
- **文档自证不可信**——同一文档内两处各自声称「对账全绿」本身就说明计数漂移；计数对账必须落到可运行的仲裁脚本单一真值，不采信文档内自述
- **修复验证要有对抗用例**——行为级复验不只复跑原路径：篡改/越界等对抗夹具才能揭出邻近未申报缺口（只重跑原路径的复验对同文件其他薄弱点全盲）
- **失败测试销案须双环境全绿**——历史「失败测试」要 verified-green 销案，须双环境复现全绿；不能让一次历史 grep 结果长期充当活 bug 证据
- **漂移指控三方一致才定谳**——版本漂移类指控须三个独立数据源一致；单点异常（如 dashboard 显示）不外推为全仓漂移
- **声称项数与正文一一对应**——收口报告声称「N 项收获」正文必须逐项展开且与 commit 文件清单对账；未展开项会在分发中丢失归属
- **豁免披露≠文件自洽**——「发行窗口中间态」豁免只覆盖跨版本待发状态；单文件内版本号与正文自相矛盾仍是缺陷，豁免区要区分「跨版本待发」与「单文件内矛盾」两类

## 工程防线规则（driver / 管道 / 门禁脚本）

- **镜像 driver 漂移**——fresh-eyes-driver 与 release-gate-driver 共享熔断架构，公共逻辑必须提 driver-base，否则修 A 忘 B 是必然
- **管道死亡四模式各有防御**——SIGPIPE（输出重定向）/ cwd 拼错（路径强制）/ 修复链漏洞（收敛重跑）/ 标题 grep 失败（标题锚点）
- **长 LLM 调用必须 timeout+retry**——无超时的 fetch 网络抖断即挂死；长跑 driver 唯一安全姿势是宿主级免沙箱后台
- **resume 断点粒度与恢复粒度对齐**——断点记「worker 完成」但恢复按「轮」走，会让新轮空转；续跑前备份上轮关键产物
- **verdict 以主体 IS_PASS 为准**——尾部追加的「修复收敛」必须与修复环节的 git diff 对账，没改代码的收敛必是假的；stepErrors 非空 = 本轮作废，不存在带伤 PASS
- **FAIL 与 PASS 都要零信任**——FAIL 逐维复跑分辨「仓库问题 vs 检查器问题」；PASS 过独立复验三件套
- **门禁脚本必须测失败路径**——强制触发 FAIL 看它真报红，只跑正常路径是假绿温床
- **脚本环境三坑**——bash 3.2 空数组 + `set -u` 崩溃；测试 finally 的 rmSync 必须 try-catch（shim 环境会拦截致假失败，先非 shim 复验）；随机断言须大量采样锁契约（概率性 CI 红）
- **二进制读前判 isBinaryBuffer**——文本快照读二进制会静默产生 U+FFFD 损坏；测试敏感数据用占位符/运行时拼接，不字面写真实格式
- **断言校准三同步**——校准过时断言时，判定条件、场景标题注释、pass 消息展示文本三处都可能残留旧值；一次改齐
- **Git Data API 绕行推送必须验 tree 一致性**——git push 死代理时的唯一通道（断网期全量推送实证有效）：三坑——tree 条目 mode 硬编码 100644 丢全部 .sh 执行位（verify CI 失败根因，恢复靠「blob 内容寻址——引用既有 blob 建新 tree」）；rename R100 在 diff 取新路径；create-tree 无法表达删除条目（rename/删除残留旧文件，须 Contents API 逐个补删）。**验收唯一标准：远端 tree sha == 本地 `git rev-parse HEAD^{tree}`，逐字节一致才算成功**
- **发布物与锚点结构对照**——release note（title `vX.Y.Z — emoji 主题短语` + body 五要素：定位句/核心变更/破坏性变更/质量验证 7 项表/尾链）生成后必须与上一版/锚点实际发布物并排对照，**不是对照 SOP 文字**（SOP 文字曾漂移——两次被作者退回：漏质量验证表 + 漏标题主题）。发布物本身是检验标准
- **执行者写权限前置验证**——只读沙箱里跑的修复环节零落盘、driver 结构性停机；派单前验证执行者对审查快照可写
- **崩溃视角强制补位**——worker 崩溃的视角是覆盖缺口，下轮补跑，不静默略过
- **降级产物完整性校验**——LLM 降级产物不能默认可信：粘贴执行前核对来源节齐全、口径对当前版，残缺产物照着执行 = 审查对象错位
- **基建降级与质量降级分离计量**——基建层失败（如 consolidate 降级）不熔断收敛判定；降级轮 finding 清单不完整是工具降级不是仓库干净，终判回原始 per-perspective 报告核对
- **「分支保留待回流」声称不可信**——worktree 清理可丢 auto-commit 引用（分支名还在但尖端=baseSha）；复验产物存在性必须实物核对（reflog/fsck），不信任何「已追加/已保留」文本
- **幽灵重启防御**——loop 收官数分钟后同 runDir 被二次启动可双亡、终态产物被回退；多 driver 并发须查 runDir 占用与 pid 存活
- **并发窗口纪律**——仓库常有他人未暂存改动与并行 session：审查全程对他人改动只读不动；期间出现新 commit，如实记录但不中断
- **长输出分批**——多视角审查的产出分批输出（每完成 2-3 个视角一批），防止单次输出过长被截断丢失；提取侧的「碎片不是报告」防的是已发生截断，本条防的是制造截断
- **深度标准**——不为准时收工而浅尝辄止，也不为消耗 token 而空转重复；深度的标准是「这个层面挖干净了」，不是「预算花够了」

## 文档治理规则（技术编辑 / 对外形象视角的常驻敏感）

- **来源删除要连标注符号删干净**——只删内容会留「📖 [行业笔记]」空壳行
- **改章节编号/文件名后全局 grep 旧值**——跨文档引用断链是必然，除非 grep
- **内部措辞定稿前专扫**——内部代号/人名/私有路径不能写进对外文档
- **Mermaid 图与正文同步**——改概念要回头查图节点数是否对应
- **迁移不留「原属 XX」注释当骨架**——迁移后建立自己的主线叙事
- **文档头日期随版本 bump 动态跟**——改了版本没改日期是漂移
- **时态漂移专扫**——用「将要/计划」描述已交付功能、用「已交付」描述规划中功能的句子是独立缺陷类；命名后好 grep，技术编辑与对外形象视角常驻敏感

## 已消化校准索引

> 历史校准笔记的消化去向——原则：能机械化的进门禁，能固化进 SOP 的进 SOP，其余留档一行。细节回溯源文件与 commit 历史。

### 已收口进 checklist / 门禁 / review 机制

- 机械检查前移（能正则判定的收口 check 脚本，LLM 只留语义发现）→ 审查纪律 + check 脚本族
- SSOT 收编收尾双查（grep 同款 + 豁免复审）→ checklist 已机械化
- changelog 数字类发现附验算过程、实录与预估分列 → changelog 书写纪律
- 版本中间态（registry/tag/URL 落后本地）→ check-version 门禁 + 任务书合法态预告知
- 举例锚定效应对冲（必答机制）、深发现免篇幅惩罚 + 推理深度标注、视角分层 → review.md
- 静态视角动态面缺口 → 视角十七/十八/十九（已增设）
- 输入健康度四级分级合并（完整/截断熔断/崩溃/碎片）→ driver 判读逻辑
- 数字口径漂移复发模式（提交史「第 N 处」「漏网 N 处」式补改）→ 数字侦探固定校准
- 文件结构陌生人视角优先保障报告完整度 → driver 权重配置

### 发版执行期踩坑（固化 releasing SOP）

- 新增 workspace 包 = lock 必同步：`npm ci --dry-run` 验证零 Missing 再 push
- 多渠道分发格式差异：发前 dry-run 探格式，缺格式用临时目录组装（不动仓库），用完即删
- 发布限流 ≥20s 间隔；changelog 描述禁按字节截断中文（码点感知工具）
- publish 中断留 staged 约 5 分钟自动 finalize——等待即可，不必动 unpublish
- 代理环境 curl 验证不可靠：用 `gh api contents` 交叉验证文件存在性
- CI 纯净环境与本机自装环境分叉是真信号：剥净 PATH 复跑模拟 CI
- API 压平 commit 与本地 commit 同 tree 双 SHA 是合法态：以 tree 对账验收，网络恢复后 rebase
- publish exit 0 ≠ 立即可查：registry 传播延迟 3-5 分钟，三次重试×15s 对账
- release 标题必须 `vX.Y.Z — 主题短语`，发布前核对 title 字段
- 平台时序竞态是 flaky 假象：先写确定性复现（mock 时钟强走边界）再修
- mock 原型方法防自递归：替换 `Date.prototype` 方法后 mock 体内用 `realFn.call(...)`
- 验证 dist 内容先 find 定位正确子路径再 grep，防「修复没进包」假阴性
- 门禁全绿≠无盲区：手写清单不含的目录就是盲区，发现当场转 check 脚本检查项
- registry 时间戳早于脚本尝试 ≠ 他人发布：以最终对账为准，勿误判发布来源
- 本地部署树 + 绝对路径 overrides 接依赖 = 本地全绿 CI 三红（npm ci 把 overrides 恢复成指本机的 symlink，CI 无此路径 TS2307）——依赖只走 npm registry 正式版本；本地 node_modules 在位时的全绿对 CI 无证明力
- 包不在依赖树时 overrides 是惰性死配置（npm 实测永不匹配、不报警），但属地雷：该包一旦进依赖立即生效——残留本地路径 overrides 应清，不因「现在没炸」留
- publish 对账重查放宽 6×30s：传播延迟常超 3 次重查，publish 日志「+ pkg@ver」已提交即可信，E409 staged 等 5 分钟 finalize
- bootstrap sha256 随版纪律：哈希从新 tag 的 `git show vX.Y.Z:<file>` 计算，改完哈希重打 tag（delete + re-tag + force push）让哈希入 tag 自洽
- sha256 预计算免重打：预计算 HEAD 哈希与安装 URL bump 同 commit，tag 一次打自洽；install.sh/lib 零改动时 6 lib 哈希沿用免回填（发版前 `git diff <上tag>..HEAD --stat -- engine/scripts/lib/` 空即免）
- GitHub Marketplace listing 勾选自动延续：v1.4.2 起每版勾选后关联保持——marketplace 版本页含本版号即免网页操作
- ClawHub verify `security.status_not_clean` 可能是既有状态：发布前先快照对照（verify 落盘），发布后对照——新引入 reasons 才处置，勿把存量当本版事故
- ClawHub plugin API latestVersion 同样有传播延迟：CLI 输出「submitted」后首查未到新版勿急判失败，复查一次（与 npm registry 同款机制）
- 同文件多处 Edit 并行调用有读写竞态（实测 5 处只落 2 处）——同文件多编辑必须串行执行
- 改守卫对象必须复跑守卫：commit 触及 acceptance/checklist 守卫对象文件后，「验证跑点晚于最后一个触及 commit」才可收编——凭上一轮绿灯收编改过的守卫 = 假绿
- SSOT 批改后按「消费方清单」全量扫：权威源演进时不止改出现冲突的那份，姐妹篇/下游引用逐份过（22 视角双清单漏改 01-review.md 实录）
- 发布态自洽是源码盲区：tag 内嵌哈希/发布产物验证必须 `git show <tag>:` 三方比对 + 线上 curl——工作区自洽对 tag 无证明力
- 守卫验证走完整触发路径：带合法参数触发目标分支再下结论，前置拦截（参数校验抢先）≠ 目标守卫工作——无参数复验的「通过」是假阳性
- 降级产物同样过收编纪律：工具超时/降级路径产出（如 gen-abc-draft prompt 落盘由 session 执行）不因「工具没跑成」跳过人工审核与分发
- Release Notes 元说明「只剥一半」：段顶部与尾部**各有一段**给流程看的元说明，只剥顶部会随 body 发出去 ⇒ 用断言查（body 须含指向本版 changelog 的链接），不靠肉眼（已固化 09-publish / 06-doc-finalize / 11-post-publish 剥元说明断言）
- CI 与本地门禁口径差：CI 的 shellcheck action 无 ignore_paths ⇒ 按 shebang 扫**全仓**（含无扩展名 hook），本地按 `*.sh` 扫 ⇒ 本地绿 CI 红 ⇒ **CI 怎么扫，本地就该有同口径门禁**（已固化 check-shellcheck.sh）
- 批量 publish 须 `bash <<'BSH'` 包执行：zsh 不对未加引号变量分词（已固化 10-distribute 通道说明）；INSTALL_SHA256 基准陷阱见上「bootstrap sha256 随版纪律」条

### 留档参考（未固化，按需取用）

- 架构级设计顺序论证：新交付的判定链顺序、跨组件恢复顺序应附「为什么」论证页，避免审查时现场推导
- 安全类交付默认过红队三探针：tmp 竞态 / chmod 时序 / PATH 解析
- 单文件职责预警：判定链+审计+HITL+限速四块同居一文件时，先拆再扩新功能
- 竞品对标叙事：卖点锚定「git diff 硬证据+拦截」，不与扫描器拼规则密度（25 vs 100+ 是定位不是劣势）

## 深度视角收编决策

## v1.4.9 审查校准收编（阶段四 C 类）

- **门禁「提取为空」≠「合规为空」**：解析链依赖宿主 locale 时（BSD sed 在本机 `LANG=C.UTF-8` 下遇多字节日志报 `illegal byte sequence`）整段输出为空，进而整包测试数被静默跳过、门禁只表现为「文档数字漂移」（真因被掩盖）。校准：文本处理工具禁依赖宿主 locale（`LC_ALL=C` 或 node）；「有输出却提不出汇总」必须判红，「真无输出」才可跳过。
- **自动化提交的大范围同构替换须核对 SSOT**：单次 auto-commit 触及 80+ 文件的「同构替换」（版本号等）并混入无关改动时，极易造成「部分文件已换、SSOT 未换」的仓内两套口径。校准：把「单提交 50+ 文件同构改动」列为高危形态，核对被替换事实的 SSOT 是否同批更新。
- **死断言（不可达块）与断言可达性**：断言位于 `exit` 之后或恒假分支 = 从未执行，且不产出 pass/fail——编号被占用、覆盖名存实亡（本版实测：Release body 卫生块位于文件尾 exit 之后）。校准：审查验「可达」而非仅验「存在」；文件尾的孤立断言块优先复核。
- **改断言必须重跑全量**：改断言只做语法校验（`bash -n`）不等于语义通过——本版实测某断言与运行上下文错配（场景 cwd 恒为隔离仓，断言只认仓内形态输出）潜伏多版未被发现。校准：断言变更的完成判据 = 全量实跑。
- **结构性协议升级类 finding 归 C 不归 A/B**：如「链头哈希未纳入签名输入 ⇒ 删条目/重排/截断不可检测」属协议版本升级决策面，单轮修复不可消化、也不该硬塞进本版——交排期决策并保留观察项，不当缺陷硬修。

## 审查校准收编（阶段四 C 类 · 最新批）

## v1.5.1 审查校准收编（阶段四 C 类）

- **豁免资格前置双探针**：driver 不可用须以两次探针实测取证（①直跑 ②`--resume` 佐证 run 未建立），并核对是否在平价时段前启动——不凭推演、不凭回忆
- **载体降级 = 可互换等价**：降级载体与标准载体产出等价（触发条件 = LLM 通道不稳），降级产物同样过人工审核与分发收编纪律，不因「工具没跑成」跳过

- **四角色分离写进报告头**：发现（零上下文 subagent，不给结论方向）≠ 修复 ≠ 复验收编；三者不得由同一执行体兼任
- **阴性结论也要报**：查过无问题同样是产出——只报问题会让读者误判覆盖
- **核证据链不核声称**：审查者须逐层验证「失败信号会不会真红」（判据 → 门控 → 场景注册），而不是核「有没有加断言」这句话
- **「可发现性」≠「缺陷」**：契约单源正确但落点文件名不体现角色 ⇒ 只提可发现性建议，不判缺陷——否则会把正确设计打成 bug
- **中间态 SKIP 口径**：push+tag+publish 后自动消解的不算 finding；但其中暴露的存量 fail-open 仍须单独登记为待拍板

- **驳回必须附反证**：不接受「我觉得不是」——读实现 + 现场复验才算驳回
- **报告须声明未出 finding 的视角**：缺的编号须声明「跑过无发现」还是「未跑」，否则读者会误读为全跑过
- **「守卫会不会红」之前先问「守卫会不会跑」——哑守卫四形态**：①哑守卫（路径写死指向已搬迁目录 + `catch { return }` 静默跳过：有代码、有注释、从未执行）②空集假绿（解析结果为空时比对恒成立）③抽取/装载失明（路径错 + 吞错 ⇒ 输入恒空）④locale 退化（中间产物非空但不具判别力——C locale 下 sed 按字节切多字节产出非法 UTF-8，perl 读到即死而 `2>/dev/null`+`|| true` 吞掉，残留「非空」反而使空集守卫失效）。共同点：**守卫存在、代码在、永不生效，而门禁全绿**。审查断言必须验两条：执行可达性 + 非空/非重言；CJK 脚本头部强制 UTF-8、排序去重阶段强制 `LC_ALL=C`，locale 不变性（默认 vs C 环境输出逐字节一致）是判据

## v1.5.0 审查校准收编（阶段四 C 类）

- **移除面断言随动**：退役 API/旗标/shim 的移除 commit 必须同批扫 acceptance 场景的旧断言——本版实测 4 场景红中两处（弃用 shim 断言、loop --legacy 弃用双面断言）均为「产品按计划移除、断言留在场上打红」同款形态。校准：移除类 diff review 必查 acceptance/门禁断言面；退役旗标产品侧必须显式拒绝（fail-closed），静默吞旗标跑新路径是产品 bug 不是兼容。
- **施工方验收虚报识别**：勾选「零信任复验通过」但产物三要素全缺（台账文件不存在/路径不存在/落行不存在）——本版 bugfix 批实测 1/33 虚报。校准：收口方对施工方勾选项 ls/grep 实物逐项核，不信汇报文本；「勾选密度」本身不是可信度证据。
- **commit 归属引用先验后引**：跨 commit 施工时 message 声称的内容可能落在相邻 commit（message 称「三 shim 移除」实则在邻笔）——历史审查报告的「commit → 内容」映射引用先 `git show --stat` 验证再采信。
- **外部面断言必须实跑外部命令**：源码在位 ≠ 交付完成——npm 包存在性要以 `npm view` 实查（本版实测源码侧证据导致验收误判 ✅ 后改判：新包 E404 属阶段九动作）。校准：含对外动作（publish/tag/deprecate）的验收项，未执行前不得勾选。
- **埋点式计数收口对账**：devlog 头部「N commit」类埋点计数易 off-by-one（本版 13 vs 实际 14）。校准：收口时以 `git log --oneline | wc -l` 实测为准，不采信施工时点手写值。
