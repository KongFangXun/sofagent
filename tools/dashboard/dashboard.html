FORGE · 自迭代质量审查工具链
FORGE README →

FORGE 是 sofagent 项目内部的开发工具链（不是 FDE 方法论的一部分），用 sofagent 自己的审计能力审 sofagent 自己的代码——"用 AI 审 AI"。两条循环：fresh-eyes-loop（双盲质量审查）与 release-gate-loop（发版门禁，十二阶段 SOP）。

1fresh-eyes-loop · 双盲质量审查
两个 Agent 互不可见：A（审查模型）不带前置上下文独立找问题，B（工程模型）收到报告独立修复，多轮迭代直到收敛（默认 5 轮）。
在你的项目中运行 fresh-eyes-loop
用 sofagent FORGE fresh-eyes-loop 对当前项目做双盲质量审查。 Agent A 找问题，Agent B 修复， 多轮迭代直到收敛。
2release-gate-loop · 发版门禁
发版前按十二阶段 SOP 逐门禁验收（build → acceptance → regression → coverage…），任一环节 FAIL 即卡关，全部通过才允许打 tag 发版。
运行 release-gate 门禁
用 sofagent FORGE release-gate-loop 跑发版门禁： build → acceptance → regression → coverage， 全部通过再报告。
3引擎执行流水线
每次 AI 任务自动走的五步（planner → engineer → audit → reviewer → human）——sofagent 引擎内部机制，与 FORGE 同类。业务角色节点（分析师/规划师/部署专家）见 FDE 引导 页。

构建本体数据的完整方法论（FDE 深挖阶段）：
什么是本体数据（ontology）

类比城市规划中的「用地性质图」——每块地是住宅/商业/工业，决定了这块地能干什么、归谁管。本体数据 = 企业知识的「用地性质图」——每个知识节点是什么类型、归哪个业务域、能看什么不能看什么。

实体 Entity

业务对象（如「客户」「订单」「员工」）

  • 业务可命名
  • 系统可查询
  • 有独立生命周期

概念 Concept

业务规则（如「审批流」「权限矩阵」）

  • 抽象规则定义
  • 跨实体复用
  • 约束行为边界

关系 Relations

实体/概念间关联

  • belongs_to（属于）
  • has_many（拥有多个）
  • depends_on（依赖）
本体 ≠ 知识图谱数据库：本体的核心是业务刻画——完整呈现业务领域的客观事实与关联关系。知识图谱只是它的一种技术实现。
业务四问（入场必填）
1关键业务对象有哪些？
客户 / 商品 / 订单 / 供应商……列清实体类型
2每个对象的归属负责人是谁？
谁对这个结果负责
3权威数据来源系统是哪个？
ERP / CRM / 自研 / Excel——避免 Agent 从非权威源编造
4动作风险等级？
低（查询/只读）/ 中高（写操作/审批/对外发）
Object Type 五条筛选标准

业务四问列出的名词不是全部都能当 Object Type——数据库表 ≠ 业务对象。五条标准缺两三条就要谨慎：

1. 业务可命名

业务人员叫得出这个名字吗？

2. 系统可查询

系统里能稳定查到它吗？

3. AI 可推理

AI 能围绕它做推理吗？

4. 动作可落地

业务动作能落在它身上吗？

5. 责任可绑定

权限和责任能绑定到它吗？

让 Agent 帮你构建本体数据
作为 sofagent FDE Harness， 帮我构建本体数据。 先用业务四问梳理关键业务对象， 然后筛选 Object Type， 建立 entity / concept / relations。 最后用 validate_ontology 验证完整性。
适配性判断：多数中小企业不必建全量本体数据。如果不需要业务域级 Agent Runtime、也不是一号位工程推进，用轻量 Agent + 企业 Skill即可。详见 FDE/GUIDE.md §3.2
