# SMB Onboarding 模板 · 无代码仓库的纯数据节点部署

> **用途**：SMB（中小企业）场景进场 onboarding——客户**没有代码仓库**，Agent 的交付物不是代码而是数据（报表 / 清洗后的数据 / 台账）。本模板把「无代码仓库」的部署路径走通：从数据源盘点 → 数据节点判定 → 数据产物审计配置 → 治理 KPI 对账。
> **与既有模板的关系**：`enterprise-profile.md`（交付手册第一章）与 `deployment-plan.md`（第二章）仍适用——本模板是**第三章的 SMB 变体**，替「部署方案」中依赖代码仓库的部分（git hook 安装 / A1-A24 代码审计面）为纯数据节点路径。
> **审计面**：SMB 场景用 `E5 数据产物审计`（勾稽 / 溯源 / 口径三类判据）+ 行业 overlay（`--ruleset smb` 或 `industry: smb` 自动发现）。

## 一、数据源盘点（进场第一件事——没有代码仓库，有的是什么）

> SMB 没有代码仓库 ≠ 没有数据。先盘点「数据住在哪、长什么样、谁能拿到」。

| # | 数据源 | 形态 | 可达性 | 更新频率 | 责任人 |
|---|--------|------|--------|----------|--------|
| D1 | （如：进销存 Excel） | .xlsx | 手动导出 | 每周 | 老板本人 |
| D2 | （如：微信收款记录） | CSV 导出 | API / 手动 | 每日 | 店长 |
| D3 | （如：供应商报价邮件） | 非结构化 | 手动转发 | 不定期 | 采购 |

> **纪律**：数据可达性差的源（手动转发 / 不定期），先做「可达化」——建共享文件夹 / 约定导出周期——再谈 AI 节点。不可达的数据源上不了任何自动化。

---

## 二、数据节点判定（三问法的数据版）

> 沿用 `plan-review.md` 的三问判定法，问题换成数据语义：

| # | 节点 | 输入能自动取？ | 规则能写清？ | 输出能自动推？ | 判定 |
|---|------|:---:|:---:|:---:|:---:|
| N1 | （如：月度销售报表） | ✅ D2 每日 CSV | ✅ 汇总口径固定 | ✅ pivot + 合计 | 🔄 |
| N2 | （如：库存对账） | ⚠️ D1 手动周导 | ✅ 差额公式固定 | ✅ 差额清单 | ⚡ |
| N3 | （如：供应商砍价） | ❌ 邮件非结构化 | ❌ 谈判策略 | ❌ | 👤 |

> **🔄 判定三问**：① 输入数据有固定格式 + 可自动获取；② 清洗 / 汇总 / 对账规则能用一句话写清（「按月汇总，合计 = 明细之和」）；③ 输出报表的格式固定（CSV / Excel 模板）。

---

## 三、数据产物审计配置（E5 三类判据的声明面）

> 每个 🔄 数据节点配一份审计声明——这是 SMB 场景的「铁律」等价物。

| # | 节点 | 勾稽口径（合计 = ?） | 溯源要求（每行须引用哪个源） | 口径声明（字段 → unit） |
|---|------|---------------------|---------------------------|------------------------|
| N1 | 月度销售报表 | `total_amount = sum(明细.amount)` | 每行 `source: D2/YYYY-MM.csv` | `amount → CNY`（全表一致） |
| N2 | 库存对账 | `差额 = 系统数 - 实盘数` | 每行 `source: D1/周导出.xlsx` | `quantity → 件` |

**审计接线**（二选一）：

```yaml
# 方式 A：config.yml 启用扩展规则（E5 在扩展集）
extendedRulesEnabled: true
rules:
  e5: true
```

```yaml
# 方式 B：industry overlay 自动发现（context.md 标注）
# frontmatter: industry: smb
# → 自动加载 smb overlay（勾稽/溯源/口径三条 pattern 规则）
```

## 四、部署路径（无代码仓库 → 纯数据节点）

| 步骤 | 做什么 | 产出 | 耗时 |
|------|--------|------|------|
| ① 建工作目录 | `~/sofagent-<企业名>/`（非 git 仓库亦可——E5 只扫数据文件 diff） | 目录骨架 | 10 min |
| ② 初始化审计 | `sofagent audit --init`（装文件监控 hook——daemon 模式，不依赖 git commit） | hook + config.yml | 15 min |
| ③ 数据源接入 | 共享文件夹挂载 / 定时导出脚本（D1-D3） | `raw/` 数据落地 | 1 h |
| ④ 数据节点上线 | 逐个跑通 N1-Nn（AI 生成报表 → 落 `outputs/`） | `outputs/*.csv` | 0.5 h/节点 |
| ⑤ 审计验证 | 故意造一个勾稽错误 → 确认 E5 拦截（FAIL / exit 2） | 审计报告 | 20 min |
| ⑥ 治理面板 | `sofagent dashboard`（KPI 六卡对 SMB 数据节点照常聚合） | 面板 URL | 10 min |

> **与标准部署的差异**：标准路径装 git hook（commit 触发审计）；SMB 路径用 **daemon 文件监控**（`outputs/` 目录变更触发）——同一套规则引擎，两种触发时机。

## 五、治理 KPI 对账面（SMB 场景的老板一页纸）

> v1.5.0 治理 KPI 面板对 SMB 场景**零改动复用**——数据节点的审计结果照常进 `history.jsonl`，六卡口径不变：

| KPI 卡 | SMB 场景读数语义 |
|--------|-----------------|
| ① 安全边界触发率 | 数据产物审计触发率（勾稽 FAIL / 溯源 WARN 占比） |
| ② 审计覆盖率 | 有 commit 锚的数据变更占比（daemon 模式 = 文件变更锚） |
| ③ HITL 响应时延 | 数据异常人审时延（勾稽 FAIL 后老板多久确认） |
| ④ 周环比 | 本周 vs 上周数据产物问题数 |
| ⑤ 任务重复执行率 | 同类报表生成的重复轨迹（数据飞轮燃料） |
| ⑥ trace 对账一致率 | 说的和干的差在哪（数据口径声明的执行一致性） |

## 六、离场检查清单

- [ ] 数据源 D1-Dn 全部可达化（自动 / 半自动，无「口头传数据」）
- [ ] 每个 🔄 数据节点有审计声明（勾稽 / 溯源 / 口径三列填齐）
- [ ] E5 审计验证过（故意造错被拦 → exit 2）
- [ ] 治理面板可访问（老板能自己看六卡）
- [ ] 数据产物决策留痕可查（`sofagent audit decision-query --kind DATA_PRODUCT`）
- [ ] 交接文档落客户平台（本模板 + enterprise-profile + 部署方案 SMB 变体）

> **填写纪律**：与 `delivery-report.md` 同——诚实记录。数据节点的「审计验证过」必须是实测（造错被拦），不能是「应该能拦」。
