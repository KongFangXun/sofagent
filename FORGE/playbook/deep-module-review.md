# 深模块审查 · 适配层

> **本文件不是方法论本体。** 方法论本体是上游 skill `improve-codebase-architecture` 及其依赖闭包，vendored 在
> [`vendor/improve-codebase-architecture/upstream/`](vendor/improve-codebase-architecture/upstream/)。
>
> 本文件只写**本地差异**（术语口径 / 铁律 / 输出载体 / 去留流程 / 升级流程）——
> 上游怎么做、判据是什么、候选卡长什么样，一律读上游原文，**本文件不重述、不转写、不改写**。
> 上游升级时只需换 pin + 重读 PROVENANCE 的偏差清单，本文件不动或微调。

> 这是一轮**设计熵勘测**，不是 bug 审查——它不问「有没有错」，问「形状好不好改」。只报告不修复。

---

## 一、它在审查体系里的位置

三种审查问三个不同的问题，互不替代：

| 机制 | 问什么 | 产出 |
|------|--------|------|
| 独立审查（22 视角） | 交付物**对不对** | bug、风险、文档/感知面问题 |
| 视角二十 · 死代码猎人 | 它**还活着吗** | 断链尸骸、零消费导出 |
| 视角二十一 · 未来架构师 | 该**往哪去** | 方向建议、投资排序 |
| **本机制** | 形状**好不好改** | 可施工的加深候选（带证据的债单） |

一句话分工：独立审查管正确性，死代码猎人管存亡，未来架构师管方向，本机制管**模块形状与设计熵**。

它不替代上述任何一个，也不并入发版单盲四角色流水线（那条链的角色与预算为发版固定）——它是独立的一轮，按需跑。

## 三、本地覆盖（与上游不同之处）

| 项 | 上游默认 | 本地口径 |
|----|---------|---------|
| **输出载体** | 写自包含 HTML 到 OS 临时目录并 `open` | **对话形式直出**，不落 HTML、不落仓库、不落交付物 |
| **触发方式** | 用户显式调用 `/improve-codebase-architecture`（`disable-model-invocation: true`） | 作为 fresh-eyes 审查的**体系外挂**由审查流程按需执行；也可单独立项跑 |
| **领域词汇来源** | `CONTEXT.md` 领域词汇表 + `docs/adr/` 决策记录 | 本仓无此二物 → 改用既有资产：README / COMMUNITY / PHILOSOPHY / ARCHITECTURE / 术语表 |
| **ADR 冲突检查** | 对照 `docs/adr/` | 改为对照既有设计决策文档；冲突只在摩擦力真实到值得重开时呈现，禁止罗列「理论上被禁止的重构」 |
| **子技能调用** | `Skill tool` 按名调用 `codebase-design` / `grilling` / `domain-modeling` | 同一闭包已 vendored → 按**路径**读取（见第二节） |
| **上游第 3 步（grilling loop）** | 选定候选后当场走到接口形状、测试存活 | **审查轮内不进入**：候选去留由人裁定，施工另派。单独立项时按上游原样走 |

术语口径：上游 `Module` → 本地「模块」；`Seam` / `Adapter` / `Depth` 保留原词 + 中文注（缝 / 适配器 / 深度）。上游明令禁用的平行词汇（component / service / API / boundary）本地**同样禁用**——术语一致本身就是产品。

## 四、流程四步

### 一 · 定范围（YAGNI 前置）

上游已定「按热点推断范围」的做法，本节只加本地约束：

- 热点推断命令：`git log --name-only --since=<数周前> -- <范围>`，按目录聚合排序，取 top 区
- **不要全仓平推**：范围越宽，结论越浅
- 读写项目术语后再开工——术语错了，全文都错

### 二 · 并行深扫

- 每个分区一个独立 worker，任务书自包含（背景、热点依据、审查清单、输出格式一次给全）
- 审查清单 = 上游 SKILL.md 第 1 步的问题清单 + `codebase-design` 的判据，逐条走
- **worker 输出硬要求**：每条 finding 附真实证据（文件路径 + 行号 + 实际读到的代码或实测命令输出）；**禁凭文件名想象**
- **审查类 worker 禁用低成本档**：证据层会大面积虚构，复核成本反超审查成本

### 三 · 零信任抽验

主理人**逐条独立复测**关键数字（不许转写 worker 的结论）：

- 抽验不过的数字，其所属候选**整条打回**
- 否定式发现（「某能力未实现」「某处是死的」）必须当轮重验——并发开发时代码面结论有保质期，期间被他人推进则整条作废
- 抽验记录一并写进交付时的报告页脚（哪些数字被独立复测过）

### 四 · 成报告与分流

- 候选卡按上游格式（Files / Problem / Solution / Benefits / Before-After 图 / 推荐强度）
- 末尾给出**首推**：先做哪个、为什么
- 人挑一个候选 → 进入用法 C

## 五、三种用法

### 用法 A · 全仓体检

季度体检、大版本收口时使用。热点全扫，全量报告。

- 按包/层分区，每个分区一个独立 worker（互不通气，避免结论互相锚定）
- worker 数量 = 热点区数量，通常 2-4 个

### 用法 B · 单区精扫

怀疑某处臃肿时使用（改一处要动三个文件、加一个功能要抄一段代码、新人对某目录反复问同样的问题）。

- 指定一个目录/模块，直接跳过热点推断
- 单 worker，分钟级，通常 1-3 个候选

### 用法 C · 候选跟进

候选不是待办清单，是**待盘的设计题**。挑定一个候选后，把它盘到「能施工」或「能作废」为止。六个必盘项：

1. **约束**：有没有既有决策挡着（架构决策、版本纪律、术语口径）——被挡的先裁决，不要绕
2. **调用方**（实测，不靠猜）：谁在消费它、外部消费方有几个——决定能不能删、能不能改契约
3. **接口形状**：加深后的接口长什么样——几个方法、什么参数、什么藏在缝后
4. **缝后收编**：哪些内部件从公开面退为私有
5. **测试如何活**：现有测试哪些留下、哪些重写、哪些删掉是**真进步**（替换而非叠加）
6. **施工切片**：第一步做什么（通常是先补兜底测试）、分几批、每批怎么验

产出二选一（没有第三种）：**写成版本条目**（含验收标准，走正常开发流程）或**明确作废**（记下原因，防后来者重复提议）。

### 什么时候跑

- 大功能合入后（一次合入容易带进一片拷贝）
- 发版收口后（可选，非必跑项）
- 「改起来越来越费劲」的体感出现时
- 季度全仓体检

## 六、本地铁律

1. **只报告不修复**。审查任务禁改一行生产代码——与发版铁律同构。
2. **产出跟随载体，不重复造报告**：挂载模式（挂进独立审查一起跑）形状问题**直接并入该次审查报告**，与其它视角 findings 同载体，**不另出独立文档**；独立模式（体检/精扫）以对话形式直出候选清单。**两种模式都不落 HTML、不写进仓库、不进交付物**。
3. **证据必须是当轮的**。路径、行号、计数、命令输出全部当轮实测；转写即失真。
4. **审查类 worker 禁用低成本档**。
5. **否定式发现必重验**（并发仓库时代码面结论有保质期）。
6. **术语受控**：模块 / 接口 / 实现 / 缝 / 适配器 / 深度 / 局部性 / 杠杆——不引入 component、service、boundary 这套平行词汇。
7. **范围 YAGNI**：只扫热点，不平推全仓。
8. **勘测不是施工**：候选经人裁定，进版本条目才动工。
9. **图优先**：能画的不写；图需要一段话才看懂 → 重画图，不写话。
10. **机械面不人肉**：可正则可判定项（重复骨架计数、注册表一致性、导出零生产消费）收口 check 脚本，工具做机械面，审查留语义面。

## 七、常见坑

| 坑 | 后果 | 规避 |
|----|------|------|
| 把强度当优先级 | 违反「写进去就做完」的版本纪律 | 强度只表置信度；去留由人裁定 |
| 报告写进仓库 | 仓库污染 + 文档预算挤占 | 对话直出，一律不落文件 |
| 单 worker 全仓平推 | 上下文耗尽，结论浅 | 分区分 worker |
| 转写他人数字 | 失真（复核时全对不上） | 当轮独立复测 |
| 凭记忆复述上游方法论 | 与上游漂移，且漂移不自知 | 每次执行前按第二节读取顺序重读 vendored 原文 |
| 只看热点不看形状 | 把「改得多」误判成「必须重构」 | 每条候选过删除测试才成立 |
| 幽灵缝留原地 | 每个后来者都要重新确认它是死是活 | 做实或退场，二选一 |
| 加深动作过大 | 一次动太多面，风险失控 | 一次只做 1-2 个候选，转版本条目分版本施工 |

## 八、升级流程

上游是活的开源仓（MIT）。升级 = 换 pin + 重读偏差：

1. 取上游新版本，记下新 commit
2. `diff -r <上游新检出>/skills/engineering <本目录>/vendor/improve-codebase-architecture/upstream/` —— 路径 1:1 对应，差异即上游变更
3. 逐条过差异：影响本地覆盖表的，更新第三节；不影响的不动
4. 更新 `vendor/improve-codebase-architecture/PROVENANCE.md` 的 pin、抓取日期与哈希清单
5. 有争议的变更先落候选，不直接改本地口径

**禁止**把上游方法论的散文改写进本文件——本文件一旦开始复述方法论，就等于开了第二条真相源。
