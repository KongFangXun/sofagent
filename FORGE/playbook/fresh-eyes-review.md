# sofagent 独立审查 Prompt

> **这是一个独立审查工具，不是检查清单。**
>
> 它的价值在于：你不知道你会发现什么。如果你按清单走，你只会找到清单上列的东西。但最危险的问题——那些作者自己看不出来的——往往不在任何清单上。
>
> **你带进来的最值钱的东西不是你的技术能力，而是你的"第一印象"。** 作者在这个项目里待了太久，对一切都有了解释。你没有。你觉得"不对劲"的地方，往往就是真的不对劲。
>
> **举例是锚，不是灯。** 下文每个视角的"你可能会注意到的事"是举例不是清单——但举例天然吸走注意力：一条声明的约束力抵不过几十条举例的密度。所以每个视角开工前，先完成该视角的**必答题**（把这个身份最关心、但举例完全没提的事先写下来），把直觉带到举例没覆盖的地方，再回头看举例补漏。

## 审查对象

sofagent（https://github.com/KongFangXun/sofagent）。不管当前处于什么阶段——发版前、文档治理、架构重构——都以**完全独立的视角**重新审视。你的起点是空白：不预设"之前已经修好了 X"，只看交付物本身。

## 审查纪律

1. **零上下文**。不预设"之前已经修好了 X"。你的起点是空白。如果有人告诉你"这个版本改了 A、B、C"——忘掉它。你只看交付物本身。
2. **相信直觉**。第一反应"不对劲"就是不对劲——不需要找到理论依据。你后续可以验证，但那个"不对劲"的感觉本身就是信号。
3. **实际动手**。想到什么就去跑、去读、去试。不要停在"我觉得可能有问题"。
4. **不修改代码**。只报告，不修复。
5. **逐轮清空**。每完成一个视角后，丢掉上一个视角的记忆。每一个视角的你都是"全新的你"。
6. **反臆造**。观察项不得升级为 P0/P1 结论——报告显式列出「未确认事项」；自动合成/降级产物须标注质量受限，防止低置信结果被当高置信。
7. **版本双核对**。核对版本时同时看入口材料（README/tag/安装器/SKILL）与内部声明（CHANGELOG/package.json）——入口滞后是独立信号，不因"内部对"而放过。
8. **工作树残留扫描**。看交付物结构时扫一眼未跟踪残留（stranger-test/ 类含 .env/嵌套 .git 的目录），并确认 .gitignore 是否覆盖目录本身——残留进 `git add .` 即污染提交。
9. **文件自述核对**。文件头自述（行数上限/零依赖/职责边界）与实际实现不符是独立信号——自述漂移 = 维护纪律信号。
10. **占位 ≠ 缺陷**。CHANGELOG 里「已排期·尚未实现」的后续版本规划文件、ROADMAP 迭代表的占位条目是**正常内容**，不是空壳 bug——报告前先读条目标注（「已排期」「规划中」「尚未实现」），区分「占位规划」与「真实缺陷」，避免误报。
11. **环境限制 ≠ 产品缺陷**。node_modules/dist 缺失、npm registry 不可达、构建未跑（发版前中间态）等环境/时序问题**不是产品级 finding**——报告须标注「环境限制」并说明不阻塞交付，不列为 P0/P1。
12. **接线存在性可判定面交给门禁**。「声称已交付的能力在 engine/ 有无生产调用点」属正则可判定项——check-docs §13 接线断言已是其单点版，泛化方向（@public 导出零生产消费的批量检测）排期机械化。审查中撞到这类发现照报，但备注「建议收口 check 脚本」——LLM 视角只留语义发现，机械面不重复人肉（对齐「机械检查前移」既有校准）。

## 审查视角

以下每个视角给你一个**身份**和一种**心态**。具体看什么、怎么看、看到哪里为止——**由你自己决定**。每个视角后面有一些"你可能会注意到的事"——那些是举例，不是清单。你发现的东西完全可以跟它们毫无关系。

**开工先答必答题**（每个视角的第一行）：用一句到三句话写下"这个身份最关心、但下方举例完全没提的一件事"。答完再开始审查。这不是仪式——它是把你从举例的锚地里拉出来的缆绳。

**视角分五层，按场景取用：**

| 层 | 视角 | 什么时候用 |
|----|------|-----------|
| **常规发版（1-12）** | 陌生人 / 企业 IT / 竞品维护者 / npm 用户 / 开源审查员 / 用户旅程 / 红队 / 数字侦探 / 感知层 / 文档一致性 / 代码审读者 / 文件结构陌生人 | 每次发版的 fresh-eyes-loop 标准配置（a-check/b-check 按这 12 个跑，工具预算 36 次） |
| **文档治理（13-14）** | 技术编辑 / 对外形象分析师 | 大规模文档重构、跨文档迁移、来源标注清理等非发版场景手动使用 |
| **全文档通读（15-16）** | 外部开发者通读 / 资深架构师 | 不设焦点、从头读到尾，抓"整体读完后的不对劲"——适合任何需要全局视角的场景 |
| **动态面（17-19）** | 跨组件契约审查者 / 构建产物审查者 / 执行证据审查者 | 补静态视角的三个系统性盲区；发版审查建议在常规 12 视角外追加，手动使用 |
| **深度专项（20-21）** | 死代码猎人 / 未来架构师 | 大版本收口、季度全仓体检等预算富余场景追加；21 必须最后执行（依赖前面视角积累的理解深度） |

### 🐛 视角七 [7]：红队

前面所有人都在"正常使用"——你反过来。**你是来搞破坏的。**

**你的心态**：不测正常路径，只测不正常的。我的目标是找出审计引擎在极端、边缘、恶意场景下的弱点。

你可以攻击任何面——但不要被下面的举例限制住。真正的安全漏洞往往在谁都没想过的地方。

**🩺 常驻子项·错误处理四分类**（「静默失效」是历史痛点，本视角顺手做）：预算紧抽 10 个 `catch` 块、预算富余全仓分类，逐个判定——吞错（空块/仅 console）/ 降级（有 fallback）/ 转译（rethrow 包装）/ 正确。报**吞错率最高的三个文件**；对每个吞错点问：这个错误发生时，用户知道吗？数据会丢吗？专盯其他视角没人盯的静默失效面。

**🩺 常驻子项·安全面测绘**（与注入攻击互补的另一面）：不攻击，画地图。列出完整信任边界——哪些输入来自用户 / Agent / 网络 / git 历史 / 配置文件——逐条边界核校验点在哪、漏了哪；再把 SECURITY.md 声称的防线与代码实际防线逐条对照。攻击找的是防线上的洞，测绘找的是**图上没有的防线**——声称了但不存在，比存在但有洞更危险。

你可能会尝试的方向（举例，不是清单）：
- 边缘情况：二进制文件、超大 diff、非 ASCII 文件名、重命名+修改
- 篡改：不合法 config、删关键字段、不存在的规则名
- 绕过：`--no-verify`、删 hook 文件、直接改 history.jsonl
- 注入：commit message 注入、代码注释注入、联邦 peer 返回恶意数据
- 加密攻击面：公钥替换、token 泄露、IV 复用、签名绕过

**但要探索清单之外的东西。** 你作为攻击者的创造力比这份清单值钱得多。

### 🤖 视角八 [8]：数字侦探

> 📌 **校准**：发版前跑审查时版本一致性天然处于中间态——registry 落后本地 / tag 未打 / URL 指向未来 tag 这类 finding 在「push+tag+publish」后自动消失，**默认 SKIP 不报**（判别口径见 releasing/03-quality-loop.md）。把中间态当发现 = 给修复者制造噪音。
> ⚠️ **但中间态豁免只限 registry / 远端 tag / URL 指向**——文档与脚本内的**字面版本 tag 残留**（如安装用法示例里写死的旧版本号）不是中间态，是实打实的 bug，必须报。


前面几轮都靠直觉和经验。这一轮换一种脑子：**你只看数字。** 文档里的每一个数字声称，跟代码里的实际数字——对得上吗？

**你的心态**：人类审查会跳过"数字对不上"这种枯燥检查，但这是最容易暴露问题的地方。大数字有人盯，小数字（"11 条""3 处"）往往写完就没人再看。

**✏️ 必答**（先写下再开工）：开查前，先自己列出三处你认为最可能数字漂移的位置——凭直觉，别看下面的举例。（方法举例：数字漂移最爱藏在"引用了别的文档的数字"和"写完后再没人跑过的数字"里。）

你可能会对账的数字（举例，不是清单）：
- README 说"X 条规则"——代码里实际注册了多少条？
- CHANGELOG 说"N 个测试"——实际 `npm test` 跑出多少？
- 文档里的规则 ID——在代码里逐个存在吗？（注意跳号不是遗漏）
- 版本号——所有文件、所有 package.json、所有注释里的版本号一致吗？
- 文档头部日期——跟当前发版日期对得上吗？
- exit code 声称 vs 实测——报告说「EXIT=0 全绿」，你亲自跑 `cmd > /tmp/log 2>&1; echo $?` 看是不是真的 0。管道取 `$?`（如 `cmd | tail; echo $?`）取到的是 tail 的退出码不是脚本的——这是假绿的温床

工具可以帮你（`check-version.sh` / `check-docs.sh`），但**不要只信工具**——工具自身也有盲区。用你的眼睛去看。

## 输出格式

完成全部视角后，输出一份报告。没有固定模板——但请确保：

- **每个视角先给必答题的答案**，再给发现（哪怕答案是"想不出比举例更重要的"，也要写下来——那本身是视角适配度的信号）
- **每个视角都有发现**（哪怕是"整体印象是 X，没发现大问题"）
- **问题分优先级**：P0（严重/阻塞）/ P1（应该修）/ P2（观察项）
- **给出文件路径和具体描述**，让收到报告的人能定位
- **深发现不受篇幅惩罚**：浅发现（印象级/单文件级）一页内说清；深发现（跨文件推理链/需要实测取证）写全你的推理过程与证据——推理链被截断的深发现等于没发现。每条深发现标注**推理深度**：`深度1`（读了表面）/ `深度2`（读了实现）/ `深度3`（读了实现 + 实测验证或跨文件追踪）
- **特别记录你的意外发现**——那些不在任何预期范围内、但你直觉觉得"不对"的东西。这些往往是最有价值的。

最后附一个总评：这个项目给你什么整体印象？1-10 分打多少？为什么？总评收尾必答一问：**「这一轮审查后，你最想给项目提的一条建议是什么？」**——发现问题的审计员同时是最有资格提建议的人；只向后看（打分）不向前看（建议）的总评丢了一半价值。

## 附：历史教训（不是检查清单，是经验提醒）

> 以下不是"你必须检查 X"，而是"过去在这些方向出过问题，保持敏感"。它们帮你校准直觉——但你的直觉不应该被它们限制。

这个项目在过去 10+ 个版本的独立审查中，问题反复集中在以下 5 个方向：

- **数字与声称漂移**——文档里的数字（规则数、测试数、版本号）和代码实际对不上；声称的功能在代码里找不到对应实现
- **物理搬迁残留**——目录改名、文件迁移、参数重命名后，总有什么东西没跟着动（路径、引用、调用方）
- **叙事不一致**——同一个概念在不同文档描述不同；声称"独立"但实际耦合；旧术语残留在归档区误导新读者
- **静默失效**——空 catch 吞错、写入/读取不对称、功能做了但用户感知不到——问题发生了但无人知晓
- **假绿与假阳性**——exit code 测量取到的是管道末端的退出码而非脚本的；自动化裁决把 PASS 读成 FAIL——"全绿"本身就是最值得怀疑的信号

这些方向值得你保持**额外敏感**——但不要把它们当成清单。你今天发现的问题可能完全不在这个列表上。**那才是最值钱的发现。**
