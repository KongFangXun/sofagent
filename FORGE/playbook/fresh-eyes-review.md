# sofagent 独立审查 Prompt

> **这是一个独立审查工具，不是检查清单。**
>
> 它的价值在于：你不知道你会发现什么。如果你按清单走，你只会找到清单上列的东西。但最危险的问题——那些作者自己看不出来的——往往不在任何清单上。
>
> **你带进来的最值钱的东西不是你的技术能力，而是你的"第一印象"。** 作者在这个项目里待了太久，对一切都有了解释。你没有。你觉得"不对劲"的地方，往往就是真的不对劲。

---

## 审查对象

sofagent（https://github.com/KongFangXun/sofagent）——当前已完成发版前全部审查（pre-push-check / acceptance-test / 回归清单全绿）。这一轮以**完全独立的视角**重新审视。

---

## 审查纪律

1. **零上下文**。不预设"之前已经修好了 X"。你的起点是空白。如果有人告诉你"这个版本改了 A、B、C"——忘掉它。你只看交付物本身。
2. **相信直觉**。第一反应"不对劲"就是不对劲——不需要找到理论依据。你后续可以验证，但那个"不对劲"的感觉本身就是信号。
3. **实际动手**。想到什么就去跑、去读、去试。不要停在"我觉得可能有问题"。
4. **不修改代码**。只报告，不修复。
5. **逐轮清空**。每完成一个视角后，丢掉上一个视角的记忆。每一个视角的你都是"全新的你"。

## 审查视角

以下每个视角给你一个**身份**和一种**心态**。具体看什么、怎么看、看到哪里为止——**由你自己决定**。每个视角后面有一些"你可能会注意到的事"——那些是举例，不是清单。你发现的东西完全可以跟它们毫无关系。

### 🧑‍💻 视角一：陌生人

你在 GitHub Explore 或技术群里看到了这个项目。你没听过它，不知道作者是谁。你只是好奇——点进去了。

**你的心态**：我是一个普通的开发者，不是来审代码的。我在判断"这东西对我有用吗？我愿意花时间装吗？"

你会在 GitHub 首页停留多久取决于好奇心。有人 3 屏就走，有人会翻进 ARCHITECTURE。但你只在做一件事：**形成第一印象**。

你可能会注意到的事（举例，不是清单）：
- 3 屏内你能搞清楚"这是干什么的"吗？还是越看越糊涂？
- 如果要装，你的第一步是什么？有障碍吗？
- README 说的东西，你信吗？有没有让你觉得"这太夸大了"的声称？
- 你会用一句话怎么跟同事介绍它？
- 装完跑 `--help` 或 `--doctor`——输出给你信心还是让你想卸载？
- 你看到的输出，你知道是谁给你的吗？还是觉得"这不就是普通的 git hook"？

**你的心态**：我关心的不是"有没有 bug"，而是"出事了谁负责"和"这东西能进公司吗"。我读任何一页文档的出发点都是：这让我更放心了，还是更担心了？

**你的心态**：我要找到它站不住脚的地方。不是恶意——是竞争本能。README 每一句话我都会问"真的吗？"

### 📦 视角四：npm 用户

**你的心态**：从敲下 `npm install` 到觉得"这东西有用"，中间花了多长时间？超过 5 分钟我就走了。

### 🛤️ 视角六：用户旅程

你不是站在一个角度看——你是**走一条路**。你假装真实用户，从零开始完整走一遍使用流程。

**你的心态**：我不是在审查，我在用。哪里让我卡住、困惑、想放弃？

走完这条路（发现 → 安装 → 初始化 → 第一次 commit → 第一次拦截 → 探索更多），每一步标注体验评分（🟢 顺滑 / 🟡 小障碍 / 🔴 卡住）。

**放弃阈值**：如果前 3 步出现 2 个🔴，标放弃点并停止——这个体验已经不及格了。

你也可以走**独立产品旅程**：从 FDE/ 或 FORGE/ 入口进来，不装主包。这条路真的能走通吗？还是"独立"只是话术？

### 🐛 视角七：红队

前面所有人都在"正常使用"——你反过来。**你是来搞破坏的。**

**你的心态**：不测正常路径，只测不正常的。我的目标是找出审计引擎在极端、边缘、恶意场景下的弱点。

你可以攻击任何面——但不要被下面的举例限制住。真正的安全漏洞往往在谁都没想过的地方。

你可能会尝试的方向（举例，不是清单）：
- 边缘情况：二进制文件、超大 diff、非 ASCII 文件名、重命名+修改
- 篡改：不合法 config、删关键字段、不存在的规则名
- 绕过：`--no-verify`、删 hook 文件、直接改 history.jsonl
- 注入：commit message 注入、代码注释注入、联邦 peer 返回恶意数据
- 加密攻击面：公钥替换、token 泄露、IV 复用、签名绕过

**但要探索清单之外的东西。** 你作为攻击者的创造力比这份清单值钱得多。

### 🤖 视角八：数字侦探

前面几轮都靠直觉和经验。这一轮换一种脑子：**你只看数字。** 文档里的每一个数字声称，跟代码里的实际数字——对得上吗？

**你的心态**：人类审查会跳过"数字对不上"这种枯燥检查，但这是最容易暴露问题的地方。大数字有人盯，小数字（"11 条""3 处"）往往写完就没人再看。

你可能会对账的数字（举例，不是清单）：
- README 说"X 条规则"——代码里实际注册了多少条？
- CHANGELOG 说"N 个测试"——实际 `npm test` 跑出多少？
- 文档里的规则 ID——在代码里逐个存在吗？（注意跳号不是遗漏）
- 版本号——所有文件、所有 package.json、所有注释里的版本号一致吗？
- 文档头部日期——跟当前发版日期对得上吗？
- exit code 声称 vs 实测——报告说「EXIT=0 全绿」，你亲自跑 `cmd > /tmp/log 2>&1; echo $?` 看是不是真的 0。管道取 `$?`（如 `cmd | tail; echo $?`）取到的是 tail 的退出码不是脚本的——这是假绿的温床

工具可以帮你（`check-version.sh` / `check-docs.sh`），但**不要只信工具**——工具自身也有盲区。用你的眼睛去看。

## 输出格式

完成全部 12 个视角后，输出一份报告。没有固定模板——但请确保：

- **每个视角都有发现**（哪怕是"整体印象是 X，没发现大问题"）
- **问题分优先级**：P0（严重/阻塞）/ P1（应该修）/ P2（观察项）
- **给出文件路径和具体描述**，让收到报告的人能定位
- **特别记录你的意外发现**——那些不在任何预期范围内、但你直觉觉得"不对"的东西。这些往往是最有价值的。

每个视角输出不超过 1 页。最后附一个总评：这个项目给你什么整体印象？1-10 分打多少？为什么？

## 附：历史教训（不是检查清单，是经验提醒）

> 以下不是"你必须检查 X"，而是"过去在这些地方出过问题，保持敏感"。它们帮你校准直觉——但你的直觉不应该被它们限制。

这个项目在过去 10+ 个版本的独立审查中，反复在以下领域发现问题：

- **文档 vs 代码数字不一致**（规则数量、测试数量、版本号散落）——每次发版都有新的漂移
- **物理搬迁后的路径残留**（目录改名/文件迁移后，边缘文件留下旧路径）——搬迁越大规模越危险
- **独立产品声称 vs 实际耦合**（"独立安装"实际依赖主包路径）——声称和实现之间有鸿沟
- **CHANGELOG 审查元信息污染**（模型名、审查轮次混入产品变更日志）
- **编码损坏**（UTF-8 多字节序列在传输中被截断，产生 U+FFFD 乱码；或更隐蔽的 null byte 嵌入——`\x00` 字节替代多字节字符，不显示为乱码但导致文件被误判为二进制）
- **CLI 契约漂移**（集成代码照着不存在的 CLI 参数写了整整一个版本）
- **测试只验证字段存在不验证行为**（`toBeDefined()` 是最弱的断言）
- **空 catch 块吞错**（最危险的代码气味——问题发生了但无人知晓）
- **跨文档叙事漂移**（同一个概念在不同文档描述不一致）
- **感知层废墟**（功能做了但用户完全感知不到它的存在）
- **部署路径 vs 读取路径不一致**（install 写到 A，handler 从 B 读——物理改名后最容易出，约束层静默失效）
- **写入/读取对称性断裂**（HMAC 签名改了写入侧算法但忘了改读取侧 → 所有记录变成不可复验；或者序列化/反序列化字段集不对称——写入用 sanitize 后的字段，读取用原始字段）
- **exit code 测量骗局**（v1.2.1 反复出现）——`cmd | tail; echo $?` 取到的是 tail 的退出码（0）不是脚本的。假绿比真红更危险——真红你会查，假绿你会放心走。发版验证脚本的 exit code 必须用 `> /tmp/log 2>&1; echo $?` 精确测量

这些领域值得你保持**额外敏感**——但不要把它们当成清单。你今天发现的问题可能完全不在这个列表上。**那才是最值钱的发现。**
