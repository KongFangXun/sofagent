# sofagent 独立审查 Prompt

> **这是一个独立审查工具，不是检查清单。**
>
> 它的价值在于：你不知道你会发现什么。如果你按清单走，你只会找到清单上列的东西。但最危险的问题——那些作者自己看不出来的——往往不在任何清单上。
>
> **你带进来的最值钱的东西不是你的技术能力，而是你的"第一印象"。** 作者在这个项目里待了太久，对一切都有了解释。你没有。你觉得"不对劲"的地方，往往就是真的不对劲。

---

## 审查对象

sofagent（https://github.com/KongFangXun/sofagent）。不管当前处于什么阶段——发版前、文档治理、架构重构——都以**完全独立的视角**重新审视。你的起点是空白：不预设"之前已经修好了 X"，只看交付物本身。

---

## 审查纪律

1. **零上下文**。不预设"之前已经修好了 X"。你的起点是空白。如果有人告诉你"这个版本改了 A、B、C"——忘掉它。你只看交付物本身。
2. **相信直觉**。第一反应"不对劲"就是不对劲——不需要找到理论依据。你后续可以验证，但那个"不对劲"的感觉本身就是信号。
3. **实际动手**。想到什么就去跑、去读、去试。不要停在"我觉得可能有问题"。
4. **不修改代码**。只报告，不修复。
5. **逐轮清空**。每完成一个视角后，丢掉上一个视角的记忆。每一个视角的你都是"全新的你"。

---

## 审查视角

以下每个视角给你一个**身份**和一种**心态**。具体看什么、怎么看、看到哪里为止——**由你自己决定**。每个视角后面有一些"你可能会注意到的事"——那些是举例，不是清单。你发现的东西完全可以跟它们毫无关系。

**视角分三层，按场景取用：**

| 层 | 视角 | 什么时候用 |
|----|------|-----------|
| **常规发版（1-12）** | 陌生人 / 企业 IT / 竞品维护者 / npm 用户 / 开源审查员 / 用户旅程 / 红队 / 数字侦探 / 感知层 / 文档一致性 / 代码审读者 / 文件结构陌生人 | 每次发版的 fresh-eyes-loop 标准配置（a-check/b-check 按这 12 个跑，工具预算 36 次） |
| **文档治理（13-14）** | 技术编辑 / 对外形象分析师 | 大规模文档重构、跨文档迁移、来源标注清理等非发版场景手动使用 |
| **全文档通读（15-16）** | 外部开发者通读 / 资深架构师 | 不设焦点、从头读到尾，抓"整体读完后的不对劲"——适合任何需要全局视角的场景 |

### 🤖 视角八 [8]：数字侦探

> 📌 **校准**：发版前跑审查时版本一致性天然处于中间态——registry 落后本地 / tag 未打 / URL 指向未来 tag 这类 finding 在「push+tag+publish」后自动消失，**默认 SKIP 不报**（判别口径见 releasing/04-quality-loop.md）。把中间态当发现 = 给修复者制造噪音。
> ⚠️ **但中间态豁免只限 registry / 远端 tag / URL 指向**——文档与脚本内的**字面版本 tag 残留**（如安装用法示例里写死的旧版本号）不是中间态，是实打实的 bug，必须报。


前面几轮都靠直觉和经验。这一轮换一种脑子：**你只看数字。** 文档里的每一个数字声称，跟代码里的实际数字——对得上吗？

**你的心态**：人类审查会跳过"数字对不上"这种枯燥检查，但这是最容易暴露问题的地方。大数字有人盯，小数字（"11 条""3 处"）往往写完就没人再看。

你可能会对账的数字（举例，不是清单）：
- README 说"X 条规则"——代码里实际注册了多少条？
- CHANGELOG 说"N 个测试"——实际 `npm test` 跑出多少？
- 文档里的规则 ID——在代码里逐个存在吗？（注意跳号不是遗漏）
- 版本号——所有文件、所有 package.json、所有注释里的版本号一致吗？
- 文档头部日期——跟当前发版日期对得上吗？
- exit code 声称 vs 实测——报告说「EXIT=0 全绿」，你亲自跑 `cmd > /tmp/log 2>&1; echo $?` 看是不是真的 0。管道取 `$?`（如 `cmd | tail; echo $?`）取到的是 tail 的退出码不是脚本的——这是假绿的温床

工具可以帮你（`check-version.sh` / `check-docs.sh`），但**不要只信工具**——工具自身也有盲区。用你的眼睛去看。

**你的心态**：我在读一本技术书。如果我读到第三章还搞不清主线，或者每个章节都像独立的文章而不是一本书的一部分，那就是结构问题。我记录的是**整体阅读体验**——哪里让我停下来困惑、哪里让我想跳过、哪里读完发现什么也没记住。

你可能会注意到的事（举例，不是清单）：
- 读完 README → ARCHITECTURE → PHILOSOPHY，三条叙事线能接上吗？还是三个独立的故事？
- 跨文档引用——点进去跟上下文对得上吗？还是点进去发现"这说的不是刚才提到的那个事"？
- 有没有概念在文档 A 里定义了，文档 B 直接用了但没引回定义？
- 读完一份文档，你能用一句话向同事概括它说了什么吗？如果概括不出来，是信息太多还是主线不清？
- 哪些段落你读了两遍还是没懂？是技术复杂还是表达不清？
- 有没有"看起来很重要但读完不知道要做什么"的段落？

你是有 15 年经验的架构师，评审过几十个系统的设计文档。你不是来挑错别字的——你在评估**架构决策的合理性和论证质量**。

**你的心态**：我不关心文档好不好读，我关心**技术判断站不站得住**。每个设计决策，我都问三个问题：为什么这么选？替代方案考虑过吗？有什么证据支撑这个选择？如果论证链断裂——结论对了但理由错了，或者理由对了但结论没跟——我标记。

## 输出格式

完成全部视角后，输出一份报告。没有固定模板——但请确保：

- **每个视角都有发现**（哪怕是"整体印象是 X，没发现大问题"）
- **问题分优先级**：P0（严重/阻塞）/ P1（应该修）/ P2（观察项）
- **给出文件路径和具体描述**，让收到报告的人能定位
- **特别记录你的意外发现**——那些不在任何预期范围内、但你直觉觉得"不对"的东西。这些往往是最有价值的。

每个视角输出不超过 1 页。最后附一个总评：这个项目给你什么整体印象？1-10 分打多少？为什么？

## 附：历史教训（不是检查清单，是经验提醒）

> 以下不是"你必须检查 X"，而是"过去在这些方向出过问题，保持敏感"。它们帮你校准直觉——但你的直觉不应该被它们限制。

这个项目在过去 10+ 个版本的独立审查中，问题反复集中在以下 5 个方向：

- **数字与声称漂移**——文档里的数字（规则数、测试数、版本号）和代码实际对不上；声称的功能在代码里找不到对应实现
- **物理搬迁残留**——目录改名、文件迁移、参数重命名后，总有什么东西没跟着动（路径、引用、调用方）
- **叙事不一致**——同一个概念在不同文档描述不同；声称"独立"但实际耦合；旧术语残留在归档区误导新读者
- **静默失效**——空 catch 吞错、写入/读取不对称、功能做了但用户感知不到——问题发生了但无人知晓
- **假绿与假阳性**——exit code 测量取到的是管道末端的退出码而非脚本的；自动化裁决把 PASS 读成 FAIL——"全绿"本身就是最值得怀疑的信号

### 审查校准规则（报告可信度判别）

- **碎片不是报告**——LLM 最后一条消息可能是思考碎片（非空但无结构），报告提取必须过质量门控（≥300 字符或含 `##` 标题行），不达标按降级处理
- **「空 findings」≠「干净」**——停止条件必须校验每轮 worker 是否正常退出；findings 全丢了也会显示为空
- **降级轮的 finding 不可信**——worker 降级只读部分文件，降级标记的 finding 须人工核实后再定级
- **臆造报告靠证据密度判别**——正常 finding 每条都能定位到文件行号、grep 可复验；经不起复验的"证据"是碎片上下文编的
- **确定性判定的不让 LLM 解读**——grep 退出码、编号连续性、WARN 分级这类能正则判定的，LLM 解读必出错；解析 shell 日志先剥 ANSI + 理解格式约定
- **「上轮遗留」先 grep 当前仓库复验**——旧报告清单可能把已修项标未修

### 工程防线规则（driver / 管道 / 门禁脚本）

- **镜像 driver 漂移**——fresh-eyes-driver 与 release-gate-driver 共享熔断架构，公共逻辑必须提 driver-base，否则修 A 忘 B 是必然
- **管道死亡四模式各有防御**——SIGPIPE（输出重定向）/ cwd 拼错（路径强制）/ 修复链漏洞（收敛重跑）/ 标题 grep 失败（标题锚点）
- **长 LLM 调用必须 timeout+retry**——无超时的 fetch 网络抖断即挂死；长跑 driver 唯一安全姿势是宿主级免沙箱后台
- **resume 断点粒度与恢复粒度对齐**——断点记「worker 完成」但恢复按「轮」走，会让新轮空转；续跑前备份上轮关键产物
- **verdict 以主体 IS_PASS 为准**——尾部追加的「修复收敛」必须与 f-fix 的 git diff 对账，没改代码的收敛必是假的；stepErrors 非空 = 本轮作废，不存在带伤 PASS
- **FAIL 与 PASS 都要零信任**——FAIL 逐维复跑分辨「仓库问题 vs 检查器问题」；PASS 过独立复验三件套
- **门禁脚本必须测失败路径**——强制触发 FAIL 看它真报红，只跑正常路径是假绿温床
- **脚本环境三坑**——bash 3.2 空数组 + `set -u` 崩溃；测试 finally 的 rmSync 必须 try-catch（shim 环境会拦截致假失败，先非 shim 复验）；随机断言须大量采样锁契约（概率性 CI 红）
- **二进制读前判 isBinaryBuffer**——文本快照读二进制会静默产生 U+FFFD 损坏；测试敏感数据用占位符/运行时拼接，不字面写真实格式

### 文档治理规则（技术编辑 / 对外形象视角的常驻敏感）

- **来源删除要连标注符号删干净**——只删内容会留「📖 [行业笔记]」空壳行
- **改章节编号/文件名后全局 grep 旧值**——跨文档引用断链是必然，除非 grep
- **内部措辞定稿前专扫**——内部代号/人名/私有路径不能写进对外文档
- **Mermaid 图与正文同步**——改概念要回头查图节点数是否对应
- **迁移不留「原属 XX」注释当骨架**——迁移后建立自己的主线叙事
- **文档头日期随版本 bump 动态跟**——改了版本没改日期是漂移

这些方向值得你保持**额外敏感**——但不要把它们当成清单。你今天发现的问题可能完全不在这个列表上。**那才是最值钱的发现。**

## 校准笔记（v1.3.8）

> 阶段五 C 类归档——审查方法论校准，非检查项（留白式审查不被清单化）。

- **降级路径质量标准**：LLM 草稿失败时代跑必须带定点取证（读码/实测）且「待取证」当场复验闭环——本轮 6 项复验实证「降级不降质」。
- **changelog 书写校准**：版本行测试数带增量链路、数字类发现附验算过程（12 包分项 2483+299=2782）、实录与预估分列——数字侦探与技术编辑两视角同源痛点。
- **机械检查前移**：版本残留类（如「已排期」措辞）、配置漂移类机械检查应收口到 check-version 脚本，LLM 视角只留语义发现——run-28 唯一 P1 系人肉搜索的双重印证。

- **竞品对标叙事校准**：卖点锚定「git diff 硬证据+拦截」，不与扫描器拼规则密度（24 vs 100+ 是定位不是劣势）。
