# 十一·发版流水线连续执行（release-gate-loop 实战）

> **定位**：FORGE release-gate-loop 自动收敛 + 放行后阶段六~十一连续执行（一揽子授权模式）的实战沉淀——「连续执行多个阶段不出大问题」的结构性原因、险情如何被机制接住、可复用判据。与 [四·Driver 编排](./driver.md)（loop 编排工程）互补：本文件聚焦「多阶段流水线的自动执行」，不改 loop 代码，只谈 SOP 流水线的跑法。
>
> 制度面权威 = [auto-converge-protocol](../../docs/changelog/releasing/auto-converge-protocol.md)（修复批协议 SSOT）+ [08-confirm](../../docs/changelog/releasing/08-confirm.md)（放行 = 发布链一揽子授权）。本文件记的是实战验证了什么、补了什么。

## 一、连续执行跑通的结构性原因（缺一不可）

1. **判定前置**：自动执行的授权基础 = 前置判定阶段产出的**结构化 verdict**（GO/BLOCKED）+ **前置条件清单**（逐条绑定在 verdict 内）。verdict 没有的授权不要自动扩展——「连续执行」≠「扩大授权面」。
2. **停手条件预置**：自动化的不是「做完」，是「护栏内做完、出护栏就停」——对外动作须请示 / 同一 FAIL 连续 2 轮不收敛停 / P0 停手重诊断 / 硬上限停。停手不是失败，是把分诊权交回人。
3. **文件即状态的接力**：跨 session 连续执行（收敛 → 发布 → 收尾）靠 runs 产物（verdict.md / status.json）+ 逐 commit 留痕 + 日志，不靠对话记忆。任何新 session 都能从「读产物 + git log」恢复全上下文续跑。
4. **每步动作后门禁即时验证**：bump 后跑 check-version、文档动后跑全套门禁（含 archaeology）、push 后盯 CI——连续执行最怕错误跨阶段传播，即时门禁把传播链掐断在发生点。
5. **外部依赖降级通道预案化**：每个外部依赖都要有「主通道挂了走哪」的预案且**登记在案**——凭证失效 → 手动发布兜底；git 协议超时 → API 对账/推送通道；发布平台故障 → 按款独立重发。预案在案 = 降级是执行细节；预案不在案 = 降级是事故。
6. **多 session 并发纪律**：pathspec 精确、只认自己 hunk；并发活跃期「冻结 HEAD 全量预检」是伪命题（HEAD 一直在动）⇒ 替代 = 最新 HEAD 上复核关键门禁 + 接受全量预检 rc=0 作整树结论。

## 二、险情实录（现象 → 修法 → 判据）

### 1. CI 测试密钥触发产品 fail-closed（整批红）
- **现象**：CI 测试用例整批红——CI 配置里的弱测试密钥被产品自身的 HMAC fail-closed 校验正确拒绝。
- **修法**：CI 配置改强密钥（`f024dfbb`）+ 测试补密钥自隔离（无密钥环境显式跳过且计数可查，`72750397`）。
- 🔴 **判据**：**测试环境依赖外部密钥 ⇒ 无密钥环境恒红 = 环境耦合缺陷**。修根因（测试自隔离 / CI 专用强密钥），不放宽产品 fail-closed——产品把弱密钥拦下正是设计在正确工作。

### 2. bump 全局替换误伤正文历史叙述
- **现象**：bump 后正文的版本历史引用（`· v旧版` / `（v旧版）` 形态）被连带改写——历史叙述被当现态标记。
- **修法**：替换规则加行首锚（`d4d04635`）+ bump 后逐文件 `git diff` 复核「只动了该动的行」。
- 🔴 **判据**：全局替换规则必须带行首锚；无锚替换 = 把历史当现态改。SOP 侧规则见 09-publish 步骤五「bump 历史引用防线」。

### 3. 文本替换锚静默空转（漏翻留到人工巡检才暴露）
- **现象**：状态翻转脚本 sed 只匹配单一措辞，锚不匹配时**不报错、直接无操作**；而对应门禁扫描面排除该目录 ⇒ 无机械兜底。
- **修法**：多模式 sed 覆盖措辞族 + **翻转后 fail-closed 断言**（输出不含目标形态即 exit 1）。
- 🔴 **判据**：**文本替换必须配「替换后断言」**——锚不匹配的静默无操作是替换类操作的头号风险；「跑过了」≠「改到了」。

### 4. 两守卫对同一文件结构性互斥
- **现象**：守卫 A 强制某行带「待发版」标注、守卫 B 把该标注判为残留 ⇒ 无论怎么写都红。
- **修法**：守卫侧根治（补行级排除、对齐另一守卫既有口径）+ **负向验证**（注入违规样本确认仍判红）。
- 🔴 **判据**：两守卫对同一文件提出矛盾要求 = 守卫缺陷而非文档问题；修守卫后必须负向验证检测力未削弱——「改完全绿」既可能是修好了，也可能是查不出来了。

### 5. 发布窗口的「合法红」误修风险
- **现象**：bump 后 verify workflow 红——npm 尚未发布该版本，供应链 fail-closed 按设计拒绝（09-publish 已成文「预期形态」）。
- 🔴 **判据**：**预期红必须成文**（哪个点位、为什么红、何时转绿），自动执行前先分清「哪些红是预期」——否则会在合法红上停手或误修真绿。

### 6. 发布物数字的时点性
- **现象**：同一门禁在 tag 时点与已发版态复跑读数不同（CHECKS 随状态分支面增减），发布后复跑者面对差异无法自判对错。
- **修法**：质量表计数带「@发版时点」注 + 「发布后复跑另记、不回改」配套（06-doc-finalize 质量表硬规则）。
- 🔴 **判据**：发布物里的机械计数**必须带时点注**；不带时点注的数字会在下一次复跑时被误判为错。

## 三、连跑模式的最小闭环判据（每阶段不打折）

- **连续执行 ≠ 跳过阶段闭环**：每阶段的最小产出（门禁读数 / commit / 产物文件）照常落盘，被一揽子授权替代的只是「人工逐段确认」，不是「阶段验证」。
- **顺序铁律不因连跑而省**：bump → 安装入口 curl 验证 → tag → npm，依赖链顺序不能压缩（tag 必须指向已 bump commit、安装入口验证后才算可发布）。
- **中断恢复**：从中断阶段步骤清单的**首个未勾项**续跑；续跑前照常做前置验证（工作区净 + 门禁基线重测）——中间态读数一律作废。
- **连跑的汇报纪律**：每阶段结束留一行「阶段 N 完成 + commit + 关键读数」到日志——接力 session 与事后复盘都靠这行定位。
