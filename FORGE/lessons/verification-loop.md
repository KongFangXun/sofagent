# 十二·收口验证循环（multi-repo 地基工程实战）

> **定位**：一次多仓地基工程（建仓 + 制度栈 + 方案文档）全程沉淀的收口方法论——「追问-物证-修复-重验」循环的结构、六层病谱系、以及把行为模式缺陷转化为机械纪律的路径。与 [十一·发版流水线](./release-automation.md)（流水线自动执行）互补：本文件聚焦「**人-代理协作下的收口验证**」——怎么在"以为做完了"的时刻继续挖出真问题。

## 一、「追问-物证-修复-重验」循环（结构）

维护者对每次收口宣告连续追问（「确定吗 / 就这些吗 / 真的吗」），每轮按固定结构响应：

1. **切换搜索模式**：宣告后默认是"验证修复"（收敛），被追问后切"假设还有病"（发散）——**默认模式应是发散**，收敛留给最终一轮。
2. **只引物证**：tag 快照（`git show <tag>:<path>`）、跨仓 diff、旧名全仓 grep、实测命令输出——宣告语气（"阶段性胜利成立"）不是证据，**汇报方自己就是不可全信方**。
3. **修完重验自洽面**：修复动作改变世界——修 A 时 B 已变，A 的修法可能基于旧世界。

## 二、六层病谱系（每层由上一层的修复引入）

| 层 | 病 | 引入者 |
|---|---|---|
| 物理 | 排版/格式不对齐 | 建仓 |
| 纪律 | 规则文档混考古/运行时指令 | 写模板 |
| 事实 | 声称与 tag 快照不符（交付表≠实况） | 制度演进未回写 |
| 时序 | tag 指向落后于修复 commit | 修复 #3 时引入 |
| 格式 | 插入行破坏既有排版约定 | 修复 #4 时引入 |
| 引用 | 改名/改节后旧引用悬空 | 早期文件未随目标更新 |

**通用规律**：每层都是「**改动扩散面 > 修改者注意力面**」的具体形态。涟漪传到的地方看不见。

## 三、险情实录（现象 → 修法 → 🔴判据）

### 1. 版本号当过程快照（骨架期发号）
- **现象**：仓库骨架刚立就打 v0.1.0，后又造 0.1.1 挂迁移——"建仓"与"迁移完成"被拆成两个版本号。
- **修法**：废 0.1.1；语义改为 **v0.1.0 = 建仓+迁移完成的正式首版**，骨架期无号无 tag；首版日志降为占位（发版时按实况改写）。
- 🔴 **判据**：**版本号是交付单元不是里程碑计数器**——过程态不配号；"分几步走到首版"与"发几个版本"是两件事。

### 2. 方案与前置门成环（判定底座归属）
- **现象**：方案写"四版迁新仓重编号 v0.2–v0.5"，但 v2.0.0 的硬前置门要求 v1.9.0 达阈——若四版迁走开发，v2.0 等分仓产物、分仓又等 v2.0，逻辑成环。
- **修法**：核对前置依赖链原文后改判——四版在老仓连续开发，分仓时只切产出。
- 🔴 **判据**：**排期方案必须对着版本前置门验一遍**——硬前置门是方案的照妖镜，能照出依赖成环。

### 3. 单数据点掀整账（tag/release 删除误判）
- **现象**：得一个新信息（fork 全是自己人）就把原判断（保留 tag）整个掀翻改判删除；被追问后实测发现 install.sh 自救链写死 tag 名（`:173/:179`），且 release 页本身是活跃度信号。
- **修法**：回滚为保留；三轮摇摆全程记录。
- 🔴 **判据**：**单个数据点只推翻它直接证据的那部分前提**，不能顺势推翻整账；**不可逆动作（删除类）的默认答案是"留"**，除非每笔账单独算清。

### 4. 桌面单文件被并行会话清空
- **现象**：方案文档（约 700 行）在追加新章时发现只剩 54 行——同期另一会话在桌面写了别的文件，疑似覆盖；无快照、无云副本、无 tmp 副本。
- **修法**：从会话上下文重建（后半逐字恢复 + 前半按当日工作日志要点重建）；重建版文件头作事故声明。
- 🔴 **判据**：**无版本控制的工作文档是单点故障——每次大改后必须另存副本**（cp 到工作区或临时目录）；多会话共用桌面时风险翻倍。

### 5. 改了 A 文件、对账文件没跟
- **现象**：changelog 加了章但 ROADMAP 计数没动（被 check-forms 的 pin 表当场拦下）；changelog 改了但方案文档（定稿）还写"待并入"；文件改了但规则（AGENTS）没写。
- **修法**：同批四件套——内容文件 + 计数声明 + pin 表 + 方案文档，任何一件掉了都是漂移。
- 🔴 **判据**：**一次动作有多个落点时全部落齐**——对账件（计数/pin/引用/规则）与内容件同批；机械护栏（pin 表）比自觉可靠。

## 四、行为模式缺陷 → 机械纪律（转化路径）

会话中暴露的三种行为缺陷，全部转成了一行可执行的规则（入三仓 AGENTS 验证节）：

| 行为缺陷 | 转化后的纪律 |
|---|---|
| 收敛太早（修完即宣告"完美"） | 收口声明只引用物证（tag 快照/diff/实测输出），不用宣告语气 |
| 单视角重复检查 | 修复后必须重验整个自洽面；改名后旧名全仓 grep 清零 |
| 临时文件忘了清 / 文档无备份 | 桌面文档每次大改后另存副本 |

**转化判据**：一条教训若不能写成「可机械验证的一行」，说明还没蒸馏到位——继续提炼到能写为止。
