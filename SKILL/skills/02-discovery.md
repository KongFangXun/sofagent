# FDE 阶段 2 · 深挖（§4-§5）

## 本阶段目标

逐岗位梳理业务流，用五要素把每个节点填满；构建本体结构（entity → concept → relations），让机器可读业务关系。达成后进入量化。

## 前置检查

如果你不是在 [做五要素深挖 / 画组织架构 / 讨论业务域 / 构建本体结构]，回到主 SKILL.md 重新判断阶段。

## 执行步骤

### §4 梳理业务流（五要素）

1. **先找主战场**——问三个问题：① 哪个环节卡住了企业？② 在不加人手前提下 AI 能承担 30% 还是 80%？③ 打赢之后（可量化结果）再复制到下一个流程
2. 逐岗位追问五要素，直到每个节点填满：

| 要素 | 追问 |
|------|------|
| **输入** | 这个节点接收什么信息/数据？谁给的？ |
| **输出** | 产出什么？交给谁？ |
| **负责人** | 谁在做？什么岗位/职级？ |
| **耗时** | 每次花多长时间？每天/每周做几次？ |
| **最卡的地方** | 最大的难点/最烦人的地方？ |

3. 追问节奏：「这个岗位每天第一件事做什么？→ 做完上一步下一步？→ 这一步输入是什么谁给的？输出交给谁？→ 这一步花多长时间？最烦人的地方？」
4. 五要素填满 → 换下一个岗位。所有关键岗位填满 → 进入 §5
5. 产出：「完整业务流节点图」——每个节点有完整五要素，按岗位分组

### §5 构建本体结构

6. **先判断是否要做**：多数中小企业不必建全量本体结构。若无需业务域级 Agent Runtime 且非一号位工程 → 跳过，用轻量 Agent + 企业 Skill
7. **如果要做**，先填业务四问：① 关键业务对象有哪些（客户/商品/订单/供应商）② 每个对象的归属负责人是谁 ③ 权威数据来源系统是哪个（ERP/CRM/自研/Excel）④ 动作风险等级（低：查询/只读；中高：写操作/审批/对外发）
8. 对每个节点补三个字段到 frontmatter：
   - **domain**：产出服务哪个部门？
   - **relations**：输入从哪来（belongs_to）？产出交给谁（has_many）？
   - **knowledge-domain**：Agent 有权读哪些（include）？不能读哪些（exclude）？
9. **给用户看建议，等用户确认（2026-08-10 落盘 · 咨询式生成）**——补完三字段后，**不要直接写入**：
   - 向用户展示推导建议：「根据五要素，我建议：「合同」entity →「审核通过」action → belongs_to 法务域；「审批流」concept → depends_on 合同。请确认或修改。」
   - 用户可改 entity/concept 名称、relations 方向、domain 归属——**每一步确认制**
   - 用户确认后才调 `create_entity` / `create_concept` 写入
   - 📌 为什么：ontology 是**企业业务知识的结构化表达**，只有用户知道「合同 belongs_to 订单」是不是真的；LLM 只辅助建议，不替代用户确认（没有模型也能生成 ontology）
10. 现场可配合**业务动作访谈表**（9 栏）把业务方口中的「愿望」拆成可执行动作链：谁触发 → 触发条件 → 读哪些系统 → 影响哪些业务对象 → 输出什么 → 写回哪里 → 出错谁负责 → 怎么审批 → 怎么复盘。访谈填完，frontmatter 的输入/产出/风险等级几乎是照抄
11. 每个节点补完后调 `read_entity`（name: 节点名）验证一致性 → `search_knowledge`（query: 关联节点）检查上下游 → `stats` 确认增长
12. 产出：富本体节点文档集 + `workflow.yml`（汇总所有节点的 relations + knowledge-domain）

> 📌 本体 ≠ 知识图谱数据库：本体的核心是**业务刻画**——完整呈现业务领域的客观事实与关联关系（如「客户下单 → 订单含哪些产品 → 产品由哪些零部件构成 → 零部件从哪些供应商采购」）。sofagent 的 ontology 包（objects.yml / actions.yml / constraints.yml）是这一业务刻画的机器可读层。

> ⚠️ Gotcha：深挖阶段最常见的错是「五要素没填满就急着判定节点」——每个节点五要素是后续所有判定的原料，缺一项就补一项。另一个是「本体结构建设过度投入」——中小企业流程相对简单，全链路本体结构建设投入产出比严重失衡，先判断再动手。

## MCP 工具调用指引

> 已连接 MCP Server：

- 每节点补完：`read_entity`（name: 节点名）验证一致性
- 上下游检查：`search_knowledge`（query: 关联节点）
- 写入本体结构：`create_entity` / `create_concept`（含 frontmatter: created_at + updated_at）
- 校验：`validate_ontology`（检查 relations 引用完整性） → 统计：`stats`
- **数据审计（S4）**：每次 `create_entity` / `create_concept` 后自动触发 D1-D5 检查：

| 规则 | 检查项 | 级别 |
|------|--------|:--:|
| D1 | domain/name 不允许从有值改为空 | FAIL |
| D2 | relations.belongs_to 引用目标必须存在 | WARN |
| D3 | 单次删除 >3 个 entity/concept 告警 | WARN |
| D4 | entity frontmatter 必须含 created_at + updated_at | WARN |
| D5 | entity/concept 内容不含 secret-like 串（密钥/手机号等） | FAIL |

**D1/D5 FAIL → 拒绝写入**：修正后重试；WARN 记录并继续。

> 未连接 MCP Server：

- 人工把五要素/三字段记到节点文档，relations 用 `belongs_to: [节点名]` / `has_many: [节点名]` 文本标注，敏感信息人工脱敏
